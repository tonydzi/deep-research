## Переносимая идентичность, безопасность и надёжность

Для fleet identity я бы не использовал absolute path как identity. Минимальный переносимый ключ должен быть **`repo_id + revision/snapshot + repo-relative slash-path + file hash`**, а host-specific path — лишь mapping. Это особенно важно между Windows `E:\...`, macOS `/Users/...`, UNC roots, case-sensitive/case-insensitive filesystems и Unicode normalization. `E:\foo` и `/Users/a/foo` нельзя автоматически считать одной и той же repository identity только из-за basename.

`codeindexer relocate <project> <new-path>` документирован лишь как “update project path without reindexing”. Документ не обещает cross-host relocation, path normalization, Windows↔macOS portability, hash validation, clone equivalence или checkout isolation. Поэтому существующий `relocate` полезен для **локального физического перемещения того же checkout**, но недостаточен как доказанная portable identity layer. Нужен простой explicit mapping, а не новый framework: `logical_repo_id → host → root`, с commit/snapshot и hash для проверки конкретного файла. citeturn606391search0

Case/Unicode следует нормализовать только для сравнения identity metadata, не для обращения к диску. Рекомендованный canonical representation: repo-relative path с `/`, Unicode NFC в manifest и отдельно raw native path; duplicate basenames всегда различаются полным repo-relative path; dirty root получает `revision=<HEAD>+dirty` и file hash конкретного файла. Это инженерная схема для вашего canary, а не claimed CodeIndexer feature.

CI-SA-2026-005 важен только при configured project-restricted API keys: в 0.11.0 часть memory/knowledge/report tools всё ещё не соблюдала per-key project restrictions; fully remediated только 0.12.0. Если вы используете один локальный wildcard/no-auth server без multi-user project ACL, именно этот advisory имеет меньшую практическую экспозицию, но версия всё равно находится в affected range. citeturn126540view2

Privacy надо разделять на core и optional flows. Core indexing, embeddings, search и audit vendor заявляет local-only; Free — no network calls, paid — daily license heartbeat с license ID + machine fingerprint. Optional Security LLM triage может обращаться к **вашему** Anthropic/OpenAI/self-hosted provider, то есть это отдельный off-host data path и его нельзя смешивать с утверждением “CodeIndexer никогда не отправляет код”. Vendor также заявляет zero telemetry/crash analytics в самом software. citeturn588528search0turn146018view1turn588528search1

Backup semantics публично слабы. Terms прямо перекладывают backups на клиента; FAQ говорит, что index/embeddings/memory — локальные файлы, но нет documented atomic backup procedure, hot-backup guarantee, file-locking behavior или cross-version restore matrix. Для upgrade canary безопасная rollback-модель должна поэтому основываться на **копии всего data directory при остановленном сервере плюс сохранении старого signed binary и config**, а не на предположении, что downgrade сможет открыть уже мигрированный store. Это conservative inference из отсутствия reversible migration guarantee. citeturn606391search3turn606391search1

## Минимальный falsifiable canary

Canary должен отвечать не “нравится ли retrieval”, а четырём независимым вопросам: **freshness, correctness, resource cost, reversibility**. Тестовый corpus лучше заморозить из реального Python/JS/TS/PowerShell snapshot, но копировать только выбранные source trees, без `.git`, archives, backups, generated JSON configs, caches и scratch folders. Это устраняет contamination, которая уже подозревается в Hub report, и позволяет чётко считать files/chunks.

Сравнивать стоит максимум две ветки за один раунд: **A = retained primary 0.11.0 в текущем режиме**, **B = tuned primary на той же версии** либо isolated 0.12.0 canary, но не оба изменения одновременно. Challenger имеет смысл только как отдельная третья arm после того, как primary baseline валиден; иначе невозможно разделить эффект freshness от эффекта retrieval engine. Любой cloud challenger получает только sanitised ordinary code без secrets/cookies/keys/confidential third-party material, как задано вашей policy.

Набор запросов должен включать EN/RU пары для symbol, exact, semantic, callers/callees/references, known no-answer и PowerShell. Для каждого вопроса answerer получает только реально сериализованный tool output; сохраняются raw MCP requests/responses, tool call count и delivered bytes/tokens. Blind source judge видит ответ и frozen source snapshot, но не знает arm. Accuracy score должен разделять **correct / incomplete / false assertion / correct abstention / false no-answer**.

Freshness mutation suite — четыре независимых операции на одном canary-файле: create, content edit, rename, delete. Каждая мутация получает random nonce и before/after SHA-256. Проверка проходит только если после заявленного freshness mechanism новый exact byte content доступен там, где должен быть, старый nonce исчез там, где должен исчезнуть, rename не оставляет ghost hit, а delete не возвращает старый source как актуальный. Job “accepted”, `indexing_complete` или изменение `last_indexed` считаются telemetry, но не success criterion.

Для watcher отдельно нужны два прохода: **W1: ничего не вызывать после save**, чтобы проверить реальный auto path; **W2: explicit incremental `reindex`**, чтобы проверить bounded manual refresh. Если W1 fails, а W2 passes, это доказывает проблему автоматического freshness path, но всё ещё не объясняет её причину. Если оба fail — тогда уже смотреть effective config, ignores, locks и index health. `--force` использовать только как отдельный recovery/control, потому что full rebuild маскирует incremental bugs. CLI подтверждает incremental-by-default и отдельный `--force`. citeturn606391search0

Resource runs на shared host должны быть **serialised**, как вы и требуете. На каждом host отдельно: cold start, idle after model load, first search, warm search, incremental edit, no-op reindex, bounded changed-file update. Метрики: process count; RSS/working set; private bytes/private dirty; CPU time и peak cores; GPU dedicated/shared VRAM на Windows, Metal/unified-memory footprint на Studio; disk read/write bytes; index directory delta; network bytes; wall time p50/p95; provider/token cost для cloud challenger. Никакие “1–2 GB” vendor numbers не подменяют эти measurements. citeturn606391search1

Rollback test для 0.12.0 canary должен быть фактическим: cloned data root или отдельный fresh index; сохранить 0.11 binary/config; стартовать 0.12 на копии; выполнить search/freshness suite; затем **не пытаться downgrade по той же копии после migration**, пока это не доказано. Rollback = выключить canary, вернуть прежний binary и прежний untouched data root. Это оставляет working installation intact и не требует предположений о downgrade compatibility.

## Решение KEEP / TRY / PARK и действия после принятия исследования

**KEEP — сейчас.** CodeIndexer остаётся primary и установленным на всех уже работающих машинах. Для Claude/Codex/Cursor baseline — один shared HTTP server на хост вместо session-scoped stdio. Это уменьшает process multiplicity и operator effort, оставаясь в официально поддержанном transport path; quantified memory benefit пока UNKNOWN. На ARM Mac Studio предпочтительный документированный acceleration path — Metal; на Windows — выбирать уже имеющийся CPU/DirectML/CUDA build без покупки нового железа/тарифа; Intel Mac Pro начинать с CPU path. citeturn305271search1turn184408search3

**TRY — только additive canary.** Первый дешёвый эксперимент — не challenger, а 20–30-минутный isolated freshness corpus на текущем 0.11.0: create/edit/rename/delete + no-call watcher path + explicit incremental reindex + exact byte readback. Он наиболее дешёво различает “плохой retrieval” и “stale index”. Второй canary — 0.12.0 на копии data/index либо fresh disposable index, потому что 0.12 закрывает реальные High advisories, но compatibility и rollback пока не доказаны публично. citeturn146018view2turn428144view0turn428144view2turn126540view2

**PARK — production upgrade до 0.12.0.** Несмотря на security pressure, ставить его поверх текущего production data directory без offline copy, compatibility smoke test и binary/data-root rollback evidence не следует. Vendor утверждает automatic migration, но не публикует reversible migration contract. citeturn810022search2

**PARK — per-client stdio.** Оно функционально поддерживается, но для вашего режима “три клиента × три хоста” создаёт ненужную вероятность нескольких server/model processes. Оставить stdio как fallback для диагностики transport isolation, а не default. citeturn184408search3

**PARK — cloud challenger как постоянный второй индексер**, пока primary freshness не измерен. Иначе дополнительный watcher/index/model увеличит local resource cost и operator surface, а comparison будет confounded. После чистого baseline challenger имеет смысл только on-demand для ordinary non-confidential code и только если независимый blind test показывает incremental accuracy/latency benefit, который превышает extra network/context cost.

Для вашей среды CodeIndexer наиболее полезен там, где один persistent index обслуживает несколько AI-клиентов, требуется cross-file semantic recall и graph navigation, а source code должен оставаться local. Он слабее как authoritative source-of-truth при freshness uncertainty, на parser-неподдерживаемых языках вроде незафиксированного PowerShell path, при dynamic cross-service edges и там, где нужен compiler-exact navigation — vendor сам оставляет эту роль LSP. citeturn606391search4turn606391search6

Сильнейший аргумент **против** моего KEEP — не stale `x_outbox` сам по себе, а совокупность: текущая 0.11.0 имеет опубликованные High advisories, текущий индекс уже продемонстрировал как минимум один stale semantic/readback result, а значительная часть critical runtime semantics proprietary и публично не специфицирована. Если paired canary покажет, что explicit incremental reindex тоже не восстанавливает exact fresh bytes либо 0.11.0 memory/idle footprint неприемлем на трёх хостах, статус primary должен быть пересмотрен.

Самый дешёвый полезный следующий эксперимент: **на текущем Hub без изменения production index** создать отдельный tiny temp repo из ~20 файлов Python/TS/JS/PS1, подключить его к уже работающему HTTP server, записать unique nonce, измерить auto freshness и manual incremental freshness, exact bytes и process resource deltas. Это даёт больше информации на единицу риска, чем массовый upgrade, новый тариф или ещё один большой benchmark.
