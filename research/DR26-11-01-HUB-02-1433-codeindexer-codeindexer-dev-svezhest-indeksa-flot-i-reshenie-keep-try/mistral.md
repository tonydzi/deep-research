4.2 Инкрементальная свежесть

Документировано:

CLI: codeindexer index <path>, reindex <project> — инкрементальный по умолчанию, --force для полной, status (статистика по проектам), delete, relocate; jobs/pause/resume/cancel (асинхронные задачи, jobs требует работающего сервера), activity-log (история мутаций), doctor (проверки метаданных, целостности индекса, дубликатов) (Docs).

Конфигурация: глобальный ~/.config/codeindexer/config.toml, per-project .indexer.toml; codeindexer init генерирует дефолтный конфиг «with every option documented inline»; project-config показывает эффективный конфиг (Docs). Расположение на Windows публично не указано (вероятно %USERPROFILE%\.config\codeindexer\ — UNKNOWN, проверить локально).

Свежесть результатов: каждый результат search_code несёт проверку «indexed commit vs current HEAD» (заявление вендора в отзыве Claude Code на главной; совпадает с нашим наблюдением предупреждений для non-git корней — «freshness unknown»). «После первого индексирования переиндексируются только изменённые файлы — обычно < 1 c при сохранении» (главная, developers, enterprise).

НЕ документировано (UNKNOWN — читать только локально, никаких выдумок о внутренностях): наличие/отсутствие автоматического файлового вочера; имя и дефолт auto_reindex-подобных ручек; приоритет .gitignore vs конфиг-игноров; поведение при dirty working tree; распространение rename/delete; лимиты больших файлов; обработка symlinks; блокировки (locks). LinkedIn-анонс 0.12 упоминает «Path safety, symlink and sandbox fixes across the board» (LinkedIn CEO) — подтверждает, что symlink-логика менялась, но не её детали.

PowerShell: .ps1/.psm1 отсутствуют во всех трёх ярусах языков (27 граф / 5 символы / 36 «распознанные» — списках PowerShell нет) (FAQ, agents). Прямого заявления «файлы PowerShell не индексируются» нет → статус UNKNOWN с высокой априорной вероятностью «только как plain text или не индексируются»; обязателен локальный тест (§4.7, H2). Bash при этом входит в полный граф — асимметрия для нашего парка реальна.

Опасность заражения корпуса: JSON/JSONL индексируются (ярус «recognized»), архивы (ZIP/TAR/RAR/…) и Telegram-экспорты (JSON) — индексируемые форматы документов — это документированное объяснение того, почему scratch/backup-копии и конфиги могут попасть в отчёты (FAQ); лечится явными exclude в .indexer.toml и физической изоляцией тестового корпуса, а не «восстановлением индекса».

Как доказать свежие байты, а не только принятие задачи (протокол):

Зафиксировать SHA-256 файла на диске до и после изменения.

Выполнить изменение (edit/rename/delete/create) вне индексации, затем триггер (по конфигу: сохранение/reindex) — не принимать indexing_complete/job-acceptance как доказательство.

Прочитать содержимое через search_code + read_file_range и сравнить возвращённые байты с диском; расхождение = несвежий индекс (без утверждения о причине).

Контроль состояния: codeindexer status (last_indexed/файлы/чанки/символы — метрики, которые мы уже снимаем hub-скриптами) и codeindexer doctor (целостность/дубликаты).

Наше наблюдение (устаревшая сигнатура x_outbox.enqueue, last_indexed=2026-10-27, disk≠index) — валидный фальсифицирующий кейс для этого протокола; из него не следует коррупция всего индекса, отказ вочера или флот-аут.

4.3 Ресурсная архитектура

Один сервер против stdio на клиента. Документированы оба транспорта: codeindexer serve — HTTP на 127.0.0.1:8978 (MCP на /mcp, дашборд на том же порту/процессе/аутентификации); serve --stdio — «no HTTP server, agent launches binary directly» (Docs). Для нашего парка опубликованы HTTP-рецепты всех трёх клиентов: Claude Code — claude mcp add --transport http codeindexer --scope user http://127.0.0.1:8978/mcp (важно: "type": "http", не "sse"); Codex CLI — codex mcp add codeindexer --url http://localhost:8978/mcp (streamable HTTP; опция --bearer-token-env-var для авторизации); Cursor 0.45+ — deeplink или ~/.cursor/mcp.json / .cursor/mcp.json с "url": "http://localhost:8978/mcp". Claude Desktop и Windsurf по умолчанию stdio; VS Code и Antigravity — HTTP. Значит: один общий процесс на хост обслуживает всех клиентов — ровно наша целевая архитектура; stdio-вариант умножал бы процессы/память/эмбеддинги на каждого клиента и противоречит ограничению RAM.

Дашборд: пароль в Settings обязателен, если дашборд виден за пределами localhost (Docs) — нам нужен и по адвайзору 001 (см. §4.6).

Специальный заголовок X-Codeindexer-Run + CODEINDEXER_RUN_ID относятся только к «card runner»-сессиям; для обычных HTTP-клиентов не нужен и инертен (Docs).

Модели и бекенды. Embedding-модель общего назначения + reranker поставляются внутри бинарника, веса закреплены хэшем и не обновляются в рантайме (Security). Бекенды по платформам — CPU / DirectML (Windows, любой DX12-GPU) / CUDA / CUDA+TensorRT / Metal (Apple Silicon) (FAQ). На Hub GPU-ускорение без установки SDK даёт DirectML; на Mac Studio — Metal; на Intel Mac Pro — CPU.

Память/диск (документировано): пик индексирования ~1–2 ГБ RAM на проект; индекс на диске — 5–15% от размера исходников; «tunes itself to your RAM — comfortable on a 16 GB laptop» (маркетинг); Free — 100k чанков на всё. Обслуживание: compact (слияние фрагментированных LanceDB-файлов), quantize, rebuild-fts (без пере-эмбеддинга), rebuild-index.

Не документировано — измерить локально: idle-RSS и lazy-loading/время жизни модели; VRAM/GPU-память под DirectML/Metal; поведение no-op refresh (переиндексация без изменений); конкуренция индексирование/поиск при одновременных клиентах (есть jobs/pause/cancel, но нет документированных приоритетов); рост RSS от количества проектов. Различать при измерении: GPU VRAM (Task Manager → GPU / Activity Monitor), process RSS vs private bytes (Process Explorer / ps -o rss,vsz), и дисковые веса индекса vs исходников (du).

Вывод для парка: на хабе и обеих Mac — по одному codeindexer serve (HTTP), клиенты цепляются по HTTP; ни одного stdio-процесса на сессию; никаких сторонних вочеров/эмбеддеров — свежесть поддерживать штатными reindex/конфигом (после локального чтения .indexer.toml).

4.4 Поиск и навигация

Режимы (Docs, Agents): search_code — semantic / symbol / exact / cascade (Pro; умный выбор symbol→semantic→exact); compact mode обрезает вывод инструмента «до 80%» (маркетинг). Многоязычные семантические запросы: английский, русский, китайский, немецкий, французский и ещё 100+ (llms-full.txt). Поведение symbol-поиска по кириллическим идентификаторам не специфицировано → тест (H5 в §4.7).

Навигация: read_chunk (чанк, владеющий строкой), read_file_range (точный срез файла, кап 500 строк), outline — Free. Pro: find_references, find_callers/find_callees (опция transitive), find_call_chain, find_call_cycles, shortest_call_path, find_by_signature; плюс dead code, complexity, bridges, execution flows, review_diff (blast radius по git-diff с оценкой high/medium/low), rank_functions (PageRank-подобное ранжирование). Кросс-язычные швы (REST/gRPC/очереди/FFI/GraphQL) — «best-effort links», честно помечено как эвристика. Dataflow-анализа нет ни в одном ярусе — только вызовы/ссылки; про границы потоков данных инструмент не отвечает.

Кейсы из отзывов вендора (полезно для ожиданий): фреймворк-зависимый код (Laravel/Livewire, динамические роуты PHP, ORM-цепочки) — граф «struggled», требовалась ручная интерпретация; обзор структуры (report/outline) — сильная сторона (главная).

Ложный «нет ответа» — различать три причины:

Неподдерживаемый язык/ярус — по опубликованным спискам (PowerShell, Verilog вне символов, и т.п.); до теста не утверждать, но это первая гипотеза для .ps1.

Несвежий индекс — предупреждение fresheness (indexed commit vs HEAD; для non-git корней «unknown» — наше наблюдение); подтверждается протоколом байтов из §4.2.

Поддерживается, но конструкция не разрешается (динамическая диспетчеризация, фреймворковые алиасы) — по определению «best-effort».

Fallback точного чтения: read_file_range (кап 500 строк) — документированный способ получить исходник без ухода из MCP; клиенты должны трактовать freshness-предупреждение как «сначала сверить байты, потом верить символу». Бенчмарки сайта (200 мс, 47 с, 1–3 мин) не считать доказанной производительностью на наших машинах.

4.5 Портативная идентичность

Документировано: проект = «единственный индексированный репозиторий или каталог»; управление tag/alias; relocate <project> <new-path> — обновление пути без переиндексации; память — переносимые файлы (импорт/экспорт карточек/roadmap, экспорт в markdown-«vault», можно коммитить в git); индекс/эмбеддинги — «plain files on your disk», доступны для бэкапа (Docs, agents, главная). Единственный документированный сигнал ревизии — «indexed commit vs HEAD» и только для git-корней.

НЕ документировано (UNKNOWN): внутренняя модель repo_id/revision/snapshot/file-hash; перенос индекса между ОС; трактовка букв дисков Windows / UNC-префиксов / чувствительности к регистру / нормализации Unicode (NFC); поведение при дублирующихся basename в разных каталогах; идентичность dirty-корней.

Практический вывод: «переносимой идентичности» в нашем смысле продукт не документирует. Нужна простая явная таблица соответствия, которую ведёт оператор: (хост, абсолютный корень, имя проекта в CodeIndexer, alias, git-коммит снапшота). Правила: relocate — только в пределах одного хоста; клон на новом хосте — новый проект + полная переиндексация (перенос индекса не документирован); никогда не приравнивать E:\repo и /Users/x/repo молча — только через явную запись таблицы; идентичность содержимого контролировать git-коммитом + хэшами (наша протокольная практика), а не внутренним идентификатором продукта. Новых фреймворков не изобретать.

4.7 Минимальный аддитивный канареечный тест (фальсифицируемый, парный)

Цели: доказать/опровергнуть пользу настройки, измерить свежесть и ресурсы, получить совместимость/откат для апгрейда — при $0 новых расходов.

Корпус: замороженный снапшот реального кода (Python/JS/TS/PowerShell) на фиксированном git-коммите; корпус физически изолирован (отдельный каталог без архивов, scratch/backup-копий и конфиг-JSON; эти категории либо исключены в .indexer.toml, либо отсутствуют физически) — защита от контаминации, источником которой документированно могут быть JSON/архивы/Telegram-экспорты (FAQ).

Руки (serialized на каждом хосте; пары A/B на одном хосте, между прогами — пауза до возврата ресурсов к idle):

A — сохранённый primary: CodeIndexer 0.11.0 как есть.

B — настроенный primary: тот же бинарник 0.11.0; .indexer.toml с явными excludes; отдельный project-alias; фиксация конфига.

C (опционально) — primary + челленджер: B плюс на одной из Mac — открытый Serena MCP (LSP-based, символная точность) (Serena); или «челленджер = обычные grep/glob-инструменты самого агента». Облачный челленджер — только для обычного кода; секреты/куки/ключи/данные третьих лиц не участвуют.

Матрица запросов (RU и EN, каждая — с известным ground truth): symbol (по имени функции/класса), exact (строка/сигнатура), semantic (простой язык), navigation (find_callers/find_call_chain/find_references), no-answer (несуществующий символ — ловля ложных «нет»/галлюцинаций), plus PowerShell-пробы (символ и семантика по .ps1), plus свежесть-проба (изменить сигнатуру-маркер, akin x_outbox case, и проверить, когда новый байт становится видим в поиске — по протоколу SHA-256 из §4.2).

Процедура: два независимых ответчика (разные клиенты/сессии: Claude и Codex, Cursor при необходимости) на каждую руку; слепой судья сравнивает ответы с ground truth, не зная руку; сериализованный контекст фиксируется после фактической доставки (размер в байтах/токенах, число и перечень tool-вызовов) — иначе повторяем ошибку 27-окт (INVALID: сериализованный контекст превышал бюджет, ноль успешных вызовов челленджеров).

Метрики: корректность и ложные ответы (по типам: symbol/semantic/exact/navigation/no-answer); доставленный контекст после сериализации; холодное/тёплое wall time; пик/idle RAM процесса (RSS и private bytes отдельно); CPU/GPU (VRAM)/диск/сеть; стоимость ($0 — только существующие подписки). Мутации create/edit/rename/delete — по изолированному срезу, с восстановлением между прогами.

Фальсифицируемые гипотезы:

H1: B снижает доставленный контекст и шум (за счёт excludes) без потери корректности против A.

H2: символы PowerShell систематически «нет ответа» в обеих руках (ожидание из §4.2; опровергается, если найдены).

H3: после edit/rename/delete инкрементальная переиндексация делает новые байты видимыми за ≤ N секунд (N фиксируется по местному конфигу) — иначе триггер свежести не работает так, как предполагает вендорская фраза «<1 c при сохранении».

H4: HTTP-шаринг: добавление второго клиента к работающему серверу не создаёт второго процесса и добавляет < X МБ RSS.

H5: RU-семантика и RU-символы (кириллица) находятся не хуже EN-аналогов (парные RU/EN запросы).

Чего не делать: не делать выводов об «архитектурной экономии» без измерений; не обобщать single-observation (x_outbox) на флот; не смешивать руки на одном хосте одновременно.

6. Открытые вопросы

Механика свежести: есть ли в 0.11.0/0.12.0 вочер, каков дефолт auto_reindex, как обрабатываются rename/delete — публично неизвестно; ответ — локальный codeindexer init-конфиг и .indexer.toml (не выдумывать).

PowerShell: индексируются ли .ps1 вообще (plain-text или никак); поведение кириллических идентификаторов.

Откат после миграции формата индекса: документирована только прямая автопасшка; обратимость не обещана — главный риск процедуры апгрейда.

Схема каталога данных и совместимость бэкапов: не опубликована.

Windows-расположение глобального конфига: не документировано (ожидать %USERPROFILE%\.config\codeindexer\ или иное — проверить).

Intel-macOS сборка: наличие x64-бинарника в дашборде загрузок.

Фактические idle/пиковые ресурсы и VRAM: нет независимых измерений; только вендорские диапазоны.

CI-SA-2026-005 на нашем парке: применимость зависит от того, настроены ли [auth] api_keys (проверить конфиги всех трёх хостах).

«42 карточки/8 фаз» и прочие Free-лимиты при откате Pro→Free после 14-дневного grace: судьба сверхлимитных данных не документирована.

GHSA-записи: идентификаторы опубликованы, но страницы GitHub-адвизориев в этом исследовании напрямую не открывались — при необходимости сверить: GHSA-c6vr-qp95-h5fr, GHSA-jxhc-h8rv-2p75, GHSA-w964-62f3-5735, GHSA-43wx-76g7-9289, GHSA-499f-7wqh-526f (из архива репозитория).
