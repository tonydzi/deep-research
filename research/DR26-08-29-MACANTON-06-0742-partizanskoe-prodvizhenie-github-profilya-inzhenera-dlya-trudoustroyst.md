# Insight (DR DR26-08-29-MACANTON-06-0742): Партизанское продвижение GitHub-профиля инженера для трудоустройства и известности

> Deep research отвечает на вопрос, какие активности на GitHub (PR, issues, ревью, документация, awesome-листы, actions) реально повышают заметность инженера и его шансы получить работу в IT-компании.

## Ключевые выводы
- Работодателей интересует не количество коммитов/зелёных квадратиков, а качество вклада: смерженные PR в авторитетных проектах — прямое подтверждение навыков (прошли peer review)
- Звёзды и форки репозиториев показывают популярность, но не гарантируют качество кода — фейковый профиль из сериала «Силиконовая долина» набрал 1560 подписчиков без реальных навыков
- 93% рекрутеров считают open-source-разработчиков дефицитными и активнее их ищут
- 65–85% опрошенных рекрутеров ценят soft skills (коммуникация, работа в ревью/обсуждениях) не меньше чистого кода
- Партизанские тактики: ранние PR в растущие проекты, мониторинг GitHub Trending/Hacker News, фикс документации и мелких багов (лёгкий вход, почти всегда принимается), нишевая специализация, создание awesome-листов и стартер-китов, свои GitHub Actions/Marketplace, участие в Hacktoberfest и Google Summer of Code
- Реальные примеры: Sindre Sorhus — 80 500 followers через awesome-лист (~490k звёзд) и сотни npm-пакетов; Kent C. Dodds — 35 000 followers через ключевые JS-библиотеки (React Testing Library); Josh Wulf — получил позицию Developer Advocate через серию PR в Zeebe/Camunda за 14 месяцев
- Взрывная активность без истории («камуфляжные PR» после публикации гайда) настораживает рекрутеров больше, чем медленный последовательный вклад
- GitHub Docs официально учитывает как вклад: репозитории/форки (всегда), issues, PR, ревью, discussions, коммиты (при условиях)

## Рекомендации / решения
- Сделать информативный README профиля со ссылками (портфолио, LinkedIn) и выбрать 1-2 ниши развития, чтобы не распыляться
- Первые 3 месяца: 2-3 quick-win PR в неделю (фикс доков, опечаток, мелких тестов) в популярных репозиториях выбранной ниши
- К 6 месяцам: браться за более сложные баги/фичи, создать PR/issue-темплейты, опубликовать первый собственный репозиторий с качественным README
- К 9 месяцам: вести блог/заметки о решённых кейсах, собрать портфолио-сайт (GitHub Pages), выпустить GitHub Action на Marketplace
- К 12 месяцам: делать код-ревью 5+ чужих PR, попробовать стать мейнтейнером небольшого проекта, опубликовать awesome-лист или стартовый шаблон
- Регулярно (раз в месяц) отслеживать метрики: followers, stars, merged PR, активность issues — и оценивать прогресс по росту
- Избегать «код-спама» ради статистики — один значимый PR ценнее десятка тривиальных коммитов
