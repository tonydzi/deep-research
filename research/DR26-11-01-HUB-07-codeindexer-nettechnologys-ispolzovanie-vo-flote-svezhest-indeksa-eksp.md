# Insight (DR DR26-11-01-HUB-07): CodeIndexer (NetTechnologys): использование во флоте, свежесть индекса, эксплуатация

> Стоит ли оставить CodeIndexer 0.11.0 основным индексатором на трёх хостах, как обеспечить и доказать свежесть индекса и безопасно ли переходить на 0.12.0.

## Ключевые выводы
- Движок CodeIndexer (NetTechnologys s.r.o., Чехия) проприетарный: публичный GitHub-репозиторий — только community/disclosure, MIT покрывает лишь README/SECURITY/LICENSE и не распространяется на бинарник. GitHub Releases нет, хронология версий восстанавливается по security advisories (0.11.0 — 2026-07-23, 0.12.0 — 2026-10-06; даты коммитов тегов, не доступности скачивания).
- Установленный бинарник 0.11.0 / 328915f / build 2026-07-24 по retrospective review от 2026-10-21 затронут тремя High-уязвимостями, полностью исправленными только в 0.12.0: DNS-rebinding/Host validation (CI-SA-2026-001), выход идентификатора проекта за корень индекса с рекурсивным удалением (CI-SA-2026-003), неполная проверка доступа по ключам к проектам в memory/knowledge tools (CI-SA-2026-005). Привязка к 127.0.0.1 не защищает 0.11.0 от DNS-rebinding без пароля дашборда. CVE-идентификаторы не назначены.
- Публичных гарантий обратимой миграции нет: vendor обещает автомиграцию формата индекса и breaking changes не чаще раза в год с уведомлением за 30 дней, но схема версий, поддержка downgrade, матрица совместимости бэкапов и экспорт/импорт индекса целиком не опубликованы. Бэкапы по Terms — на клиенте. Поэтому апгрейд на 0.12.0 поверх продуктивного data directory небезопасен без копии и доказанного отката.
- Архитектурно лучший режим для Claude/Codex/Cursor — один постоянный HTTP-процесс на хост (127.0.0.1:8978), а не отдельный serve --stdio на каждую сессию. Экономия RAM/CPU при этом не измерена и не задокументирована; vendor даёт лишь грубые ориентиры (пик индексации 1–2 ГБ на проект, диск 5–15% от исходников).
- Свежесть индекса не доказана: наблюдён как минимум один устаревший результат (stale x_outbox.enqueue, последний индекс на Hub 2026-10-27, 28 265 chunks / 3 738 файлов, предупреждение «freshness unknown» для non-git root). Причина (сбой watcher, игнор-правила, блокировки) неизвестна; механизм auto_reindex, дефолты, debounce, обработка rename/delete и precedence ignore-правил публично не специфицированы, есть лишь обещание «reindex on save» и инкрементальный reindex по умолчанию (--force — полный).
- Сильнейшее доказательство свежести — сравнение точных байтов (nonce + SHA-256 + независимое чтение с диска, search_code и read_file_range), а не indexing_complete/last_indexed/принятие job. Для проверки нужны отдельные проходы: W1 (без вызовов после save, проверка авто-пути) и W2 (явный инкрементальный reindex), --force только как recovery-контроль.
- PowerShell отсутствует в опубликованном перечне языков (19 full call graph, 9 AST-symbol, 8 searchable), поэтому .ps1 нельзя заранее требовать с AST/callers/callees. CodeIndexer не заменяет LSP; результат «нет вызывающих» нельзя считать уверенным ответом без проверки поддержки языка, свежести и точного чтения источника.
- relocate документирован только как смена пути проекта без reindex и не обещает переносимой идентичности между хостами (Windows↔macOS). Предлагаемая схема идентичности: repo_id + revision/snapshot + repo-relative slash-path (NFC) + file hash, пути хоста — лишь маппинг.
- Лицензирование и платформы: планы Free/Pro/Security/Enterprise; цены конфликтуют (FAQ Pro $20/Security $40 против pricing page $16/$32 при годовой оплате); платные тарифы шлют раз в сутки license ID и анонимный fingerprint железа, оффлайн-grace 14 дней, air-gapped только Enterprise. Metal для Apple Silicon, DirectML/CUDA для Windows задокументированы; явной x86_64/arm64-матрицы для macOS (Intel Mac Pro) нет. Ядро индексации/поиска локально, vendor заявляет нулевую телеметрию; опциональный LLM-triage идёт к вашему провайдеру.

## Рекомендации / решения
- KEEP: оставить CodeIndexer primary на уже работающих хостах, режим — один shared HTTP-сервер на хост; stdio держать как диагностический fallback, не дефолт.
- TRY 1: 20–30-минутный изолированный freshness-canary на текущем 0.11.0 без изменения продуктивного индекса — временный репозиторий ~20 файлов Python/TS/JS/PS1, create/edit/rename/delete с nonce и SHA-256, проходы W1 и W2, точное чтение байтов и замер ресурсов процесса.
- TRY 2: канарейка 0.12.0 только на копии data/index или свежем одноразовом индексе, с сохранённым старым бинарником и конфигом; откат = выключить канарейку и вернуть прежний бинарник с нетронутым data root, downgrade по мигрированной копии не пробовать.
- PARK: продуктивный апгрейд до 0.12.0 до появления offline-копии data directory, smoke-теста совместимости и доказательства отката, несмотря на давление безопасности.
- До апгрейда: не давать недоверенным агентам произвольные аргументы управления проектами и не открывать HTTP за пределы localhost.
- PARK: облачный challenger как постоянный второй индексатор — только on-demand, на обычном неконфиденциальном коде и после чистого baseline; сравнивать не более двух веток за раунд.
- Политика клиентов: сначала symbol/exact, затем semantic/cascade, граф — только для поддерживаемых языков; при freshness warning, non-git root или неожиданном no-answer — обязательный read_file_range и для критичного ответа проверка по диску.
- Измерять ресурсы локально и последовательно на каждом хосте (RSS/private bytes, число процессов, CPU, VRAM/Metal, диск, сеть, p50/p95), а не опираться на цифры vendor.
- Исключить из canary-корпуса .git, архивы, бэкапы, сгенерированные конфиги, кэши и scratch-копии; проверить effective config (project-config) на причину их попадания в индекс.

## Открытые вопросы
- Что стало причиной устаревшего результата x_outbox.enqueue: сбой watcher, правила игнорирования, блокировки файлов или иное; затронут ли весь индекс из 28 265 chunks?
- Точный механизм и дефолты auto_reindex/watcher, обработка rename/delete/overflow и precedence .gitignore/.indexer.toml.
- Реальная экономия RAM/CPU от shared HTTP против stdio и стационарный footprint на Windows Hub, Apple Silicon Studio и Intel Mac Pro.
- Совместимость data directory 0.11→0.12 и возможность downgrade после миграции.
- Какие аппаратные идентификаторы входят в fingerprint, сколько одновременных активаций разрешено купленной лицензии, есть ли постоянная офлайн-активация для Pro/Security.
- Нативная поддержка Intel macOS (x86_64) и срок её поддержки; путь глобального конфига на Windows.
- Фактическое поведение PowerShell в 0.11.0 и 0.12.0.
- Модели эмбеддингов и реранкера (название, размерность, квантизация) не раскрыты; полная история релизов 0.5/0.6/0.8/0.10 не восстановлена.
