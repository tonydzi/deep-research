# Insight (DR DR26-07-06-HUB-04): Визуальная типографика GitHub-markdown для сериализованной книги (The Journey)

> Отчёт отвечает на вопрос, как средствами GitHub Flavored Markdown + ограниченного HTML построить устойчивую редакционную визуальную систему для книги-сериала, читаемой прямо на github.com.

## Ключевые выводы
- GitHub даёт GFM + санитизированный HTML: заголовки, alerts (NOTE/TIP/WARNING/CAUTION/IMPORTANT), `<details><summary>`, таблицы, footnotes, Mermaid/geojson/topojson/stl, MathJax (inline и ```math```), `<picture>`, `<kbd>`, `<sub>/<sup>/<ins>` — но агрессивно вырезает `<script>`, inline `style`, `class`, `id` и старый `<font color>`, поэтому кастомных цветов текста и CSS-типографики на github.com нет в принципе.
- `<details>/<summary>` — надёжный способ прятать вторичный слой (техдетали, приложения), но alerts нельзя вкладывать в другие элементы и особенно в `<details>` — это известная зона багов рендеринга; правило: details — да, alert-в-details — нет.
- Таблицы GFM — инструмент для данных (артефакты, KPI, статусы), а не для журнальной вёрстки; на мобильном широкие таблицы превращаются в тяжёлый горизонтальный скролл и убивают ритм чтения.
- Тёмная/светлая тема изображений закрывается тремя рабочими стратегиями: `<picture>` с `prefers-color-scheme`, Markdown-фрагменты `#gh-dark-mode-only`/`#gh-light-mode-only`, либо одна нейтральная картинка, переживающая обе темы.
- Ключевой редакционный принцип — «один приём = одно значение»: за каждым типом блока (вопрос читателю, челлендж/tip, warning, техдеталь-details, цитата, артефакты-таблица, пост автора) закрепляется ровно один устойчивый markdown-паттерн, повторяющийся из главы в главу.
- Числовые редакционные нормы для главы 1000–2000 слов: абзац 2–4 предложения/40–90 слов (потолок 120–140), подзаголовок каждые 150–250 слов, 4–8 H2/H3 на главу, 1–3 жирных акцента на абзац, 1–3 горизонтальных разделителя, максимум 3–5 акцентных блоков и всего 1–2 alert на главу.
- GitHub автоматически строит Outline-меню по заголовкам (при 2+ headings), но кастомные якоря `<a name>` в Outline не попадают, а автоякоря заголовков ломаются при переименовании/дублировании (получают суффиксы -1, -2) — для стабильных ссылок нужны явные именованные якоря.
- Issue/PR автоссылки формата `#123` не работают внутри markdown-файлов репозитория (только в комментариях/PR) — в тексте книги нужны явные ссылки.
- Разобранные образцовые репозитории дают конкретные паттерны: GitHub Docs (дисциплина alert-ов: 1–2 на материал, не подряд), sindresorhus/awesome (центрированный hero, `<picture>` для лого, ручной TOC), jwasham/coding-interview-university (личный cold open + task-list прогрессия), rust-lang/book (ровный chapter rhythm без layout-трюков), codecrafters-io/build-your-own-x (один hero + одна цитата → сразу структура), sharkdp/bat (скрин рядом с тезисом, который он подтверждает).
- Главные антипаттерны: передоз emoji, «box on box» (alert внутри alert/details), таблица как способ повествования, хрупкие автоякоря при переименовании заголовков, нечитаемые в тёмной теме картинки, ставка на CSS/цветной текст, ленивая issue-нотация `#123` в тексте главы.

## Рекомендации / решения
- Зафиксировать «семафор блоков» на всю книгу: вопрос читателю → `### ❓`, tip/челлендж → `[!TIP]`, риск/цена ошибки → `[!WARNING]`/`[!CAUTION]`, техдеталь → `<details><summary>`, цитата → обычный blockquote, финансы/артефакты → таблица, пост автора → обычный текст без callout-обрамления.
- Использовать готовый шаблон главы-эпизода: баннер через `<picture>` (light/dark SVG) → холодный опен → блок «Польза дня» → «Намерения» (`[!IMPORTANT]` + чек-лист) → «История дня» с вопросом читателю и цитатой → сворачиваемая техдеталь → Mermaid-схема при необходимости → «Epic Fails» (`[!CAUTION]`) → таблица «Артефакты» со скрином-квитанцией → «Пост автора» → сноска.
- Хранить все assets внутри репозитория по относительным путям (`/assets/chapters/<id>/...`), не полагаться на внешние хостинги — так сохраняется история версий и целостность при клонировании.
- Каждый баннер/картинку делать theme-aware: SVG-баннер через `<picture>` с отдельными light/dark вариантами, либо фрагменты `#gh-dark-mode-only`/`#gh-light-mode-only` для чистого Markdown без HTML.
- Держать жёсткий лимит: максимум 1–2 alert на главу, никогда не вкладывать их друг в друга или в `details`; details — только для факультативного, не для смыслового backbone.
- Mermaid — для схем, которые должны быть diffable и часто обновляться (flowchart, timeline, sequence); статичную картинку/скриншот — для брендовой типографики, доказательства (квитанции) или сложной ручной композиции.
- Писать краткий, содержательный русский alt-текст для каждой картинки (передавать смысл в контексте, не описание пикселей); для чисто декоративных — `alt=""`.
- Не пытаться обойти платформу через inline style/class/id/`<font color>` — заранее принять, что кастомной CSS-типографики на github.com не будет, и строить визуальный язык только на разрешённых примитивах.

## Открытые вопросы
- Не существует единого исчерпывающего официального публичного allowlist HTML-тегов/атрибутов для GitHub Markdown — практический подход: опираться на документированные элементы, остальное проверять вживую на github.com.
- Предпросмотр в веб-редакторе GitHub иногда отличается от финального рендера committed README; рендер GitHub Pages не эквивалентен рендеру самого github.com для alerts.
- Поведение `align="left/right"` у изображений имело регрессии и не задокументировано как надёжный layout-механизм — требует точечной проверки перед использованием.
