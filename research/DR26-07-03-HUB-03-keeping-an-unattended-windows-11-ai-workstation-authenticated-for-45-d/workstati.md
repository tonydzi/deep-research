# Keeping an Unattended Windows 11 AI Workstation Authenticated for 45 Days

## Bottom line

For a 45-day unattended Windows 11 Pro box, the winning strategy is not “hope sessions last.” It is to harden **four separate layers** so that each one survives independently: Google **browser sessions**, Google **OAuth refresh tokens**, the **Windows interactive desktop session**, and **out-of-band rescue**. The strongest current pattern is: keep each critical Google account in its **own Chrome profile**, keep that profile on the **same device / same browser / same usual network path**, avoid any cookie-clearing or unnecessary re-consent events, pin Windows to the current feature release, set Windows Update to **notify before download/install** so no update is staged automatically, and configure **Sysinternals Autologon** plus **no sleep / no sign-in on wake** so a surprise reboot still lands back in the same user context where Chrome can decrypt its cookies. For recovery, do not rely on the Google web session itself as your only lifeline; add a **console-attaching remote-access path** from the owner’s phone, and ideally a **hardware KVM with ATX power control** for the “OS is down / login screen / BitLocker prompt” class of failure. citeturn34search0turn21search0turn7view5turn7view6turn22search24turn11view2turn26view0turn8view2turn6search0turn36search10turn35search2turn20view10turn20view11

The uncomfortable truth is that Google does **not** publish a fixed lifetime for consumer Google web sessions in desktop Chrome. What Google does publish is the machinery around them: cookies must persist, trusted-device state depends on cookies, unusual sign-ins from a different device or location can trigger extra verification, sensitive actions can force “Verify it’s you,” and Workspace admins can centrally impose session timeouts. For managed Google Workspace web sessions, the default web session length is **14 days**, but admins can shorten it or set it to **never expire**; for consumer accounts, no equivalent public fixed TTL appears in the Help documentation. ## Google web sessions in Chrome

For Google web UI access, the most important distinction is **consumer Google Accounts versus Google Workspace accounts**. For Workspace, Google explicitly documents session control: the default web session length for Google services is **14 days**, admins can change it, and even set it so the session **never expires**. When the configured session expires, users hit a “Verify it’s you” page and must sign in again. Google also notes that admins can forcibly invalidate sign-in cookies, and that changing the session-length policy only takes full effect after sign-out/sign-in. None of that gives you a fixed TTL for consumer Chrome sessions, but it does prove that session lifetime is policy- and risk-driven rather than a single universal cookie expiry constant. citeturn19view1

For ordinary Google Account web sessions, the public documentation points to **cookie persistence** as the foundation. Google’s “Stay signed in” help says to keep cookies enabled, warns that some antivirus or related software may delete them, recommends using the latest browser, and explicitly tells 2-Step Verification users to add **trusted computers**. Google’s trusted-computer page is equally blunt: checking “Don’t ask again on this computer” is only durable if the browser keeps cookies; if cookies are disabled or deleted after a period of time, Google can ask for 2-Step Verification again. In other words, for your use case, **cookie survival is not a side issue; it is the session.** citeturn7view5turn7view6turn22search2

Google also documents the main **risk triggers** that can push a normally persistent session into re-verification. When Google sees a sign-in from a **different location or device than normal**, it may block or challenge it as suspicious. Google’s recovery guidance says recovery works better from a **familiar device**, the **same browser**, and a **usual location**. Google prompt documentation says that if Google notices something different about how you sign in, like your **location**, you may be asked to take extra steps to confirm it’s you. That strongly supports a practical rule: do not let the unattended PC appear to “travel.” Keep it on a stable ISP path, or if you must use VPN, use a **single fixed exit** and do not rotate endpoints or geography during the unattended period. citeturn7view7turn21search0turn20view1

Google also has **cool-down windows** around trust-building. For sensitive actions, Google may block changes for **7 days** if it cannot verify identity, and specifically calls out factors that have not been associated with the account for at least 7 days, including the device used to sign in, phone number, security key, and passkey. Google separately says a trusted passkey or physical security key can help speed up trust for a new passkey, physical security key, 2-Step Verification phone number, or recovery phone number. Operationally, that means you should finish all identity plumbing **at least a week before departure**: recovery number, passkey, Google Prompt on the owner’s phone, and any security keys or trusted-device decisions should be settled and then left untouched. citeturn7view8turn20view2

The best device-hardening tactics are therefore boring rather than clever. Put each critical Google account in its **own Chrome profile**, because Chrome profiles keep passwords, history, settings, and related browsing state separate; this reduces blast radius if one profile gets signed out or corrupted. In each critical profile, complete 2SV once and check **“Don’t ask again on this computer.”** Make sure Chrome is not set to clear cookies on exit, and that any privacy tool, antivirus suite, or browser cleaner is not deleting Google cookies. Use the same machine, same browser profile, and stable location/path long enough before the trip that the device becomes “normal” in Google’s risk model. citeturn34search0turn7view6turn7view5turn22search2turn21search0

On the specific question of whether regular automated activity **helps or hurts** session longevity, the public evidence is asymmetric. I found no public Google document saying that “periodic activity keeps the session alive” for consumer browser sessions. What Google does document is that **familiarity** helps, while unusual sign-ins or unusual patterns raise verification. So the defensible conclusion is this: **ordinary use inside the same established profile/device/location is not the problem; repeated re-logins, IP/geo churn, and activity that trips Google’s risk engine are the problem.** Routine low-risk browsing in the already-authenticated profile is unlikely to hurt; using automation to repeatedly touch sensitive account pages or to simulate fresh sign-ins is a bad idea. There is no public evidence that synthetic “keepalive browsing” provides extra durability beyond simply keeping the existing authenticated profile intact. citeturn21search0turn7view7turn20view1turn22search24

Two emerging platform changes matter here. First, Chrome on Windows now protects secrets with **App-Bound Encryption**, which ties cookie decryption to the application identity and machine, building on DPAPI. Second, Google is rolling out **Device Bound Session Credentials**, which cryptographically bind eligible web sessions to device-held keys so stolen cookies quickly become useless off-device. For your architecture, this cuts both ways: it is good for security, but it also makes “just copy the profile/cookies elsewhere” a progressively worse backup plan. The reliable strategy is to preserve the **same machine + same Windows user + same Chrome profile**, not to count on portable cookie artifacts. citeturn30view2turn30view0turn30view4

One more trigger matters because it is easy to forget: **password changes**. Google says that if you change or reset your password, you are signed out everywhere except devices used to verify that it’s you, some devices with third-party app access, and helpful home devices. Separately, Google’s OAuth docs say refresh tokens with **Gmail scopes** are revoked if the user changes password. For this unattended window, a password change is essentially a self-inflicted outage for both browser sessions and Gmail API tokens. The rule is simple: **no password changes during the unattended period unless you are willing to do live rescue.** citeturn20view4turn33view3

## OAuth refresh tokens and what can revoke them

Your Gmail API layer is much easier to reason about than browser sessions because Google actually documents the revocation conditions. Google’s OAuth documentation says refresh tokens can stop working because the **user revoked the app**, the refresh token was **unused for six months**, the **user changed passwords and the token contains Gmail scopes**, the account exceeded the maximum number of granted live refresh tokens, or the user granted **time-based access** and that access expired. Google’s policy page adds that refresh tokens can be invalidated **at any time**, including by automated protection systems, and recommends integration with **Cross-Account Protection** if you want notification of account-security events. citeturn33view3turn31view0

The specific quota trap is real. Google says there is currently a limit of **100 refresh tokens per Google Account per OAuth 2.0 client ID**; if you mint new ones past that limit, the **oldest refresh token is invalidated without warning**. Google also says there is a larger total cap across all clients, and recommends limiting the number of authorized clients per account to around **15–20** if you need many programs or machines. So the operational tactic is obvious: **do not keep generating fresh consent grants for the same mailbox/client unless you absolutely have to.** Reuse the same durable production refresh token, keep a primary and a tested spare only if you truly need one, and stop any code path that opportunistically requests new grants every redeploy. citeturn33view0turn33view2

Project state also matters. Google’s OAuth readiness docs note that apps in **Testing** status get **7-day refresh tokens**, while production publishing is required for long-lived behavior. Google’s policy docs further say Google can delete **unused OAuth clients** after six months of inactivity, and that if a production app is no longer approved to use certain scopes, Google may revoke tokens carrying those scopes without notice. Since you already moved the desktop app client to **Production**, the main practical follow-through is: do not ever move that project back to Testing, keep the consent screen/configuration healthy, keep the project contacts current, and use the client regularly so neither the tokens nor the client become “neglected infrastructure.” citeturn32search4turn32search3turn31view0

The avoidance checklist for refresh-token loss is therefore tight and not complicated. Keep each mailbox’s refresh token in encrypted long-term storage and use it regularly. Do not rotate primary account passwords during the unattended period. Do not create needless new consent grants. Do not split the same mailbox across a large number of test machines using the same client ID. Keep the OAuth consent screen in Production and retain any verification tied to Gmail scopes. If you want better incident awareness, integrate Google’s Cross-Account Protection/RISC events into the same alerting fabric as your connector watchdog. citeturn33view0turn31view0

For rescue from the owner’s phone, the two best Google-native factors are **Google Prompt** and **passkeys**, with **backup codes** as an offline spare. Google Prompt lets the owner confirm a sign-in from the phone and may ask for number matching if the location/sign-in looks unusual. Google says a passkey bypasses the second authentication step because possession of the passkey device proves the device is yours. Backup codes are one-time and can be regenerated, which makes them a good cold spare in the owner’s phone password manager. The design implication is that “recovery that requires typing the primary password or live OTP into the unattended agent” is bad, but “owner taps phone prompt / passkey / backup code during a rescue session” is viable. citeturn20view1turn20view0turn20view3

## Windows updates, surprise reboots, and how to survive them

The Windows side has one central lesson: **do not rely on pause alone** if the desktop absolutely must not restart while you are away. Microsoft still documents a **35-day** pause limit, but current support documentation now also says you can **extend the pause again later**, as long as the new end date is within 35 days from “today.” Microsoft further says that while updates are paused, Windows does not download or install new updates, updates that require a restart are postponed, and the device does not restart automatically to complete installation. That is useful, but it is still not autonomous; someone or something has to extend the pause again before expiry. citeturn11view0turn11view1

For a 45–60 day unattended stretch, the safer foundation is **policy-based non-installation**, not timer-based pausing. Microsoft’s update policy documentation says **Configure Automatic Updates = 2** means “Notify for download and auto install”: Windows finds applicable updates, notifies that updates are ready to be downloaded, and the user must then go into Windows Update to download and install them. When this policy is disabled, updates must be downloaded and installed manually; when not configured, Windows can manage updates through normal Settings behavior. In plain English: if you set AU option **2**, Windows should not even stage the update without manual action, which is stronger than trying to suppress reboots after an update has already landed. citeturn11view2

Blocking **feature** updates is a separate control and should also be used. Microsoft’s Policy CSP says **ProductVersion** plus **TargetReleaseVersion** lets you specify the Windows product and the target feature release you want devices to move to and/or **stay on until end of service or policy change**. Microsoft also documents feature deferral up to **365 days** on the general-availability channel. For an unattended box, that means pin the current stable Windows 11 release so the machine does not decide to jump to a new feature version while no one is there to deal with fallout. Do this even if you also use pause or metered networking. Feature-version pinning and quality-update non-download solve different problems. citeturn26view0

Metered networking is only an **adjunct**, not a guarantee. Microsoft says metered connections reduce data usage and that **some updates for Windows won’t be installed automatically** on a metered connection. That wording is the tell: some, not all. So metered Ethernet/Wi-Fi is worth turning on as an additional friction layer, but it should sit under policy controls rather than replace them. The order of trust is: **target release pinning + Configure Automatic Updates = 2** first, **metered connection** second, **pause UI** third. citeturn11view5

You also should not build your strategy around the old “no auto-restart with logged on users” folklore. Microsoft’s current documentation increasingly classifies several auto-restart notification/restart policies as **legacy** and “not applicable for Windows 11,” and their newer recommendation is to use compliance-deadline policies like **Don’t auto-restart until end of grace period**. That is fine for enterprise compliance, but it is not what you want here, because deadline policies are explicitly designed to eventually force progress toward installation and restart. For a one-off unattended workstation, **preventing download/install** is cleaner than trying to win a policy battle about restart behavior after the payload is already on disk. citeturn11view3turn11view4

If the box reboots anyway, the fallback must restore an **interactive user desktop** automatically. Sysinternals **Autologon** is the best current Microsoft-supported convenience tool for this because it stores the password as an **LSA secret** instead of the older plain-text Winlogon `DefaultPassword` approach. Microsoft’s older KB on raw AutoAdminLogon explicitly warns that the manual registry method stores the password in **plain text** in the registry and that the key can be remotely read by authenticated users. Sysinternals Autologon is still not “safe” in the strong sense—Microsoft warns that an administrator can retrieve and decrypt the LSA secret—but it is materially better than the raw registry method. Microsoft also notes that holding **Shift** during boot/logoff bypasses autologon for that login, legal/logon-banner policy can break autologon, and Exchange ActiveSync password restrictions can disable it. citeturn8view3turn8view2turn8view5

That interactive logon matters because Chrome on Windows protects cookies and related secrets with **DPAPI** and now **App-Bound Encryption** tied to the machine and application identity. If the same Windows user is automatically logged back into the console, Chrome is in the right context to decrypt its cookies again. If instead the machine is sitting at the sign-in screen, or you launch browser automation under a non-interactive security context, you are in the failure zone. The same logic applies to GUI automation tasks: Microsoft’s Task Scheduler docs show that **InteractiveToken** runs only in an existing interactive session, while S4U/no-logged-on-user modes have serious limitations and no access to encrypted files or visible desktop UI. For browser-driving agents, you want processes started **after autologon**, in the actual user desktop. citeturn30view2turn36search3turn36search10turn36search12

Power policy should be made brutally simple: **never sleep while plugged in**, and **never require sign-in on wake**. Microsoft’s Windows 11 power settings expose “Make my device sleep after,” and sign-in settings expose the “Require sign-in” behavior when waking from sleep. For your scenario, sleep is not a power-saving feature; it is an outage vector. Also disable reliance on “restartable apps” as a recovery mechanism; Microsoft exposes that toggle in Sign-in options, but for a headless automation workstation you want **explicit startup orchestration**, not optimistic app resurrection. Use autologon, then start the agent through Startup or a task set to run **only when the user is logged on**. citeturn6search0turn6search1turn28search1turn28search2turn36search11

A final Windows landmine is **BitLocker**. Microsoft documents that BitLocker recovery can be triggered by security risk or hardware change, and its recovery overview exists precisely because startup may fail to unlock automatically. That means your phone-rescue kit must include the **BitLocker recovery key** in a place the owner can access from the phone. If the machine lands on a BitLocker recovery screen after firmware or recovery-events, no amount of OAuth or Chrome hardening will help until that key is entered. citeturn29search0turn29search1turn29search6

## Messenger sessions and remote rescue from a phone

Telegram is the easy one, but only if the session artifacts are treated like credentials. Telethon documents that its session state is written to `.session` files and that those files contain enough information to log in **without re-sending the code**. It also says to call `Client.disconnect()` before exiting so the session is saved, and warns that leaking the session file grants a third party immediate account access. So for the unattended PC, the durable pattern is: keep the Telethon session on stable disk, back it up securely, and never regenerate it unless necessary. citeturn20view8turn20view7turn18search6

WhatsApp via linked devices is durable enough for your stated design, but only if the primary phone remains in the loop. WhatsApp’s help center says linked devices work **without the phone online**, but will log out if the phone is **unused for over 14 days**. Baileys explicitly says it uses WhatsApp’s **Linked Devices** architecture rather than the business API, and its docs say successful reconnection depends on persisting credentials and encryption keys; after login, Baileys emits `creds.update` events that you must save, and valid stored credentials allow reconnect **without QR**. That means your current assumption is basically correct, but the operational condition is strict: the phone must remain active in normal WhatsApp use, and Baileys auth state must be durably persisted. citeturn18search7turn37view3turn37view0turn37view1

For phone-based rescue, you need **two different remote-access classes**. The first is a software remote-control path that attaches to the already-running desktop. Chrome Remote Desktop is the low-friction option: Google says you can set up remote access to a Windows computer and then securely access it whenever you are away, using your **phone, tablet, or another computer**; iPhone/iPad access is supported through the Chrome Remote Desktop app or web flow, and Android access is also supported. The downside is obvious: CRD itself depends on access to a Google account, so it is easy but not independent of the Google identity layer you are trying to protect. citeturn35search2turn35search3turn35search1turn17search2

The second class is an **independent control plane**. Tailscale gives devices a stable Tailscale IP and MagicDNS name even when they are behind NAT or change networks, which makes it a good transport to a self-hosted or non-Google console tool. RustDesk markets itself as secure remote access with self-hosting available, and Tailscale has published an integration pattern for RustDesk over a tailnet. This combination is not as turnkey as CRD, but it avoids making your rescue path depend on Google web auth remaining healthy. citeturn20view11turn15search2turn15search3

The real state-of-the-art rescue layer, though, is **hardware KVM with power control**. PiKVM exposes **ATX power management** functions via its API, including reading power state, changing power state, and sending an ATX button press; its hardware docs also describe optional ATX wiring so you can manage the PC’s power from the KVM. This is the difference between “I can remote into Windows if it’s alive” and “I can still interact when Windows is at BIOS, BitLocker, boot failure, frozen login, or black screen.” For a workstation that will run unattended for weeks while a non-technical owner is far away, that is the single most valuable extra layer. citeturn20view10turn15search10turn15search16

## Limits of the evidence

Two things remain genuinely underspecified in public documentation. First, Google does **not** publicly document a fixed consumer desktop-Chrome session TTL for Google Account web sessions, and I did not find a public Google source that says a routine **Chrome version update alone** forces Google re-authentication. Second, Google documents risk-based challenges around unfamiliar devices, locations, sensitive actions, and cookies, but it does **not** publicly enumerate “automation-like activity” as a specific re-auth trigger in a way that lets you engineer a guaranteed safe browser-automation pattern. The safest reading is therefore conservative: keep the device/profile/network path familiar, avoid repeated sign-ins and sensitive flows, and assume that any behavior which makes the machine look less like its usual self increases re-auth risk. citeturn7view5turn7view7turn20view1turn21search0
