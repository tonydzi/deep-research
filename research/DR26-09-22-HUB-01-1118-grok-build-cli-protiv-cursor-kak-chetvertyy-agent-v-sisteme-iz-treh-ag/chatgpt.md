A. ВЫВОД ДЛЯ РЕШЕНИЯ — срез на 22.09.2026

Короткий вердикт: Cursor сейчас не стоит добавлять четвёртым постоянным пишущим агентом в тот же checkout. Он сильно пересекается с Codex CLI и Grok Build CLI, но не приносит встроенной межвендорной блокировки файлов. Четвёртый писатель увеличит число гонок, каналов конфигурации, счетов и вариантов расхождения канона.

Рекомендуемая конфигурация:

1. Claude Code остаётся оркестратором.
2. Codex CLI остаётся независимой OpenAI-рельсой и исполнителем.
3. Grok Build пока остаётся, но его право записи надо условно приостановить до проверки полного чтения канона.
4. Cursor не добавляется как четвёртый автономный писатель.
5. Если Cursor нужен ради IDE, Marketplace или отдельного лимита, использовать его сначала только как read-only reviewer через Ask mode или в отдельном worktree.

Критическая находка: опубликованная документация Grok Build говорит, что каждый найденный файл инструкций ограничивается 10 000 символами и при превышении обрезается с предупреждением. Один CLAUDE.md примерно на 30 000 токенов заведомо больше этого порога. Поэтому утверждение «Grok грузит общий канон целиком» сейчас документами не подтверждается и, вероятно, неверно. При обычном соотношении символов и токенов Grok может видеть лишь малую начальную часть файла. Это не мелкая несовместимость, а нарушение управляющего контура: он может не увидеть правила про лизы, внешние действия и независимую приёмку. Факт о лимите: https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-shell/README.md

Оценка: главный следующий шаг — не установка Cursor, а приёмочный тест Grok 1.0.40: метка в хвосте CLAUDE.md, `grok inspect --json`, вопрос агенту о хвостовой метке, проверка числа обнаруженных скиллов и попытка нарушения запрещённого правила в безопасной песочнице. До этого Grok годится для чтения, анализа и работы в изолированном worktree, но не как равноправный писатель в общей папке.

Если проверка подтвердит обрезание, лучший выбор — заменить Grok Build на Cursor в роли третьего локального агента, а не держать обоих. Claude и Codex при этом не заменять.

Уверенность в основном вердикте: высокая. Уверенность в фактическом поведении именно установленной версии Grok Build 1.0.40: средняя, потому что публичная документация и ветка main могут отставать или опережать установленный бинарник. Нужен локальный приёмочный тест версии.

B. АРХИТЕКТУРНЫЙ КЛАСС

B1. Grok Build CLI и Cursor

Факт на 22.09.2026: Grok Build — терминальный агентный harness. Он работает интерактивно, headless через `grok -p`, выдаёт JSON или streaming JSON и предоставляет ACP-интерфейс для интеграции с IDE и другими приложениями. Это самостоятельный исполнитель, а не только чатовая оболочка. Источники:

https://x.ai/news/grok-build-cli

https://docs.x.ai/build/cli/headless-scripting

https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-shell/README.md

Факт: Cursor остаётся IDE-продуктом, но его CLI уже нельзя считать декоративным приложением к GUI. `agent -p` официально предназначен для скриптов и CI; CLI поддерживает Agent, Plan и read-only Ask modes, сессии и передачу работы Cloud Agent. Windows поддерживается отдельным установщиком. Источник:

https://prod.cursor.com/docs/cli/overview

Однако Cursor прямо предупреждает, что часть функций работает иначе либо доступна только в редакторе. Поэтому CLI равноправен GUI по базовым режимам агента, но не по всей поверхности продукта: Agents Window, визуальный review, canvas и часть editor-интеграций остаются GUI-функциями. Источник:

https://prod.cursor.com/help/integrations/cli

Оценка: для Telegram-будильника и ночного запуска оба относятся к одному эксплуатационному классу — локальные headless coding agents. На уровне всего продукта классы разные:

- Grok Build: CLI-first агентный runtime.
- Cursor: IDE-платформа с полноценным, но не полностью эквивалентным IDE, CLI-агентом.
- Практическое следствие: Cursor не обязан держать открытое GUI-окно для ночной работы, но установка Cursor ради одного headless worker даёт заметное пересечение с уже имеющимися Codex и Grok.

B2. Grok Build и Grok Bot

Факт: это разные продукты и разные вычислительные среды, а не два режима одного процесса.

Grok Build выполняет инструменты на локальном компьютере, где запущен CLI. Grok Bot — постоянный облачный агент с собственным браузером, файловой системой и терминалом; его «компьютеры» работают в облачной инфраструктуре Cursor. Он доступен через отдельные desktop/mobile surfaces и может подключаться к внешним сервисам. Источник:

https://docs.x.ai/grok-bot/overview

Факт: Grok Bot отдельно умеет работать с локальным компьютером через управляемый механизм разрешений Ask/Allow/Never. Его облачные боты могут делить один persistent computer, а значит файлы и логины на этом компьютере также становятся общими между ними. Источник:

https://docs.x.ai/grok-bot/approvals-security-and-privacy

Оценка: Grok Bot нельзя подставить вместо Grok Build в существующий локальный протокол «одна папка + файловые лизы». Это отдельный удалённый узел флота. Для него потребуются:

- отдельная идентичность узла;
- синхронизация нужного репозитория;
- доставка канона и скиллов;
- отдельный trust boundary;
- новый маршрут конвертов и ACK;
- явное правило, какие облачные боты делят компьютер.

Формулировка «Grok Bot — агенты в приложении X» уже неточна. Связь с X и SuperGrok есть, но текущая документация описывает самостоятельного persistent cloud teammate.

C. ОБЩАЯ ПОЛКА ПРАВИЛ, СКИЛЛОВ И MCP

C1. Grok Build

Факт: xAI официально заявляет совместимость Grok Build с Claude Code без дополнительной настройки. Grok автоматически обнаруживает `CLAUDE.md`, `.claude/rules`, Claude skills, agents, hooks, plugins, marketplaces, MCP-конфигурации и «внутренний путь лаборатории». Он также читает семейство `AGENTS.md`. Это официальная функция, а не случайное совпадение путей. Источники:

Для существующей полки «внутренний путь лаборатории»<имя>/SKILL.md` это лучший zero-copy вариант: junction в `.grok` не требуется.

Но совместимость неполная семантически. Например, Grok принимает поле `allowed-tools` в SKILL.md, однако прямо пишет, что оно не выдаёт и не ограничивает инструменты. Аналогично некоторые поля, включая `model`, `effort`, `license` и `compatibility`, распознаются, но не применяются. Источник:

https://docs.x.ai/build/features/skills-plugins-marketplaces

Грабля: скилл, который в Claude выглядит безопасным из-за `allowed-tools`, в Grok не получает такого ограничения. Реальное ограничение надо задавать политикой Grok или CLI-флагами, а не переносимым frontmatter.

Критическая грабля: каждый файл инструкций ограничен 10 000 символами. Документация также говорит, что Grok сканирует правила от корня репозитория к текущей папке, а более глубокие файлы добавляются позже и фактически получают приоритет при конфликте. Источник:

https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-shell/README.md

Оценка: совместимость Grok с каталогом из 290 скиллов официальная и сильная. Совместимость с одним монолитным 30K-token CLAUDE.md — провалена по документированному лимиту, пока локальный тест версии 1.0.40 не докажет иное.

C2. Cursor

Факт: локальный Cursor официально обнаруживает скиллы не только в своих каталогах, но и в `.claude/skills`, `.codex/skills`, «внутренний путь лаборатории» и `~/.codex/skills`. Значит локальный Cursor/CLI может читать ту же физическую полку без копирования. Источник:

https://prod.cursor.com/docs/skills

Факт: Cursor также признаёт CLAUDE.md как постоянно применяемый формат правил наряду с AGENTS.md и имеет собственные `.cursor/rules`. Источник:

https://prod.cursor.com/help/customization/rules

Факт: MCP является нативной частью Cursor, включая локальные и удалённые MCP-серверы. Источник:

https://prod.cursor.com/docs/mcp

Важное ограничение: это справедливо для локального Cursor. Cloud Agents не получают автоматически содержимое «внутренний путь лаборатории». Cursor синхронизирует в облако только личные скиллы из `~/.cursor/skills`; остальные локальные каталоги остаются локальными. Для self-hosted workers документация предлагает repo-level skills или предварительное встраивание в образ. Источник:

https://prod.cursor.com/docs/skills

Оценка:

- локальный Cursor: совместим с общей полкой без копии;
- Cursor Cloud Agent: несовместим с вашим требованием «одна физическая полка, ноль копий» без изменения архитектуры;
- Grok Build локально интегрируется в Claude-экосистему глубже: кроме skills и rules он заявляет прямой импорт Claude plugins, hooks, agents, marketplaces и конфигураций;
- Cursor лучше подходит для переносимого стандарта Agent Skills, но его облако создаёт отдельный канал распространения.

C3. Два канона одновременно

Факт для Grok: несколько найденных instruction-файлов конкатенируются; файлы глубже в дереве идут позже и фактически выигрывают при конфликте. Источник:

https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-shell/README.md

Факт для Cursor: существуют team, project и user rules с определённой иерархией. Но в открытой документации нет достаточно строгого контракта, однозначно описывающего разрешение конфликта между одинаково применимыми CLAUDE.md, AGENTS.md и `.cursor/rules` при разных версиях канона. Источник:

https://prod.cursor.com/help/customization/rules

Оценка: одновременная загрузка двух версий канона — недопустимое состояние, даже если известен порядок. Модель может следовать более позднему правилу локально, но продолжать использовать понятия и исключения из старого файла. Это не транзакционное «последний файл заменил первый».

Правильный invariant:

- только один authoritative full canon;
- альтернативные AGENTS.md или `.cursor/rules` содержат только короткий адаптер и ссылку на версию, а не копию канона;
- стартовый preflight сверяет hash/version;
- несовпадение версии означает NO-WRITE;
- проверяется не факт обнаружения CLAUDE.md, а хвостовая метка и критические правила из разных частей файла.

D. ТРИ АГЕНТА В ОДНОЙ ПАПКЕ

D1. Что есть из коробки у Grok

Факт: Grok поддерживает отдельный git worktree для сессии и операции создания, применения и удаления worktree. Headless и resume-сценарии также поддерживаются. Источники:

https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/17-sessions.md

https://docs.x.ai/build/cli/reference

Факт: через набор разрешённых и запрещённых tools можно собрать reviewer без редактирования и shell, а `grok inspect --json` показывает обнаруженные инструкции, skills, MCP, hooks и источники конфигурации. Источник:

https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-shell/README.md

Нет данных о встроенном Grok-механизме распределённых файловых лизов, понимающем Claude Code и Codex CLI. Worktree — изоляция git checkout, а не межвендорная блокировка произвольного файла.

D2. Что есть из коробки у Cursor

Факт: Cursor Agents Window создаёт изолированные worktrees для параллельных агентов. Отдельный checkout предотвращает прямое перетирание рабочих файлов; setup hooks помогают подготовить зависимости на Windows и других платформах. Источник:

https://prod.cursor.com/docs/configuration/worktrees

Факт: Cursor предупреждает, что subagents по умолчанию могут разделять checkout родителя и способны перезаписывать изменения друг друга; изоляцию надо явно запросить, чтобы получить отдельный worktree или VM. Источник:

https://prod.cursor.com/docs/subagents

Факт: Cursor CLI имеет Ask mode как read-only режим. Дополнительно permissions позволяют запрещать Read, Write, Shell, MCP и WebFetch по правилам. Источники:

https://prod.cursor.com/docs/cli/overview

https://prod.cursor.com/docs/cli/reference/permissions

У Cursor также нет документированной межвендорной lease-системы для общего checkout.

D3. Что worktree не решает

Оценка: worktree изолирует отслеживаемые git-файлы, но не защищает общие внешние ресурсы:

- SQLite и другие базы вне worktree;
- «внутренний путь лаборатории», `~/.codex`, `~/.grok`;
- логи и очереди с абсолютными путями;
- Telegram offset/state;
- secrets;
- generated outputs вне репозитория;
- локальные сервисы, порты и браузерные профили;
- действия наружу.

Следовательно, существующие файловые лизы и протокол конвертов сохраняются. Worktree добавляется поверх них, а не заменяет их.

Главные реальные грабли четвёртого агента:

- два агента честно работают в разных worktrees, но одновременно мигрируют одну общую БД;
- reviewer запускается в Ask mode, но разрешённый MCP имеет write-side effect;
- агент завершает patch в worktree, а другой применяет его поверх уже изменившегося main;
- общий автотест использует фиксированный temp/output path;
- два headless процесса подбирают один Telegram-конверт;
- агент считает собственный зелёный тест независимой приёмкой;
- правила загружены из разных версий канона.

D4. Сравнение защиты на Windows

Факт: Cursor документирует sandbox на Windows через WSL2, а также режим `workspace_readonly`. При этом автоматический command-review классификатор сам по себе не считается границей безопасности. Источники:

https://cursor.com/blog/agent-sandboxing

https://prod.cursor.com/docs/reference/sandbox

https://prod.cursor.com/docs/agent/security/run-modes

Факт: документация Grok описывает OS-level sandbox через Landlock на Linux и Seatbelt на macOS; сопоставимый Windows backend в открытой документации не указан. Источник:

https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/18-sandbox.md

Оценка: для недоверенного автономного кода на Windows у Cursor сейчас лучше документированная граница. У Grok tool deny-list остаётся полезной, но это не равно доказанной OS-level изоляции Windows.

https://docs.x.ai/build/enterprise

https://docs.x.ai/developers/faq/security

Факт: CLI предлагает opt-in на хранение данных для улучшения продукта. При использовании потребительского Grok правила использования данных зависят от privacy settings; без opt-out часть взаимодействий может использоваться для обучения. Источник:

https://x.ai/legal/faq

Факт: инструменты можно ограничивать через CLI/config, включая allow/deny списки. Но `allowed-tools` внутри чужого SKILL.md не является механизмом безопасности. Источники:

https://docs.x.ai/build/cli/reference

https://docs.x.ai/build/features/skills-plugins-marketplaces

Факт: корпоративное ограничение Claude `disableBypassPermissionsMode` не наследуется автоматически. Для Grok требуется собственная enterprise policy. Источник:

https://docs.x.ai/build/enterprise

Оценка: нельзя считать, что Claude-настройки безопасности приехали вместе с Claude-совместимостью. Skills, MCP и rules могут импортироваться, а административные запреты — нет.

Официально подтверждённого публичного инцидента, где текущий Grok Build показывал выключенный file tool, но продолжал тайно читать файлы, в просмотренных первичных источниках не найдено. Это не доказательство отсутствия проблемы. Документированная «фиктивность» уже есть на более узком уровне: `allowed-tools` в SKILL.md выглядит как ограничение, но Grok прямо говорит, что не применяет его.

F2. Cursor

Факт: Cursor отправляет на свои серверы промпты и релевантный кодовый контекст, а запросы могут передаваться выбранным model providers. Privacy Mode запрещает обучение на данных пользователя; для Teams он включён по умолчанию и может принудительно применяться администратором. Источник:

https://prod.cursor.com/help/security-and-privacy/privacy

Факт: Cursor сообщает о временном зашифрованном файловом кэше и оговаривает, что abuse-classifiers могут хранить срабатывания даже при Privacy Mode. BYOK-запросы всё равно проходят через backend Cursor, после чего действуют правила внешнего провайдера. Источник:

https://cursor.com/data-use

Факт: `.cursorignore` ограничивает прямое чтение файлов функциями Agent/Tab/Inline, но документация прямо предупреждает, что terminal и MCP tools этим механизмом не блокируются и полной защиты секретов он не гарантирует. Источник:

https://prod.cursor.com/docs/reference/ignore-file

Это критическая грабля: «файл исключён из индекса» не означает «агент технически не способен прочитать его». Для реального запрета надо одновременно:

- deny Read по пути;
- deny Shell либо sandbox без доступа к пути;
- ограничить MCP;
- держать секреты вне доступного workspace/VM.

Известный подтверждённый случай обхода: advisory GHSA-vhc2-fjv4-wqch описывает уязвимость Cursor до версии 2.0, при которой вредоносный агент мог создать новый ignore-файл и прочитать защищённые данные. Исправлено в 2.0, поэтому это исторический пример, а не утверждение о текущей версии. Источник:

https://github.com/cursor/cursor/security/advisories/GHSA-vhc2-fjv4-wqch

Оценка: Cursor предоставляет более явные read-only и sandbox-механизмы, особенно на Windows. Но `.cursorignore` нельзя использовать как границу безопасности, а Privacy Mode не превращает продукт в полностью локальный.

G. ПУБЛИЧНАЯ ЗАМЕТНОСТЬ И ВКЛАД

G1. xAI / Grok

Факт: исходный код Grok Build опубликован под Apache 2.0, но CONTRIBUTING прямо говорит, что внешние pull requests и patches в основной проект сейчас не принимаются. Источник:

https://github.com/xai-org/grok-build/blob/main/CONTRIBUTING.md

Следствие: исправление core Grok Build через PR — плохая ставка на заметность перед командой xAI, несмотря на публичный репозиторий. Issue или fork могут быть полезны как доказательство работы, но не дают обычного пути merge.

Факт: у xAI есть публичный plugin marketplace. Каталог расположен в отдельном репозитории; сторонние плагины могут добавляться через PR, фиксируются на конкретных commit SHA и проходят CI/review. Источник:

https://github.com/xai-org/plugin-marketplace

Факт: Grok Build поддерживает плагины, содержащие skills, agents, hooks, MCP и LSP components. Источник:

https://docs.x.ai/build/features/skills-plugins-marketplaces

Оценка: лучший xAI-канал заметности — не попытка патчить закрытый для внешних PR core, а сильный публичный plugin/skill/MCP с:

- реальным пользователем;
- воспроизводимым benchmark;
- интеграцией Claude/Codex/Grok;
- issue с минимальным repro;
- публикацией в официальном marketplace.

Это шанс попасть в поле зрения людей, реально рассматривающих marketplace PR. `/feedback` полезен для продукта, но хуже как публичный портфель.

G2. Cursor

Факт: Cursor имеет официальный plugin marketplace и процедуру публикации с ручным review. Плагины могут включать rules, skills, agents, hooks и MCP-конфигурацию. Источники:

https://prod.cursor.com/docs/plugins

https://prod.cursor.com/docs/reference/plugins

Факт: у Cursor есть публичная GitHub-организация с репозиториями plugins/community-plugins, но основной продукт не представлен как обычный полностью открытый core, куда ожидаются произвольные внешние feature PR. Источник:

https://github.com/cursor

Оценка: для цели «быть замеченным командой вендора» Cursor Marketplace сейчас выглядит сильнее публичного вклада в Grok core, потому что submission неизбежно проходит официальный review. Но Marketplace-вклад заметен только при качестве и использовании. Ещё один wrapper без потребителей утонет.

Наиболее сильный публичный артефакт для обеих экосистем: один vendor-neutral skill/plugin, демонстрирующий безопасную координацию Claude Code, Codex, Grok и Cursor через leases, worktrees, envelopes и независимую приёмку. Для xAI публиковать адаптер в xAI Marketplace; для Cursor — отдельную тонкую упаковку того же authoritative source, не копию логики.

H. ЧТО СЛОМАЕТСЯ ПРИ ДОБАВЛЕНИИ CURSOR

До:

- три агентных runtime;
- один оркестратор;
- одна полка скиллов;
- один канон;
- одна межагентная шина;
- файловые лизы;
- две независимые исполнительские рельсы помимо Claude.

После добавления Cursor как четвёртого писателя:

- появляется четвёртый parser правил;
- появляется собственная система `.cursor/rules`, permissions, hooks и MCP;
- появляется ещё один автoupdater CLI;
- появляется отдельный месячный usage pool;
- возникает риск, что локальный Cursor видит «внутренний путь лаборатории», а Cloud Agent — нет;
- растёт число пар потенциальных гонок с трёх до шести;
- независимая приёмка становится неоднозначнее: «Cursor проверил Cursor» нельзя принимать;
- worktree patches требуют нового apply/merge этапа;
- Cursor Router может снижать модельную независимость, если незаметно выбрана та же семья модели.

Фактическая основа различий по локальным и облачным skills:

https://prod.cursor.com/docs/skills

Фактическая основа worktree/subagent-риска:

https://prod.cursor.com/docs/configuration/worktrees

https://prod.cursor.com/docs/subagents

Оценка: наиболее вероятная поломка — не git-конфликт, а расхождение политик. Все четыре агента смогут «видеть один CLAUDE.md», но применять разные части frontmatter, разные security settings и разные precedence rules.

I. ОКОНЧАТЕЛЬНЫЙ ВЕРДИКТ

I1. Решение сейчас

Не добавлять Cursor четвёртым постоянным агентом-писателем.

Оставить архитектуру из трёх, но Grok Build перевести в состояние «условно допущен»:

- чтение и анализ — да;
- работа в отдельном worktree — да;
- запись в общий checkout — только после проверки полного канона;
- внешние действия — только после проверки собственных Grok permissions, а не импортированных Claude settings.

Если документированный лимит 10 000 символов подтверждается в Grok 1.0.40, заменить Grok Build локальным Cursor CLI. Не добавлять Cursor сверху.

Почему именно Grok является кандидатом на замену:

- Claude нельзя заменять: он задан как оркестратор.
- Codex даёт независимую OpenAI-рельсу и уже интегрирован.
- Grok и Cursor сильнее всего конкурируют за одну роль: дополнительный headless coding executor, читающий Claude/Codex skills.
- Cursor лучше документирует Windows sandbox и read-only Ask.
- Grok лучше нативно импортирует широкую Claude-экосистему и сжигает уже оплаченный SuperGrok-пул.
- Но усечённый канон перечёркивает эти преимущества для пишущего агента.

I2. Когда Cursor всё же имеет смысл без замены

Только в одной из ограниченных ролей:

- визуальный IDE для человека;
- read-only четвёртый reviewer;
- изолированный marketplace/plugin test bench;
- Cloud Agent для задач, которым не нужна локальная полка «внутренний путь лаборатории»;
- отдельная подписочная рельса, если её включённый пул действительно будет использоваться.

Безопасный первоначальный режим:

- `--mode=ask`;
- запрет Write и Shell;
- запрет неаудированных MCP;
- отдельный worktree для тестов, требующих исполнения;
- результат только `artifact.proposed`;
- приёмщик — не Cursor и не модель того же запуска.

I3. Условие, при котором решение меняется на противоположное

Ответ меняется с «не добавлять» на «добавить Cursor» только если 14–30-дневный измеряемый пилот одновременно покажет:

1. Cursor потребляет включённый лимит подписки, который иначе пропадает, без usage-based доплат.
2. Он закрывает класс задач, который Claude, Codex и Grok не закрывают столь же надёжно — например, Windows-sandboxed review или визуальная IDE-приёмка.
3. Headless запуск стабильно отдаёт parseable result, корректный exit status и явное состояние при исчерпании лимита.
4. Он видит нужное количество скиллов из «внутренний путь лаборатории» без копии.
5. Он распознаёт версию и хвостовую метку канона.
6. Ask/deny действительно не позволяют записать файл, вызвать shell и записывающий MCP.
7. Worktree не делит mutable state с другими агентами.
8. Telegram-конверт обрабатывается ровно один раз и получает ACK.
9. Privacy Mode включён, а секретные пути недоступны через Read, Shell и MCP.
10. Повторная работа и стоимость конфликтов на одну принятую задачу ниже, чем у текущей тройки.

Если все десять условий выполнены, Cursor можно добавить как специализированного reviewer/IDE-agent. Даже тогда не следует делать его четвёртым универсальным писателем в общем checkout.

Если же Grok не проходит проверку полного канона, условие проще: Cursor заменяет Grok сразу после того, как сам проходит пункты 3–9.

I4. Честные пробелы в данных

- Нет опубликованной точной таблицы «N Grok Build задач» для SuperGrok/X Premium+; используется общий compute-weighted недельный пул.
- Нет универсального числа Cursor agent requests для текущих планов; старые квоты относятся к прежней схеме.
- Нет строгого публичного контракта Cursor о precedence конфликтующих CLAUDE.md, AGENTS.md и `.cursor/rules`.
- Нет найденного официального доказательства, что Grok Build 1.0.40 отменил опубликованный лимит 10 000 символов.
- Нет найденного подтверждённого публичного инцидента, где актуальный Grok Build тайно продолжал читать файлы после корректного запрета tool; есть документированное неприменение `allowed-tools` из SKILL.md.
- Поведение этих продуктов меняется еженедельно. Вердикт следует пересматривать при изменении Grok instruction limit, Cursor cloud skill sync или схемы подписочных пулов.

J. ПРОСТЫМИ СЛОВАМИ

Сейчас в мастерской уже три рабочих. Cursor — хороший четвёртый рабочий, но собственного замка на общий верстак он не приносит. Зато добавляет ещё один набор ключей, правил и счетов.

Сначала надо проверить более опасную вещь: Grok, возможно, читает только начало вашей длинной инструкции. Если это так, он работает, не зная половины техники безопасности. Тогда его надо убрать от общего верстака и поставить Cursor вместо него.

Если Grok действительно читает весь канон, оставляйте нынешних троих. Cursor берите только под отдельную работу: глазами смотреть код, проверять без записи или публиковать сильные плагины в его Marketplace.
