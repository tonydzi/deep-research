# DR26-09-22-HUB-01-1118 — Grok Build CLI vs Cursor для системы из трёх(четырёх) агентов в одной папке

## A. Архитектурный класс — это разные классы инструментов, не варианты одного

**Cursor.** Основной продукт — IDE (форк VS Code) с агентом внутри. У Cursor есть отдельный `cursor-agent` / Cursor CLI, который официально позиционируется как «агент Cursor без окна редактора» для CI/SSH/скриптов — это НЕ урезанная демка, а тот же движок, что в IDE: делится MCP-серверами, rules и авторизацией с десктопом (https://cursor.com/docs/cli/headless, https://cursor.com/blog/cli, дата материалов — 2026). Отдельно есть Background Agent — облачный агент, управляемый через API, который клонирует репозиторий в изолированную VM и открывает PR (https://trigger.dev/docs/guides/example-projects/cursor-background-agent, 2026). То есть у Cursor фактически ТРИ поверхности одного движка: GUI-агент, headless CLI (локально, для безлюдных прогонов), и облачный Background Agent (cloud VM, тоже безлюдный). Для целей заказчика («безлюдные ночные прогоны без открытого GUI») подходит именно headless CLI — он не «второй сорт», предупреждение только одно: CLI и IDE это ОДИН и тот же продукт разных обёрток, но литература 2026 года всё ещё пишет "Cursor матурировал в отдельную агентную IDE" (https://www.deployhq.com/guides/cursor) — то есть headless-режим появился и окреп лишь недавно, это не изначальный core-сценарий продукта, как у Claude Code/Codex/Grok Build.

**Grok Build vs Grok Bot — это РАЗНЫЕ продукты, не уровни одного.** Grok Build (иногда «Grok CLI») — терминальный агент для локального кода: TUI + headless (`grok -p`) + Agent Client Protocol для встраивания в редакторы, до 8 сабагентов в изолированных git worktree (https://github.com/xai-org/grok-build, https://x.ai/news/grok-build-cli, https://docs.x.ai/build/overview). Grok Bot — облачный «ИИ-коллега со своим компьютером»: постоянная виртуальная машина, свой браузер, свои логины, работает после того как вы закрыли ноутбук, управляет ВЕБ-приложениями через клики/тайпинг, а не через git/файлы (https://www.layer3labs.io/guides/what-is-grok-bot, https://zentor.ai/blog/grok-bot-vs-cursor-cloud-agent, 2026). Официальная документация xAI прямо называет Grok Bot «следующим шагом после Grok Build» (docs.x.ai/build/overview) — то есть это соседние продукты одной линейки, а не пересборки друг друга. Для задачи заказчика (три CLI-агента в одной папке кода) релевантен только Grok Build; Grok Bot ближе по классу к Cursor Background Agent/браузерным автоматизациям, а не к тройке в папке.

**Вывод по классам:** Claude Code / Codex CLI / Grok Build CLI — один класс (терминальные코딩-агенты, файловая модель, git-native). Cursor headless CLI — тот же класс по функции, но выращен из IDE, поэтому местами «второй гражданин» (см. грабли headless в разделе C). Cursor Background Agent и Grok Bot — третий класс (облачные, PR-ориентированные или browser-ориентированные), нерелевантны для «в одной папке».

**Уверенность:** высокая по фактам о продуктовой линейке (первичные источники xAI и Cursor), средняя по «насколько headless CLI Cursor реально равноправен GUI» — конкретных бенчмарков паритета не нашёл, только маркетинговые формулировки.

## B. Совместимость с чужой полкой правил — Grok Build официально шире, Cursor у́же и с известной проблемой рассинхрона

**Grok Build читает CLAUDE.md/AGENTS.md/`.claude/` НАТИВНО и это задокументировано, а не побочный эффект.** Официальная страница `docs.x.ai/build/features/project-rules` описывает точный порядок: в каждой директории проверяются `Agents.md, Claude.md, CLAUDE.md, CLAUDE.local.md, AGENT.md, AGENTS.md` (все совпадения грузятся, более глубокие директории имеют приоритет при конфликте), плюс `.grok/rules/*.md`, а `.claude/rules/` и `.cursor/rules/` — «читаются для совместимости». Skills-loader обходит `./.grok/skills/`, `~/.grok/skills/`, папки плагинов, `~/.agents/skills/`, а также «Claude Code plugins и Skills» (https://docs.x.ai/build/features/project-rules, https://docs.x.ai/build/features/skills-plugins-marketplaces). Это прямо подтверждает заявленное в контексте заказчика: «Grok 1.0.40 читает полку нативно через Claude-совместимость» — согласно докам это ОФИЦИАЛЬНО поддержанная фича, не хак. MCP — тоже нативно, обнаруживается через `grok inspect` (https://mer.vin/2026/05/grok-build-cli-xai-terminal-coding-agent-with-plan-mode-subagents-and-headless-ci/).

⚠️ Риск того, что вендор это уберёт: xAI явно строит Grok Build как «drop-in» для пользователей Claude Code/Codex — это часть стратегии переманивания, у неё есть коммерческий стимул СОХРАНЯТЬ совместимость, а не убирать. Но: сама совместимость идёт с оговоркой из независимого разбора миграции — «некоторые Claude-совместимые поверхности могут задвоить срабатывание хуков» и «Grok может унаследовать совместимые Claude-хуки, даже если `.grok/hooks` пуст» (https://www.codeagentswarm.com/en/guides/grok-build-from-claude-code, 2026, вторичный источник — не официальная документация xAI, поэтому это ⚠️ гипотеза уровня «сообщество заметило», а не подтверждённый факт вендора). Для системы заказчика с хуками (SessionStart/UserPromptSubmit, будильник шины) это ПРЯМОЙ практический риск: хук может выстрелить дважды — один раз через нативный `.claude`-путь, второй раз если что-то в `.grok/` тоже на него ссылается.

**Что происходит при расхождении версий канона.** Доки xAI говорят «все совпадения грузятся, глубже — приоритетнее» — то есть это разрешение конфликта ПО ПУТИ В ДЕРЕВЕ, а НЕ по свежести/дате правки. Если на каком-то узле лежит устаревший локальный `.grok/rules/*.md` или старый `CLAUDE.local.md`, он молча выигрывает у актуального корневого CLAUDE.md — ровно тот класс бага, который в каноне заказчика называется «canon-drift-node-silent» (виден в системных подсказках этой сессии как реально пойманный класс поломок). Это не гипотеза о Grok — это МЕХАНИЗМ конфликта, задокументированный самим xAI, который создаёт риск того же класса, что уже ловился в системе заказчика на других инструментах.

**Cursor.** AGENTS.md — официально один из «rule types первого класса», подхватывается из корня и любой поддиректории без конфигурации (https://cursor.com/help/customization/rules, вторичное подтверждение https://codersera.com/blog/agents-md-vs-claude-md-vs-cursor-rules-comparison-2026/, 2026). CLAUDE.md ТОЖЕ читается, но с важной оговоркой независимых разборов: «CLAUDE.md всегда применяется к каждому разговору вне зависимости от `alwaysApply`, то есть Claude-специфичные инструкции просачиваются в сессии Cursor» без возможности их выборочно приглушить как обычный rule-файл (https://dev.to/rulestack/agentsmd-vs-claudemd-vs-cursorrules-what-cursor-actually-reads-now-and-in-what-order-17bo, 2026 — блог, не официальная документация Cursor, поэтому 🤔 гипотеза среднего доверия, но правдоподобная и совпадает по духу с несколькими независимыми блогами). При этом когда AGENTS.md и CLAUDE.md существуют ОБА — «вы получаете два побочных эффекта: избыточный контекст, который жжёт токены, и когда правите один файл, второй становится устаревшим и противоречит первому» (тот же источник). Это ХУЖЕ ситуации Grok Build: xAI хотя бы формализовал порядок приоритета путей; для Cursor независимые разборы не находят у вендора официального документированного алгоритма разрешения конфликта между двумя каноническими файлами — по факту оба грузятся, и «какой победит» решает не документированное правило, а порядок в промпте, собираемом бэкендом Cursor (не раскрыт публично).

.cursorrules — легаси, работает для обратной совместимости, но новый формат `.cursor/rules/*.mdc` с YAML-фронтматтером её вытесняет; официальная документация её больше не описывает (https://github.com/sanjeed5/awesome-cursor-rules-mdc/blob/main/cursor-rules-reference.md, 2026).

**MCP у Cursor** — официально поддержан и в IDE, и в CLI: CLI «автоматически обнаруживает и уважает ваш `mcp.json`, включая те же MCP-серверы и тулы, что настроены для редактора» (https://cursor.com/docs/cli/using, 2026). Здесь паритет с Grok Build хороший.

**Вывод B:** Grok Build формально совместимее и лучше задокументирован по части чтения ЧУЖОГО канона (порядок приоритетов, явная поддержка `.claude/`), Cursor тоже читает AGENTS.md/CLAUDE.md, но конфликт двух файлов у него менее предсказуем и не описан вендором так же чётко. Оба риска — «глубже в дереве побеждает» (Grok) и «непрозрачный мердж двух файлов» (Cursor) — НЕ решают проблему протухшей версии канона; систему заказчика (canon_write_gate, единый источник правды) это не заменяет ни один из инструментов.

## C. Три (четыре) агента в одной папке — оба инструмента предлагают git worktree, ни один не даёт кросс-инструментного файлового лока

**Grok Build:** до 8 сабагентов запускаются в изолированных git worktree «из коробки» (https://github.com/xai-org/grok-build, https://www.buildfastwithai.com/blogs/grok-build-xai-cli-ai-agents-2026, 2026). Плюс формальная модель sandbox-профилей: `off` (дефолт) / `workspace` / `devbox` / `read-only` / `strict`, обеспечена через Landlock на Linux и Seatbelt на macOS (https://github.com/xai-org/grok-build/blob/main/crates/codegen/xai-grok-pager/docs/user-guide/18-sandbox.md, 2026). Для роли «ревьюер без права записи» есть штатная связка `--sandbox read-only` + `dontAsk` + allowlist через `--tools` — «read-only композируется с dontAsk для по-настоящему запертого headless-прогона» (https://agenticcontrolplane.com/controls/grok-build, 2026). ⚠️ Найдена конкретная грабля: `--disallowed-tools` в независимых тестах «молча фейлится открытым (fails open), включая на выдуманном имени тула, тогда как `--tools` (allowlist) работает» (https://agenticcontrolplane.com/controls/grok-build) — то есть блок-лист инструментов Grok Build ненадёжен, а allowlist — надёжен; при построении роли «ревьюер без записи» нужно использовать allowlist + `--sandbox read-only`, а не пытаться просто запретить write-тулы. Это прямая практическая инструкция для внедрения у заказчика. Также в headless-документации явно сказано: «deny-правила, хуки и admin locks всё ещё применяются» даже под `--yolo` (auto-approve) (https://github.com/xai-org/grok-build/blob/…/14-headless-mode.md) — то есть механизм принудительных ограничений (аналог файловых лизов) на уровне «админ пишет правило — юзер не может его обойти флагом» есть.

Sandbox на Windows: важная оговорка — Landlock/Seatbelt — это Linux/macOS механизмы; для Windows-узла заказчика (хаб хаб) официальная песочница Grok Build, скорее всего, слабее или отсутствует (в найденных материалах явного описания Windows-реализации sandbox-профилей нет — 🤔 не нашёл, а не «её нет»). Это стоит проверить напрямую (`grok inspect` / `grok --help` на Windows-хабе) прежде чем полагаться на `--sandbox read-only` как на настоящую защиту при записи на Windows.

**Cursor:** механизм тот же по идее — при параллельных агентах Cursor «автоматически создаёт изолированные worktree, так что каждый агент работает в своей ветке без файловых конфликтов» (https://cursor.com/docs/configuration/worktrees, 2026). Но явная оговорка вендорской и независимой документации: «если два агента должны изменить один и тот же файл, у вас будет merge-конфликт при применении» — то есть конфликт не устраняется, а ПЕРЕНОСИТСЯ на этап мерджа в основную ветку, где его разрешает обычный git (https://www.learncursor.dev/learn/cursor-origin/parallel-agents-merge-conflicts, https://www.mindstudio.ai/blog/git-worktrees-parallel-ai-coding-agents, 2026). Найден баг-репорт: «multi-agent и worktrees не работают вместе с несколькими project folders» (https://forum.cursor.com/t/multi-agent-and-worktrees-dont-work-with-multiple-project-folders/139522) — статус тикета не проверен на «исправлено/открыто», но сигнализирует о незрелости именно многофолдерного/многоагентного сценария в Cursor по состоянию на дату публикации треда (2026, точная дата в самом URL не указана).

**Главный вывод для сценария заказчика:** ни Grok Build, ни Cursor НЕ решают задачу «три РАЗНЫХ вендорских агента (Claude Code + Codex + Grok/Cursor) пишут в ОДНУ некопируемую папку без git-веток» — их worktree-механизмы изолируют ветки ВНУТРИ своего продукта (сабагенты одного инструмента), а не между разными CLI. Файловые лизы, которые уже построены в системе заказчика (`_shared` lease-механизм), остаются ЕДИНСТВЕННЫМ реальным механизмом взаимного исключения между Claude Code / Codex / Grok Build одновременно — оба вендора предполагают, что «параллельность» = параллельность ИХ СОБСТВЕННЫХ агентов, а не чужих CLI рядом. Добавление Cursor как четвёртого писателя увеличивает нагрузку на ЭТУ же самодельную систему лизов, а не снимает её.

## D. Цена и лимиты

**Cursor.** Модель — не «N агентных запросов», а **долларовый пул compute**: Pro = $20/мес и включает «$20 месячного кредита на premium-usage» плюс расширенные agent-лимиты (https://www.eesel.ai/blog/cursor-pricing, 2026). В стандартном Agent Mode — до 25 tool calls за одно взаимодействие, в MAX mode — до 200 (https://apidog.com/blog/cursor-tool-call-limit/, вторичный источник, но конкретные цифры совпадают с несколькими независимыми блогами 2026 года — средняя-высокая уверенность). Background Agent «потребляет запросы по более высокой ставке, чем интерактивное использование, потому что делает несколько вызовов за итерацию» (https://forum.cursor.com/t/how-cursor-premium-models-usage-is-counted/69719). При упоре в лимит — «агент останавливается посреди сессии», предлагаются 3 варианта: сменить модель / апгрейднуть план / доплатить за usage сверх пула (https://continuumcode.ai/guides/cursor-hit-usage-limit/, 2026); неиспользованный лимит НЕ переносится на следующий месяц. Командный тариф в 2026 году переименовывался минимум дважды в течение года: встречаются одновременно формулировки «Business ($SOC2/SSO/admin)» и «Teams Standard $40/мес/место, Teams Premium $120/мес/место (5x usage Standard)» (https://www.vantage.sh/blog/cursor-pricing-explained, https://dev.to/rahulxsingh/…, https://tech-insider.org/ca/…) — ⚠️ противоречивые источники внутри 2026 года, точное текущее название и цена командного тарифа на 22.09.2026 не подтверждены одним первичным источником; рекомендую проверить `cursor.com/pricing` живьём перед решением о закупке.

**Grok (SuperGrok/X Premium+).** Тиры на сентябрь 2026: SuperGrok Lite $10/мес (1 агент, базовый Imagine), SuperGrok $30/мес (5x диалоги, доступ к Grok Bot), SuperGrok Plus $100/мес (видео/маркетинг), SuperGrok Heavy $300/мес («крупнейшая агентная команда, максимальный usage», для «инженеров, гоняющих долгие агентные задачи») (https://www.ai-toolbox.co/grok-models/grok-pricing-plans-api-2026, https://aitoolanalysis.com/supergrok-subscription-price-2026/, 2026). X Premium+ включает SuperGrok-доступ и Grok Bot отдельной строкой (https://aibusinessweekly.net/p/grok-ai-pricing). Grok Build конкретно: ранний бета-доступ был у SuperGrok Heavy ($299/мес по состоянию на май 2026, до общего relaunch за $300), расширен на все SuperGrok/X Premium+ 25 мая 2026, вышел из беты в v1.0 7 августа 2026 (https://www.buildfastwithai.com/blogs/grok-build-xai-cli-ai-agents-2026). После открытия исходного кода 15–16 июля 2026 (см. раздел E) xAI одновременно **сняла usage-caps** («Grok Build goes open source — and drops usage limits», https://gagadget.com/en/718648-grok-build-goes-open-source-and-drops-usage-limits/, июль 2026) — то есть по состоянию на публикацию этой заметки формальных дневных лимитов на Grok Build не было; вместо этого действует «еженедельный компьют-пул, показываемый в процентах, без опубликованного числового размера» (https://seowannabee.com/grok-supergrok-rate-limits-2026/, 2026), а при опустошении пула — «платные фичи приостанавливаются, пользователь падает на free-tier» (тот же источник, вторичный, средняя уверенность — конкретно для Grok BUILD (не для Imagine/чата) отдельного авторитетного подтверждения не нашёл, это 🤔 экстраполяция с общей политики SuperGrok).

**Для цели заказчика «жечь включённые лимиты, а не платить за API поштучно»** оба варианта формально подходят (обе модели — подписка с пулом, не pay-per-call), но у Grok Build пул НЕПРОЗРАЧНЕЕ (проценты без абсолютных цифр, нет официальной таблицы «сколько токенов/задач в SuperGrok»), тогда как у Cursor пул выражен в конкретных долларах ($20/$… кредита), что легче встроить в существующий у заказчика `token_cost.py`/`rail_plan.py` учёт по рельсам — практическое преимущество Cursor для аналитики трат.

## E. Приватность — у Grok Build ЗАФИКСИРОВАННЫЙ инцидент утечки, у Cursor задокументированные, но менее катастрофичные разрывы

**Grok Build — реальный, подтверждённый несколькими независимыми источниками случай именно «заявленное отключение оказалось фиктивным».** Хронология по датам:
— 13–14 июля 2026: независимый исследователь **cereblab (Tinh Dang)** опубликовал wire-level доказательство, что Grok Build (версия 0.2.93) по умолчанию упаковывал и грузил ПОЛНЫЕ git-репозитории — включая всю историю коммитов, непрочитанные файлы, `.env`-секреты, SSH-ключи, базы паролей — в контролируемый xAI Google Cloud Storage bucket, объём — «~27 800× больше, чем требовалось для задачи» (https://www.techtimes.com/articles/320420/20260714/grok-build-shipped-entire-codebases-xai-cloud-privacy-toggle-did-nothing.htm; https://betterstack.com/community/guides/ai/grok-cli-data-leak/; https://reptile.haus/journal/grok-build-xai-privacy-data-exfiltration-ai-coding-agents-2026/).
— **Ключевой факт для вопроса заказчика «известны ли случаи фиктивного отключения»: ДА, задокументирован именно такой случай.** Существовавшая команда `/privacy` для отключения хранения данных на уровне сессии **не влияла на то, что реально уходит с машины** — «трассы сессии постились на xAI полностью в обоих состояниях» (https://www.bodegaone.ai/blog/grok-build-cli-uploaded-private-repos, июль 2026). Тумблер «Improve the model» (согласие на обучение) и серверный флаг выгрузки репозитория оказались РАЗНЫМИ переключателями на архитектурном уровне — первый управлял только использованием данных для тренировки, второй (единственный реальный барьер между кодовой базой и облаком) не был публично экспонирован пользователю вообще.
— 14 июля 2026: xAI отключила механизм выгрузки на СТОРОНЕ СЕРВЕРА (`disable_codebase_upload: true`) в тот же день.
— 15–16 июля 2026 (источники расходятся на 1 день, вероятно из-за таймзон): xAI опубликовала полный исходный код Grok Build под Apache 2.0 как реакцию на критику (https://en.wikipedia.org/wiki/Grok_Build; https://dev.to/ashraf_chowdury09/xai-open-sourced-grok-build-two-days-after-it-got-caught-exfiltrating-your-ssh-keys-4g4h). Маск публично пообещал полное удаление ранее выгруженных данных — по независимой оценке подтверждения этого удаления от третьей стороны на момент публикации источников не было («independent verification is pending», https://www.developersdigest.tech/blog/grok-build-open-source-damage-control).
— Важная деталь для оценки надёжности сегодняшнего Grok Build: «код, который молча грузил репозитории в Google Cloud, всё ещё присутствует в open-source релизе — просто отключён» (тот же источник) — то есть механизм не удалён из кодовой базы, а выключен флагом; регрессия (случайное/будущее включение) архитектурно возможна, если полагаться только на дефолт, а не на явный конфиг. Практическая рекомендация независимых постмортемов — принудительно выставить `disable_codebase_upload = true` в `~/.grok/config.toml` как персистентное вето (https://www.bodegaone.ai/blog/grok-build-cli-uploaded-private-secrets — источник упомянут ранее в поиске как `grok-privacy-filter` разбор).

**Cursor — не катастрофический инцидент, но реальный зазор между заявленным и фактическим.** Официальная страница https://cursor.com/data-use подтверждает: Privacy Mode при включении даёт «Customer Data не используется для тренинга Cursor» и ZDR-соглашения с провайдерами моделей; НО даже при включённом Privacy Mode «провайдеры моделей (включая Cursor) могут запускать risk-классификаторы для обнаружения нарушений политики использования», и данные, попавшие под такой классификатор, «могут храниться для расследования» — то есть абсолютного ZDR без исключений НЕТ даже в режиме приватности, это по первоисточнику, не по слухам. Независимые разборы (вторичные источники, средняя уверенность) утверждают также, что Privacy Mode отдельно от телеметрии: «отключение privacy_mode останавливает только выгрузку кодового контекста, а телеметрия (аналитика использования, feature flags, crash reports) продолжает течь на серверы Cursor, пока явно не выставлена `CURSOR_TELEMETRY=0`» (https://www.truefoundry.com/blog/cursor-security, 2026) и «Privacy Mode по умолчанию ВЫКЛЮЧЕНА на Free и Pro планах» (https://drel.ai/blog/cursor-security-review, 2026) — то есть риск не «фиктивное отключение», а «дефолт не тот, который думает пользователь», что мягче кейса Grok Build, но того же корневого класса ошибки (индикатор приватности не значит то, что кажется).

**Как выключаются инструменты чтения файлов:** У Grok Build — формальный флаг `--sandbox` (5 профилей + Landlock/Seatbelt) плюс подтверждённая проблема, что `--disallowed-tools` «фейлится открытым» (см. раздел C) — то есть один конкретный инструмент отключения инструментов у Grok Build задокументированно НЕНАДЁЖЕН, а другой (`--sandbox read-only` + allowlist) — надёжен. У Cursor нет отдельного `--read-only` флага в CLI, есть режимы `--mode=ask` / `--mode=plan`, которые по описанию не пишут в файлы, но независимой аудиторской проверки «действительно ли ask-режим на 100% не даёт записи через побочные каналы (терминал, MCP-тул)» я не нашёл — это 🤔 пробел в данных, не подтверждённый факт ни в одну, ни в другую сторону.

**Вывод E:** Grok Build имеет ПОДТВЕРЖДЁННЫЙ, свежий (13–16 июля 2026, т.е. чуть больше двух месяцев назад от даты этого отчёта) и очень серьёзный инцидент именно того типа, о котором спросил заказчик — «заявленное отключение оказалось фиктивным», с полными репозиториями, включая секреты и SSH-ключи, ушедшими наружу. Для машины заказчика, где в `secrets\` лежат реальные пароли (§3.4 канона) и работает leak-scan перед публикацией, это ПРЯМОЙ повод: (1) прогнать `secrets-in-git-history`-подобную проверку и `_test_*` перед первым же запуском Grok Build в рабочей папке, (2) явно выставить `disable_codebase_upload=true` в конфиге Grok на этой машине ДО первого прогона, а не полагаться на дефолт «уже почищено разработчиком».

## F. Заметность (цель №2 — оффер от топ-LLM-компании через публичный OSS-вклад)

**Grok Build:** код открыт под Apache 2.0 (15–16 июля 2026), но это **source-availability, не community governance**: «контрибьютинг-гайд репозитория говорит, что внешние pull request'ы и неcогласованные патчи не принимаются… GitHub issues отключены… это прозрачность исходников, а не открытое управление сообществом» (https://medium.com/@sathishkumar.babu89/grok-build-went-open-source-after-a-data-breach-heres-the-full-story-6da266f7c765, июль 2026). То есть путь «сделать вклад, который увидит команда xAI» через сам `xai-org/grok-build` **закрыт по конструкции** — заметность в этом репозитории физически недостижима стандартным PR-путём. Что открыто: (1) bug bounty через HackerOne на `hackerone.com/x`, который явно включает сам Grok Build («обход sandbox-профилей», «обход Trust gate при старте» — с возможным бонусом) — это РЕАЛЬНЫЙ канал, где отчёт увидит security-команда xAI, с SLA (первый ответ 2 рабочих дня, триаж 10 дней, bounty 14 дней) (https://hackerone.com/x, https://bug-bounties.as93.net/x-xai/). (2) Сторонний, не аффилированный с xAI экосистемный слой — множество community-репозиториев-обёрток (`grok-build-desktop`, `grok-app`, `grok-skills` и т.п.) — вклад туда НЕ засчитывается как касание вендора, это чужие проекты.

**Cursor:** сам продукт (`Cursor`/Anysphere) **закрытый код** — вклад в ядро невозможен в принципе, GitHub-репозиторий `cursor/cursor` не является исходниками продукта (его существование как площадки для контрибьюторов не подтверждено официальной документацией, только упоминание в общем поиске — 🤔 не проверено напрямую, вероятно это просто орг-аккаунт/issue-tracker, не монорепо). Каналы заметности у Cursor: (1) **Open VSX / расширения** — Cursor использует Open VSX как реестр расширений с марта 2026, но это ЧУЖАЯ (Eclipse Foundation) инфраструктура, вклад туда виден экосистеме VS Code-совместимых редакторов (Cursor, Kiro, Antigravity, VSCodium, Windsurf), а не лично команде Cursor/Anysphere (https://newsroom.eclipse.org/…, https://www.opensourceforu.com/2026/03/…). Публикация расширения на Open VSX — реальная,技ически рабочая площадка контрибьюшена, но она НЕ Cursor-специфична и не отвечает цели «заметность именно у вендора». (2) **Community Forum** (`forum.cursor.com`) — там есть открытые треды с прямыми просьбами о bug bounty программе (`forum.cursor.com/t/start-a-bug-bounty-program/135120`), что косвенно говорит: **у Cursor на сентябрь 2026 НЕТ публичной bug bounty программы** (в отличие от xAI/HackerOne) — это прямое отличие не в пользу Cursor для цели заметности через security-контрибьюшен. (3) Cursor как компания активно **нанимает и поглощает** (Koala security team, Supermaven, Continue — акви-хайр с последующим сворачиванием продукта и передачей кода в community, https://thenewstack.io/cursor-acquires-continue-coding/) — то есть у них есть аппетит к талантам, но формализованного публичного «contributor ladder» уровня Anthropic Skills Marketplace или GitHub PR-практики я не нашёл.

**Сравнение с фактической целью заказчика («вклад во ВСЕ крупные экосистемы, GitHub-коммиты видны команде вендора»):** ни у Grok Build, ни у Cursor нет открытого PR-пути в ядро продукта. Единственный реально работающий канал прямой видимости у команды вендора — **HackerOne bug bounty у xAI**, у Cursor такого канала на сегодня не найдено вообще (только пожелания в форуме). Это довод В ПОЛЬЗУ Grok Build конкретно для цели №2, но только в узкой нише security-репортов, а не «вклад в код».

## G. Вердикт

**Условие вопроса:** Claude Code остаётся оркестратором и не меняется. Вопрос — добавлять Cursor четвёртым, оставить троих (Claude Code + Codex + Grok Build), или Cursor должен ЗАМЕНИТЬ кого-то.

**Рекомендация: НЕ добавлять Cursor четвёртым сейчас; оставить троих.** Аргументы:

1. Cursor как класс инструмента — IDE-центричный продукт, headless-режим у него вторичен и моложе core-сценария (в отличие от Claude Code/Codex/Grok Build, которые headless-native с рождения). Добавление IDE-происходящего инструмента в headless-флот повышает риск нестыковок именно в безлюдных ночных прогонах — том самом сценарии, который у заказчика критичен (§4.6 канона, ночное окно).
2. Grok Build уже занял функциональную нишу «третий терминальный кодер, совместимый с полкой скиллов» — по документации xAI даже ЛУЧШЕ формализует совместимость с чужим каноном (явный порядок приоритета файлов), чем Cursor (непрозрачный мердж AGENTS.md+CLAUDE.md). Cursor не добавляет здесь новой функции, только дублирует уже закрытую нишу с худшей документированной совместимостью.
3. Единственная реальная возможность Cursor — Background Agent (облачный, PR-ориентированный) — это ДРУГОЙ класс работы (одна задача → одна ветка → PR), для которого у заказчика пока нет явного назначенного use-case в сценарии «одна папка, три живых процесса разом». Если он появится (например, нужен параллельный воркер, открывающий PR-ы в GitHub-репозитории заказчика, независимо от локальной папки на хабе), это отдельная, ясная роль — не «четвёртый агент рядом», а «пятый, отдельный, облачный».
4. Приватность: у Grok Build уже есть один подтверждённый инцидент (закрыт, но осадок остаётся — «код всё ещё в релизе, просто выключен»); ВНОСИТЬ ЕЩЁ ОДНОГО кандидата (Cursor) с собственным, менее изученным набором privacy-зазоров (телеметрия отдельно от Privacy Mode, дефолт выключен на Pro) в ту же чувствительную папку с секретами — это удвоение поверхности риска без ясной новой пользы.

**Условие, при котором ответ переворачивается на противоположный:** если заказчику понадобится ИМЕННО облачный, PR-ориентированный, работающий В GITHUB (а не в локальной папке хаба) параллельный агент — например, вести пачку внешних contributor-PR'ов или чинить issues на множестве репозиториев одновременно, пока хаб занят локальной работой — тогда Cursor Background Agent (не GUI, не headless-CLI-как-четвёртый-locals-писатель) становится оправданным ПЯТЫМ инструментом отдельного класса, не конкурирующим за файловые лизы с тройкой в папке. Второе условие переворота: если независимая проверка (не найдена в этом ресёрче) покажет, что headless CLI Cursor 2026 года действительно достиг паритета с GUI и что конфликт AGENTS.md/CLAUDE.md у него формализован так же чётко, как у Grok Build — тогда разница в §B перестаёт быть решающей, и вопрос сводится к чистой экономике лимитов (§D), где нужно сравнивать актуальные цены на дату решения, а не на 22.09.2026.

## Явные пробелы (не додумано, а честно не найдено)
- Точный номер версии «Grok Build 1.0.40» и его changelog не подтверждён напрямую (нашёл только вехи 0.2.93 → v1.0 GA 7 августа 2026; 1.0.40 как поздний патч в эту хронологию укладывается правдоподобно, но конкретной записи не видел).
- Официальное название и цена текущего командного тарифа Cursor на 22.09.2026 — источники внутри самого 2026 года расходятся («Business» vs «Teams Standard/Premium»); нужно смотреть `cursor.com/pricing` в моменте принятия решения.
- Реализация sandbox-профилей Grok Build на Windows (Landlock/Seatbelt — Linux/macOS-специфичны) — не нашёл официального описания Windows-эквивалента; для хаба на Windows 11 это нужно проверить `grok --help`/`grok inspect` вживую перед тем как полагаться на `--sandbox read-only` как на настоящую защиту.
- Не нашёл независимого аудита, действительно ли `--mode=ask`/`--mode=plan` в Cursor CLI гарантированно не пишут в файлы через побочные каналы (терминал-тулы, MCP-тулы) — только описания намерения в документации.
- Подтверждение от третьей стороны, что xAI реально удалила ранее выгруженные репозитории пользователей (обещание Маска от 14–16 июля 2026) — на момент публикации использованных источников независимой верификации не было; актуальный статус на 22.09.2026 не перепроверялся отдельно.
