# Designing a Token-Budgeted Memory Index for Long-Running Coding Agents

## Executive Summary

The long-term shape that fits both the literature and production systems is a **three-tier memory design**. Put only cross-session, behavior-changing, globally applicable rules in the canonical instruction layer. ## Key Findings

Removing a pointer from the always-loaded index does **not** make the underlying topic unrecoverable. It changes the recall mode from **direct in-prompt availability** to **retrieval-mediated availability**. Anthropic documents exactly this split for Claude Code: `MEMORY.md` is loaded at startup only up to the first 200 lines or 25KB, while topic files are not loaded at startup and are read later when needed. Anthropic’s API memory tool describes the intended pattern as “just-in-time context retrieval,” keeping active context focused on the current task instead of preloading everything. Letta makes the same distinction between always-visible memory blocks and on-demand archival memory, and its docs explicitly say archival memory must be queried via tools rather than pinned to the context window. citeturn13view1turn18view0turn13view3turn13view4turn15view6

That means the real question is not “is the topic still on disk?” but “how queryable is it when needed?” Current frameworks consistently emphasize **description-driven retrieval**. Letta says the `description` field is the main signal used by the agent to decide how to read and write a memory block. Mem0’s search pipeline uses natural-language queries plus filters, thresholds, and optional reranking. Zep retrieves recent context and then applies multiple search techniques with reranking to surface relevant facts. OpenAI’s current memory product similarly does **not** search history on every request; it looks for relevant context only when it expects that context to improve the response. Practical recall probability therefore depends heavily on descriptive labels, trigger phrasing, aliases, entity names, tags, and reranking, rather than on raw file persistence alone. citeturn15view5turn17view3turn17view4turn25view3turn24view0

For **standing rules**, not episodic facts, the most useful tiering analogy is procedural/core memory rather than generic long-term store. Letta’s context hierarchy recommends placing smaller, more important data directly in context and pushing larger material into files or archival memory. Mem0 explicitly layers memory into conversation, session, user, and organizational scopes, and says retrieval ranks these layers rather than flattening them. OpenAI’s latest memory controls prioritize the most relevant details, move less important ones into the background, and use recency and frequency as promotion signals. Across these systems, the recurring production pattern is: **hot memory for always-relevant operating rules, warm memory for medium-frequency domain knowledge, and cold memory for low-frequency but still retrievable details**. citeturn17view0turn17view1turn24view1turn24view2

The competitive landscape is already fairly clear. In direct memory-layer tooling, the major visible approaches are Anthropic’s file-based memory tool and Claude Code auto memory, Letta/MemGPT’s core-plus-archival hierarchy, Mem0’s layered selective memory, Zep’s temporal knowledge graph, and LangMem’s hot-path plus background-memory architecture. OpenAI’s ChatGPT memory is a consumer-facing comparator rather than a general developer memory API, but it is still strategically important because it operationalizes background synthesis, prioritization, and conditional retrieval at product scale. Indirect competitors and substitutes are full-context prompting, compaction/context-editing systems, pure RAG, prompt-compression stacks, and raw filesystem note stores. citeturn18view0turn13view1turn20view0turn13view3turn13view4turn17view1turn13view8turn13view5turn13view6turn19search0turn6search19

On cross-layer deduplication, the evidence favors **canonicalization over blanket redundancy**. Anthropic says shorter `CLAUDE.md` files produce better adherence, warns against laundry lists of edge cases, and frames context engineering as optimizing the utility of limited tokens. Liu et al.’s “Lost in the Middle” shows that long-context models do not use longer context uniformly well and often degrade when relevant information sits in the middle. Anthropic also explicitly cites “context rot” and recommends minimal viable tool/context sets for long interactions. The implication for your case is that duplicating a standing rule in both `CLAUDE.md` and `MEMORY.md` should be treated as a special-case exception, not the default. citeturn15view3turn15view0turn15view1turn3search7

There is a real debate here, though. Prompt repetition **can** improve compliance in some settings. Google researchers reported gains from repeating prompts for non-reasoning LLMs, and Robinette et al. showed that long-context instruction-following can be improved substantially with mitigation strategies, up to 79% in their setting. But those findings do not amount to a general license to duplicate every rule in a long-running coding agent. The strongest repetition evidence is not specific to procedural coding-agent memory, while the strongest context-management evidence points the other way: keep working context compact and high-salience. In practice, redundancy is warranted only when it creates a different retrieval path, different trigger vocabulary, or different positional salience that you can prove matters in regression testing. citeturn6search8turn14view10turn13view17turn15view0

On flat indexes versus index-of-indexes, the research trend is decisively toward **structured organization once memory corpora become nontrivial**. RAPTOR improves retrieval by recursively clustering and summarizing information into a tree. A-MEM creates interconnected knowledge networks with descriptions, keywords, tags, and dynamic linking. HORMA organizes experience into a file-system-like hierarchy linked to raw trajectories and reports strong efficiency gains under constrained context budgets, using at most 22.17% of baseline token usage in long conversation tasks. Memex(RL) similarly keeps concise summaries and stable indices in working context while storing full-fidelity evidence externally for dereferencing. These are not all identical systems, but they all push toward the same architectural conclusion: once flat lists become crowded, **hubs and hierarchical dereferencing outperform one-line flat sprawl**. citeturn13view14turn28view0turn14view5turn14view4turn14view8turn14view9

Validation methodology is increasingly benchmarked rather than improvised. LoCoMo measures long-term conversational memory over 300-turn, multi-session conversations. MemoryAgentBench evaluates four competencies especially relevant to your problem: accurate retrieval, test-time learning, long-range understanding, and selective forgetting. LongMemEval-V2 extends memory evaluation into customized web environments and large trajectory histories, explicitly asking memory systems to gather compact evidence from long histories. For instruction adherence under long contexts, LIFBench and VerIFY are directly relevant because they test instruction-following stability and verifiable compliance, which is much closer to “did the compressed or tiered layout preserve behavior?” than ordinary QA recall metrics. citeturn13view9turn13view10turn4search0turn13view17turn14view10

Recent frontier work also changes the forgetting discussion. ## Contradictions and Debates

The biggest contradiction in the literature is that more context can help **and** hurt. Full-history or longer-context baselines can recover information that aggressive summarization may lose, but long-context studies also show strong position sensitivity and degraded use of information as contexts get larger. Anthropic’s own guidance is explicit that larger context windows do not make context engineering obsolete, because context pollution and information relevance remain problems even as raw window sizes grow. The operational takeaway is that “always loaded” is not a free lunch; it is a trade against attention quality. citeturn3search7turn15view1

A related debate is whether summaries are enough. Production systems increasingly say **no**. Zep explicitly warns against grounding LLM responses solely on summaries and recommends including relevant facts with timestamps. Anthropic warns that overly aggressive compaction can drop subtle-but-critical context whose importance appears only later. Memex(RL) was motivated by the same failure mode, arguing that truncation and running summaries are fundamentally lossy because they discard evidence itself. This is why cluster hubs should point to raw material rather than replace it. citeturn25view3turn18view5turn14view9

Another unresolved debate concerns learned versus rule-based forgetting. Production stacks today still lean toward explicit lifecycle controls, provenance, and human-auditable retrieval rules, while frontier academic work is moving toward decay-driven accessibility, reinforcement-learned memory editing, and self-adaptive retrieval policies. MemAct reframes memory editing as policy actions optimized end-to-end, while Oblivion and FadeMem apply reinforcement and decay to memory access and retention. These approaches are promising, but they remain newer and less operationally transparent than explicit hot/warm/cold policies and archive logs. For a coding-agent operating file, explainability still matters. citeturn12search1turn14view6turn14view7

There is also a product-level debate over background synthesis. OpenAI’s current memory direction moves toward background curation, prioritization, and versioned revisions, and LangMem explicitly ships a background manager that extracts, consolidates, and updates agent knowledge outside the hot path. That improves ergonomics and may reduce stale or duplicated memory, but it can also introduce silent evolution that is harder to audit if the memory store is treated as ground truth. For a rule-bearing memory index, background managers are useful, but only if paired with diffs, provenance, and regression tests against canonical behavior. citeturn15view7turn15view8turn16view0

## Best Practices

The best current practice is to separate **canonical instruction**, **routing memory**, and **retrievable detail** into distinct contracts. `CLAUDE.md` should contain only rules that must alter baseline behavior across essentially every relevant session, written once in canonical form. `MEMORY.md` should contain only hot triggers, retrieval aliases, and cluster hubs that improve the chance the agent will look in the right place at the right time. Everything else belongs in topic files, sub-indexes, or archival stores that are searchable on demand. Anthropic, Letta, Mem0, and OpenAI all converge on this pattern even though they implement it differently. citeturn15view3turn18view0turn17view0turn17view1turn24view1

For **hot/warm/cold tiering of standing rules**, use this operational split. Hot: global procedural invariants, safety rails, and frequently triggered routing hubs. Warm: domain- or subsystem-specific hubs that are not needed every session but are likely to be needed in a recognizable class of tasks. Cold: detailed rationale, incident history, examples, superseded variants, and low-frequency rules that remain searchable. Recent forgetting work suggests the right model is not hard deletion but **salience demotion** driven by recency, frequency, and contribution to successful responses. OpenAI’s “top of mind vs background” controls, FadeMem’s differential decay, and Oblivion’s separation of consultation and reinforcement all point in the same direction. citeturn24view1turn24view2turn14view7turn14view6

For **cross-layer deduplication**, deduplicate by *behavioral role*, not by string equality. If `CLAUDE.md` already contains the trigger, the directive, and the behavior-changing caveats in a way that survives cold-reader testing, remove the duplicate line from `MEMORY.md`. Keep a `MEMORY.md` line only if it serves one of three distinct purposes: it adds retrieval aliases not present in `CLAUDE.md`; it routes to a cluster of related material; or it captures a highly recurrent task trigger that is unlikely to be matched from `CLAUDE.md` wording alone. This preserves recall pathways without paying twice for the same always-loaded rule. citeturn15view0turn15view3turn3search7turn17view3

For **cluster design**, keep hubs semantic, not chronological. A cluster line should name a stable domain or failure mode, not a date or incident. Each hub should point to a sub-index or topic file that is internally organized by trigger phrases, canonical decision, “when to use,” “when not to use,” and recovery aliases. The literature behind this is not specific to Markdown files, but the architectural pressure is the same: RAPTOR’s tree summaries, A-MEM’s dynamic linking, and HORMA’s hierarchical navigation all work because they create multi-level access paths while preserving linked raw evidence. citeturn13view14turn28view0turn14view5

For **retrieval descriptions**, optimize for what the agent will ask, not for what a human archivist likes to read. Letta explicitly says descriptions are the main signal for memory use, and Mem0’s search infrastructure is built around natural-language queries, filters, and reranking. That means your one-line pointers should include the strongest likely query terms: subsystem names, failure symptoms, tool names, verbs, and canonical aliases. Sparse but discriminative language beats poetic compression. Word-level compaction is near exhausted in your environment anyway; the evidence says structural compaction is where the major gains come from. citeturn15view5turn17view3turn17view4

For **safe forgetting**, archive before delete, and archive with provenance. OpenAI’s current system keeps history and allows restore of prior memory versions; Zep timestamps facts and warns against summary-only grounding; Anthropic’s compaction guidance says to maximize recall first and only then increase precision. In practice, that translates into this rule: no standing rule leaves the system unless it is superseded, tested, and still recoverable from an archive or version log. Safe forgetting for rules means “removed from hot startup context,” not “destroyed beyond audit.” citeturn16view0turn25view1turn18view5

For **budget guidance**, the literature does not provide a universal percentage of context that persistent instructions and memory should occupy. The published guidance is qualitative: keep always-loaded context as small and canonical as possible, because context growth degrades salience and adherence. Given your hard startup ceiling and the documented long-context failure modes, a practical engineering target is to operate **well below ceiling**. As a recommendation, not a published constant, aim for a hot `MEMORY.md` around roughly **60–100 lines or about 8–12KB**, with a soft redline before 15KB, and treat the documented 25KB limit as an emergency boundary rather than a design target. That recommendation follows directly from the evidence, even though the exact numbers are system-specific. citeturn15view1turn15view3turn17view0turn3search7

## Failure Modes

The first failure mode is the obvious one: **startup truncation and silent loss of salience**. Claude Code documents that content beyond the first 200 lines or 25KB of `MEMORY.md` is simply not loaded at session start. In practical terms, this means the bottom of the file is not “weaker” memory; it is potentially *nonexistent* memory for startup behavior. This makes oversize a correctness problem, not merely an efficiency problem. citeturn13view1

The second failure mode is **memory drift**: the index, topic files, and actual project state diverge. A public Claude Code issue documents a common version of this problem: unless memory files are proactively updated mid-session, completed work can be lost at session end, leaving stale next steps, already-done tasks suggested again, and incomplete project context in the next session. The proposed mitigations in that issue—session-end diffing, concise updates, size caps, promotion to topic files, and explicit archives—are exactly the kinds of controls a production memory-index system needs whether or not the platform bakes them in. citeturn27view2

The third failure mode is **behavioral non-application**: the system stores memory but does not reliably act on it. A public Claude Code issue reports repeated failure to obey stored rules across sessions even when the memory file was updated multiple times. That is not definitive proof of a platform-wide model defect, but it is a concrete real-world incident showing that “is remembered” and “changes behavior” are not the same thing. For your design, this means every compaction or tiering change must be tested at the behavior level, not just the storage level. citeturn27view0

The fourth failure mode is **summary distortion**. OpenAI states that its earlier saved-memory system became stale and contradictory, and Zep explicitly says not to rely solely on summaries for grounding responses. Anthropic similarly warns that overly aggressive compaction can lose subtle critical context. The lesson is straightforward: never let the live index become a lossy substitute for the underlying source of truth. The hot layer should route; the warm/cold layers should preserve specifics. citeturn15view9turn16view0turn25view3turn18view5

The fifth failure mode is **orphaning and broken references in real deployments**. A recent Claude Code issue describes memory and chat history being keyed to absolute path, such that moving or renaming a repository silently strands the original memory, splits the corpus, and can leave the new session with a near-empty working set. Again, that issue is a public user report rather than an official postmortem, but the mitigation recommendations are sound: tie memory to stable project identity, provide migration tools, and audit cross-references after moves. citeturn27view1

The sixth failure mode is **ungoverned growth**. Anthropic’s own context-engineering article argues that long interactions require compaction, note-taking, and focused working memory rather than uncontrolled accumulation. Public requests from Claude Code users echo the same operational reality: without size management, memory becomes self-defeating by increasing context consumption and degrading inference quality. New research systems like FadeMem, Oblivion, HORMA, and Memex(RL) exist precisely because naive append-only memory stops scaling. citeturn15view1turn27view2turn14view7turn14view6turn14view5turn14view9

## Strategic Recommendations

**H1 — confirm, with an explicit exception list.** If a standing rule already has a trace in `CLAUDE.md` that preserves behavior in cold-reader and trap-scenario tests, archive the duplicate `MEMORY.md` line. The exception is when the `MEMORY.md` line adds retrieval vocabulary, subsystem aliases, or a hub pointer that the canonical instruction does not provide. The goal is not “one copy only” as an ideology; it is “one always-loaded behavioral copy, plus zero or one retrieval-routing copy only when it materially changes recall.” This is the best fit with Anthropic’s advice on shorter instruction files, minimal working context, and avoidance of prompt bloat. citeturn15view0turn15view3turn15view1

**H2 — confirm, but implement clustering as hub-and-spoke, not summary replacement.** Grouping five related Telegram-stack lines into one hub line is likely a net win *if* the hub points to a sub-index or topic file that preserves fine-grained triggers and if the hub line contains the vocabulary the agent is likely to query. This is consistent with RAPTOR, A-MEM, HORMA, and Memex(RL): higher-level organization improves retrieval, but only when raw or lower-level detail remains linked and dereferenceable. Do not compress clusters into vague umbrella summaries that erase the exact symptom phrases you will need later. citeturn13view14turn28view0turn14view5turn14view8

**H3 — strongly confirm, and refine into a target architecture.** The right long-term shape is not a bigger cap. It is a smaller live index plus aggressive tiering and explicit lifecycle control. For your use case, the strongest architecture is: `CLAUDE.md` as canonical procedural core; `MEMORY.md` as hot dispatcher of global invariants and domain hubs; warm sub-index files for clusters; cold topic/archive files for rationale, examples, and superseded variants; and retrieval via semantic search plus grep-like exact lookup. This is much closer to state of the art than continuing to pack more one-line entries into a flat startup file. citeturn13view1turn18view0turn17view0turn14view5turn14view8

A further refinement is to treat **standing rules as two different species**. Some are true canonical instructions and belong only in the procedural core. Others are “retrieval guides” that exist to help the agent find the right detailed note when a recognizable trigger appears. The first class should almost never decay except through explicit supersession. The second class can be demoted from hot to warm when usage drops, because their job is routing rather than baseline control. This distinction is supported by how Letta separates always-visible blocks from archival memory and how OpenAI now distinguishes top-of-mind from background memories. citeturn13view3turn13view4turn24view1

Finally, adopt **safe forgetting as accessibility control**, not content destruction. Newer memory papers explicitly move toward decay-driven activation, reinforcement-based strengthening, and hierarchical loading of details. For your harness, the practical version is: demote first, archive second, delete only on supersession, and preserve an auditable recovery path. That gives you compaction without amputating recall. citeturn14view6turn14view7turn16view0

## Action Plan
