Prior Art Mapping: Consensus over Asynchronous File ReplicationImplementing leader election and consensus over an eventually consistent substrate without direct TCP RPCs fundamentally alters the available coordination primitives. Traditional distributed consensus algorithms, such as Paxos and Raft, operate on the assumption of synchronous request-response mechanisms, utilizing immediate quorum acknowledgments to advance state. The absence of this synchronous communication channel requires adapting alternative mechanisms to the sharded, single-writer file-sync topology. Key finding: [established] Traditional synchronous consensus protocols cannot be directly applied to asynchronous file-sync substrates without introducing unbounded latency. Lease-Based Leadership and Fencing TokensDistributed locks and leader leases require robust mechanisms to prevent split-brain scenarios when a leader experiences a "stop-the-world" pause or a network partition. In standard architectures, a time-to-live (TTL) lease is granted to a leader. However, as demonstrated by foundational critiques of systems like Redis's Redlock, time-based locks alone are highly vulnerable to clock skew, garbage collection pauses, and unbounded network delays. To achieve true mutual exclusion, the literature insists on the implementation of "fencing tokens". A fencing token is a strictly monotonically increasing integer generated by a consensus-backed lock service each time a lease is granted. When the leader attempts to write to shared storage, it must present this token. The storage layer acts as a synchronous gatekeeper; if a higher token has already been presented by a new leader, the stale write is explicitly and immediately rejected, preventing data corruption. When mapping this to the specified file-shard world, a critical architectural incompatibility emerges. In the Syncthing-backed fleet, the "storage layer" is the local file system. Because the logs are sharded per machine (log-<MACHINE>.jsonl) and are single-writer, there is no centralized, synchronous gatekeeper to evaluate and reject a stale fencing token. If the Hub and the HP17 laptop are partitioned, both machines can locally generate what they believe are valid arbitration events and append them to their respective shards without immediate contradiction. The fencing tokens would eventually sync, but only as post-hoc auditing markers rather than preventative safety gates. Key finding: [established] Fencing tokens provide no preventative safety in a decentralized file-sync architecture because the local storage layer cannot synchronously reject stale writes from partitioned peers. Preserving disagreement on this topic requires examining the contrarian view regarding time-based leases. While strict theorists assert that physical time-based locks are inherently unsafe without fencing tokens, counter-arguments emphasize that in practical systems with bounded clock drift and predictable maximum network delays, TTL-based locks provide high empirical safety. Steelmanning this position suggests that if a system operates on highly stable infrastructure where process pauses are negligible and NTP synchronization is tightly bound, a purely time-based expiry is operationally sufficient. However, considering the personal fleet includes a laptop that routinely sleeps and travels across variable networks, physical time guarantees are completely void. Therefore, the risk aligns heavily with the strict theoretical models that reject naked TTL leases. Epoch and Term Numbers in Append-Only SubstratesAlgorithms like Raft utilize term or epoch numbers to strictly order leadership transitions and ensure that older leaders are gracefully deprecated when a network heals. In a file-sync topology, a node attempting to become the roaming arbiter could theoretically write an EPOCH_CLAIM event to its ledger shard. To adapt this mechanism safely, a node must write the epoch claim, wait for Syncthing to replicate the file to a majority of peers, and subsequently wait for acknowledgment events to sync back to its local disk. This essentially implements State Machine Replication (SMR) over file-sync. Research indicates that completing an SMR command can be significantly more expensive and complex than solving a single consensus instance, especially in asynchronous or partially synchronous models. The primary failure mode in this adaptation is the "dead-air" partition. Given Syncthing's eventual consistency, where syncs can take seconds under ideal conditions but stretch to hours if a node is sleeping, a single election cycle could halt the system indefinitely. If an epoch claim is issued but the sync is paused due to sleeping nodes, the cluster cannot achieve a quorum and permanently deadlocks. The cost of implementation is high due to the necessity of building complex state machines to track asynchronous acknowledgments.Witness and Tiebreaker NodesA witness or tiebreaker node is a lightweight participant that holds no state data but possesses a vote to break deadlocks in even-numbered clusters. In the specified context, the "Mayak" Virtual Private Server (VPS) serves this purpose perfectly. Invariant-Based Approaches and CRDTsConflict-Free Replicated Data Types (CRDTs) embrace eventual consistency by designing data structures where concurrent updates inherently commute and merge deterministically. Rather than preventing a split-brain, CRDTs render the resulting state divergence mathematically harmless, guaranteeing that all replicas eventually converge to the same state without coordination. Distributed ledgers utilizing append-only mechanisms rely heavily on state-based CRDTs. In these architectures, the ledger itself is a CRDT (specifically, a Grow-Only Set or G-Set), ensuring that operations only move upward in a partial order. CRDTs handle state convergence but cannot reverse real-world side effects. However, for state tracking and internal configuration changes, this approach provides immense resilience. Safe-Mode Semantics and Arbiter RestrictionsWhen a partition is definitively suspected, the roaming arbiter must immediately adopt safe-mode semantics. The goal is to limit the blast radius of a potential split-brain scenario. The following operational postures are compared to determine the optimal balance of availability and consistency at the N=4 scale.Option A: Total Freeze of Auto-ArbitrationUnder this semantic, a node that suspects it is partitioned immediately strips itself of the arbiter role. All Tier-0 and Tier-1 proposals are forcibly downgraded to Tier-2 status, requiring human escalation via the established Telegram rail.This approach aligns with strict CP (Consistency/Partition Tolerant) systems within the CAP theorem matrix, where returning an error or halting is preferable to risking data corruption or divergence. At the N=4 scale, this is highly effective. Because the human escalation rail is explicitly defined as "cheap" in this context, the operational cost of freezing auto-arbitration is minimal. It provides the most robust defense against ledger divergence by simply refusing to make autonomous decisions under uncertainty. Option B: Idempotent and Reversible Operation ConfinementThis approach allows the arbiter to continue processing Tier-0 and Tier-1 events during a partition, but strictly limits execution to proposals flagged as idempotent or perfectly reversible. For example, a proposal to Update_Local_Display_Config would be processed, but a proposal to Execute_Financial_Transfer would be frozen. This aligns with AP (Availability/Partition Tolerant) systems and CRDT logic, where operations are designed to be replayed or merged without adverse side effects. While theoretically elegant, it requires extensive architectural tagging of every proposal type and introduces significant complexity into the execution engine to guarantee that side effects are truly idempotent. For a ~1,500-line Python engine, this level of semantic parsing may violate the requirement for mechanical simplicity. Option C: Tentative-Commit with Challenge WindowsThe arbiter records a TENTATIVE_COMMIT event in its ledger. The execution of the proposal is delayed. When the partition heals, peers have a predefined challenge window to review the tentative commits. If a conflict is detected, the peers can issue a COUNTER to reject the commit before it finalizes.This mechanism is used in disconnected operations architectures, famously pioneered by systems like Bayou. While Phase A quorum is already built into the engine, relying on tentative commits for all operations during a partition requires building a complex rollback and compensating transaction mechanism (Sagas) to handle the state transitions if a commit is successfully challenged. In an append-only ledger, rolling back implies writing explicit negation events, drastically increasing the complexity of the state reconstruction logic. Option D: Fencing ExpirationsThe arbiter actions carry a logical epoch, and peers are programmed to refuse actions if they have seen a higher epoch. However, as established in the prior art analysis, true fencing is impossible in this architecture because there is no central synchronous storage layer to enforce the rejection of stale epochs in real-time. Safe-Mode Industry Consensus for Micro-Fleets: Industry experience dictates that for small-scale, high-value decision engines without synchronous enforcement, Option A (Total Freeze) is the only responsible choice. When the cost of human escalation is low, attempting to build autonomous, conflict-resolving safe modes (Options B and C) introduces catastrophic complexity risks that far outweigh the benefits of temporary availability. Key finding: [established] In highly constrained asynchronous environments, failing closed (halting autonomous action) is significantly safer and easier to maintain than attempting complex tentative execution.4. Post-Partition Reconciliation and Merge DisciplinesDespite robust local detection mechanisms, edge cases remain. For instance, two nodes might simultaneously wake from sleep, fail to detect the network immediately, and concurrently believe they are the valid arbiter. If both nodes record a COMMIT or TIE-BREAK event for the same proposal, the append-only logs will semantically diverge. Reconciliation requires establishing a deterministic total order of events post-sync to ensure all machines converge on identical state. Precise Detection of the Conflict SetBefore the system can reconcile a split-brain, it must precisely detect that a conflict occurred. Relying on physical timestamps to detect concurrency is fundamentally flawed due to clock drift. To detect conflicts efficiently in a static cluster (N=4), the system must implement Vector Clocks (or Version Vectors). A vector clock is an array of logical counters, one for each node in the system. Every event written to log-<MACHINE>.jsonl includes the current vector clock: e.g., {"HP17": 42, "hub": 114, "Mayak": 89, "Mac16": 12}. When Syncthing eventually replicates the files, the local engine parses the combined logs. If it finds two COMMIT events for the same proposal_id, it compares their vector clocks. The mathematical rule is strict: if every component of Vector A is less than or equal to Vector B, then A causally preceded B. However, if neither vector strictly dominates the other (i.e., HP17's commit had Hub at 114, but Hub's commit had HP17 at 41), the events are mathematically proven to be concurrent. This precise detection eliminates false positives caused by NTP drift. Determinism in Total OrderingOnce concurrent COMMIT events are definitively detected via vector clocks, the execution engine must deterministically choose a single winner.Human Review Queue: Flagging the conflict for human review is the safest semantic option but halts automated state progression. It should be reserved only for critical Tier-0 events where automated resolution is deemed too risky.Epoch-Wins: If logical epochs were implemented, the event with the higher epoch would win. However, since epochs are difficult to synchronize without dead-air, this is impractical.Timestamp + Machine-ID Tiebreak (LWW): Standard Last-Write-Wins (LWW) relies on physical timestamps. While physical clocks drift, they are perfectly suitable as a secondary sorting mechanism once vector clocks have identified the concurrency. The optimal merge discipline is a deterministic tiebreaker. If two concurrent events exist, the engine orders them by:Physical timestamp (assuming nodes run basic NTP/chrony). Lexicographical order of the Machine ID (e.g., hub > HP17).The event that sorts first is treated as the canonical COMMIT. The secondary event is semantically mapped to an IGNORED_DUPLICATE state. Crucially, because the ledger is append-only, the raw JSON data of the "losing" event is never deleted. The immutable audit trail is preserved, but the state machine simply ignores the duplicate during its deterministic projection reconstruction. Key finding: [established] Combining Vector Clocks for precise concurrency detection with deterministic LWW sorting provides robust, automated reconciliation without requiring destructive rollbacks. 5.
