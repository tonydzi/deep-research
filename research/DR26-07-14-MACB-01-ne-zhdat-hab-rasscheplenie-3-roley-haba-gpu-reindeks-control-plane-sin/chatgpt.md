# Engines sync topology for a peer-equal AI fleet

## Executive verdict

The best fit for this fleet is **Option D: Git for engines, Syncthing for data, with a roaming human-controlled canonical push right and a separate signed deployment rail**. In plain terms: stop treating `~/_imports` as a live multi-writer shared folder, move engines into a small self-hosted Git repository, let any trusted machine make local commits, let only the roaming leader advance the canonical branch, and let runtime nodes deploy only an explicitly approved commit SHA through a canary-first rollout. That matches what the literature says about optimistic replication, what Git is built for, and what Syncthing is **not** built for. **[established]** Foundational replication work says optimistic systems propagate first and reconcile later; Git is the standard copy-modify-merge system for source code; Syncthing’s own docs describe file-sync conflict behavior rather than code-review/history semantics. citeturn20view2turn25view0turn22view1turn23view0

The short version of the decision is blunt. **Option A** is the wrong rail for canon code because Syncthing resolves conflicts at the file level, not at the commit/history/policy level. **Option B** can work as a fallback, but only if the “pen” handoff uses a real lease plus fencing token semantics; deterministic first-alive order by itself is not enough against partitions, sleep/wake pauses, or stale writers. **Option C** is already almost the right answer, but in this environment it is strongest when turned into **Option D**, because deployment should not blindly follow authoring. Canary rollout and rollback discipline are the main blast-radius controls, not the DVCS alone. **[established]** Git’s hooks and non-fast-forward protections are built for policy enforcement; canary/staged rollout is the documented pattern for limiting fleet-wide damage during deployments. citeturn25view2turn25view4turn29view0turn29view3turn29view2

My single recommendation is therefore: **adopt Option D**. The main assumption behind that recommendation is that the operator can tolerate a one-time migration to a very small wrapped Git workflow. If that assumption is false, the fallback is **Option B with a fenced roaming writer**, not Option A. **[established]**

## What current research implies

The academic baseline is old but still decisive. Saito and Shapiro’s 2005 survey on optimistic replication describes exactly the failure mode you are living with: background propagation, then conflict discovery after the fact, then some application-specific resolution procedure. That pattern is excellent for availability and disconnected operation, but the hard part is always conflict detection, conflict resolution, propagation discipline, and bounding divergence. In other words, optimistic replication is the right *family* of ideas for sleepy laptops and intermittently connected peers, but it does **not** tell you that a generic filesystem synchronizer is a good source-control system for Python. **[established]** The best source here is old; I am using it explicitly because newer work mostly specializes the same trade-off rather than overturning it. citeturn20view2

That is also why DVCS tools keep winning for source code. A DVCS does not try to make the filesystem itself the consensus object; it makes the **commit graph** the shared object, and it turns conflicts into explicit merge events with durable provenance. Git’s own distributed-workflow documentation emphasizes offline committing and local branching/merging, which directly matches bag-sleeping laptops and intermittent availability better than “live writable shared folder” semantics do. **[established]** citeturn34search5turn34search1turn25view0

The CRDT question is where the evidence is interesting but not yet operationally useful for your exact setup. Recent collaborative-programming research is not saying “CRDTs magically fix source files on disk.” The opposite: the 2026 ECOOP paper on a Stable Lossless Syntax Tree says ordinary text propagation by keystroke or text patch often produces syntactically invalid intermediate states, and it proposes a **structure-aware** substrate that propagates syntactically valid changes only. Automerge’s own docs similarly describe a JSON-like document model with CRDT text and rich-text datatypes that applications integrate into editors and app-specific schemas. That is promising for editor-centric collaborative programming, but it is not a drop-in answer for hundreds of ordinary `.py` files edited through heterogeneous tools on Windows, macOS, and Linux. **[emerging]** There is real progress, but it is runtime/editor integration work, not a filesystem-level replacement for Git in 2026. citeturn20view1turn27view0turn27view1turn26view4

There is one credible counter-position worth preserving. Local-first and CRDT proponents are right that convergent offline-first collaboration can outperform centralized workflows for some data types, and the 2026 code-structure paper is strong evidence that source-code-specific CRDTs are maturing. But the steelman version of that argument still lands on **custom representation plus custom sync logic**, not “let Syncthing multi-write arbitrary Python files.” So the disagreement is real, but it does not rescue Option A. **[emerging]** citeturn20view1turn27view2

Leader handoff research points the same way. Raft’s classic safety story is built on a leader plus majority overlap, and its membership-change safety comes from overlapping majorities. More recent work, especially LeaseGuard from late 2025 / April 2026 publication, argues that lease protocols are often vaguely specified or incorrectly implemented, and that careful lease design matters for availability during failover. Redis’s current distributed-lock docs now explicitly warn that you should implement **fencing tokens**, because a stale lock holder can wake up after a pause and still try to write. Kleppmann’s locking analysis makes the same correctness point in a more general way: timeouts are guesses, pause lengths and network delay are not trustworthy, and correctness-sensitive writer exclusion needs more than “the old leader probably died.” **[established]** LeaseGuard’s claim that most Raft lease implementations are wrong is still **[single-source]**, but it is a credible research warning, not fringe speculation. citeturn20view0turn28view0turn28view2turn22view3turn31view0

For your fleet, the practical implication is simple: **if you keep a roaming designated writer model, the pen handoff must be fenced**. But moving engines to Git largely dissolves the hardest part of that problem, because “who may write right now?” becomes “who may advance the canonical ref right now?” That is a much easier and safer control point than live shared-folder mutation. **[established]** citeturn25view2turn25view4turn31view0

## What documented practice says about Syncthing

Syncthing’s strengths are real, but they are the wrong strengths for canonical code. Its own synchronization docs describe block-based file transfer and eventual convergence of shared folder contents. That is why it remains a strong data plane for non-semantic artifacts. But for code, the decisive issue is not block transfer efficiency; it is **who is allowed to mutate canon, how conflicts are represented, and how a bad change is prevented from becoming fleet-wide state**. Syncthing does not natively answer those questions as a source-control system. **[established]** citeturn23view0turn22view1

The receive-only behavior you already know from experience is exactly what the docs say. Syncthing’s *Folder Types* page for v2.1.0 says that in a receive-only folder, local changes are not distributed, the folder shows a red **Revert Local Changes** button, and if a locally modified file is later changed by the cluster, the cluster version wins; the sync-conflict copy stays local and can be deleted by revert. That means a peer fix in a receive-only engines folder is not a first-class change proposal; it is just a local divergence. This is your “local additions limbo,” documented. **[established]** citeturn22view1turn24view0turn24view1

The multi-writer case is worse. Syncthing’s *Understanding Synchronization* docs say that when the same file is modified simultaneously and the content differs, one copy is renamed to `.sync-conflict-...`; the file with the **older modification time** is the one renamed, and if modification times are equal a device-ID tiebreaker is used. That is not semantic code merge; it is file-level conflict splitting. On receive-only folders, the cluster version wins. On send-receive folders, the conflict copy becomes an ordinary file. Syncthing maintainer comments on the forum and a related GitHub issue confirm that `sync-conflict` files propagate as normal files after creation. In a codebase, that means the fleet can converge on a messy state that is “all bytes preserved” but operationally wrong. **[established]** The maintainer/forum statements are **[single-source][low-authority]**, but they align with the official conflict documentation. citeturn10search0turn22view1turn24view2turn24view3

File versioning does not fix that. Syncthing’s versioning docs say `.stversions` archives files that are deleted or replaced **due to a remote change**, and explicitly say that if a file is changed locally, Syncthing “will not and can not” archive the old version on that same machine. So `.stversions` is a recovery cushion for replication events; it is not commit history, branch history, authorship history, or a semantic rollback system for source code. **[established]** citeturn23view1

There is another practical footgun in hybrid setups. Syncthing’s `.stignore` file is local and “will never be synced to other devices.” That is useful if you want per-node exclusions, but it also means that any “let’s just ignore `.git` everywhere” strategy must be maintained per device unless you deliberately include a shared patterns file. In a small heterogeneous fleet, that is survivable; in a sleepy always-on fleet with colleagues’ machines, it is yet another source of drift and repair work. **[established]** citeturn23view2

The anti-pattern of syncing Git metadata through Syncthing is documented, if mostly through maintainer/community channels rather than formal docs. In a 2018 Syncthing forum thread, maintainer Jakob Borg wrote that syncing Git repositories with concurrent changes is “a terrible idea” because Git repository files are not independent and Syncthing’s merge can produce a repository state that is inconsistent in Git terms. A frozen GitHub issue reports destroyed repositories when `.git` was not ignored. Those are not formal studies, but they match how Git’s object database works and they are exactly the kind of failure a small team only needs once. **[established]** The forum and issue evidence should be read as **[single-source][low-authority]** warnings, not as a statistical prevalence estimate. citeturn23view3turn23view4

One more cautionary datapoint: the Syncthing community documented a known v1.22.0 conflict bug in 2022 that generated spurious `sync-conflict` files. That bug is old, not current, but the lesson matters: even mature sync tools can produce fleet-wide conflict noise from a version-specific defect. For code deployment, that means your safety model should assume the sync layer can be wrong and must not be the only gate protecting canon. **[established]** This is **[single-source][low-authority]** incident evidence, not a current claim about the latest release. citeturn24view4

## Comparative assessment of the named options

**Option A — Syncthing send-receive multi-writer for engines.** This is the worst fit. It gives you concurrency at the filesystem layer, but the merge semantics are mtime/device-ID conflict naming, not commit-level three-way merge with policy controls. It also makes every sleeping laptop and every half-connected Windows box a potential surprise writer. The best case is low-friction byte propagation; the worst case is silent fleet-wide spread of a bad active file while the “saved” alternative survives only as a conflict copy. Because the engines tree is only about 3 MB, there is no compensating scale advantage here. **[established]** citeturn10search0turn23view0turn23view1

**Option B — Receive-only everywhere plus a roaming designated writer.** This is viable if you absolutely refuse Git, and it is compatible with your current SKILLS precedent. But it only becomes safe if the writer handoff is explicit: short lease, monotonically increasing epoch/fencing token, freshness gate before edit, and a write path that rejects stale epochs. A deterministic “first-alive order” without a single authority or majority-backed lease is not a correctness proof; it is a convention. If the VPS anchor is the lease authority, you gain safety but lose availability when that box is down. If you distribute lease authority without quorum, you gain availability but reopen split-brain. So Option B is **operationally simplest**, but it preserves a lot of the current pain around patch shuttling, weak history, and a single merge point. **[established]** LeaseGuard’s critique of poorly specified lease behavior is **[single-source]**, but the fencing requirement is widely corroborated. citeturn20view0turn28view0turn22view3turn31view0

**Option C — Switch the engines layer to Git.** This is the first option that actually matches the artifact type. Git gives you durable history, local offline commits, explicit divergence, branch-based collaboration, server-side rejection of unsafe pushes, and cheap clones because the repository is tiny. A bare repository is explicitly the normal exchange format for push/fetch; `receive.denyNonFastForwards` and `receive.denyDeletes` can stop destructive history rewrites; client- and server-side hooks can run your existing portability/import/lint/tests as a poor man’s CI. On deploy nodes, `git pull --ff-only` gives a clean “only move forward if not diverged” rule. **[established]** citeturn25view0turn25view1turn25view2turn22view2turn25view4

The weakness of Option C is not technical; it is operational. Git solves authorship and merge semantics, but by itself it does **not** solve blast radius. A bad commit merged into `main` can still be deployed everywhere if your runtime nodes automatically follow it. So pure Option C is much better than A or B for authoring, but you still need a deployment gate. **[established]** citeturn29view0turn29view3turn29view2

**Option D — Hybrid.** This is the strongest design because it splits authoring from deployment. The best hybrid is **not** “Git repo inside Syncthing”; the best hybrid is **Git for engines authoring and history, Syncthing only for data, plus a separate signed release/deploy signal**. If you keep Syncthing anywhere near engines, it should be only for read-only exported release bundles or an approved manifest, not for live source trees or for `.git`. This lets the roaming human leader keep canon control without reintroducing hub-centric filesystem governance: the canon right roams with an **operator key**, not with a folder mode on one machine. Any trusted machine can author locally; only the roaming leader may advance the canonical ref; colleagues can push branches without being able to mutate canon directly. **[established]** The exact “operator-key plus approved-manifest” pattern is my synthesis for your topology, not a named standard for 4–7-node AI fleets **[no source found] [speculative]**; the underlying pieces are standard Git and staged rollout components. citeturn25view2turn25view4turn29view0turn29view3

## Lightweight substitutes and their fit

Small-fleet operators do in fact tend to put **desired state into Git and then apply it**, rather than live-syncing mutable code. The evidence comes from adjacent practice rather than “AI fleets” specifically: chezmoi stores desired dotfile state in a local Git repo and applies it to target paths; Tailscale documents GitOps for tailnet policy because Git gives versioning and auditability; Nix/Colmena style tools are explicitly stateless deployment tools that ship desired state to nodes instead of letting the nodes co-edit the live config. That is not identical to your use case, but it is the same architectural instinct: author in version control, deploy by promotion. **[established]** citeturn26view3turn30view1turn32view1

**Unison** is honest bidirectional file sync and is better behaved than naive mirroring, but its own description is about synchronizing **two replicas** and detecting/displaying conflicts. That makes it respectable for pairwise sync, not ideal for a seven-node mesh with roaming authors, issue history, and branch semantics. It is safer than Option A, but it is still a synchronizer, not a source-control workflow. **[established]** citeturn26view1turn14search3

**Fossil** is the strongest non-Git alternative. Its docs say autosync is the default, supports disconnected operation when needed, and is intended to reduce pointless forking and merging. Steelmanning Fossil: for a single owner who values one binary, one SQLite repo, and integrated autosync, Fossil may actually be closer to the AK-47 simplicity ideal than Git plus add-ons. That case is real. The reason I still do not recommend it here is not that Fossil is bad; it is that your existing deterministic scripts, cross-platform Python habits, and need for boring repair knowledge all align better with Git’s much broader ecosystem of hooks, examples, and operator familiarity. **[established]** Fossil’s “autosync reduces pointless forking” claim is from Fossil’s own docs and should be read as **[single-source]**. citeturn26view2turn25view4

**Mercurial** remains a viable DVCS, and its official site still positions it as a distributed source-control tool with local clone/push workflows. But for this fleet it has no decisive advantage over Git, while Git has more universal operator knowledge, more examples for hooks and protected refs, and more repair folklore. So Mercurial is viable, but not the best use of migration calories. **[established]** citeturn32view2turn25view4

**ansible-pull** is useful only as a deployment mechanism layered on top of Git. Its docs explicitly say it inverts the usual push architecture so nodes pull from a source repository, and it warns that the CLI tools are not designed to run concurrently with themselves, so you need external scheduling/locking. That makes it plausible later for Linux/macOS deploys, but not as the primary authoring/merge layer, and it is a weak fit for a Windows-heavy fleet unless you want to maintain a second ops framework. **[established]** citeturn26view0

**chezmoi** is excellent for one user’s machine-specific config, but that is exactly the issue: it assumes a desired-state source repository projected onto machine-local targets. For shared mutable engines, the desired-state idea is helpful; chezmoi itself is not the right abstraction unless the engines become effectively “managed dotfiles,” which they are not. **[established]** citeturn26view3

**git-annex** is the wrong tool for your engines because it exists to split **large** content from ordinary Git content. Its own mixed-content docs say source code should stay in Git and large assets can go into the annex. Your engines tree is tiny; using git-annex here would add moving parts for no payoff. It may be relevant later for large fleet datasets, not for `_imports`. **[established]** citeturn33view0

## Recommendation and migration order

The recommendation is **Option D**: **Git for engines authoring, Syncthing for data only, and a signed approved-commit deployment rail with canary-first rollout. [established]** Git solves your authoring and merge semantics; the deployment rail solves blast radius; Syncthing stays where it is strongest. The “roaming leader” concept remains useful, but it should govern **who may advance canon**, not **which folder is writable right now**. Canon should be a protected Git ref, not a live mutable directory. citeturn25view2turn25view4turn29view0turn29view3

The concrete answers to your core questions are these. **Who may write engine code?** Any trusted node may author locally; the canonical branch should be advanceable only by the roaming leader’s operator identity, preferably an admin SSH key that can be used from any currently attended machine **[no source found] [speculative]**. Colleagues should default to branch-only pushes unless you intentionally grant them canon rights. **Over which rail?** Over Git push/fetch to a bare repository over SSH; not through Syncthing folder mutation. **What merge/conflict semantics?** Git’s explicit history-based merge, with non-fast-forward rejected on canon, manual merge/rebase on divergence, and hooks executing your existing checks before acceptance. **What blast-radius controls?** An approved commit SHA, signed and promoted by ring; nodes do not auto-run whatever just hit canon. citeturn25view0turn25view1turn25view2turn22view2turn25view4turn29view0turn29view3

The migration order should be:

1. **Freeze the engines folder as a canonical live-sync surface.** Stop using Syncthing send-receive for engines; either remove engines from Syncthing entirely or leave only a temporary read-only bridge during cutover. This is the step that stops another file-sync conflict from becoming “normal.” citeturn22view1turn23view3  
2. **Initialize a Git repo from the current canonical engines tree and tag the baseline.** Because the tree is tiny, full clones and history are cheap. Host a **bare** remote on the VPS anchor and keep a second mirror bare remote on the GPU desktop/hub as resilience against another single-box outage. The dual-remote part is a design recommendation for your incident pattern **[no source found] [speculative]**. Git’s bare-repo format is explicitly for exchange by push/fetch. citeturn25view0  
3. **Protect canon.** Enable `receive.denyNonFastForwards` and `receive.denyDeletes` on the bare remote, and add server-side `pre-receive` or `update` hooks that run your existing deterministic gates: preflight collision check, portability verifier, import probe, and whatever “live-run” ritual can be scripted. Git’s hooks and protected receive settings are designed for exactly this kind of policy enforcement. citeturn25view2turn25view3turn25view4turn22view2  
4. **Move authoring to local clones.** Each trusted machine gets a local clone outside any Syncthing-managed directory. Optional per-machine branches are cheap. If you want two simultaneous local contexts on one node—say `main` plus `hotfix`—Git worktrees exist precisely for that. citeturn32view0turn34search5  
5. **Separate deploy from dev.** Runtime nodes should deploy from an explicitly approved commit SHA or release tag, not from whatever the developer checkout currently contains. If you want to keep your existing HMAC/propagate-verify habit, make the control-plane artifact a small signed `approved.json` containing commit SHA, epoch, ring, and checksum. That exact artifact shape is my synthesis **[no source found] [speculative]**. The important principle—staged promotion instead of immediate fleet-wide rollout—is well established. citeturn29view0turn29view3turn29view2  
6. **Roll out by ring.** Promote one canary first, then a small second ring, then the rest. If the canary fails its runtime probe or operator ritual, stop promotion and roll back to the previous known-good SHA. Device-fleet vendors and deployment systems all converge on this pattern because it sharply reduces the probability that one bad change takes down the whole fleet. citeturn29view0turn29view3turn29view2  
7. **Only after the above, allow colleagues into the authoring flow.** Give them push rights to personal branches first. If, later, you want true multi-author canon writes, you can expand trust gradually. Do not start by giving many machines direct write-to-canon ability. **[established]** citeturn25view2turn25view4

If you need a fallback because Git adoption stalls, take **Option B** and do it properly: one lease authority, one monotonically increasing fencing epoch, one writer at a time, and all other peers still receive-only. But understand what that fallback is: it preserves the current single-writer worldview, just with a roaming crown instead of a permanent hub. It does **not** give you the durable merge semantics or offline-first authoring ergonomics that Git gives almost for free. **[established]** citeturn31view0turn22view3turn20view0

The **single safeguard that matters most against fleet-wide blast radius** is this: **never let runtime nodes auto-follow live authoring state; make them follow only an explicitly approved commit through a canary-first promotion path. [established]** If you get only one thing right, get that right. Git without staged promotion can still spread a bad commit everywhere; staged promotion without Git still leaves merge pain; but staged promotion is the line between “one node is sick” and “the fleet is sick.” citeturn29view0turn29view3turn29view2
