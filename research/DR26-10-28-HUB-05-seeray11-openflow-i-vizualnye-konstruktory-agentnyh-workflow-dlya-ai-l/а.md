**Execution model. [established]** Один node соответствует одной primary OpenCode session. Pipeline разбивается на topological layers, nodes в одном layer реально dispatch одновременно, а run log постепенно пишется в `.openflow/runs/<id>.json`. По умолчанию parallelism = 4, single-node timeout = 30 минут. README сам предупреждает, что широкий layer увеличивает вероятность 429 и непредвиденных затрат. citeturn21view2turn22view0

Это важно для требования **one writer per file**. OpenFlow предотвращает некоторые session-level races — например, один и тот же orchestration card нельзя dispatch дважды в одном batch, а diamond graph запрещён, — но это **не file-level exclusion**: два разных builder nodes могут быть параллельными sessions, направленными на один `OPENFLOW_PROJECT`. Документация gauntlet даже рекомендует назначать tightly coupled work одному последовательному builder, что является хорошей orchestration policy, но не lock. citeturn22view0turn22view1

**[speculative] Поэтому OpenFlow нельзя считать механизмом enforcement вашей one-writer-per-file политики без внешнего lease adapter.** Статическая документация показывает архитектуру, совместимую с collision; я не нашёл документированного worktree/file-lock primitive. Однако я не выполнял source-wide local grep/динамический race test, поэтому формулирую это именно как «гарантия не обнаружена», а не как математически доказанное отсутствие любой внутренней проверки.

**Resumability. [established]** Здесь различие особенно важно. Run log checkpointed постепенно. Если node уже закончен, после Resume его output повторно не запускается. In-flight cards возвращаются к существующим sessions; `Re-run failed` использует завершённые outputs и создаёт fresh sessions только для неуспешных частей. Это существенно лучше простого «начать workflow сначала». Но сама документация прямо говорит: engine runs in the page; reload/crash/closed tab оставляет run без процесса, который завершит state. Поэтому это **manual recovery from checkpoints**, не Temporal/Restate-подобный durable executor. citeturn22view1

Для внешних side effects разница критична. Наличие run checkpoint не доказывает, что MCP/HTTP/CLI side effect завершился или не завершился перед crash. В документации нет transaction/idempotency-key protocol, связывающего OpenFlow step с внешней системой. Значит, «resume without duplicate side effects» для CRM/email/etc. должен обеспечиваться самим tool adapter или существующим ledger.

**Gauntlet/reviewer independence. [established]** Это наиболее интересный элемент для лаборатории. Reviewer определяется ролью `reviewer`; каждый verdict получает fresh session, чтобы critic не оценивал «улучшение относительно прошлой версии» вместо текущего артефакта. Orchestrator не вправе `final`, пока critic не проверил текущий state; critics-only batch считается валидным verdict, а critic, одновременно запущенный с builder, специально не считается финальным review. citeturn22view0turn22view1

Это **реальная независимость контекста**, но не полная независимость среды: reviewer читает тот же workspace. Для code review это обычно плюс; для adversarial isolation это слабее отдельного immutable checkout.

**Coach. [established]** Post-run coach является deterministic code, не LLM. Он, например, сигнализирует о critic, который объявил pass по command-shaped acceptance bar, но не выполнил успешный shell check; об orchestrator, который ничего не dispatch; и о rejected tool calls. Это полезный audit feature и лучше, чем генерировать ещё один самооценочный LLM verdict. citeturn22view1

**Permissions и security boundary. [established]** Per-node toggles транслируются в explicit allow/deny rules. Но unspecified actions, например `external_directory`, обычно остаются `ask`; default runtime policy `auto` автоматически отвечает `once`, разрешая вызов. Поэтому default OpenFlow **не соответствует модели “deny unless explicitly authorized”**. Для такой модели надо явно deny ненужные tools и использовать `ask me`; даже тогда shell с разрешённым `bash` остаётся широким capability. citeturn21view3turn22view2

Это особенно важно для outbound policy: запрет `webfetch`/`websearch` не обязательно запрещает `curl` или network-capable program через `bash`. OpenCode security policy также предупреждает, что local operation не является sandbox/isolation boundary. Следовательно, настоящий «forbidden outbound» следует enforcement-ить OS/container/firewall layer, а не prompt/tool labels. citeturn0search9

**Web authentication. [established]** `packages/flow/README.md` однозначен: `/flow/api` пишет pipeline/run logs, меняет `opencode.json`, и «nothing authenticates the caller». Поэтому оба hosts по умолчанию отказываются bind не на loopback; `FLOW_ALLOW_REMOTE=1` явно снимает этот барьер. **Новый сильный вариант, который стоит учитывать:** LangSmith ecosystem к 2026 уже не только observability: официальный LangGraph overview перечисляет durable runtime, Studio и no-code/building layers, а Agent Builder стал GA в январе 2026. **Langflow тоже заметно изменился именно в последние месяцы.** Версия 1.13 от 22 октября 2026 добавила audit logging, reusable OAuth connections и concurrent editing checks; версия 1.12 в сентябре добавляла OpenTelemetry. Поэтому оценивать Langflow по его состоянию 2024–2025 уже некорректно. citeturn26search5

### Durable runtime — отдельный слой, а не «ещё один конкурент»

Temporal и Restate не следует ставить в один UX ranking с OpenFlow.

Temporal прямо требует проектировать Activities как idempotent, потому что retries могут повторно выполнять работу; его преимущество — durable workflow state/replay/recovery, а не agent canvas. citeturn10search4turn10search10turn10search16

Restate ещё ближе к agentic case: он позиционирует durable steps так, чтобы LLM/tool/routing decisions сохранялись и execution мог продолжиться после crash. citeturn10search5turn10search11turn10search35

Если вашей реальной болью станет **“SQLite leases + retry logic превратились в собственный маленький Temporal”**, тогда отдельное исследование Temporal/Restate оправдано. Но добавлять их просто ради visual workflows сейчас увеличит maintenance, не решая UX самостоятельно.

## D — Различия, спорные места и соответствие четырём сценариям

### Что OpenFlow даёт, чего почти не дают generic builders

**[established] Сильнейший аргумент ЗА OpenFlow:** gauntlet представляет reviewer как **эпистемически отдельного critic**, а не просто следующий node. Fresh session per verdict уменьшает anchoring на собственном предыдущем reasoning; orchestrator технически не может считать работу завершённой без critic verdict текущего state. Именно для лаборатории с explicit writer/reviewer roles это гораздо более интересная особенность, чем количество SaaS connectors. citeturn22view0turn22view1

Другие builders легко рисуют `builder → reviewer → revise`, но наличие двух прямоугольников на canvas само по себе не доказывает независимость контекста. В OpenFlow это explicitly encoded scheduler behavior.

**[established] Второе преимущество:** pipeline/run artifacts локальны и понятны: graph JSON, run JSON, generated agent definitions, OpenCode SQLite sessions. Нет обязательной SaaS control plane для самого v1.3.0. citeturn22view1turn22view2

**[emerging] Третье:** проект очень молодой, поэтому implementation ещё достаточно прост для аудита небольшой командой. Это одновременно плюс и риск.

### Сильнейший аргумент ПРОТИВ

**OpenFlow сейчас находится не в том reliability layer, который у вас уже построен.** Ваш SQLite task/lease ledger, scheduler и n8n уже решают ownership и recovery как control-plane задачи. OpenFlow добавляет второй execution state:

`OpenFlow run JSON → browser page state → OpenCode sessions → actual filesystem/tools`

вместо:

`canonical task/lease ledger → harness worker → explicit side-effect adapters`.

Это не означает, что OpenFlow «не нужен»; конкуренция не доказывает отсутствие value. Но **замена** вашего runtime OpenFlow уменьшила бы гарантийную поверхность именно там, где вы её уже сознательно построили.

### Использование существующих subscriptions

Здесь generic agent builders системно проигрывают вашему текущему подходу.

Anthropic официально различает Claude plans и API. Claude Code может использовать Pro/Max subscription через собственный supported login; сторонний developer не должен превращать Claude.ai OAuth/session token в backend своего продукта. citeturn14search0turn13search3

OpenAI теперь также поддерживает `Sign in with ChatGPT` для участвующих сторонних apps, но это специальный supported mechanism; наличие ChatGPT/Codex subscription не превращает произвольный OpenAI API key в бесплатный subscription endpoint. citeturn13search2turn14search1turn14search4

Поэтому архитектурно ваш существующий способ **«оркестрировать сами Claude Code/Codex harnesses»** ценнее для subscription reuse, чем очередной model-level visual platform.

Это было сильнейшей привлекательностью Vibe Kanban: он просит сначала авторизоваться в выбранном coding agent, затем запускает agent в workspace. Но sunset продукта практически снимает его с short-list. citeturn16view0

### Что не следует дублировать

При любом успешном trial я бы **не создавал вторую canonical copy** ролей, tool policies, task IDs и lease state внутри OpenFlow.

Лучший интеграционный паттерн:

`shared source of truth → thin adapter → OpenFlow pipeline`

а не:

`shared skills + OpenFlow-specific manually maintained copies + n8n-specific copies + harness-specific copies`.

Например, writer/reviewer policy и allowed capabilities должны оставаться в вашем общем role/skills definition, а OpenFlow JSON — генерироваться или синхронизироваться адаптером. Это особенно важно, потому что OpenFlow сам генерирует agent keys и merge-ит definitions в `opencode.json`. citeturn22view1

**Интеграционная сложность, без выдуманных часов:**

- OpenFlow как disposable shadow UI: **низкая–средняя**.
- OpenFlow как production replacement task ledger: **высокая**, потому что потребуется внешний lease/idempotency/action gateway.
- Flowise/Dify/Langflow как новый general automation platform: **средняя–высокая**, потому что основная работа будет migration/duplication уже существующих n8n integrations.
- LangGraph как новый durable agent runtime: **высокая**, но потенциально оправдана, если нынешний собственный scheduler/ledger станет maintenance bottleneck.
- Добавить новый flow непосредственно в существующий n8n: **низкая относительная**, потому что infrastructure уже есть; это не утверждение о фактических человеко-часах.

Большинство feature evidence в этой области — first-party documentation. Поэтому таблица выше показывает **capability existence**, а не доказанную production reliability.

Для OpenFlow независимых adoption data практически нет: два HN items почти не вызвали обсуждения. citeturn0search8turn0search7

Для Langflow есть гораздо более старый HN signal — acquisition announcement 4 апреля 2024 года получил заметное обсуждение, включая скепсис сообщества по поводу будущей openness после acquisition, — но это **старый social signal, не benchmark Langflow 1.13 2026**. citeturn24search7

| **API cost runaway** | Gauntlet имеет app-level spend bound; другие current modes universal cap не имеют; PR #24 пытается это исправить. citeturn22view0turn22view3 | Pilot только `$0` free models; production API usage до merge/verification universal cap — отдельно ограничивать provider-side. |
| **Secret leakage** | MCP values в `opencode.json` plaintext; run logs содержат prompts/output; OpenCode sessions persist в SQLite. citeturn22view1turn22view2 | Disposable profile + no real secrets/private data в первом trial. |
| **Config corruption** | Merge `opencode.json` делает original `.bak` и previous backup; commented JSON OpenFlow отказывается rewrite, чтобы не strip comments. citeturn21view3turn22view1 | Хорошая defensive engineering деталь, но pilot всё равно должен использовать disposable project config. |
| **Free Zen unavailable** | Shared free tier может выдавать 429/400. citeturn21view1 | Это не повод автоматически подключать платный API; по pilot rules — stop/inconclusive. |

**[established] Важный security distinction:** наличие audit log не превращает permission UX в sandbox. OpenFlow хорошо записывает permission decision; это помогает post-hoc audit. Но enforcement capability всё ещё зависит от OpenCode tools, shell, OS и MCP server. citeturn21view3turn0search9

**[established] “No known CVE” здесь вообще не используется как аргумент.** Даже если upstream advisories отсутствуют, young local file-writing orchestration app с unauthenticated loopback API остаётся отдельной attack surface. И наоборот, upstream OpenCode advisory не следует автоматически приписывать `packages/flow`: их надо связывать с конкретным affected path/version.

## F — Decision memo

**Решение: TRIAL OpenFlow — но строго как complement/shadow, не как новый system of record.**

Причина не в том, что OpenFlow «победил» Flowise/Dify/LangGraph. Причина в том, что он проверяет **единственную действительно новую для вашего stack гипотезу** с низкой migration стоимостью:

> даёт ли визуальный graph + fresh-context critic loop настолько лучшую human visibility и reviewer independence, что его стоит интегрировать поверх существующего durable control plane?

Generic visual builders в основном проверяли бы то, что уже известно: визуальный n8n-подобный graph удобен.

### Аргумент за trial

**[emerging] OpenFlow — unusually good fit именно для experimental multi-agent engineering.** Scheduler специально различает builder и independent critic, fresh sessions, fail-closed reviewer requirement, deterministic coach и visible run state. Код этой логики достаточно локализован в `packages/flow`, а current release свеж и активно меняется. citeturn20view1turn22view1turn22view5

Для anonymized disposable code task это можно проверить без private data и без денежных обязательств через Zen free. citeturn21view1

### Аргумент против adoption

На сегодняшний день OpenFlow не заслуживает роли authoritative executor для вашей лаборатории, потому что три ключевые гарантии должны жить снаружи:

**ownership:** нет доказанного one-writer-per-file/worktree/lease enforcement;

**durability:** page-owned orchestration требует Resume, а не background durable worker;

**side-effect exactly-once:** checkpointed run log не является transaction/idempotency protocol.

Эти три вещи — как раз сильные стороны вашего текущего Python/SQLite/n8n design context.

### Почему не выбрать конкурента прямо сейчас

**Flowise Agentflow V2** — мой выбор, если потребуется именно **новый generic visual agent builder**. Он имеет более зрелый direct visual workflow surface, MCP и HITL, не требует 12 GB minimum как Sim и имеет понятный self-host/community path. Но он всё равно в основном дублирует n8n и не решает coding-harness subscription/worktree requirement. citeturn25search0turn25search4turn7search6turn7search9

**Dify** лучше Flowise для business-facing meeting→CRM/content automation из-за triggers, Human Input и deployment surface; однако это ещё более явное дублирование n8n и более ограничительная лицензия. citeturn8search5turn8search20turn8search29turn8search1

**Langflow** выглядит наиболее зрелым OSS visual builder по общей ecosystem/maintenance картине, особенно после v1.13, но его главные достоинства — general AI prototyping, RAG/MCP, audit/observability — не закрывают ваши file ownership/durable side-effect требования. citeturn26search5turn26search11

**LangGraph/LangSmith** — лучший технический candidate, если вы решите заменить собственный durable runtime, а не визуальный UI. Но это принципиально более серьёзная архитектурная миграция. citeturn16view2turn26search3

**Vibe Kanban** архитектурно был наиболее точным complement для Claude Code/Codex harnesses и workspaces, но sunset делает его плохой новой зависимостью. citeturn16view0

**Sim** привлекателен как современный UI, но official 12 GB RAM minimum self-host footprint плохо совпадает с вашей целью минимизировать runtime/RAM. citeturn25search2

**AutoGen Studio/Rivet** не имеют достаточного преимущества над текущим stack, чтобы оправдать дополнительный runtime.

### Что изменило бы рекомендацию

Рекомендация сдвинется из **“shadow trial” → “integrate OpenFlow”**, если одновременно подтвердятся следующие вещи:

1. Runtime pilot покажет, что OpenFlow существенно улучшает visibility/reviewer workflow без ухудшения correctness/recovery.
2. В него можно поставить thin adapter к **вашему существующему lease ledger**, а не создать второй ownership database.
3. File ownership можно enforce внешним worktree/lease bridge.
4. Background/durable execution появится в продукте либо OpenFlow сможет безопасно быть UI поверх вашего scheduler.
5. PR #24 или эквивалент будет merged/released и проверен, а cost controls пройдут failure tests.
6. Появится официальный HARNESS adapter для Claude Code/Codex, использующий только provider-sanctioned authentication, либо это перестанет быть приоритетом.

Рекомендация сдвинется в **“keep existing tools, no OpenFlow”**, если shadow pilot покажет, что текущие n8n/harness traces позволяют оператору столь же быстро отвечать на вопросы «кто сейчас работает, что завершено, почему reviewer отказал, где восстановиться после crash».

Рекомендация сдвинется в **“adopt LangGraph/Restate/Temporal layer”**, если реальная измеренная боль окажется не visual UX, а поддержание собственной crash/retry/idempotency state machine.

## G — Спецификация безопасного shadow-pilot

Это **спецификация будущего теста, не выполненное действие**.

**Цель:** измерить только incremental value OpenFlow как visual orchestration/reviewer interface. Не тестировать production deployment, remote access, CRM writes или private data.

**Версия:** pinned **v1.3.0**, а не moving `dev` и не PR #24. Причина: иначе результат невозможно воспроизвести, а PR-only features загрязнят вывод. Release опубликован 18 октября 2026 года. citeturn22view4

**Денежный ceiling: `$0.00`.** Только OpenCode Zen `-free` model. Никаких Anthropic/OpenAI API keys, credit cards или subscription-token workarounds. Если shared free tier из-за 429/availability не позволяет закончить bounded run, результат записывается как `INCONCLUSIVE_PROVIDER_CAPACITY`, а не как разрешение перейти на платный backend. citeturn21view1

**Изоляция:** disposable local Git project, отдельный test profile/home без реальных provider credentials, no private data, loopback-only host, no MCP servers в первом pass. OpenFlow API не имеет app auth, поэтому remote bind в pilot запрещён. citeturn21view0

**Тестовая задача:** небольшой deterministic code change, например pure parser/validator в toy repository с unit tests и тремя roles:

`planner [read only] → builder [read + edit] → reviewer [read; optionally bash tests; edit denied]`.

Для gauntlet reviewer acceptance bar должен быть объективным, например tests exit successfully, exact edge cases present, no files outside allowed set. OpenFlow coach специально умеет обнаруживать command-shaped pass, где critic фактически не выполнил успешную shell check. citeturn22view1

**Baseline:** та же самая anonymized task через уже существующий laboratory path: current harness + current explicit writer/reviewer roles + current task/lease ledger. Это важно, потому что предоставленный контекст **не является измеренным performance baseline**.

Не нужно сравнивать «кто написал лучший код один раз». Нужно сравнить операционную систему управления работой.

**Записываемые метрики:**

| Метрика | Как оценивать |
|---|---|
| Correctness | Одинаковый deterministic test suite; OpenFlow не получает облегчённых tests. |
| Reviewer independence | Reviewer session должна быть fresh; reviewer не имеет edit capability; verdict должен ссылаться на observable artifact/tests. |
| Writer ownership violations | `0` допустимых несанкционированных writes. |
| Duplicate external side effects | `0`; в первой фазе реальные external writes вообще отсутствуют. |
| Recovery completeness | После deliberate interruption: сколько finished steps восстановлено без rerun, какие steps ambiguously in-flight. |
| Operator repair time | Время от failure до понимания: «что завершено, что надо продолжить, что безопасно не повторять». |
| Visibility | Оператор по UI/log должен без чтения внутренней SQLite БД определить active/failed/reviewer state. |
| Audit completeness | task prompt, role, output, permission decision, reviewer verdict и interruption должны быть reconstructable. |
| Runtime overhead | Idle RSS и peak RSS суммарно для OpenFlow/OpenCode/Bun; CPU idle/peak; startup process count. **Не сравнивать с вымышленными benchmarks.** |
| Model consumption | Sessions/turns/token usage, где runtime его показывает; отдельно gauntlet critic sessions. |
| Cash | `$0.00`. |
| Repair complexity | Число ручных interventions/restarts/config fixes. |

**Лабораторные thresholds, а не прогнозы продукта:**

- hard stop при любом paid charge;
- hard stop при write за пределы disposable project;
- hard stop при network outbound, который был обозначен forbidden;
- hard stop при использовании/запросе реального subscription token;
- hard stop при corruption/loss исходного baseline project;
- hard stop при неожиданном non-loopback bind;
- OpenFlow не может считаться replacement runtime, если two-writer test не предотвращается/не детектируется;
- OpenFlow как complement считается успешным, если correctness не хуже baseline и median operator reconstruction/recovery time на scripted failures ощутимо лучше baseline; порог улучшения следует зафиксировать **до** теста, например 25–30%, а не выбирать после результатов;
- sustained additional memory ceiling тоже должен быть задан лабораторией заранее; до измерения я не предлагаю объявлять «нормальным» конкретное потребление RAM.

### Deliberate failure suite

**Browser close/reload.** Прервать run после завершения planner и во время builder. После reopening использовать только documented Resume. Проверить, не rerun ли planner, сохранился ли builder session, понятен ли operator state. Ожидаемое documented behavior — finished cards не выполняются снова, in-flight cards продолжаются через существующие sessions. citeturn22view1

**Process crash/restart.** Аналогично остановить owning process в disposable environment, затем восстановить. Критерий — не «можно ли руками починить», а сколько ambiguous work остаётся после restart.

**Provider 429.** Не следует намеренно hammer shared Zen service. Для controlled test нужен уже разрешённый test proxy/provider double, способный вернуть 429; если такого существующего approved facility нет, эту проверку надо пометить **UNTESTED**, а не генерировать нагрузку на публичный provider. Документированное gauntlet ожидание — три retries с 20/40/80 s backoff. citeturn22view0

**Two writers.** Это важный negative control. Создать два builder cards, оба получающие инструкцию изменить один sentinel file. Необходимо проверить:

- есть ли предупреждение до run;
- кто фактически пишет первым/последним;
- виден ли collision;
- может ли reviewer обнаружить потерянное изменение;
- можно ли внешний lease adapter сделать mandatory.

Если оба cards бесконтрольно пишут один файл, это **не обязательно провал OpenFlow как UI**, но окончательно исключает его из роли native ownership enforcement.

**Reviewer unavailable.** Сделать critic model/session недоступным в controlled manner. Gauntlet не должен выдавать false success. Документация предполагает error при all critics failed. citeturn22view1

**Forbidden outbound.** Отключить `webfetch`, `websearch`, MCP; если `bash` требуется reviewer для tests, дополнительно обеспечить OS-level egress deny. Затем дать adversarial instruction попытаться получить внешний URL. Успех = zero packet/outbound connection, а не просто «websearch tool denied». OpenCode local permission model не является sandbox. citeturn0search9turn22view2

**Unauthorized external path.** Попросить agent записать файл вне project. При `ask me` operator должен увидеть request и reject; при explicit deny write не должен произойти. Default `auto` в этом тесте использовать нельзя, поскольку он сам отвечает `once`. citeturn22view2

**Interrupted pseudo-side-effect.** Вместо CRM использовать disposable local mock ledger с operation ID. Прервать run между “request accepted” и “completion observed”. Это покажет, умеет ли OpenFlow определить ambiguous completion. Реальных emails/CRM updates в pilot быть не должно.

### Ограничение gauntlet

Даже при `$0` model price monetary cap бессмысленен как workload limiter, поэтому дополнительно ограничить:

- минимально необходимый depth;
- низкий dispatch count;
- parallelism `1` для первого deterministic run;
- короткий wall clock;
- один builder и один critic;
- заранее ограниченное число повторных trials.

Это предотвращает ситуацию «бесплатно, значит бесконечно».

### Rollback

Pilot project не должен быть тем же checkout, где находятся реальные laboratory skills/tasks.

OpenFlow документированно пишет `.openflow/*` и может merge agent definitions в project `opencode.json`, предварительно создавая `.bak` и `.prev.bak`. Поэтому rollback должен опираться прежде всего на **disposable repository/test profile**, а не на надежду на backups. citeturn22view1turn21view3

Не использовать provider “repackage” в первом pilot: он способен менять global OpenCode config и требует engine restart. citeturn21view2

После trial сравнивать только зафиксированные показатели; не сохранять OpenFlow config как новый source-of-truth до принятия решения.

**Окончательный выбор:**

**Вариант OpenFlow:** лучший **экспериментальный** выбор для визуального planner → builder → fresh reviewer и проверки независимого critique UX; слаб в native durability/file ownership/provider-subscription reuse.

**Вариант Flowise Agentflow V2:** лучший из рассмотренных прямых generic visual competitors, если лаборатория сознательно хочет второй general agent-workflow platform; минус — значительное пересечение с n8n и отсутствие решения harness/worktree проблемы. citeturn25search0turn25search4

**Вариант LangGraph/LangSmith:** лучший кандидат, если проблема на самом деле в durable stateful agent runtime, а не в visual UX; цена — большая архитектурная/операционная поверхность. citeturn16view2turn26search3

**Вариант keep existing:** наиболее сильный production baseline для meeting→CRM, approvals, scheduling и one-writer/idempotency policies, потому что n8n/Python/SQLite уже находятся в вашем design и не требуют второго authoritative scheduler.

**Одна рекомендация:** **не менять production stack; специфицировать и затем отдельно авторизовать bounded `$0` shadow-trial OpenFlow v1.3.0 на одном disposable code task.** Его задача — доказать или опровергнуть ценность visual independent-review loop. Не давать ему ownership production files, CRM/email side effects, real MCP credentials или provider API spend.

**Главное допущение:** ваш существующий n8n/Python/SQLite control plane в целом пригоден как canonical source of task ownership и durability; предоставленный контекст не доказывает его performance, поэтому pilot обязательно должен впервые измерить baseline.

**Главные неизвестные:** реальный RAM/CPU OpenFlow на хаб и других OS; behaviour под настоящим crash на Windows; точная величина possible cost overshoot in-flight; runtime collision двух writers; стабильность Zen free; portability export schema; и то, насколько visual gauntlet уменьшит operator/debugging cost относительно уже существующих explicit writer/reviewer roles.
