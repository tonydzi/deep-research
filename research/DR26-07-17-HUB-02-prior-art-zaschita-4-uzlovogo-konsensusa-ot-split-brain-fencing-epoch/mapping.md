# 1. Prior‑art mapping

**Lease‐and‐fencing:** Many systems (ZooKeeper, etcd) use *monotonic leases* or epoch numbers with fencing tokens. Each “leadership” change increments a token, and all subsequent commits must include the current token. Stale leaders’ writes are then rejected by detecting old tokens. In our file‐log setting, we could tag each COMMIT event with an increasing *epoch*. Before applying a commit, peers check that its epoch ≥ any seen token. This blocks an old leader’s decisions after a new election. **Cost:** requires adding an epoch counter to proposals and enforcing it in all peers. **Failure modes:** If epochs get out of sync (e.g. due to clock skew or multi‐leader forks), fences may not prevent inconsistency. Fencing also assumes a shared “storage” that honors tokens; here that would be our own sync‐merge logic.

**Epoch/term numbers (Raft style):** Raft uses a monotonically increasing *term number* on every election, and peers ignore messages from lower terms. We can mimic this by having each arbiter election bump a term and include “term” in each PROPOSE/ACCEPT event. Peers who see a higher term reject lower‐term commits. This effectively implements a lease: only the current‐term arbiter’s writes are valid. **Cost:** moderate; need global term counter and endorsement in each event. **Failure modes:** Without a reliable broadcast, two nodes might independently increment terms, leading to split-brain anyway. Also requires care to avoid term overflow or reset. 

**Witness/tie‑breaker nodes:** In some clusters, *witness* nodes (non‐voters) or arbiters are used. We effectively have a “roaming arbiter” chosen by fixed priority. We could strengthen this by designating one or more *passive witnesses*: e.g. require a backup “Mayak” (VPS) to confirm if available. In our log‐sync model, a witness could post its stamp (or vote) to the shared state or Telegram. For example, require not just the first‐priority fresh node, but also a witness stamp before auto-commit. **Cost:** minimal (just add one more check), but relies on witness availability. **Failure modes:** If the witness is unavailable (e.g. sleeps or partitioned), progress stalls. 

**Rendezvous via Telegram (side‑channel):** We have a shared real‐time Telegram group. If every node posts signed heartbeats or epoch claims there, it acts like a low‐bandwidth bulletin board. For instance, an arbiter could *announce* its claim on TG. Peers seeing a conflicting claim could refuse to proceed. In effect, TG is an out-of-band “token service.” This can help tie-break simultaneous leaders. **Cost:** trivial tech (just HTTP/TG bot calls), but adds reliance on Internet/TG uptime. **Failure modes:** TG itself can partition (if a node loses Internet). If two partitioned nodes both reach TG, they may each see only themselves, so they might both post. Without extra rules, TG can also suffer split-brain (see below). 

**Invariant/CRDT approaches:** One could design the state so that *divergent commits are harmless*. CRDTs allow concurrent updates to merge deterministically. For example, make each proposal idempotent (so committing twice is fine) or have commutative merge of decisions. However, CRDTs only guarantee convergence for specially designed operations (e.g. grow-only sets, counters), and cannot enforce global invariants (two leaders both taking different actions is generally a non-commutative conflict). In practice, building our consensus protocol atop CRDTs would be very complex (we’d need tombstones or vector clocks). **Cost:** high design/implementation effort for limited benefit. **Failure modes:** if two arbiters commit different results on the same proposal, resolving that via CRDT merge is nontrivial or impossible without drops; we’d likely still need reconciliation. 

**Summary (Q1):** Common patterns include **leases with fencing tokens** (ensure old leaders’ events are ignored), **term numbers** (as in Raft) and **quorum/minority-freeze** (which prevent split-brain by construction). In our file-sync world, these would map to adding an *epoch* counter or fence token to events (cost: adding logic in the log parser), and possibly requiring explicit confirmation (quorum). A **witness** (e.g. a VPS) could be used as an extra arbiter vote. A **Telegram side-channel** can act as a makeshift log or lock server for tie-breaking, but it itself is unreliable if network is partitioned. CRDT/invariant approaches largely avoid consensus but would require transforming all proposals into commutative operations, which is probably infeasible for our ledger operations. 

# 2. Partition detection

We need cheap local signals to suspect a partition. Candidates:

- **Syncthing connection status:** Each node can query its own Syncthing via REST (`/rest/system/connections`). This returns for each known device whether a connection is active. If a peer goes from “connected: true” to “false”, we likely are partitioned relative to it. This is a *direct, immediate local oracle* (does not rely on eventual sync). **Signal/noise:** High signal if a node was recently connected and suddenly disconnects; noise if a node is simply offline (sleeping). We expect HP17, hub, Mayak may often see each other, but MacBook sleeps for weeks – it will show disconnected normally, which we should treat as expected. Thus the key is detecting *changes* (it was up, now down) or multiple simultaneous disconnects.

- **Presence‐stamp asymmetry:** Our existing presence stamps `.robot-alive-<M>.log` are synced via files. If Node A sees Node B’s stamp stale while Node B sees A fresh, that asymmetry indicates a split. **Signal/noise:** Moderate. If a node is merely sleeping, both will see staleness in expected ways. But if two normally-alive nodes stop seeing each other’s stamps beyond threshold (~45–70 min), that suggests a partition. The problem is that stamps may themselves lag behind in a partition, so this detection might be late or ambiguous. Still, checking “I think B is dead but B thinks A is alive” is a red flag.

- **Ledger‐progress divergence:** Monitor event flow. E.g., “If I am generating PROPOSEs/ACCEPTs but see no new events from others for a long time, perhaps I’m isolated.” Conversely, “others are making events but none reach me.” Each node can compare its local log progress to the latest synced events from peers. **Signal/noise:** Low in regular use (it’s common that no one is proposing anything). But if proposals should be happening and stops, it could hint at a partition. Hard to automate.

- **Telegram heartbeat cross-check:** If nodes post signed heartbeats (or epoch numbers) in the TG group, each node can see who is “active” on that side channel. If Syncthing shows A connected to B but TG shows B’s last heartbeat was stale, there’s inconsistency. Or vice versa. **Signal/noise:** Emergent: TG adds an external perspective, but again suffers if the Internet is down for one side. If TG is reachable from both partitions, it can confirm real liveness. If one partition cannot reach TG (say VPN vs no VPN), then it looks dead erroneously. Overall, TG has some noise but can supplement detection.

**Ranking (4‑node with sleep):** The *cleanest local signal* is Syncthing’s own connections. If a node suddenly loses >1 connections (especially to peers that should normally be up), that’s a strong partition indicator. We’ll label this “Established (high confidence)”. Presence-stamp asymmetries are “Emerging”: it’s deliberate but relies on eventual sync latency. Ledger divergence is “Speculative” (since no obvious metric). Telegram liveness is “Emerging”: could catch cases Syncthing misses (e.g. IPv6 vs relays), but adds complexity. 

# 3. Safe‑mode semantics under partition

If a partition is suspected, the arbiter should limit damage. Options:

- **(a) Freeze (manual fallback):** Cease all automatic arbitration/commits and escalate to human intervention. This is the simplest safe mode (stop the machine). In practice, many consensus systems *prefer availability over progress*: a minority partition simply refuses to elect a leader or accept writes. For our size (N=4), we can afford to stop Tier-0/1 proposals until the operator (Anton) manually inspects. **Pros:** trivially safe (no conflicting commits can happen). **Cons:** stalls automatic operation; requires human to resolve when partition is false alarm. **Industry precedent:** Majority‐quorum systems (Raft, ZK) essentially do this – the smaller partition is read-only. (Confidence: established.)

- **(b) Idempotent/reversible proposals only:** Limit what actions can be taken in partitioned mode. For example, only propose operations that can be safely retried or rolled back (like no net effect commands). This is akin to operating in “readonly” or “safe” mode. **Pros:** allows some progress. **Cons:** Requires defining what is safe per-operation; complex to enforce. Many operations may not be reversible. Industry doesn’t usually do this at the protocol level (business logic might). (Confidence: speculative.)

- **(c) Tentative‐commit with challenge window:** Allow commits but mark them *tentative*, with a chance for another partition to challenge. Essentially, require a de facto two-phase commit: one partition “tentatively commits” (and logs it), but when partition heals, if conflicting commits occurred, they must be reconciled (e.g. by rollback or choosing one). We already have Phase A (snapshot + tentatives) built. This is like optimistic lock: commit assuming others will agree, else resolve after. **Pros:** keeps system running. **Cons:** adds complexity to mark/track tentative state and resolve later. If conflicts occur, automatic resolution is hard (see next section). Industry: in Paxos/Raft there is no rollback – if a minority committed, it's a bug. Some systems (like distributed version control) do allow merging, but that’s manual/complex. (Confidence: speculative.)

- **(d) Fencing/epoch stamps:** As discussed, tag all arbiter decisions with an *epoch* and make nodes ignore any commit from a lower epoch. In safe mode, if a node suspects it’s not the rightful arbiter (e.g. sees a higher epoch on TG or its log), it stops. This is like a logical fence on old actions. **Pros:** prevents “stale” branch from tainting state. **Cons:** requires careful tracking of epochs (what if two leaders concurrently bump it?). Unless combined with a *majority or external source* for unique epochs, simultaneous isolated increment leads to collision.

**Industry lessons:** Most robust systems combine (a) and (d). E.g. Zookeeper/etcd use consensus (essentially (a) and (d) since only majority obtains lease). They never do (b) or (c) – if quorum is lost, they simply block. For our personal use, the safest minimal approach is to **freeze when in doubt** (per (a)), possibly allowing only trivially safe operations. We should *not* rely on untested auto-merge schemes. Fencing (d) is useful to prevent a lagging node (after heal) from replaying old decisions, so including an epoch in each commit (and refusing old epochs) is recommended. The tentative‑commit scheme (c) is powerful but adds major complexity for limited benefit at N=4 – likely overkill here. (Confidence: emerging for fencing, established for freeze/quorum.)

# 4. Reconciliation on rejoin

If a split‐brain occurred (two nodes each acting as arbiter), merging their logs is tricky. Our state is an append-only multi-shard log; conflicts arise only in *decision events* (COMMIT/tie-break events). Reconciling could use one of:

- **Deterministic total ordering:** Collect all events from all nodes, then order them by (timestamp, machine ID) or similar deterministic rule. Replay in that global order. This ensures all nodes converge to the same interleaving. **Effect:** Some proposals may be effectively applied “out of original context”. If two conflicting commits exist, the one earlier in sort order wins. **Pros:** fully automatic. **Cons:** may violate real causality and business logic; effectively arbitrarily favors one side of partition. Requires reliable clocks or vector-time merges, which we lack. (Confidence: speculative due to complexity.)

- **Epoch-wins (priority):** If we use fencing (epoch) for each arbiter, the easiest reconciliation is to say *“the higher‐epoch leader’s branch wins.”* Discard (or roll back) all commit events from the lower epoch. For example, if HP17 acted at epoch 10 and Mayak at epoch 11, then all epoch 11 decisions stand, and epoch 10 decisions are treated as if aborted. **Pros:** simple; consistent with fencing. **Cons:** one side’s work is lost, possibly silently; requires logging conflicting proposals for human review. If both sides incremented the epoch independently (tie of token number), we need a tie-break rule (e.g. higher node ID wins). (Confidence: emerging.)

- **Manual review of conflicts:** Detect exactly which commits conflict and present them to the user. For each proposal ID with >1 COMMIT, ask “which outcome to keep?” or auto-drop one side’s commit (e.g. the lower-priority arbiter’s). **Pros:** safe (human decides); can salvage non-conflicting divergent data. **Cons:** burdensome if many conflicts; not fully automated. The conflict set can be precisely identified by matching on proposal IDs: if two shards have COMMIT events for the same proposal ID but different contents, that’s a conflict. (The logs are append-only, so we’d scan all COMMIT events for duplicate IDs or overlapping time windows.) (Confidence: spec/emer.)

**Conflict detection:** A concrete approach is: after merge, gather all (ProposalID, COMMIT) pairs from every log. Group by ProposalID. Any ID with more than one COMMIT implies a conflict. Alternatively, if proposals are not globally unique, compare content or timestamps of COMMITs that would have overlap in intended execution. In short: “conflict = two leaders committed the same or overlapping proposal differently.” For each conflict group, apply the chosen resolution rule (e.g. drop lower-epoch). Document all such conflicts for auditing.

**Industry note:** Very few systems auto-merge splits. E.g., Elasticsearch avoids it entirely – it simply discards one side’s diverged data, asking operators to handle it. This underscores that automatic reconciliation is error-prone. At our scale, we should likely salvage as much as possible (since we control all data) but err on human-in-loop for true conflicts.

# 5. Telegram side‐channel protocol

Using the shared Telegram group can *potentially* reduce split-brain, but it’s not a cure-all. Treating TG as a “secondary consensus rail” means nodes broadcast signed heartbeats or leadership claims there. For instance, a simple protocol:

- Every node posts a periodic “I am alive (epoch X)” message to TG. 
- To become arbiter, a node first *proposes* itself by posting “LeaderCandidate(epoch E, timestamp T, signature)” and then waits a challenge window (e.g. T = 30 s). If no other conflicting post (same epoch or higher) appears, it proceeds. 
- If another node posts an equal/higher claim, both back off (escallate).
- On reconnection, nodes accept the highest-epoch stable claim as leader.

This mirrors concepts from distributed atomic registers in a human channel. **Safety:** If TG is globally reachable, it helps ensure only one leader proceeds; it effectively serves as a linearizable “lock service.” But if the Internet link splits differently than the local net, one partition might see TG and the other not – possibly giving false confidence. In short, TG is “just another eventually consistent channel.” It can improve safety *if* used with rules (e.g. require a leader-post to be uncontested for a duration), but it can also become an extra point of failure (if the TG bot crashes or is slow).

**Does it solve split-brain or shift it?** It helps if *both* partitions connect to Telegram. Then a node with no TG updates (due to partition) knows it’s isolated. But if *both* partitions have Internet, they both see each other on TG and may conflict there too – unless we enforce ordering (e.g. by timestamp or waiting). So TG doesn’t magically solve asynchronous split; it must be used with a clear protocol. Minimal improvement can come from requiring any arbiter action to be *announced* on TG and watching for a timeout. This effectively adds a delay but prevents blind takeovers. 

**Confidence:** speculative. In practice, side channels are used in human-in-the-loop or site-to-site failovers (for example, some clusters use external “witness” boxes). Our TG channel could serve as a decentralized witness. A minimal safety measure: **“Before an arbiter applies a Tier-0/1 decision, it must post its intent on Telegram and wait (e.g. 30 s). If another node posted a conflicting arbiter claim in that time, cancel.”** That prevents simultaneous commits. Still, if the Telegram group itself partitions (e.g. blocked by firewall on one node), it fails silently. So TG should only be **secondary**: useful when available, but we must still rely on (a) freeze and (d) fencing as primary guarantees.

# 6. Recommendation

**Minimal approach for 4-node personal fleet:** Given simplicity and human oversight, I recommend combining **(d) Epoch+Fencing + (a) Freeze** with **a connectivity check**, as follows:

- Keep the **fixed priority arbiter** but embed an **“epoch” counter** in every decision event. The acting arbiter increments its epoch on (re)becoming arbiter. Include epoch+arbiter-ID in COMMIT records. Upon loading logs, reject any COMMIT from an epoch lower than the highest seen. (Implementation: ~100–200 lines; modifying consensus.py to tag events and compare epochs). *Confidence: established.* This implements logical fencing as in ZK/etcd.
- Use the **Syncthing REST API** as a local oracle: if a node loses connection to ≥2 others (including any always‑on nodes like the hub/Mayak), assume partition and **freeze** (auto-commit off). Practically, check `/rest/system/connections` every few minutes. If “connected” drops unexpectedly, switch to safe mode. (Modest code: a few HTTP calls and JSON parsing.) *Confidence: established.* This mirrors quorum logic but applied heuristically (we can allow 2-of-4 to function, freeze if it dips to 1-of-4).
- Upon suspected partition, **only allow Tier-2 (human‑approved) proposals** to proceed. For Tier-0/1, refuse auto-commit and send an alert. (Tier-2 already is human-only.) Optionally mark in the log “STALLED_DUE_TO_PARTITION”. *Confidence: emerging.* This prevents unnoticed conflicts with minimal code changes.
- For **reconciliation**, adopt an “epoch-wins” rule: after healing, replay logs but discard any commit from a lower epoch when conflicting with a higher epoch (detect conflicts by matching proposal IDs in COMMIT events). Flag dropped proposals to the user. (A small post-merge script or code in consensus.py can do this.) *Confidence: emerging.* This keeps logic simple. 
- **What *not* to build:** Do not implement full Raft or BFT: they require multiphase RPC, major refactoring, and are overkill for 4 self-managed nodes. Don’t attempt a full CRDT or multi-round commit protocol – too complex for N=4. The existing architecture (single-writer shards, manual Tier-2) already bounds damage; adding heavy consensus would greatly increase code (likely thousands of lines) and failure modes. Keep it understandable. Our focus is on robust, simple fail-safes (fencing+freeze) rather than full consensus. 

In summary, a two-mechanism defense: **logical fencing (epoch)** to refuse stale commits and **partition-detection freeze** to halt on splits. These together prevent split-brain without huge complexity. Optional: use Telegram simply as a cross-check (e.g. post warnings or pause), but don’t rely on it exclusively. 

**Confidence levels:** fencing/quorum methods are *established* in distributed systems. Telegram side-channel is *speculative/emerging* and auxiliary. Proposed design is conservative by consensus standards but suitable for our single-owner, N=4 scale.

**Executive summary (Russian)**

Система из четырёх узлов (стандартный персональный кластер с настольным компьютером, ноутбуком, облачным VPS и ноутбуком). Синхронизация осуществляется через файлы Syncthing (eventual consistency). Риск: при разделении сети два узла могут оба принять себя арбитром, что приведёт к «развилке решений» (каждый проводит свои коммиты по заявкам). Сырьё хранения (сами события) не повредится, но решения могут расхождаться.

**Рекомендации:** Не вводить сложные алгоритмы консенсуса или BFT – это избыточно для N=4, одной ответственной персоны. Вместо этого использовать простую «кастомную» защиту:

- **Логическое ограждение (fencing):** При каждом избрании арбитра привязывать к событиям возрастающий номер эпохи (epoch). В итоге любая попытка «старого» арбитра применить коммиты с меньшим номером эпохи будет отвергнута другими узлами. Это аналогично механике zookeeper/etcd. Реализация: добавить в каждое COMMIT поле epoch и при чтении журналов игнорировать устаревшие.
- **Детектор разделения сети:** На каждом узле опрашивать локальный Syncthing (REST API /rest/system/connections). Если внезапно пропадает связь с основной частью кластера (например, с двумя из трёх остальных), считать это разрывом и перевести систему в «безопасный режим».  
- **Безопасный режим:** В режиме возможного разделения **замораживать автоматические коммиты** (Tier‑0/1). Отключить автопринятие решений, требуя вмешательства человека (Tier‑2 всегда был ручным). Простое решение: не добавлять новые COMMIT-события при подозрении на разрыв, возможно – отправлять уведомление владельцу.
- **Схема слежения по Telegram:** Телеграм‐канал можно использовать как внешний маяк: каждый узел публикует свою метку живучести или «кандидатуру» (подписанное сообщение с epoch). Если два узла одновременно претендуют на арбитраж, конфликт будет виден из ленты. Минимальная схема: узел перед COMMIT публикует «я арбитр, epoch=E» и ждёт, нет ли ответного сообщения. Однако Telegram сам может недоступен при локальном разрыве, так что это – вспомогательное средство, а не основная защита.
- **Слияние после восстановления:** Если всё же произошло «двухголовье» (две ветви решений), объединять журналы событий по простому правилу. Один вариант: **побеждает большая эпоха** – исключаем коммиты из меньших эпох, либо вручную разрешаем конфликты. Например, если были COMMIT для одного и того же предложения с разными epoch, взять только больший epoch и пометить другое побитым. Это лучше простого «переписывания всего лога», но нуждается в проверке (можно списком предложений выявлять дубли). Полное автоматическое слияние без потерь будет сложно (попытка избежать потерь может ввести ошибки).

**Чего не нужно:** Никакого полного Raft/Paxos или BFT. Они потребуют многократных RPC, коэффициент сложности вырастет в разы, а пользу в нашем сценарии мала. Не стоит пытаться строить полноценную CRDT‑совместимую модель – опять же, сложно, и это задача «для большего кластера». Наша задача – гарантировать отсутствие «тихо просочившегося» рассинхрона, а не автоматическое согласованное решение в любой топологии. 

Таким образом, сочетание **номера эпохи+ограждения (fencing)** и **локальных детекторов разделения** (с последующим отключением автомата) даёт простую и понятную защиту. В обычном режиме система сама разыгрывает лидерство по списку, а при подозрении – «встает на паузу». Владелец (Антон) всегда может вмешаться или разрешить ситуацию вручную. Опыт доказывает: с меньшим числом узлов проще руководствоваться простыми правилами большинством, чем строить тяжеловесные алгоритмы .
