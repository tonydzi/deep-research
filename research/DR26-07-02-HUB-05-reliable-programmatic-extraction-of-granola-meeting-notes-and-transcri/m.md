## Best Practices

For extraction, the best current pattern is **official API first, folder-based metadata second, CSV only as a backup, and private/cache methods only as contingency tooling**. The public API is supported, documented, rate-limited, and aligned with Granola’s own direction of travel. Cache and private-API methods are now explicitly discouraged by Granola’s product team, and the change cadence in the cache formats proves the reason why. citeturn14view0turn13view0turn12search5

For your **one-time full backfill**, build a bounded crawler around the official API. Enumerate folders with cursor pagination, enumerate notes, and persist immutable upstream identifiers plus sync cursors in SQLite. Use the CSV export once as a **reconciliation artifact** rather than as the import source: it is useful for comparing counts and for recovering edge notes that were somehow missed, but its “summary-only / owned-only / once-per-day / link-expires” constraints are too awkward for primary ingestion. citeturn7view2turn14view0turn9view0

For the **nightly unattended incremental**, prefer one of two patterns. The second is more event-driven: create a Granola folder policy and push notes to **Zapier** as soon as they enter that folder, then forward the Zapier payload to your local automation endpoint or durable queue. That second pattern is the closest you can get to “webhooks” in Granola today without a documented public webhook API. citeturn14view0turn9view1turn12search1turn9view2

For note routing, exploit Granola’s **folder auto-add for recurring meetings** and **folder auto-post** features. If you add one meeting in a recurring series to a folder and enable auto-add, future meetings in that series can be routed into the same folder automatically; once there, folder integrations can auto-post them to Slack, HubSpot, Attio, or Zapier. The practical consequence is that Granola does have a workable **semantic routing plane**; the missing piece is a general first-party webhook endpoint. citeturn10search2turn9view2turn9view3turn9view4

## Failure Modes

The most common product-level failure is the simple one: **the meeting was never actually captured**. Granola’s own docs repeat this in multiple ways. Notifications can appear, the app can be open, the icon can sit in the tray, and yet nothing is recorded unless the user opened the meeting note or started a Quick Note. If your team assumes “app running = recording,” your pipeline will be cleanly engineered and still miss meetings. citeturn9view6turn11view2turn11view1

The second failure mode is **OAuth/session fragility in MCP-based automations**. Granola MCP itself is browser-OAuth-only, and external client issues in 2026 show expiring tokens, silent failures, and missing refresh behavior. That matches your observed “silently expired after ~10 days” experience closely enough that it should be treated as a category problem, not a one-off incident. citeturn15search14turn31view1turn31view2turn31view3

The third failure mode is **depending on private endpoints or local cache contracts that Granola is actively mutating**. The reverse-engineered repo that once documented private endpoints is now archived specifically because Granola released an official API. Multiple open-source tools broke when the cache changed, including the v3→v4 jump; one current local-cache MCP server explicitly warns that Granola’s cache format may change without notice; and Granola’s own changelog states that cache/private API workflows were never a supported target. citeturn18view0turn17view5turn16view6turn13view0

The fourth failure mode is **assuming integrations are retroactive**. Folder-based auto-post to Slack, HubSpot, and Zapier applies only to notes added **after** the automation is enabled. Zapier’s folder trigger also only fires for future additions. If you switch on automation after months of meetings already exist, it does nothing for the historical corpus. The fifth failure mode is **Windows/macOS credential-path assumptions hardcoded from one era**. In early 2025, reverse engineering was rational because Granola lacked a public API. In mid-2026, it is no longer rational as the default. **Best push-style augmentation:** folder routing + Zapier trigger forwarding transcript payloads.

## Action Plan

**Immediate move:** create a dedicated Granola API key with the narrowest scopes that still satisfy your archive requirement, then implement the official-API backfill first. Use a local schema with tables for workspaces, folders, notes, transcripts, sync checkpoints, and raw payload snapshots. Treat meeting IDs as immutable keys and keep markdown generation as a pure downstream transform. This gets you out of the token-expiry trap immediately. citeturn12search0turn14view0

**Next move:** add a nightly incremental sync that runs from API keys only. Respect the 5 rps cap, keep exponential backoff for 429/5xx responses, and do periodic re-fetches of recently updated notes rather than assuming notes are immutable right after creation. Granola notes can continue to evolve after the meeting due to enhancement, folder movement, and user edits. The official docs do not explicitly define webhook semantics or update guarantees, so the safe engineering stance is incremental reconciliation rather than single-pass ingestion. citeturn14view0turn7view2

**Parallel move:** set up Granola folders as routing units for your call categories, enable **auto-add for recurring meetings**, and connect at least one **Zapier folder trigger** that forwards the transcript-bearing payload to your own ingestion endpoint. **Coverage hardening:** on each possible capture machine, use OS-native startup/login-item controls plus a process health monitor to ensure Granola is launched and updated. On Windows, Granola is a per-user app that can auto-update when installed in a user-writable location; Granola also publishes stable installer/version endpoints that your IT tooling can poll. **Break-glass fallback:** if official API coverage is temporarily insufficient for a subset of notes, keep a quarantined fallback toolchain that can inspect local cache/auth state on a single sacrificial machine.
