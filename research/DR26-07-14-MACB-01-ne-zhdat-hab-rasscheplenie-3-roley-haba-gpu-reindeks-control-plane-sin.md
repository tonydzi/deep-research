# «Не ждать хаб»: 3 роли хаба разъезжаются в 3 дома

Два независимых внешних вендора (ChatGPT DR, 34 источника; Grok Expert, 97 источников) отвечали на вопрос: как ~600 Python-движков (`_imports`, ~3 МБ) должны жить в peer-equal флоте из 4-7 машин (Win+Mac+Linux, ноуты спят, хаб может встать), чтобы никто не ждал хаб. Родственный DR26-07-10-MACB-01 уже постановил: Syncthing для ДАННЫХ чиним и оставляем. Этот DR — про слой КОДА и власти.

## TL;DR

Хаб исторически держал три несвязанные роли, и все три «ждали» его. Вердикт DR (гетеро-консенсус 2/2): роли расщепляются на три дома, и ни один не блокирует остальные:

1. **GPU-реиндекс** (тяжёлый компьют) → остаётся на хабе, но как ВОРКЕР, не как власть: его простой не блокирует ни авторинг кода, ни координацию.
2. **Control-plane** (координация, lease, нотификации, bare-git-канон) → Маяк-VPS (всегда-вкл якорь) + зеркало bare-репо на хабе против single-box-outage.
3. **Single-writer-мёрдж кода** → вообще не машина: право двигать канон-ветку роумит с ОПЕРАТОРОМ (ключ Антона), а Git превращает «кто пишет сейчас?» в «кто двигает защищённый ref?» — задача на порядок проще и безопаснее живой мутации папки.

Инструментально: **движки → Git (bare-репо на Маяке), Syncthing → только данные, деплой → staged/canary, не авто-след за HEAD.** Syncthing send-receive для кода — худший вариант (вердикт обоих вендоров).

## Ключевые выводы

- **[established]** Syncthing — не рельс для канона кода. Конфликты решаются на уровне файла по mtime/device-ID (переименование в `.sync-conflict-*`), не семантическим merge; задокументированы тихая потеря без конфликт-файла, «local additions»-лимбо в receive-only (ровно наша боль движков), и разрушение `.git` при синке git-папок (мейнтейнер Jakob Borg: «a terrible idea»). `.stversions` — подушка репликации, не история коммитов.
- **[established]** Git — первый инструмент, совпадающий с типом артефакта: оффлайн-коммиты для спящих ноутов, явные merge-события, история/blame/rollback бесплатно, репо крошечное (~3 МБ). Bare-репо + `receive.denyNonFastForwards`/`denyDeletes` + pre-receive/pre-push хуки, гоняющие наши гейты (verify_portable, lint_path_hardcode, import-probe, /tt-ритуал) = «poor-man's CI» без сервера — АК-47 соблюдён.
- **[established]** Канон-власть = операторский ключ, не машина. Роуминг-лидер сохраняется, но управляет «кто двигает канон-ветку», а не «чья папка writable». Это 1:1 наше решение о роуминг-короне (#b89596dd), перенесённое на код.
- **[established]** Главный blast-radius контроль — НЕ сам git, а staged/canary раскатка: runtime-ноды не следуют слепо за live-веткой; плохой коммит в main без staged-промоушена всё равно разъедется на весь флот. «Единственный важнейший safeguard» (ChatGPT).
- **[established]** Fallback (вариант B: receive-only + роуминг-писатель) жизнеспособен ТОЛЬКО с настоящим fencing: короткий lease TTL + монотонная эпоха + отбраковка stale-эпох на пути записи. Детерминированный «first-alive» сам по себе — конвенция, не защита от split-brain (Kleppmann, Redis-доки; LeaseGuard **[single-source]**: большинство Raft-lease реализаций специфицированы неверно).
- **[emerging]** CRDT для исходников (Automerge, ECOOP-2026 «Stable Lossless Syntax Tree») — реальный прогресс, но это editor-/structure-aware интеграция, не drop-in замена git для сотен обычных `.py` на разношёрстных Win/Mac/Linux-инструментах. Не для нас сейчас.
- **[established]** Fold-паттерн (append-шарды + детерминированный merger, как fold_all.py для данных) НЕ переносится на код: у кода import-графы и межфайловые инварианты, а не append-семантика (Grok, вариант D2 отвергнут).
- **[established]** Альтернативы взвешены и отклонены: Unison (парный синк, не 7-узловой mesh), Fossil (честный steelman по АК-47 — один бинарь, один SQLite — но экосистема/фольклор ремонта у Git несравнимо шире), Mercurial (нет решающего плюса), git-annex (для БОЛЬШИХ файлов, не для 3 МБ), chezmoi (dotfile-state, не флот-код), ansible-pull (только деплой-слой, нужен внешний lock, слабо для Windows-тяжёлого флота).

## Где вендоры расходятся

Оба сошлись на «вариант D: git для движков + Syncthing только данные + роуминг-канон». Развилка — в жёсткости деплой-оси:

- **ChatGPT (жёстче):** деплой полностью ОТВЯЗАТЬ от авторинга. Runtime-ноды следуют только за подписанным артефактом `approved.json` (SHA + epoch + ring + checksum, наш HMAC-паттерн); раскатка кольцами canary → ring2 → все; движки из Syncthing убрать совсем (максимум read-only экспорт релизов). Форма артефакта — синтез вендора, не именованный стандарт **[speculative]**.
- **Grok (мягче):** `git pull --ff-only` по нотификации control-plane; простой lease-скрипт на Маяке (статический приоритет-список + TTL + operator claim); guard-hook против несанкционированных локальных правок (наш проверенный SKILLS-паттерн); canary как ветка/тест-нода; на миграции движки временно остаются receiveonly в Syncthing как страховка.

Синтез Decision Memo (approved Антоном «+++» 16.07): начинаем с мягкой оси Grok (меньше движущихся частей, АК-47), жёсткую ось ChatGPT (approved-manifest) закладываем как кольцо-2 на потом.

## Что делаем во флоте Антона

Конкретика (по Decision Memo [[DR26-07-14-MACB-01-engines-git-decision-memo]], Фаза 1 уже запущена 16.07):

1. **Фаза 1 (обратимая, идёт):** bare-репо на Маяке + зеркало на хабе; `git init` из текущего канона + baseline-tag; локальные клоны на каждом узле ВНЕ Syncthing-папок; Syncthing-папка engines пока живёт receiveonly (страховка отката).
2. **Фаза 2:** хуки = наши существующие гейты (pre-receive/pre-push: portability, lint, import-probe, md5-verify); канон-ветку двигает только оператор-Антон (роуминг-ключ); пиры — ветки/PR-стиль; «почтовые» md5-патчи через `_transit` отмирают сами.
3. **Фаза 3:** `git pull --ff-only` по нотификации в шину + canary-нода (Mac16) → остальные; при необходимости — подписанный approved-manifest (ось ChatGPT).
4. **Роли по домам:** GPU-реиндекс живёт на хабе как воркер; control-plane (lease, нотификации, bare-канон) — на Маяке; канон-власть — с оператором. Пир авторит локально оффлайн и не ждёт никого.

**Чего НЕ делаем (АК-47):**
- НЕ синкаем `.git` через Syncthing никогда (анти-паттерн, рвёт репо).
- НЕ включаем Syncthing send-receive multi-writer на движках (вариант A — худший у обоих вендоров).
- НЕ строим CRDT-слой, не тащим Raft/etcd/Kubernetes — overkill для 4-7 узлов.
- НЕ мигрируем на Fossil/Mercurial/Unison — калории миграции не окупаются против экосистемы Git.
- НЕ трогаем Syncthing для ДАННЫХ — вердикт DR26-07-10-MACB-01 «чинить, не менять» в силе; рельсов остаётся два (git-код + Syncthing-данные), не три.
- НЕ даём коллегам (Наташа/Руслана) канон-права сразу — только ветки; расширение доверия постепенное.
- НЕ пускаем runtime-ноды авто-следовать за live-HEAD — только staged/canary промоушен.

**Инварианты целы:** канон-ЗАКОН и Tier-2 — Антон; риск «git = второй рельс» гасится тем, что движки уходят из Syncthing. Открытые хвосты: форма approved.json (нужен конкретный дизайн), двойной bare-remote (Маяк+хаб) — рекомендация под наш инцидент-паттерн, не индустриальный стандарт **[speculative]**; Gemini-отчёт этого DR на 16.07 ещё in progress.

## 🧒 Простыми словами

Раньше один большой компьютер (хаб) был и складом кода, и начальником, и счётной машиной — и когда он спотыкался, все стояли и ждали его. Два внешних умных исследователя проверили и сказали одно и то же: раздай эти три работы в три места. Тяжёлые вычисления пусть остаются на большом компьютере, но он теперь просто работник. Дежурство и «главная полка с кодом» переезжают на маленький сервер, который никогда не спит (Маяк). А право менять общий код носит с собой Антон, как ключ на шее — на какой машине он сидит, там и можно писать. Код переезжает в git — это как тетрадь, где видно каждую правку и можно отмотать назад. Syncthing (наш «общий шкаф») остаётся только для данных — для кода он плохой, потому что молча затирает правки. И главное правило: новую версию кода сначала пробует одна машина-разведчик, и только потом её получают все — так одна ошибка не заражает весь флот.
