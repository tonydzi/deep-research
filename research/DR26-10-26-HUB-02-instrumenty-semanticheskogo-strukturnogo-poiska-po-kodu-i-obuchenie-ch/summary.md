# A. Executive Summary  
We compared five mandatory tools and key alternatives for semantic and structural code search/indexing in a mixed local/cloud AI coding environment. **CodeIndexer** (proprietary, MCP server) provides broad language support and call-graph analysis but is closed-source and resource-heavy (historically ~5 GB RAM for a few repos). **grepai** (open-source, MIT) is a CLI using vector embeddings and file-watcher to maintain an up-to-date index, emphasizing privacy (100% local by default) and call-graph tracing. **CocoIndex Code** (open-source, Apache-2.0) uses AST-based parsing (Tree-sitter) for incremental indexing, delivering semantic search and call graphs with sub-second updates. **Serena** (open-source, GPL-3.0) is an “IDE for agents,” relying on language servers to provide symbol-level navigation (find-refs, rename, move, etc.) and semantic retrieval. **mgrep** (open-source CLI, Apache-2.0) offloads indexing and search to MixedBread’s cloud vector service: it continuously syncs code to the cloud, then performs semantic or regex search (with reranking) on demand. Major alternatives include **Zilliz’s “Code Context”/“Claude Context”** (open-source, MIT) – a vector-index approach with AST chunking and optional Milvus vector DB (local or cloud) – and **Sourcegraph** (commercial, with free on-prem options) offering scalable regex/structural search, code intelligence (LSIF), and GitHub-like IDE features. 

In practice, these tools complement each other: AST-based indexers (CocoIndex, CodeIndexer, Code Context) offer multi-language semantic search and call-graph analysis; LSP-based tools (Serena) excel at precise symbol navigation; vector+cloud tools (mgrep, Zilliz) provide heavy-weight semantic retrieval and context assembly. Our environment favors minimal local resource usage, so **we propose a hybrid stack**: primarily local indexers (CocoIndex Code and grepai) and agents accessing Serena for LSP queries; augmented by cloud services (MixedBread/mgrep for large-scale semantic search, and optional Zilliz Code Context for advanced embedding search). Detailed comparisons and a decision matrix follow. 

**Key findings:** CocoIndex Code and grepai are mature, open, incremental indexers (GPL/MIT, actively maintained) that cover most codebases locally with moderate resources. Serena adds IDE-level precision (GPL) but requires language-server overhead. CodeIndexer (v0.12.0, proprietary) adds call graphs and audit tools but at cost ($16–32/mo) and heavy CPU. mgrep (free CLI) and MixedBread’s cloud offer unbeatable freshness and scale (queries $4/1K semantic plus $3.50 rerank), at the expense of sending code to the cloud. Zilliz’s Code Context (MIT) emerges as an open, fully local semantic search engine (AST-chunks, vector DB). All tools have trade-offs in coverage vs resource cost. 

We recommend **Pilot** of CocoIndex Code (KEEP), grepai (KEEP), and mgrep (KEEP) with expanded use; **Park** Serena for now (high config burden, GPL limitations) but monitor usage; **Park** CodeIndexer’s Pro tier (already deployed) and lean on free/local options instead; **Pilot** Zilliz Code Context as a promising open-source alternative to CodeIndexer. The minimal offline stack is CocoIndex+grepai+basic grep/LSP. The best cloud-assisted stack adds MixedBread/mgrep and Zilliz (with assumed cloud vector DB). See below for detailed analysis and a proposed rollout plan.

# C. Contradictions, Evidence Gaps, Objections  

- **Semantic vs. Exact Search:** Some tools (grepai, CocoIndex, Code Context) advertise “search by intent”. However, “semantic” is loose; e.g., grepai still needs embeddings for each query and returns best-match code chunks. Unlike an LSP, it cannot guarantee finding a symbol hidden by dynamic language features. False negatives (missing a function because it wasn’t in embedding index) are possible. Meanwhile, regex-based tools (mgrep, grepai exact mode) are precise but miss intent matches. There is no single tool that does *both* perfectly; we must accept trade-offs (exact coverage vs. recall).

- **Call Graph vs. Dynamic Call Resolution:** Tools like CodeIndexer and CocoIndex build static call graphs, but dynamic dispatch or reflection can elude static analysis. Serena (via LSP) resolves references accurately for languages with proper tooling. If code uses heavy metaprogramming, all approaches fail some calls. No open evidence quantifies this, we mark [speculative] that LSP methods (Serena) handle more cases.

- **Local vs. Cloud Trade-offs:** The owner accepts cloud use for code. Tools like mgrep/Zilliz involve uploading code. The vendor policies (MixedBread DPA, Zilliz terms) might allow training use unless opted out. We found MixedBread’s DPA but not explicit no-training clause; lacking clarity, we label this [single-source/unknown] – likely training/generalization allowed. If this concerns the owner, a decision is needed. Local tools (grepai, Code Context) avoid this entirely.

- **Resource Consumption:** We lack public benchmarks for each. CocoIndex claims “sub-second” updates – presumably meaning very fast delta indexing. Serena’s video claims “large Python codebase” used by agents with no problems, but no RAM numbers. CodeIndexer’s current RAM usage isn’t published; old data (~5GB) may be outdated. We label memory estimates [estimates/speculative] except where cited. MixedBread provides clear per-request costs, but not per-query latency; likely <1s (cloud). Local embed-LLMs can be slow if large. We need on-site testing.

- **Startup/Scale Economics:** Many tools index incrementally (CocoIndex, Code Context, mgrep watch) so large repos are manageable with change-indexing. Tools without incrementality would re-index everything each time (bad). Data on 30-agent concurrency is absent. MixedBread’s query quotas (2400/min for $20 plan) suggest scaling to ~40 queries/s; even 30 agents at ~1 query/sec each is safe. For local tools, concurrency means either one shared server or separate instances (heavy). Likely architecture: one shared CocoIndex/grepai per machine, not 30 separate.

- **Staleness and Coverage:** Many products claim “always up-to-date” (grepai, Code Context live indexing). In practice, file watchers can miss events (e.g. renames, network drives). Tools relying on manual index push (mgrep requires explicit sync) risk staleness. Verification of index freshness is unclear; e.g., CodeIndexer or CocoIndex may not surface “last indexed” timestamp on a file. Agents getting empty results might not know if that means “truly absent” or “not yet indexed”. No product explicitly logs coverage (except maybe audit for CodeIndexer Pro). This is a known open issue ([single-source/marketing] claims vs no proof). 

- **Embeddings Models:** Many tools default to OpenAI embeddings (grepaI, CocoIndex optional), incurring variable cost and requiring API keys. Alternative local models (VoyageAI, Ollama) are [emerging]; their quality vs cost trade-off is not fully known. We do not assume embedding quality differences, but note any evaluation should consider this variable (LLM usage with same model).

- **Lock-in and Data Export:** Cloud tools can be a black box. MixedBread allows some data export via API, but vector DB content isn’t easily exportable. Zilliz Cloud is proprietary, but Milvus is open-source; however syncing data out-of-cloud is non-trivial. Sourcegraph’s cloud is by contract (no exit option without repointing code host). Local tools are fully exportable (unless DB internal). We have no price lock-in data for MixedBread’s long-term price or what happens if plan ends, but likely index remains (though queries disabled).

# D. Best Practices and Resource/Cost Scenarios  

- **Local-Heavy Scenario:** (Minimal remote usage) Use **CocoIndex Code** and **grepai** on each workstation (Hub/Studio/Pro). These index local repos with incremental updating. Use Serena MCP for LSP tasks (symbol find/rename). Heavy LSP (e.g. Pyright for Python) can run per agent or shared. Local resource notes: expect cocoindex Python+Rust ~ few hundred MB memory, plus embeddings (~1–3GB if local model) on larger repos. GrepAI Go CLI is lightweight (index small, uses OpenAI or Ollama as needed).

- **Cloud-Enabled Scenario:** Leverage **MixedBread/mgrep** for large-scale semantic search. We’d run a single `mgrep watch` process per machine or on one shared server (e.g. Mac Pro) to sync all repo content to the cloud. Queries cost money (we estimate ~10k semantic queries/month per agent, i.e. ~$40–75/month at scale). Vector DB (Zilliz Cloud or similar) can back **Code Context** or **Claude Context** to supply context to Claude Code or Gemini CLI via MCP (embedding cost separate). E.g., using OpenAI text-embedding-3-small at $0.0004/token, indexing 10M tokens costs ~$4k (large!). Better: use VoyageAI or smaller models locally (cost minimal).

- **Compute vs. Network Trade-off:** Cloud offloading (MixedBread, Zilliz) conserves local CPU/GPU, but adds network I/O. If network is slow or code is huge, initial sync may take time. MixedBread’s pricing already suggests building index cheaply ($1.50 per million tokens) but then query cost adds up. Local approaches require local CPU (to embed) but eliminate per-query cost. In practice, a hybrid: use cloud for rarely-run global queries, keep development-phase searches local.

- **Scaling with Agents (1/10/30):** 
   - *1 Agent:* Can afford independent LSP or index process. 
   - *10 Agents:* Prefer one shared index server (CocoIndex serve, Serena MCP, one mgrep/watch). 10 concurrent semantic searches might saturate grepai’s CPU/embedding if all local (we don’t have data on concurrency; better to share a vector DB). Mgrep’s 100 q/min (Starter) is enough for ~2 q/s, so likely upgrade to Scale (2400/min) if >2 agents or heavier use.
   - *30 Agents:* Must consolidate. One CocoIndex/grepai/Serena instance per host, not per agent. MixedBread Scale plan handles up to 40 q/s; 30 agents * 1 q/s = 30 q/s, borderline (would use 2400/min ~40 q/s capacity). If each agent issues multiple queries per minute, cost scales linearly (30 agents * 10 q/min = 300 q/min ~4x Starter cap, so 4x queries billing). Shared query multiplexing could reduce load.

- **Cost Example:**  
   - *Assumptions:* 10 repos (~100k LOC each, total ~1M LOC ~ 5M tokens), changing 10% weekly, 10 semantic queries per day per agent (2 agents). 
   - *Mgrep:* Ingest 5M tokens → ~$7.50 (fast indexing mode $1.50/1M). 2 agents ×10q/day=20q/day=600q/month → $2.40 (at $4/1k) plus rerank if used. Manageable.  
   - *CocoIndex/grepai:* On-prem, no direct cost. Hardware: need maybe 8–16 GB RAM spare for embedding tasks.  
   - *Embedding API:* If using OpenAI embed, 5M tokens at 0.0004/token = $2000 (!) for initial full index. Too high. Better to use local (VoyageAI free) or train small LLM.  
   - *Serena:* Free. Only cost is the machine RAM (say 16 GB for LSPs).  
   - *Sourcegraph:* If considered, typical pricing is per-user/per-month (e.g. $10–20) which exceeds e.g. MixedBread’s throughput usage. Not counted here due lack of public data.

- **Developer Workflow:** Put indexing on high-CPU hosts (Mac Pro/Studio). Agents on any machine call MCP over network (or via sockets). Use CI hooks (`mgrep sync` in CI) to keep cloud index up-to-date on merges. Keep local caches on each desktop for immediate small searches (e.g. grepai/ast). 

# E. Failure Modes and Correctness Pitfalls  

- **Ignored Files:** Tools mostly follow VCS ignore rules. Mgrep explicitly “ignores anything from git” (build outputs, deps). CocoIndex likely needs config to skip; grepai may index all files in workspace. If build products slip into index, false hits may appear (or errors indexing binary).

- **Symlinks/Worktrees:** Rarely addressed. Likely indexed as separate folders, possibly duplicating code. Tools relying on file hashes (CocoIndex, grepai) may miss updates if using symlinks or alternate branches. We should manually exclude such cases or treat them as separate projects.

- **Rename/Delete:** 
   - *CocoIndex* claims live re-sync: single-file edits reindex, and code changes auto-evolve schema. Likely tracks renames (via FS events). If a file moves, some tools might treat it as delete+create (so missing continuity).
   - *grepai* uses fs watcher; test needed to confirm rename detection (if the watcher notices rename event).
   - *Serena/LSP* will see a rename event in the IDE and update symbol tables accordingly.
   - *mgrep* requires manual sync or continuous watch; a rename would appear as delete+add unless intelligent dedupe is done. No mention of rename handling; likely not perfect.
   - *Zilliz/Code Context* incremental schema says “auto evolve”; unclear if renames are linked. Probably similar limitations.
  
- **Stale Index / Coverage:** 
   - Tools usually don’t present an explicit “index completeness” signal. E.g., if grepai returns nothing, agent cannot know if file was skipped (e.g. by .gitignore) or simply no match. Agents might ask “why blank?” which few tools answer. 
   - Some (Serena) can query LSP if no results, but not seamlessly (requires separate query).
   - One can assume indexing is eventual but not certain. Possibly implement a checksum log (not built-in).
  
- **Concurrent Updates:** If two agents trigger indexing simultaneously, risk duplicates or locks. CocoIndex/grepai don’t document concurrency. We should run only one indexing daemon per repo. mgrep cloud handles concurrency by serializing uploads or merging updates in its backend.
  
- **Crash Recovery:** 
   - *CocoIndex* promises “no index swap, no downtime”; unclear how crash recovery works. Probably preserves partial index and resumes. 
   - *Serena* state is ephemeral (LSP in-memory); a restart loses context, but can reload from code.
   - *mgrep* watch continues where left off (cloud store persists).
  
- **Search Semantics (Imports/Aliases):** 
   - None of the embedding tools resolves imports or inheritance. They only match text patterns or vector similarity. So a query for an abstract method might miss its concrete override. A call to an aliased import is a text hit (grep) or semantic if embedding covers usage context, but not guaranteed.
   - Static analyzers (CocoIndex’s call graph) handle imports; Serena via LSP will resolve alias or inheritance. 
   - E.g., “find all uses of `foo()`” in Python: Serena (via Jedi) will find them if correct LSP; grepai may miss usages named differently.
