# 1. Сравнение каналов связи  

| Канал               | Описание                              | Преимущества                                                  | Ограничения / режим отказа                                                                        |
|---------------------|---------------------------------------|---------------------------------------------------------------|--------------------------------------------------------------------------------------------------|
| **Syncthing (файловая шина)**  | Общая папка на всех машинах               | • Локальный P2P – не зависит от внешнего сервера<br>• Высокая скорость обмена данными при LAN<br>• Легко увидеть историю изменений файлов | • Отказ при «разрыве сети» между машинами (или конфликте папок)<br>• Синхронизация требует доступа к общей папке<br>• Зависит от корректной работы самого Syncthing |

**Вывод:** для каждой пары агентов следует установить резервный канал надёжной связи. Согласно практике, «приоритетные» каналы переключаются автоматически при сбое первичного. При этом важно избегать «повторных» сообщений: каждому сообщению следует присваивать уникальный идентификатор (или ключ идемпотентности). Агент при получении нового сообщения проверяет его ID – если он уже обрабатывался (на любом канале), сообщение отбрасывается, обеспечивая идемпотентность операций. Это защищает от двойного выполнения команды при переотправках по разным каналам.  

Дополнительно следует предусмотреть логику автопереключения: например, если отправка через Syncthing не подтверждается (или файл не синхронизируется) в течение заданного таймаута, агент переходит к Telegram; если и Telegram недоступен – переходит на e-mail. Рекомендуется задавать таймауты значительно больше периодов heartbeat (см. ниже), чтобы избежать ложных срабатываний из‑за временных задержек. Кроме того, можно реализовать «пинг» состояния (heartbeat) – см. ниже.  

# 2. Настройка E-mail как резервного канала  

- **SMTP (скрипт с Gmail).** Самый простой вариант – прямо отправлять письма по SMTP (порт 587) с учётки Gmail. Можно использовать «пароль приложения» (App Password) или OAuth2. *Плюсы:* простота (на большинстве языков есть «smtplib», `msmtp`, `sendmail` или готовые библиотеки типа Nodemailer), достаточно указать логин/пароль и хост `smtp.gmail.com`. Пароль приложения легко сгенерировать в настройках Google (если включен 2FA). *Минусы:* Google ограничивает 500 писем в день для бесплатного аккаунта. Хранение статического пароля – менее безопасно (Google постепенно отказывается от «менее безопасных приложений»). Кроме того, встроенные библиотеки SmtpClient (в некоторых языках) не поддерживают OAuth, потребуется использовать более продвинутые (MailKit, Python `smtplib.SMTP` поддерживает OAuth). Но для домашней сети это, возможно, излишне: App Password – удобен и невысокоуровнев (техник может просто поменять пароль в конфиге при необходимости). *AK-47:* рекомендуем начать с этого пути (SMTP+App Password), т.к. он потребует минимум внешних компонентов и прост для диагностики.  

- **Self-hosted n8n.** n8n – это локальный workflow-движок с узлом отправки e-mail. Можно запустить n8n (например, в Docker) и настроить Gmail-учётку через его **Gmail Node** или **Send Email Node**. *Плюсы:* графический интерфейс, гибкие соединения с другими источниками, встроенная поддержка OAuth (Gmail Node) или SMTP (Send Email). Полезно, если нужен сложный «цепочный» workflow или агрегирование событий перед отправкой. *Минусы:* это дополнительный сервис, который нужно держать запущенным и обновлять. Настройка n8n более сложная для непрофильного пользователя (надо развернуть, создать креденшлы и workflow). Отказоустойчивость канала зависит от n8n: если он упадёт – письма не уйдут. *Примечание:* n8n подходит, если вы уже знакомы с этим инструментом; в противном случае он выглядит как ненужный «оверхед» для простой отправки почты.  

- **Gmail API (специально Send Scope).** Официальный REST API Gmail с областью `gmail.send`. *Плюсы:* современный OAuth2, нет необходимости в пароле: выдаёте токен на один раз, и он сам обновляется. Высокие квоты (500/день бесплатный Gmail, 2000/день Workspace), возможность работать не только с отправкой, но и метками/драфтами. *Минусы:* самая высокая техническая сложность: нужно зарегистрировать проект в Google Cloud Console, получить OAuth-клиент, настроить screen для приложения (особенно если аккаунт не в вашем домене, будет «неверифицированное приложение»). Процесс получения и хранения refresh-токена может быть трудоёмким для нетехнаря. Кроме того, запросы идут через HTTPS/JSON, т.е. нужно писать HTTP-запросы или использовать Google API-клиент. *Рекомендуем:* Gmail API оправдан для долгосрочных автоматизированных систем, но для «семейной» настройки превышает требования AK-47. Однако, если вы разбираетесь с OAuth, этот вариант даёт максимальную надёжность и гибкость.  

**Пример сравнения (от Unipile):** Gmail API vs SMTP  
Authentication: OAuth2 (API) vs App Password/OAuth (SMTP). Лимиты: **API** – 500 писем/день (gmail), **SMTP** – 500/день (gmail). Сложность: **API** – высокая (Google Cloud), **SMTP** – низкая (App Password). Использование: **API** – для приложений с массовой почтой; **SMTP** – для простых скриптов/личного использования.  

**Рекомендация (AK-47):** начать с простого SMTP: настроить на одной машине отправку через `smtp.gmail.com` с App Password. Например, в Python: 
```python
import smtplib
smtp = smtplib.SMTP("smtp.gmail.com", 587)
smtp.starttls()
smtp.login("[email protected]", "APP_PASSWORD")
smtp.sendmail(src, dst, msg.as_string())
```
Если Gmail перестанет поддерживать App Password для вашей учётки, можно перейти на OAuth2 или развёрнутый Gmail API.  

# 3. Heartbeat / Dead-man-switch  

Для надёжности агенты должны периодически «помечать своё присутствие». Наглядный пример – механизм Heartbeat в распределённых системах: каждый агент **каждые N секунд посылает сообщение «alive»** (например, в Telegram или добавляя файл в синхро-папку). Если другой агент не получает несколько последовательных «пингов» от данного участника, считается, что он упал. При выборе параметров опираемся на правило: таймаут проверки должен быть на 2–3× длиннее интервала heartbeat, чтобы избежать ложных срабатываний. И дополнительно требуем не менее 2–3 подряд пропущенных «пинга» перед экстренным сигналом (см. пример: пропустил 3 сигнала подряд – доложить о сбое).  

Пример: пусть agents отправляют heartbeat каждые 2 минуты. Задаём таймаут 6 минут (3×интервал). Если в течение 6 минут от какого-то агента не было ни одного ping-сообщения, считается «молчуном». После этого остальные агенты могут эскалировать ситуацию (например, дополнительно написать об этом в общий канал/на почту или переключиться на следующий канал). Такой подход позволяет фильтровать единичные потерянные пакеты и краткие блокировки.  

**Пример метаданных heartbeat (JSON):**  

```json
{
  "agent": "notebook",
  "timestamp": "2026-06-26T14:02:00Z",
  "status": "alive"
}
```  

Где каждое сообщение подписано (см. ниже), а получатель проверяет `timestamp`. Если несколько подрядых сообщений от одного агента «просрочены», то предполагается отказ. Это эффективнее, чем мгновенное “сутупание» при однократной задержке.  

# 4. Безопасность и аутентичность сообщений  

При организации нескольких каналов важно предотвратить фальсификацию и реплей-модификации. Рекомендуется:  

- **Цифровая подпись (Ed25519).** Каждое сообщение (в Telegram, Syncthing или email) можно сопроводить подписью отправителя. Ed25519 – легкая и быстрая схема для подписания JSON-/текстовых тел сообщений. Подпись гарантирует, что сообщение действительно вышло от указанного агента, и не было изменено «по дороге». Это защищает от внедрения ложных команд извне.  

- **Nonce / Timestamp (защита от повторов).** В тело сообщения включается уникальный `nonce` (или последовательный номер) и/или метка времени. Получающий агент хранит использованные `nonce` или последние временные метки каждого отправителя. Если приходит сообщение с уже виденным nonce или с прошлым timestamp, оно отбрасывается. Такой приём препятствует повторной доставке старых сообщений. (См. пример структуры сообщения с nonce и timestamp.)  

- **Разделение ролей (координация vs полномочия).** В простом сценарии все агенты доверяют друг другу и выполняют одинаковую логику. Можно сэкономить отложив сложные схемы PKI и разрешений: семейной установке достаточно одного набора ключей (по крайней мере для целостности). Если не планируется, что один агент будет «командовать» другими в силовом режиме, можно опустить ролевое разделение.  

С учётом, что у вас всего 4 доверенных машины в локальной сети, **глубокое шифрование трафика и постоянная ротация сертификатов выглядят избыточно**. Однако простая схема с **подписями и проверкой nonce** даёт базовую безопасность: даже если кто-то получит доступ к почтовому ящику или Telegram-боту, он не сможет подделать подпись под чужим агентом. Replay-защита и уникальные ID также пригодятся для дедупликации (см. раздел 1).  

# 5. Реализация: минимальный набор (AK-47) vs over-engineering  

**Минимальный (AK-47):**  
- **Настроить цепочку каналов:** убедиться, что все агенты умеют писать/читать из Syncthing, Telegram и (по крайней мере) через SMTP. Прописать логику авто-переключения при ошибках передачи.  
- **Уникальные ID/идемпотентность:** реализовать в коде генерацию UUID или порядкового номера для каждого сообщения. Хранить историю принятых ID (например, в локальном файле или базе), чтобы игнорировать дубликаты. Это предотвратит двойное исполнение одного задания при переходе с канала на канал.  
- **Heartbeat:** сделать периодические «я жив» сообщения. Настроить таймауты (например, 2–3 пропущенных «пинга» = сбой). При отказе одного из агентов выводить тревогу и пробовать дополнительно подключиться к нему через оставшиеся каналы (и/или уведомить оператора).  
- **Простая подпись:** хотя можно временно опустить подписи, рекомендуем на уровне приложения хотя бы сравнивать ID отправителя и начинать структуру с «source_id»: например, `от: agent1 -> agent2` формат. Это помогает убедиться, что сообщение не «подброшено» неизвестным. Если время позволяет – использовать легкую подпись (каждый агент хранит свою пару ключей).  

**Overkill (можно отложить):**  
- **Полномасштабная PKI/mTLS:** нет смысла настраивать сертификаты и PKI для четырёх машин в семье. Использование HTTPS или gRPC с mTLS – сильная защита, но слишком сложно.  
- **Шифрование трафика на каждом уровне:** VPN, TOR или подобные – избыточно. Если вы не общаетесь по публичным сетям между машинами (только локально или через доверенный интернет), достаточно TLS канала (уже есть в HTTPS API Telegram/Gmail).  
- **Сложные схемы оповещений:** например, динамическое переименовывание отправителей, приватные крипто-раунды и т.д. – пропустить сейчас.  

**Чек-лист внедрения:**  
1. **Организовать резервные каналы:** настроить Telegram-бот (уже есть) и SMTP-отправку. Убедиться, что email-отправка работает (получатель видит письмо).  
2. **Реализовать логику авто-переключения:** при неудаче Syncthing – сразу в Telegram; при неудаче Telegram – сразу на email. Настроить обработку ошибок сети/сервиса.  
3. **Включить уникальные ID:** добавить генерацию `message_id` (UUID) и отслеживать историю – отвергать дубли.  
4. **Настроить heartbeats:** агентов так, чтобы они регулярно отсылали метки (можно через любой активный канал, например Telegram). Написать монитор: если от кого-то нет метки длительное время (например 3 интервала) – считать узел умершим и эскалировать.  
5. **Тестирование:** симулировать отключение одного канала и убедиться, что система переключается на следующий без потери данных/сообщений (и что дубликаты не создают лишних действий).  
6. **Улучшения безопасности:** по возможности добавить простую подпись (или хотя бы проверку поля `sender_id`), включить защиту от replay с nonce. Это не критично на старте, но увеличит надёжность.  

Ниже приведена **рекомендуемая последовательность внедрения** (AK‑47): построить цепочку каналов → обеспечить уникальность/идемпотентность сообщений → включить heartbeat-мониторинг. После этого можно постепенно интегрировать меры безопасности (подписи/nonce) и более сложные механизмы, не являющиеся первоочередными.  

**Источники и полезные материалы:** резервные коммуникационные каналы и отказоустойчивость, сравнение Gmail API и SMTP, паттерны идемпотентности, алгоритмы heartbeat, примеры защищённой межагентной коммуникации. Эти рекомендации основаны на лучшей практике в разработке надёжных распределённых систем.
