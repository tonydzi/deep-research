# Insight (DR DR26-08-25-MACANTON-05-0740): Партизанское продвижение GitHub-профиля инженера для видимости и трудоустройства

> DR разобрал, какие GitHub-активности (PR, review, issues, документация, packages, Actions) реально повышают заметность инженера у рекрутеров и какие партизанские тактики это ускоряют.

## Ключевые выводы
- Важно не количество коммитов («зелёные квадратики»), а качество и значимость вкладов — merged PR в авторитетных проектах служат прямым подтверждением навыков (peer review мейнтейнером)
- Звёзды и форки отражают популярность, но не гарантируют качество кода; пример — фейковый профиль из сериала «Силиконовая долина» набрал 1560 подписчиков (0.002% лучших на GitHub) без реальных навыков
- 93% рекрутеров считают open-source-разработчиков дефицитными и активно их ищут; soft skills (коммуникация, ревью, обсуждения) рекрутеры ценят почти наравне с кодом
- Работа с документацией (README, Wiki) — дёшево в исполнении, почти всегда принимается мейнтейнерами и хорошо сигнализирует заботу об удобстве пользователей
- Партизанские тактики: ранние PR в растущие/трендовые проекты (мониторинг GitHub Trending), нишевая специализация (меньше конкуренции — быстрее заметят), курирование awesome-листов и стартер-китов, собственные GitHub Actions/пакеты
- Реальные примеры траекторий: Josh Wulf (@jwulf) получил позицию Developer Advocate через системные PR в Zeebe/Camunda за 14 мес; Kent C. Dodds (@kentcdodds, 35k followers) построил репутацию через популярные JS/React пакеты; Sindre Sorhus (@sindresorhus, 80.5k followers) — через сотни npm-пакетов и awesome-лист (~490k звёзд)
- Взрыв активности без истории вклада настораживает рекрутеров сильнее, чем отсутствие активности (может означать работу на закрытом коде) — последовательность важнее внезапного всплеска
- Комбинация PR + документация + промоушен в соцсетях (LinkedIn/Twitter/Dev.to) даёт «бесплатный маркетинг» и трафик на профиль

## Рекомендации / решения
- Заполнить README профиля: 3-5 ключевых навыков, ссылки на портфолио/LinkedIn, зафиксировать 1-2 ниши развития вместо распыления
- Первые 3 месяца: 2-3 quick-win PR в неделю (доки, опечатки, мелкие баги) в трендовых/растущих репозиториях своей ниши
- До 6 месяцев: браться за более сложные issues, завести PR/issue-темплейты, опубликовать первый собственный репозиторий с качественным README
- До 9-12 месяцев: вести блог/статьи о своих PR, собрать портфолио-сайт (GitHub Pages), выпустить GitHub Action или пакет на Marketplace/npm/PyPI, опубликовать awesome-лист или стартер-кит
- Регулярно (1-2 раза в неделю) ревьюить чужие PR в топовых репозиториях своей области для наращивания доверия и связей
- Ежемесячно отслеживать метрики: followers, stars/forks ключевых репо, число merged PR, активность issues — против прошлого месяца
- Избегать «код-спама» ради статистики — один значимый PR ценнее десятка тривиальных коммитов

## Открытые вопросы
- Не приведены количественные пороги конверсии «PR/звёзды → оффер» — только качественные кейсы без строгой causal-связи
- Не оценена применимость партизанских тактик (awesome-листы, ранний вклад в трендовые проекты) к узким/непопулярным техническим нишам, где трендов почти нет
- Не разобрано, как быстро мейнтейнеры крупных проектов реагируют на PR новичков и какова реальная вероятность отказа/игнора
