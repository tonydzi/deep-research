# Insight (DR DR26-07-07-MACB-01): Гигиена, дедуп и перелинковка знаниевого графа 175k заметок (Obsidian+RAG) для AI-двойника

> Как чистить и поддерживать личный knowledge graph на 175k заметок / 37k контактов (entity resolution, link hygiene, dedup, sync-conflict, метрики качества графа), чтобы он надёжно питал AI-двойника без деструктивных или косметических фиксов.

## Ключевые выводы
- В бенчмарке OpenSanctions Pairs (2026) rule-based матчер даёт 91.33% F1, а LLM-матчеры выше (98.23% F1 у локального DeepSeek-R1-Distill-Qwen-14B) — но парное сопоставление близко к потолку, усилия нужно смещать на blocking/кластеризацию/review с неопределённостью, а не на лучший матчер.
- Публичные CRM (Attio, HubSpot, Folk, Clay) авто-мёржат только по сильным идентификаторам (email/domain/phone/social URL) и часто необратимо (HubSpot: merge нельзя откатить) — жёсткий авто-мёрдж безопасен только для сильных ключей.
- Консенсус PKM-практиков (Matuschak, Milo, Ahrens) — НЕ zero-orphans everywhere, а tiered: курированные evergreen-заметки (инсайты/решения/хабы концептов) должны быть плотно связаны, архив/сырые импорты могут законно оставаться orphan при сохранении метаданных.
- Измеренная патология волта — ~50% инсайт-заметок без входящих ссылок — реальная проблема (инсайты как раз тот класс, что должен быть связан), а орфаны среди 100k сырых импортов чатов — вопрос классификации, не нарушение методологии.
- Доминирующая архитектура систем памяти (Mem0, Graphiti/Zep, Letta, Basic Memory, Khoj) — асинхронная, инкрементальная, с сохранением происхождения: безопасное извлечение/индексация автоматически, консолидация медленнее, деструктивные правки требуют бэкапов/human review (Letta хранит память в git-backed FS с историей версий).
- Польза GraphRAG условна: выигрывает на multi-hop/reasoning/synthesis задачах, но plain RAG лучше для single-hop и быстро меняющихся фактов; в одном бенчмарке только ~65.8%/65.5% entity-ответов присутствовали в построенных KG — покрытие сущностей/рёбер важнее плотности графа.
- Syncthing — реплицируемая файловая система, а не протокол совместной работы: параллельные правки одного файла порождают sync-conflict копии; для тонкого мёржа нужны CRDT/local-first подходы (Ink & Switch), а не файловый синк.
- Один lease не гарантирует взаимного исключения для параллельных писателей (etcd docs, Kleppmann) — нужны условные записи или fencing tokens.
- Локальный CPU-only дедуп на масштабе 175k заметок решается стандартными инструментами: exact hashing, SimHash (Google: 64-bit, Hamming distance k=3 на 8 млрд страниц), MinHash/LSH (datasketch, sub-ms запрос), Faiss/HNSW для семантической генерации кандидатов с последующей точной верификацией.
- Текущее измеренное состояние волта: 900 sync-conflict копий, 1200 коллизий Telegram-хендлов, 1900 суффиксных дублей людей, 1000 идентичных по телу import-стабов, 70k битых wiki-ссылок — объём sync-conflict говорит, что система генерирует порчу быстрее, чем её чистят.

## Рекомендации / решения
- Сначала остановить кровотечение: канонические директории (people/, concepts/, decisions/) сделать single-writer (один узел send-only, остальные receive-only), включить файловое версионирование Syncthing на receivers, карантинить *.sync-conflict-* файлы в явную очередь ревью.
- Никогда не мёржить/удалять деструктивно нечёткие совпадения — использовать обратимую модель канонической заметки (одна каноническая заметка человека, источники как алиасы, поля superseded_by/same_as/merged_from); жёсткое удаление — только для exact-hash мусора.
- 3-стадийный пайплайн entity resolution: (A) детерминированный blocking + авто-резолв по точному Telegram handle/ID, email, E.164 телефону, social URL; (B) дешёвые нечёткие blocking-проходы (фамилия+инициал, имя+домен, имя+город); (C) структурный скорер + LLM-судья (adversarial two-role a la OpenSanctions) только для неоднозначной полосы.
- В первую очередь чинить 1200 коллизий Telegram-хендлов и 1900 суффиксных дублей людей как ER-проход с наивысшим ROI, сразу схлопнуть 1000 identical-body import-стабов через exact hash dedupe.
- Чинить 70k битых wiki-ссылок через детерминированную rename/supersede-карту до попытки творческой LLM-перелинковки.
- Концентрировать перелинковку только на курированном слое (~2k инсайт-заметок и 270 concept-хабов), цель <15% инсайтов без входящих ссылок и >80-90% reachability от хаба за два прыжка; не тратить те же усилия на 100k архивных импортов чатов.
- Ввести многоуровневый janitor-каденс: on-ingest (нормализация+exact dedupe+инкрементальный индекс), ночной (exact-ID ER + починка битых ссылок по rename-картам + триаж конфликтов), недельный (нечёткие кандидаты + предложения перелинковки + чистка мёртвых стабов), месячный (ревью канонизации + перенастройка порогов + откат плохих мёрджей).
- Отслеживать end-to-end качество ответов AI-двойника (answer correctness, faithfulness/groundedness, citation accuracy, context precision/recall, context-entity recall) на фиксированном eval-сете до/после каждой чистки; метрики структуры графа — только вспомогательная диагностика, не главный сигнал.
- Для дедупа: лексические методы (SimHash Hamming <=3 авто, 4-6 review; MinHash/Jaccard >=0.90 авто-кластер, 0.80-0.90 review) для авто-мутаций, embedding similarity — только для расширения recall внутри уже заблокированного кандидатного набора, всегда exact-verify перед деструктивной мутацией.
- Если неизбежен настоящий конкурентный multi-writer доступ к шарду — добавить лёгкий координатор (etcd или ZooKeeper) с lease + fencing token на заметку/шард, не полагаться на 'first writer wins' семантику Syncthing.

## Открытые вопросы
- Нет канонических численных порогов в PKM-литературе для плотности связей, MOC-покрытия или доли орфанов — пороги отчёта (<15% zero-inlink инсайтов, >90% hub reachability) — инженерные дефолты для этого волта, не установленная доктрина.
- Нет прямого опубликованного бенчмарка, связывающего '% битых Obsidian wiki-ссылок' с измеримым приростом качества RAG-ответов — это обоснованный системный вывод из результатов покрытия/полноты GraphRAG, а не напрямую опубликованная находка.
- Внутренние эвристики сопоставления Attio, Folk, Clay и нескольких OSS memory-инструментов публично не документированы — выводы опираются на наблюдаемое внешнее поведение, не на верифицированные внутренние алгоритмы.
- Обобщается ли LLM-judge адъюдикация (валидированная на sanctions-list домене OpenSanctions) с той же точностью на персональный контакты/CRM волт — не проверено, оценено как 'emerging' уверенность.
- Точный набор KPI на уровне волта и точный человеко-контролируемый workflow ревью для нечётких мёрджей/удалений/переписи хабов предложены как разумные, но ещё не валидированы на практике для этого конкретного волта.
