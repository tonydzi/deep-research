Каждый запрос инструмента или вопрос за конечное время T обязан стать одним из:

ALLOW
DENY_POLICY

Состояние WAITING_FOR_CLICK в unattended lane запрещено.

Практически это означает двухлейновую систему:

                       Linux VPS / independent control plane
              queue · leases · policy broker · OTel · alerts · retries
                                  |
              +-------------------+-------------------+
              |                                       |
     HEADLESS / UNATTENDED                    INTERACTIVE / ATTENDED
     claude -p / Agent SDK                    Claude Desktop / Chrome / RPA
     isolated worktrees                      OAuth, MFA, CAPTCHA
     deterministic policy                    site trust
     no dialogs                              Windows GUI
     defer/deny/fail                         requiresUserInteraction
              |                                       |
         run artifacts                         pre-authorized state
         completion contract                   handed back to headless

2. Правило маршрутизации лейнов
Одностраничное правило

Работа помещается в interactive lane, если хотя бы один её обязательный шаг:

требует OAuth consent, MFA, CAPTCHA, login repair;

требует browser/site trust или sensitive-action confirmation;

требует Windows screen/GUI либо OS secure desktop;

использует tool с requiresUserInteraction;

подпадает под org connector ask;

создаёт/изменяет автономную persistence-механику, для которой приложение ставит hard gate;

не имеет заранее заданной policy для необратимого, денежного, внешнего или secret-bearing действия.

Работа помещается в headless lane, только когда:

полный tool surface известен до запуска;

unresolved tool request может безопасно стать deny или defer;

любой вопрос имеет named default либо asynchronous escalation policy;

side effects либо idempotent, либо имеют idempotency key и receipt;

результат можно проверить машинно;

run способен закончиться без UI независимо от того, успешен он или нет.

[established] Рекомендуемый split: interactive lane не выполняет длинную работу. Он только создаёт устойчивое предварительное состояние — refresh credential, site authorization, downloaded input, GUI-exported artifact — и передаёт это состояние headless worker’у.

3. Профилактика: агент не должен заканчивать ход вопросом
3.1. Task manifest с явными default

Prompt «не задавай вопросов» недостаточен: модель всё равно может вызвать AskUserQuestion, а tool runtime — запросить permission.

Каждая unattended task должна иметь machine-readable decision manifest:

JSON

  "task_id": "DR26-08-05-HUB-01-1858",

  "max_deferred_questions": 1,
  "defaults": {
    "overwrite_existing_file": "no",
    "retry_network_error": "yes_once",
    "choose_between_equivalent_formats": "prefer_json",
    "send_external_message": "defer",
    "spend_money": "deny",
    "delete_remote_data": "deny",
    "expose_secret": "deny"
  },
  "completion_requires": [
    "artifact_manifest",
    "acceptance_checks",
    "side_effect_receipts",
    "no_unresolved_blockers"
  ]

[established] Механика: PreToolUse или AskUserQuestion hook читает manifest. Если named default существует, он возвращает allow + updatedInput и пишет default_used в audit. Если default отсутствует, он возвращает defer либо deny. 
Claude
+1

3.2. Политика вопросов

Для unattended lane:

blocking_question_budget = 0
deferred_question_budget = 1 per run

Результат первого действительно необходимого вопроса:

сохранить вопрос, options, context hash, tool call ID;

вернуть defer;

завершить Claude process;

освободить lease;

продолжить другие jobs;

отправить вопрос оператору через внешний канал;

после ответа либо --resume, либо создать fresh session из handoff.

Это не «прогон продолжает ту же задачу без ответа»; он не блокирует worker и очередь.

3.3. Stop и TaskCompleted hooks

Stop hook может не дать модели завершить ответ, если она просто написала вопрос или не выпустила completion contract.

TaskCompleted может заблокировать объявление task complete, если не прошли tests/lint/acceptance checks.

Оба должны иметь loop cap и внешний wall-clock watchdog: бесконечный self-correction loop не лучше модалки. 
Claude
+1

Практический gate:

Запретить Stop, если:
- последний assistant turn оканчивается вопросом;
- есть pending tool use;
- нет run-result.json;
- acceptance_status != passed;
- side-effect ledger содержит unknown.

Если hook не может исправить это за N циклов, run становится failed_retryable, а не продолжает разговаривать сам с собой.

3.4. askUserQuestionTimeout

Это допустимый временный symptom patch для Desktop sessions, но не fleet architecture. Он закрывает только AskUserQuestion, выбирая текущий option после timeout; PowerShell/MCP/browser/app approvals остаются.

4. Восстановление: resume против свежей сессии
4.1. Когда делать resume

Resume оправдан, когда одновременно истинны все условия:

сохранён session ID;

существует исходный project/worktree;

transcript/session store не повреждён;

pending tool call известен;

выполненные side effects перечислены;

model/tool/MCP environment совместим;

при запуске повторно переданы dynamic parameters: --mcp-config, --settings, --plugin-dir, --add-dir и другие run-specific flags;

задача моложе заданного resume TTL.

Claude документированно восстанавливает conversation, tool calls, active goal/tasks, model/agent и часть permission state, но не все динамические CLI parameters; plan и bypassPermissions также не следует считать автоматически восстановленными. 
Claude
+1

Лучший resume case: run завершился штатным tool_deferred, broker получил вопрос, оператор дал ответ, environment не менялся.

4.2. Когда нужен handoff + fresh session

Fresh session предпочтительнее, если:

live session отсутствует, как в ваших пяти incidents;

остался только append-only transcript;

неизвестно, успел ли tool выполнить side effect;

изменились credentials, MCP server, app version или repo base;

session слишком старая;

context накопил противоречия;

предыдущий run был Desktop-specific и не имеет machine-readable pending state.

[established] Вывод из ваших данных: попытка «найти и нажать старое окно» для четырёх из пяти incidents бессмысленна: UI-object уже не существует. Recovery unit должен быть work artifact, не chat window.

Для remote side effects нужны idempotency key и receipt. Иначе fresh agent может повторно отправить сообщение, купить, удалить или создать второй объект. Общий background-job guidance также рекомендует idempotency и проектирование под at-least-once execution; источник обновлён 2026-03-31 и уже старше трёх месяцев, поэтому конкретные platform details могут быть устаревшими, но сам принцип стабилен.

4.4. Как доказать, что работа завершена

session closed, lastRunAt updated, отсутствие процесса или наличие финального текста не являются success conditions.

Success наступает только при атомарном completion contract:

status == succeeded
AND acceptance_checks == passed
AND required_artifacts exist and hashes match
AND unknown_side_effects == 0
AND pending_questions == 0
AND pending_tool_calls == 0
AND cleanup obligations recorded

Для coding task это обычно:

commit/diff;

tests, lint, build;

artifact hashes;

список изменённых файлов;

side-effect receipts;

machine verifier verdict.

Для research task:

финальный report;

source manifest;

citation validator;

coverage checklist;

отсутствие unresolved placeholders.

5.2. Решающий security-дефект

Blind clicker снимает не конкретный benign gate. Он создаёт новую policy:

Любой диалог, достаточно похожий на Allow, автоматически получает YES.

Это означает автоматическое разрешение будущих неизвестных gate classes:

денежная операция;

удаление/перезапись;

исходящее сообщение третьему лицу;

ввод/отправка secret;

authorization на внешнем сайте;

загрузка потенциально опасного файла;

создание persistence;

изменение scope доступа.

Иллюзия особенно опасна: владелец считает, что продуктовый safety gate всё ещё существует, хотя automation фактически превратил его в unconditional allow.

Это сильнее обычного bypassPermissions: bypass виден в конфигурации и audit, а кликер неофициально обходит gate после того, как продукт уже классифицировал действие как требующее отдельного consent.

6.4. Где должен жить watchdog

Ваш прошлый watchdog нарушал базовый fault-domain principle: он находился внутри той же среды и зависел от той же unattended capability, отказ которой должен был исправлять.

Правильное размещение:

Linux VPS:
- queue DB / ledger
- lease authority
- process-dispatch API
- OTel collector
- config registry
- alert sender with separate credentials
- retry/requeue logic

Windows/Mac worker:
- claude process
- local worktree
- local tools
- heartbeat agent
- artifact uploader

Supervisor не должен:

быть Claude scheduled task;

отправлять alert через тот же MCP, который завис;

считать Desktop session list источником истины;

пытаться «написать что-то в чат» как основной recovery action.

Supervisor должен иметь другой OS/process/account/credential path и хотя бы один direct notification channel, не проходящий через Claude runtime. Разделение control plane и worker fault domains соответствует общему guidance для background processing, хотя использованный Microsoft architecture source от 2026-03-31 старше трёх месяцев. 
Microsoft Learn

6.5. Synthetic canary

После каждого Claude Code update и минимум раз в сутки запускаются тесты:

Safe exact-allowed tool → должен пройти.

Unknown tool → должен стать deny, не hang.

AskUserQuestion с manifest default → должен получить updatedInput.

AskUserQuestion без default → должен стать tool_deferred.

MCP requiresUserInteraction → должен быть отклонён/явно classified, не hang.

Broken hook → должен поднять hook_nonblocking_error и security alert.

Kill worker mid-side-effect → supervisor должен обнаружить lease expiry и не повторить действие без reconciliation.

Удалить session store → fresh agent должен продолжить из handoff.

Конкретная архитектура для ваших пяти машин
Control plane

На Linux VPS:

SQLite/PostgreSQL queue;

single lease authority;

task manifest registry;

policy broker;

OTel collector;

config/version registry;

direct alert sender;

resume/fresh-session decision engine;

immutable event ledger.

Worker plane

На каждой Windows/Mac машине:

маленький supervisor service, не Claude;

отдельный worktree на run;

claude -p/Agent SDK child process;

stdout stream-json;

heartbeat независимо от model progress;

artifact writer;

process hard timeout;

cleanup и lease release.

Interactive service lane

На Windows hub:

Claude Desktop;

Chrome/live sessions;

login/MFA/CAPTCHA;

browser site trust;

Windows-only GUI;

scheduler slot management до миграции;

операции с requiresUserInteraction.

Interactive result обязан экспортироваться как artifact или credential status. Он не должен оставлять длинный workflow внутри Desktop chat.

Recovery decision engine
IF completion contract valid:
    mark SUCCEEDED

ELSE IF stop_reason == tool_deferred
     AND session exists
     AND environment compatible:
    mark DEFERRED_INPUT
    enqueue resume after answer

ELSE IF process dead
     AND side effects fully reconciled
     AND handoff valid:
    start fresh session from handoff

ELSE IF side effect status unknown:
    mark FAILED_REQUIRES_RECONCILIATION
    do not blindly retry

ELSE:
    mark LOST
    alert and rebuild from latest trusted artifact
Итоговые варианты решения
Вариант A — Desktop-first + UI-кликер

Плюсы: минимальная миграция; сохраняет live browser и GUI.

Минусы: недетерминированное состояние, orphan transcripts, app-version fragility, скрытое превращение hard gates в auto-yes, невозможность надёжно автоматизировать UAC/auth boundaries.

Вердикт: отклонить для production.

Вариант B — Hybrid split-lane

Desktop только для human-only boundaries; все recurring deterministic jobs — claude -p/SDK; Linux VPS — control plane; вопросы — defer; результат — completion/handoff contract.

Плюсы: использует текущую подписку и Claude stack; не требует одномоментной замены всех MCP/browser workflows; закрывает сам класс невидимых modal stalls.

Минусы: нужно построить broker, state machine, telemetry и artifact discipline; часть GUI tasks останется attended.

Вердикт: рекомендуемый вариант. [established]

Вариант C — Full SDK/API isolated workers

Все операции переводятся на API/local MCP, workers запускаются в disposable VMs/containers, Desktop исключается из production path.

Плюсы: максимальная детерминированность и policy control.

Минусы: API billing, миграция connectors, потеря части subscription/browser integrations, больше engineering work.

Вердикт: целевой режим для наиболее критичных task classes, но не обязательный первый шаг.

Единственная рекомендация

Выбрать вариант B сейчас: hybrid split-lane с Linux VPS control plane, claude -p/Agent SDK workers, dontAsk + exact allowlist + defer, обязательным completion contract и полным запретом долговременного WAITING_FOR_UI. Уверенность: [established].

Главное предположение: основную массу вашей работы можно разрезать так, чтобы browser/GUI/auth boundary была короткой подготовительной стадией, а собственно исследование, код, тестирование, обработка файлов и отправка через policy-controlled APIs выполнялись headless. Если измерение покажет, что большая часть задач неразделимо зависит от live GUI, тогда потребуется отдельная attended/RPA service lane, но это всё равно не делает blind clicker безопасным control plane.
