# Insight (DR DR26-11-20-MACANTON-01-0941): потолок CPU на Mac16 и горячий корпус

> Вопрос заказа: какой следующий неразрушающий тест выбрать для медленного и горячего MacBookPro16,1 (i9-9980HK, macOS 26.3.1 (a), сборка 25D771280a), не выключая машину и не останавливая агентов.
> Machine: Mac · Agent: claude-code · Operator: Anton · 2026-11-21

## Вердикт одной строкой

Причина потолка **не установлена**, и по публичным данным её назвать нельзя: `CPU_Speed_Limit` показывает итог, а не того, кто его выставил. Все четыре ноги сходятся: первым идёт **запись показаний только чтением, привязанная ко времени** (потолок + реальная частота + мощность CPU и видеокарты + ток батареи и адаптера + процессы). Руки, перезагрузка, сброс SMC, вскрытие и покупки идут позже и только по результату записи.

Лечения, подтверждённого «до и после», нет ни у Apple, ни у сообщества.

Из прошлой работы (горячая память, сессия 19.11 на этом узле): эмбеддер шардов на холостом прогоне переписывал весь шард и был назван «главным дневным обогревателем» при `CPU_Speed_Limit` 20%. То есть ветка «законная нагрузка» уже имеет одного названного кандидата.

## В чём ноги сходятся (4 из 4)

1. **`CPU_Speed_Limit` = потолок политики, а не измеренная частота.** Заголовок Apple IOPM.h: ограничение, чтобы уложить CPU в «тепловые **и силовые** рамки». Кто его выставил (датчик, контроллер питания, прошивка), публичные интерфейсы не говорят.
2. **61-64 °C на ядрах ничего не оправдывают.** Обратная причинность: потолок сам держит ядра прохладными. Это не проверка запаса охлаждения.
3. **Обороты вентиляторов не равны потоку воздуха.** Высокие RPM значат только, что контроллер просит охлаждение.
4. **Отсутствие «thermal warning» ничего не исключает**: предупреждение и потолок скорости идут разными каналами.
5. **`kernel_task` это отдельный механизм** (отнимает время CPU, а не режет частоту). Scheduler = 100 говорит, что он сейчас не задействован.
6. **Apple ничего не признавала** для этой модели на ветке Tahoe: ни статьи, ни сервисной программы, ни строки в заметках к 26.0-26.7.3. Суффикс «(a)» это фоновое обновление безопасности WebKit от 17.03.2026, к питанию и теплу отношения не имеет.
7. **Распространённость неизвестна**: знаменателя нет, длина тредов не частота.
8. **Родной инструмент один: `powermetrics`** (нужен `sudo`). Intel Power Gadget мёртв, сторонние мониторы требуют установки.
9. **Улучшение после перезагрузки или сброса SMC причину не доказывает**: меняется сразу много переменных, и корпус просто остывает.

## Безопасный порядок проверок

**Шаг 0. Взгляд без `sudo` (секунды).** Сделан выше. Быстрая развилка: отрицательный ток батареи на сети, ватты адаптера ниже заявленных или флаг ошибки адаптера сразу ведут в ветку питания.

**Шаг 1. Поймать потолок в деле (только чтение, без рук).** Поправка к отчётам по свежему замеру: потолок сейчас 100, поэтому 15 минут записи дадут только фон. Нужна лёгкая запись в файл раз в 30-60 секунд на сутки, чтобы поймать момент, когда лимит падает:

```bash
date -u +%FT%TZ; pmset -g therm; pmset -g batt
ioreg -rn AppleSmartBattery -w0 | egrep '"(Amperage|InstantAmperage|Voltage|ExternalConnected|IsCharging|AdapterDetails|Temperature)" '
ps -Ao pid,state,pcpu,comm -r | head -12
```

Писать в файл, а не в конвейер (`pmset -g thermlog` в трубе ведёт себя странно). Отмечать, идёт ли бэкап волта.

**Шаг 2. Одна минута `powermetrics` в момент активного потолка (нужен пароль `sudo`, то есть Антон):**

```bash
sudo powermetrics -i 5000 -n 12 --show-plimits --samplers cpu_power,gpu_power,thermal,smc
```

Даёт реальную частоту, ватты CPU и видеокарты, `Plimit`, датчики SMC. Остановка: Ctrl-C (не Ctrl-Z), сразу если агент встал. Нагрузочных тестов не запускать.

**Как читать результат:**

| Что видим при низком лимите | Куда ведёт |
|---|---|
| Лимит идёт за ваттами CPU и сам возвращается к 100, когда работа спадает | Обычная работа под тепловым бюджетом. Разносить тяжёлые задачи по времени |
| Мощность dGPU много выше 6 Вт при малых ваттах CPU | Видеокарта. Смотреть, кто её держит (WindowServer, приложение) |
| Отрицательный ток батареи на сети, или лимит идёт за током и ваттами адаптера | Питание: адаптер, кабель, порт. Шаг 3б |
| Малые ватты CPU и dGPU, питание в норме, лимит всё равно низкий, горячий датчик вне ядер | Плата / VRM / датчик. Шаг 4, затем сервис |
| Высокие градусы на ватт, когда лимит снят (например выше 90 °C при 35 Вт и меньше) | Охлаждение: пыль, паста. Только сервис |

**Шаг 3. Только с Антоном у машины, по одной переменной, схема A/B/A по 10 минут, запись идёт:**
- а) если подключён внешний монитор: вынуть только его сигнал;
- б) родной адаптер Apple 96 Вт и родной кабель вместо стороннего PD (если есть под рукой, покупать не надо);
- в) перенести зарядку с левой стороны на правую тем же кабелем;
- г) отключение сети последним и коротко.

**Шаг 4. Только в окно обслуживания (работа сохранена, агентов остановил сам Антон), по одному, с записью до и после и наблюдением 7 дней:** Apple Diagnostics → обновление до 26.7.3 → сброс SMC последним.

**Шаг 5. Сервис только по сигналу:** код Apple Diagnostics (PPF, PFM, PPN, PPT004/006/007, NDT, PFR), «Service Recommended» у батареи, вздутие (тугой трекпад, качающееся дно: это немедленный стоп), повторяемый сбой питания, заблокированные рёбра радиатора.

## Чего не трогать

- Отключение PROCHOT и тепловых защит, правка или удаление plist-ов SMC / IOPlatformPlugin: отказ без условий, снимает защиту преобразователя питания.
- Принудительные кривые вентиляторов: вентиляторы и так на максимуме, а сигнал для записи пропадает.
- Андервольт (Volta), выключатели Turbo Boost, сторонние kext-мониторы, Intel Power Gadget.
- Вскрытие, замена пасты, термопрокладки на VRM: в отчётах сообщества нет замеров и есть рецидивы; по текущим показаниям не оправдано.
- Покупки (батарея, адаптер, подставка) по одним только цифрам.
- Чистильщики, `mdutil -Ea`, удаление кэшей, ускоренная переиндексация: сами греют.
- Массовое выключение демонов и рутин, остановка агентов ради замера.
- Перезагрузка, сброс SMC / NVRAM, обновление ОС до записи: стирают состояние, которое надо поймать.
