## 0. Главный вывод одной строкой

**Git силён как «журнал состояния и доска объявлений» и слаб как «почтальон».** Поэтому рекомендация — гибрид: ядро-волта в GitHub-репо (облегчённый S3, БЕЗ папки messages/ как транспортной шины) + доставка/будильник поверх существующих рельс (Telegram + дешёвый ETag-поллинг + Actions-будильник). Чистая git-шина (S2) и Issues-шина (S4) — нет. Брокер (S5) — правильный, но второй очередью, по боли.

Ключевая улика из чужого опыта: вся индустрия (GitOps: Flux, Argo CD) уже решила эту развилку — **git хранит декларативное состояние, а не сообщения**; контроллеры читают его поллингом/вебхуком и «доводят мир до состояния». Flux по умолчанию поллит GitRepository с `spec.interval`, а вебхук-Receiver — опция для мгновенности ([fluxcd.io — Receiver](https://fluxcd.io/flux/components/notification/receiver/), [документация источников Flux](https://fluxcd.io/flux/components/source/gitrepositories/)). Это ровно наша развилка «ядро в git vs шина в git» — рынок уже проголосовал за первое.

## 1. Вердикты по S1–S5

### S1. СТАТУС-КВО+ (dual-send остаётся, добавляем пробуждение на все пиры)
- **Жизнеспособность: высокая** (технически), **средняя** (по эффекту).
- **Главный риск:** doorbell сегодня будит только хаб, потому что у пиров нет постоянного слушателя. «Пробуждение на все пиры» = на каждом пире появляется always-on процесс-слушатель (TG-клиент или long-poll). На ноутах в сне крышки он мёртв — событие доедет только при пробуждении, т.е. мы получаем тот же лаг, что сейчас, но с новой обслугой.
- **Цена:** 4–8 ч настройки, $0. Не решает главную боль — конфликты мега-волта на 150–180K файлов (Syncthing сам не мержит, только плодит `.sync-conflict-*` копии — [docs.syncthing.net](https://docs.syncthing.net/users/faq.html), [форум Syncthing](https://forum.syncthing.net/t/cause-and-can-i-delete-sync-conflict-files/21004)).
- **1 мес:** работает, дешевле всех. **6 мес:** конфликтные волны волта никуда не делись; пробуждение пиров остаётся «мягким».
- **Сломается на:** спящих пирах и на очередном конфликте волта — то есть на исходной боли.

### S2. РЕАНИМАЦИЯ RAIL #5 КАК ЕСТЬ (git_bus.py третьим рельсом, triple-send)
- **Жизнеспособность: низкая.** Rail #5 умер не случайно — он не даёт ни одного свойства, которого нет в Telegram + Syncthing, но добавляет три новых граблей.
- **Главный риск:** параллельные push. Две машины коммитят в одну ветку одновременно → non-fast-forward → rebase-циклы. Git решает это только сериализацией (merge queue — так работает [bors-ng](https://github.com/bors-ng/bors-ng) и нативные GitHub Merge Queues: очередь PR, тест на staging-ветке, fast-forward в main — [bors.tech](https://bors.tech/documentation/getting-started/)); для машины-шины это лишний движок. Плюс secondary rate limits на git-операции: GitHub точные пороги **не публикует** (анти-абуз, отдаёт 403/429 с `Retry-After` — [docs.github.com — Rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)); тройная запись каждого сообщения утяжеляет шину в 1.5 раза без выгоды.
- **Цена:** 2–4 ч (рельса готова), но постоянный налог на каждый send.
- **1 мес:** работает на малом трафике. **6 мес:** рельса снова мертва, потому что Telegram удобнее, а история репо — шум из коммитов-конвертов.
- **Сломается на:** первом одновременном send с двух машин.

### S3. ЯДРО-РЕПО (малое ядро волта в GitHub + messages/ как шина + webhook будит хаб, хаб будит пиров)
- **Жизнеспособность: высокая для ядра, средняя для messages/.**
- **Главный риск (ядро):** расхождение ядра и склада при двунаправленной синке. Лечится жёстко: **ядро = единственный источник правды для канона** (правки только в ядре; в склад ядро реплицируется однонаправленно скриптом). Опыт комьюнити с obsidian-git на это прямо указывает: многомашиный волт в git без дисциплины молча перетирается ([HN-тред про Obsidian Git](https://news.ycombinator.com/item?id <tg-id>), [форум Obsidian](https://forum.obsidian.md/t/multiple-vaults-in-one-git-repository/60919)).
- **Главный риск (messages/):** те же параллельные push, что в S2, + история репо растёт от конвертов (нужна периодическая компакция).
- **Цена:** 16–24 ч построить + 1–2 ч/нед поддержки; $0 — приватный репо в существующих квотах (GitHub рекомендует репо <1 ГБ, <5 ГБ «strongly recommended», файлы >100 МБ блокируются — [GitHub Pages limits / размерные гайдлайны](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)).
- **1 мес:** канон (регламенты, реестры, fleet_nodes.json, OnAir-доска) синкается быстрее и **мержится** вместо конфликта — это прямое улучшение против `.sync-conflict`. **6 мес:** устойчиво, если ядро держится в сотнях-тысячах мелких текстовых файлов и не пускает медиа.
- **Сломается на:** (а) попытке запихнуть склад в репо, (б) messages/ при росте трафика.

### S4. GITHUB ISSUES КАК ШИНА
- **Жизнеспособность: средняя технически, низкая операционно.**
- **Главный риск:** нет ordering, ACK делается костылём (реакция/комментарий), каждый message = issue/comment событие, на которое подписаны webhooks → растёт поверхность и шум; security-аудит прямо указывает, что `issue_comment`-триггеры (IssueOps) — вектор эскалации привилегий, права надо резать ([пример предупреждения в cicd-abuse-detector](https://github.com/ericwb/cicd-abuse-detector), [гайд «AI Agent Behind a Webhook»](https://www.developersdigest.tech/ai/put-an-ai-agent-behind-a-webhook)). Прецедент «комментарии = команды» существует и работает (bors-ng `r+`/`try` — [github.com/bors-ng/bors-ng](https://github.com/bors-ng/bors-ng)) — но там очередь для людей с ревью, а не межмашинный транспорт.
- **Цена:** 8–16 ч; $0. Но гигиена issues постоянна.
- **1 мес:** демо работает, людям удобно смотреть. **6 мес:** машино-созданный спам замусоривает репо, лимиты API (5000 req/ч primary — [docs.github.com](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)) не болят, но токены/права ползут.
- **Сломается на:** объёме и смешении «человеческих» тредов с машинными. Для внешних касаний инженеров (contrib-watch) Issues уже у нас — и там остаются.

### S5. ПРАВИЛЬНЫЙ ИНСТРУМЕНТ (NATS/MQTT на VPS-якоре + Tailscale; GitHub только для ядра)
- **Жизнеспособность: высокая.** Единственный вариант, дающий честные транспортные гарантии.
- **Главный риск:** это ЕЩЁ ОДИН сервис, который надо держать живым. NATS JetStream = durable-стримы, at-least-once, replay и retention ([обзор JetStream](https://dev.to/nats/a-practical-introduction-to-jetstream-nats-persistence-layer-402h), [docs.nats.io](https://docs.nats.io/nats-concepts/jetstream)); у mosquitto персистентность ограничена сессиями и `max_queued_messages` для офлайн-клиентов ([mosquitto.conf(5)](https://mosquitto.org/man/mosquitto-conf-5.html)) — для нашей задачи «пир спал 12 ч, проснулся, забрал всё» JetStream подходит лучше (replay по watermarks). Отдельная грабля: NATS MQTT-мост имел issue с нарушением порядка QoS-1 ([nats-io issue, Jul 2023](https://github.com/nats-io/nats-server/issues/4741)) — если брать NATS, брать нативных клиентов, не MQTT-фасад. Плюс операционные мелочи Tailscale (протухание ключей узлов = внезапная слепота пира) и VPS как единая точка отказа, если нет резервного брокера на хабе.
- **Цена:** 16–32 ч построить + 0.5–1 ч/мес обслуги; $0 софтовых (VPS уже есть).
- **1 мес:** пилот на 2 узлах надёжен. **6 мес:** главный вопрос не «работает ли», а «кто чинит брокер в 3 ночи» — при нашем ритме (2 синка/сутки, аварийный — чаще) это редкие события.
- **Сломается на:** энтузиазме обслуживания: брокер без хозяина протухает быстрее, чем git-репо.

## 2. Рекомендованный сценарий: **S3-lite → S5 по боли** (двухфазный гибрид)

**Фаза 1 (сейчас, AK-47):**
1. **Ядро-репо** `fleet-core` (приватный): канон/регламенты-индекс, реестр рутин, `fleet_nodes.json`, OnAir-доска, машинные JSON. Сотни файлов, не тысячи. Склад на 150–180K файлов остаётся на Syncthing и в git НЕ едет.
2. **Направление правды одно:** канон правится в ядре → скрипт-экспорт разносит в склад (однонаправленно). Двунаправленный sync ядра и склада запрещён — это главный источник смерти S3.
3. **Шиной GitHub НЕ делаем.** Сообщения остаются на dual-send (Telegram + «внутренний архив лаборатории» через Syncthing).
4. **Дешёвое событийное пробуждение без новой инфраструктуры:**
   - Поллинг ядра условными запросами: `GET /repos/OWNER/fleet-core/commits` с `If-None-Match`/ETag — **304 не расходует primary rate limit** (официально: [Best practices for using the REST API](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#make-conditional-requests)). Пир может спрашивать раз в 2–5 минут бесплатно.
   - Срочный будильник: push в ядро → GitHub Action (`on: push` или `repository_dispatch` через `POST /repos/OWNER/REPO/dispatches` — [доки workflows API](https://docs.github.com/rest/actions/workflows), [пример curl](https://blog.marcnuri.com/triggering-github-actions-across-different-repositories)) → workflow шлёт сообщение в TG-03 → **существующая Telegram-рельса уже доставляет push на все машины** → локальный watcher будит сессию через `spawn_queue.py`. Ноль новых слушателей на пирах: будильник едет верхом на рельсе, которая уже живёт на каждом узле.
   - Вебхуки напрямую на домашние машины не тянем (нет публичного endpoint, и гарантии вебхуков сами по себе мягкие: at-least-once, возможен out-of-order, таймаут 10 с, «не единственный источник истины — сверяйтесь с API» — [Best practices for using webhooks](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)).
5. **Гигиена:** секреты в ядро не попадают никогда (история git — навсегда; сканер [gitleaks](https://github.com/gitleaks/gitleaks) + чистка [BFG](https://rtyley.github.io/bfg-repo-cleaner/) — это лечится только ротацией секрета + переписыванием истории + перклонированием у всех — [обсуждение GitHub](https://github.com/orgs/community/discussions/157748)).

**Фаза 2 (только если Фаза 1 прожила месяц и болит):**
6. Если лаг «пир увидел событие» > потребности (например, аварии требуют <1 мин) или «внутренний архив лаборатории» на Syncthing продолжит терять/конфликтовать — ставим **NATS с JetStream** на VPS-якоре (нативные клиенты, не MQTT-мост), subjects = адресация (`machine.<имя>`, `all`, `mayak`, `onair`), watermarks вместо ACK-файлов. Telegram остаётся человеческим зеркалом. Месячный ритм (2 прогона/сутки, 20 msg/мин на группу с запасом ×100 — [Telegram Bots FAQ](https://core.telegram.org/bots/faq)) брокеру не конкурент; конкурент у него только срочность.

## 3. Ответы на вопросы A–E

### A. Архитектуры «git как message bus»
- **GitOps (Flux, Argo CD)** — главный прецедент: git = desired state, не очередь; поллинг по интервалу + опциональный webhook Receiver для мгновенной сверки ([fluxcd.io](https://fluxcd.io/flux/components/notification/receiver/)). Урок нам: класть в git **состояние** (канон, реестры, OnAir), а не транзиентные сообщения.
- **Merge-очереди (bors-ng, GitHub Merge Queues)** — прецедент «комментарии = команды» и сериализация писателей в main ([bors-ng](https://github.com/bors-ng/bors-ng), [история merge queues](https://mergify.com/blog/the-origin-story-of-merge-queues)). Урок: параллельные писатели в одну ветку — решаемо, но ценой отдельного движка-арбитра.
- **IssueOps** — issues = задачи, labels = маршрутизация, comments = команды; работает для human-in-the-loop ([пример](https://www.developersdigest.tech/ai/put-an-ai-agent-behind-a-webhook)), но security-ревью предупреждает о повышении привилегий через comment-триггеры.
- **CRDT-over-git / git-for-data:** DVC (git + внешнее хранилище по указателям), lakeFS (git-семантика прямо на объектном хранилище), Dolt (git для реляционных данных) — [сравнение](https://kanerika.com), [lakeFS vs DVC](https://sider.ai/blog/lakefs-vs-dvc). Урок: «версионировать тяжёлое» — решённая задача, но НЕ внутри git-репо, а рядом с ним.
- **Рабочие паттерны конвертов, если всё же git-шина:** (1) append-only `messages/` с именами `<ts>-<sender>-<uuid>` — никто никого не перезаписывает; (2) ветка-на-писателя `from-<machine>` — параллельные push исчезают как класс; (3) компакция периодическим переносом в `archive/` (история всё равно хранит всё — это фича аудита и проклятие размера).
- **Грабли:** непубличные secondary limits ([rate limits docs](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)); репо >1–5 ГБ деградирует ([гайдлайны](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)); вебхуки = at-least-once + out-of-order + 10 с таймаут ([best practices](https://docs.github.com/en/webhooks/using-webhooks/best-practices-for-using-webhooks)); gist как шина — гонки перезаписи целого файла.

### B. Ядро в git + склад вне git
- **Критерии отбора ядра:** текстовый файл <100 КБ; изменение = решение (канон, регламенты, реестры, статусы машин); нужен аудит «кто когда поменял». НЕ идут: медиа, сырьё, `_originals`, черновики.
- **Консистентность дубля:** однонаправленно! Ядро = источник правды, склад получает экспорт. Генерация ядра из склада допустима как одноразовый bootstrap, после — только ядро→склад. Чужой опыт: обсидиан-комьюнити на git-синке волтов стабильно жалуется на silent overwrite и конфликты ([HN](https://news.ycombinator.com/item?id <tg-id>)) — двунаправленный git+Syncthing на одни файлы это удвоит.
- **LFS/partial clone/sparse checkout:** для ядра из мелких текстов не нужны; если в ядро попадёт тяжёлое — `git clone --filter=blob:none` + `sparse-checkout` стандартно снимают боль больших репо (архитектор этих фич — Derrick Stolee, [интервью Software at Scale](https://softwareatscale.dev/podcast/derrick-stolee/)); LFS — последний выбор (квоты и отдельный механизм).

### C. Событийное пробуждение
- **Webhook → самохостнутый приёмник:** нужен публичный endpoint; у нас его нет и не надо — GitHub Actions закрывает это без порт-форвардов: `repository_dispatch`/`on: push` → Action → сообщение в Telegram-рельсу → существующий doorbell/watcher ([workflows API](https://docs.github.com/rest/actions/workflows)).
- **Поллинг с бэкоффом:** условные запросы с ETag делают поллинг почти бесплатным ([best practices REST API](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api)) — это самый недооценённый вариант; Flask... простите, Flux так и живёт по умолчанию.
- **Доставка в уже идущую сессию:** файловый inbox + хук на границе хода (SessionStart/Stop hooks читают inbox), watcher пишет файл и/или поднимает новую сессию через spawn_queue (без «чёрных» запусков). Кросс-вендорно (Codex/Cursor/Grok) — только файловый контракт.
- **Анти-паттерны:** шторм пробуждений (debounce: одно пробуждение на батч коммитов; cooldown по subject), петли «агент будит агента» (ACK-сообщение не должно матчить правила пробуждения — будим только по адресованному «мне» сообщению с idempotency key), предохранитель (макс. пробуждений/час на узел).

### D. Матрица альтернатив (наша задача: 5–6 узлов, десятки сообщений/сутки)

### E. Риски
- **Секреты в истории навсегда:** да; лечение только ротация + BFG/gitleaks + перклон ([BFG](https://rtyley.github.io/bfg-repo-cleaner/), [обсуждение](https://github.com/orgs/community/discussions/157748)). Митигация: в ядре секретов нет по построению, сканер в pre-push.
- **ToS/abuse:** прямой запрет задокументирован для Pages-as-CDN ([GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)); для «репо как очередь/база» явного запрета в доках не нашёл (формулирую честно: «не нашёл», не «не существует») — точные пороги secondary limits GitHub скрывает. Наш профиль (десятки push/сутки) на радары не попадает; риск растёт со scale.
- **SPOF GitHub:** да —_outages случаются; поэтому ядро-репо не единственный носитель (экспорт в склад = живая копия), а шина им не становится.
- **Шум коммитов:** для ядра это фича (аудит), для messages/ — проклятие (ещё один аргумент против S2).

## 4. Минимальный пилот на 2 недели (дёшево докажет или убьёт)

**Состав:** хаб хаб + этот мак (MacPro192Ram). Один новый приватный репо `fleet-core-pilot`.

**Шаги:**
1. День 1–2: собрать ядро из ~100–300 файлов (регламенты-индекс, реестр рутин, fleet_nodes.json, OnAir-доска). Экспортер ядро→склад.
2. День 3: на обоих узлах скрипт `core_sync`: pull → merge → push (rebase только своих), pre-push gitleaks. Кронтаб: раз в 10 мин.
3. День 4: поллинг-даEMON с ETag (условный GET commits API, лог расхода лимита) раз в 5 мин.
4. День 5: Action-будильник: on push → Telegram-сообщение в 03 → локальный watcher пишет inbox-файл.
5. Дни 6–14: гонять боем. Оба узла правят канон параллельно (нарочно, включая одновременные правки одного файла с двух машин).

**Метрики (счётчик JSONL, как у нас принято):**
- доставка правки канона до второго узла: P50/P95 (цель P95 < 5 мин);
- конфликты: количество и минуты разрешения (git merge vs старые `.sync-conflict`);
- расход GitHub API-лимита (должно быть ~0 за счёт 304);
- потерянные события будильника;
- человеко-минуты обслуги в неделю.

**Критерий убийства идеи:** конфликтов больше, чем давал Syncthing на тех же файлах, ИЛИ обслуга >1 ч/нед, ИЛИ будильник теряет события чаще 1/50.
**Критерий успеха:** 0 потерянных событий; конфликты решаются git-merge'ем автоматически или за <5 мин; канон доезжает P95 <5 мин. Тогда S3-lite принимается в строй, а S5-брокер выносится отдельным решением по факти боли.

**Что пилот НЕ проверяет:** NATS-брокер (Фаза 2) и поведение на 5+ узлах — честно фиксирую: «не проверено: масштабирование писателей».
