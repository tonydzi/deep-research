# DR26-10-02-HUB-02-1811 — GitHub as a second sync bus for a personal AI fleet + Vault core/mega-store split + event-driven session wake-up

# Deep Research: GitHub как вторая шина синхронизации AI-флота + разделение Vault на ядро и мега-склад + событийное пробуждение сессий

## Контекст (наша система, факты)

- Личный AI-флот: 5-6 машин (Windows-хаб всегда включён, 2 мака, ноут, Linux VPS-якорь). На каждой машине параллельно работают несколько сессий кодовых агентов (Claude Code, Codex, Cursor, Grok CLI).
- Общий Obsidian-vault ~150-180 тысяч файлов (~несколько ГБ + 7.4 ГБ черновиков + 3 ГБ оригиналов), синхронизируется Syncthing. Боль: на таком числе файлов скан тяжёлый, были волны конфликтов (959 файлов за раз), узел без сети задерживает доставку.
- Межмашинная шина сообщений сегодня: dual-send = Telegram-группа + файловая папка «внутренний архив лаборатории» через Syncthing. Конверт сообщения: адресат (MACHINE | ALL | @capability), подпись HMAC, ACK обязателен.
- Уже существует НЕИСПОЛЬЗУЕМЫЙ rail #5: приватный GitHub-репо `machine-bus`, обёртка git_bus.py (pull перед чтением, commit+push после отправки), переиспользует движок machine_bus.py. Построен июнь-2026, одно сообщение, потом ни разу.
- Пробуждение по событию: сегодня polling (inbox-робот 2 раза в сутки) + «doorbell» push, который будит только хаб и только по строгому глаголу. Пиры входящее видят с лагом до 12 часов.
- Прошлое исследование (июль-2026) советовало: разнести три нагрузки — склад файлов (Seafile/облако), конфиг агента (chezmoi/git), «рация» (MQTT/NATS через Tailscale); файловая папка как шина названа плохой идеей (нет ordering и подтверждений).
- Конфиг `.claude` уже ездит git-ом (приватный репо, автоснимок каждые 15 минут).

## Идея, которую исследуем (слова владельца)

1. Разделить Vault на две части: мега-хранилище всей когда-либо бывшей информации (остаётся на Syncthing/локально) и МАЛОЕ ЯДРО самого важного (сотни-тысячи файлов, не сотни тысяч), которое ДУБЛИРУЕТСЯ в GitHub-репо и служит слоем синхронизации.
2. GitHub как вторая шина межпирового и межсессионного общения: любая сессия на любой машине кладёт в репо сообщение с адресацией (конкретной машине / конкретной сессии / Маяку / ALL / просьба о помощи / OnAir-объявление «я работаю с X, не трогайте»).
3. Событийное пробуждение: демон мониторит шину и будит нужную сессию (или порождает новую) когда приходит важное входящее; при этом обычный ритм — 2 синка в сутки, частый ритм только на онбординге нового пира и в аварии.

## Вопросы к исследованию

A. Архитектуры «git как message bus» в реальном мире: кто так делает (gitops, git-based task queues, CRDT-over-git, juicefs/dolt/dvc, nostr-like), какие паттерны конвертов/папок/веток работают, где грабли (конфликты при параллельном push, rate limits GitHub API/pushes, лимиты размера репо, приватность).
B. Разделение знаний на «ядро в git» + «склад вне git»: критерии отбора ядра, как держать дубль консистентным (одно-направленная репликация? генерация ядра из склада?), опыт monorepo-vs-split, git LFS/partial clone/sparse checkout для больших волтов.
C. Событийное пробуждение агентских сессий: GitHub webhooks → самохостнутый приёмник vs polling с бэкоффом vs GitHub Actions как будильник; как доставить событие в уже идущую локальную сессию кодового агента (hooks, файловые inbox, MCP-нотификации); анти-паттерны (шторм пробуждений, петли «агент будит агента»).
D. Сравнение с альтернативами для той же задачи: Telegram-шина (уже есть), Syncthing-папка (уже есть), MQTT/NATS, GitHub Issues/Discussions как шина (комменты = сообщения, labels = адресация), gist, отдельный repo-per-peer. Матрица: ordering, подтверждение доставки, offline-устойчивость, стоимость, наблюдаемость человеком.
E. Риски: приватный репо = секреты в истории навсегда (git history leak), GitHub ToS на «abuse as message queue», single point of failure (бан/недоступность GitHub), шум коммитов.

## Пять сценариев развития (оцени каждый: что будет через 1 месяц и через 6 месяцев, где сломается, цена владения)

S1. СТАТУС-КВО+: git-шину не воскрешаем, остаёмся на dual-send (Telegram + Syncthing-папка), добавляем только событийное пробуждение поверх существующего doorbell на все пиры.
S2. РЕАНИМАЦИЯ RAIL #5 КАК ЕСТЬ: включить существующий git_bus.py на всех пирах третьим рельсом (triple-send), cron-pull каждые N минут, без разделения волта.
S3. ЯДРО-РЕПО: вынести «самое важное» ядро волта (канон, регламенты, реестры, OnAir-доску, машинные JSON) в отдельный GitHub-репо; он же несёт папку messages/ как шину; Syncthing остаётся для мега-склада. Webhook/Action будит хаб, хаб будит пиров.
S4. GITHUB ISSUES КАК ШИНА: сообщения = issues/комменты в приватном репо, адресация = labels/assignees, пробуждение = webhooks; файлы волта в git не трогаем вообще.
S5. ПРАВИЛЬНЫЙ ИНСТРУМЕНТ: шину уводим на лёгкий брокер (NATS/MQTT на всегда-включённом VPS-якоре с Tailscale), GitHub используем только для ядра-репо (S3 без messages/), пробуждение = подписка на брокер.

Рекомендуемый сценарий: S3.1 (Ядро-репо + начальная шина на его основе) с последующей миграцией к S5

Гибридный план:

Фаза 1 (Ядро): Реализовать S3 (выделение ядра в GitHub-репо).
Фаза 2 (Шина): Настроить на основе этого же репо (папка messages/) облегчённую версию git-шины, но не через прямой push от каждого пира, а через централизованный "postman", работающий на хабе. Хаб будет периодически (или по событию) собирать сообщения из локальных папок пиров (через Syncthing), коммитить и отправлять их в репо-шину от своего имени. Это устранит конфликты.
Фаза 3 (Пробуждение): Настроить GitHub webhook для уведомления хаба о новых сообщениях. Хаб, в свою очередь, будет отправлять локальные push-уведомления (через Telegram или нативные механизмы) на нужные машины.
Фаза 4 (Долгосрочная миграция): Параллельно с работающей git-шиной начать развертывание NATS на VPS-якоре. Постепенно переводить все новые агенты на NATS, а git-шину оставить для редко используемых, но требующих строгого аудита сообщений (например, OnAir-объявления).
Ключевые преимущества гибрида:
Немедленное решение боли с Vault: Разделение на ядро и склад снизит нагрузку на Syncthing.
Надёжная шина с аудитом: Git-репо обеспечивает неизменяемую историю всех сообщений, что критически важно для отладки и compliance.
Минимизация конфликтов: Централизованный коммитер на хабе решает главную проблему параллельного доступа к git.
Постепенный переход: Нет необходимости в "большом взрыве" — миграция на NATS может происходить органически, по мере готовности каждого компонента.
🔬 3. Ответы на вопросы A-E
A. Архитектуры "git как message bus" в реальном мире

Git используется как шина в нескольких нишах, но чаще всего в специфических контекстах, а не как универсальный мессенджер.

GitOps и Configuration Management: Здесь git выступает как "источник истины" для декларативного состояния. Системы (например, Flux, ArgoCD) следят за изменениями в репо и применяют их к инфраструктуре. Это не шина сообщений в реальном времени, а скорее механизм синхронизации состояния с некоторой задержкой.
Git-based Task Queues: Существуют экспериментальные проекты, использующие git для управления задачами, например, через ветки или папки в репо. Паттерн: Каждая задача — отдельный файл или папка. Статус меняется через коммит. Грабли: Отсутствие встроенного механизма блокировки для атомарного "взятия задачи в работу" приводит к гонкам 
tansengming.github
 .
CRDT-over-Git: Это теоретическая концепция, где CRDT (Conflict-free Replicated Data Type) используется для репликации данных поверх git. На практике это скорее исследовательская область, чем production-решение. Git сам по себе не является CRDT.
Специализированные системы: Некоторые системы (например, DVC для версионирования данных) используют git как метаданные, но хранят большие файлы во внешнем хранилище (S3, GCS). Это хороший паттерн для разделения метаданных и payload

Вывод: Git как шина сообщений в реальном времени — это anti-pattern для высоконагруженных систем из-за проблем с блокировками и конфликтами. Однако он может быть полезен для асинхронных, аудируемых и редких обменов, где важна история изменений

B. Разделение знаний на "ядро в git" + "склад вне git"

Критерии отбора ядра:

Частота доступа: Файлы, к которым обращаются часто (реестры, регламенты, конфиги).
Критичность для работы: Файлы, без которых система не может функционировать (OnAir-доска, машинные JSON).
Размер: Небольшие текстовые файлы (Markdown, JSON), не бинарные артефакты.
Версионирование: Файлы, история изменений которых важна для аудита и отката.

Обеспечение консистентности дубля:

Однонаправленная репликация: Наиболее безопасный подход. Ядро генерируется из склада с помощью скрипта (например, make_core.py), который запускается периодически (cron) или по изменению хэша файлов. Изменения в ядре вручную запрещены.
Хеширование и верификация: После генерации ядра можно вычислять хэши и хранить их в манифесте, чтобы клиенты могли проверить целостность.

Опыт monorepo-vs-split и инструменты:

Git LFS (Large File Storage): Подходит для хранения больших бинарных файлов (оригиналы, черновики) вне основного репо, сохраняя метаданные в git. Ограничение: Бесплатный лимит LFS на GitHub — 1 ГБ хранилища и 1 ГБ трафика в месяц. Для вашего объёма (7.4 ГБ + 3 ГБ) это не подходит без оплаты.
DVC (Data Version Control): Специализированная система для управления датасетами и моделями. Интегрируется с git, но хранит данные во внешнем хранилище (S3, Azure, GCS). Это более гибкое и масштабируемое решение, чем LFS, для больших объёмов данных 
doc.dvc
+1
 .
Sparse checkout / Partial clone: Позволяет клонировать только часть репозитория. Это может быть полезно, если ядро и склад находятся в одном репо, но разные папки.

Вывод: Для вашего сценария DVC выглядит более подходящим решением, чем чистый git, из-за ограничения на размер. Однако если ядро действительно будет небольшим (сотни-тысячи файлов, а не сотни тысяч), то можно обойтись и без LFS/DVC.

C. Событийное пробуждение агентских сессий

Варианты доставки события:

GitHub Webhooks → самохостнутый приёмник:
Как: Настроить webhook в репо на отправку POST-запроса на URL вашего VPS-якоря (или хаба).
Плюсы: Реалтайм, полный контроль, возможность сложной обработки (фильтрация, агрегация).
Минусы: Требует публичного HTTPS-эндпоинта (или туннеля), что может быть уязвимостью. Необходимо обеспечить безопасность (валидация подписи, HMAC).
Polling с бэкоффом:
Как: Написать скрипт, который периодически (с экспоненциальным бэкоффом) проверяет наличие новых сообщений в шине.
Плюсы: Простота реализации, не требует публичного эндпоинта.
Минусы: Задержка, неэффективное потребление API-лимитов.
GitHub Actions как будильник:
Как: Настроить Action, который запускается по расписанию или по push и выполняет пробуждение.
Плюсы: Использует существующую инфраструктуру GitHub.
Минусы: Ограниченное время выполнения (6 часов для бесплатных runner'ов), задержка, стоимость за превышение лимитов.

Доставка события в уже идущую сессию:

Файловый inbox: Демон-пробуждения записывает событие в файл в папке «внутренний архив лаборатории» на машине агента. Агент проверяет эту папку (polling) или использует inotify/FSEvents для уведомления.
MCP-нотификации: Если agents поддерживают MCP (Message Control Protocol), можно использовать его для отправки push-уведомлений напрямую в процесс.
Интеграция с агентами: Некоторые агенты (например, Claude Code) могут иметь хуки или API для внешнего управления. Это идеальный вариант, но требует изучения документации каждого конкретного агента.

Анти-паттерны:

Шторм пробуждений: Одно событие вызывает цепную реакцию пробуждений на всех машинах. Решение: чёткая адресация (конкретная машина/сессия), ограничение количества активных уведомлений.
Петли "агент будит агента": Агент A в ответ на пробуждение отправляет сообщение, которое будит агента B, и так далее. Решение: добавление в сообщение TTL (time to live) или флага "don't reply".

E. Риски
Секреты в истории git: Приватный репо не гарантирует безопасность. Если секрет попадёт в коммит, он будет в истории навсегда. Решение: Использовать .gitignore для чувствительных файлов, периодически аудитить историю, рассмотреть инструменты для сканирования секретов.
GitHub ToS на "abuse as message queue": Использование GitHub не по назначению (например, для высокочастотного messaging) может нарушать Условия предоставления услуг (ToS). Это может привести к блокировке аккаунта. Решение: Убедиться, что использование соответствует "нормальному" сценарию разработки, а не spam или abuse.
Single Point of Failure (SPOF): Блокировка или недоступность GitHub парализует всю систему. Решение: Иметь план миграции (например, на self-hosted Gitea), дублировать критичные данные.
Шум коммитов: Большое количество автоматических коммитов (например, от шины) может замусорить историю и затруднить поиск значимых изменений. Решение: Отдельная ветка или репо для шины, периодическое squash-соединение коммитов.
🧪 4. Минимальный пилот на 2 недели

Цель: Проверить ключевые гипотезы: (1) Можно ли надёжно разделить Vault на ядро и склад, (2) Работает ли GitHub как шина с минимальными конфликтами, (3) Возможно ли событийное пробуждение с задержкой < 1 минуты.

Шаги пилота:

Создать минимальное ядро:

Взять 10-20 файлов из текущего Vault (реестры, конфиги, OnAir-доска).
Создать приватный репо core-vault на GitHub.
Написать скрипт sync_core.sh, который копирует эти файлы из локального Vault в папку репо и делает коммит. Запустить через cron.

Настроить тестовую шину:

В репо core-vault создать папку messages/.
На хабе написать скрипт postman.sh, который:
Сканирует папку «внутренний архив лаборатории» (полученную через Syncthing) на наличие новых файлов.
Для каждого нового файла: добавляет его в messages/, делает коммит с осмысленным сообщением и делает push.
После успешного push перемещает исходный файл в архивную папку на хабе.
Запустить postman.sh каждые 2 минуты (cron).

Настроить пробуждение на хабе:

Создать простой скрипт watcher.py, который использует GitHub API для проверки последнего коммита в репо core-vault.
Если время последнего коммита больше последнего известного, отправить Telegram-уведомление на хаб с текстом последнего сообщения.
Запустить watcher.py через systemd-таймер или простой while-цикл.

Оценить результаты:

Задержка пробуждения: Измерить время от отправки сообщения на пиратской машине до получения Telegram-уведомления на хабе. Цель < 60 секунд.
Конфликты: Проверить, возникают ли конфликты при push в postman.sh. Если да, оценить их количество и причину.
Нагрузка: Оценить количество коммитов и потребление API-лимитов.

Успех пилота:

Задержка пробуждения < 1 минуты.
Конфликты при push либо отсутствуют, либо их можно легко избежать (например, за счёт очереди сообщений в postman).
Не наблюдается исчерпания API-лимитов.

Если пилот успешен, можно смело разворачивать полный S3. Если нет — это будет сигналом к тому, что git как шина не подходит, и стоит сразу смотреть в сторону S5.
