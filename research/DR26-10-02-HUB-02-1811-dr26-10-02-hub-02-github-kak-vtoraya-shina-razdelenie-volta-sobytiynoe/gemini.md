# Deep Research: GitHub как вторая шина синхронизации AI-флота + разделение Vault

## 1. Вердикт по сценариям (S1–S5)

**S1. СТАТУС-КВО+ (Telegram + Syncthing-папка + doorbell)**
* **Жизнеспособность:** Высокая, но проблемная при масштабировании.
* **Главный риск:** Продолжение волн конфликтов Syncthing. База данных SQLite внутри Syncthing крайне тяжело переносит 150-180к файлов при высокочастотных изменениях, что ведет к I/O-голоданию [established] (https://docs.syncthing.net/users/faq.html, 2026). Лаг в 12 часов для не-хаб узлов сохранится.
* **Цена владения:** Низкая (бесплатно), но высокая в плане ручного разрешения тысяч конфликтующих `.sync-conflict` файлов.
* **Прогноз (1/6 мес):** Через месяц работает как сейчас, через 6 месяцев база Syncthing деградирует от роста числа агентов и межмашинных логов.

**S2. РЕАНИМАЦИЯ RAIL #5 КАК ЕСТЬ (git_bus.py)**
* **Жизнеспособность:** Крайне низкая.
* **Главный риск:** Git не является CRDT (Conflict-free Replicated Data Type) [established] (https://crdt.tech/, 2026). Параллельный push от нескольких агентов в одну папку `messages/` неминуемо создаст merge conflicts, которые автоматика решить не способна. Использование Git как базы данных или очереди также нарушает Terms of Service.
* **Цена владения:** Высокая (постоянные ручные мёрджи и блокировки пушей).
* **Прогноз (1/6 мес):** Сломается на первой же неделе при одновременном ответе двух агентов на броадкаст-сообщение.

**S3. ЯДРО-РЕПО (GitHub для Core + messages/)**
* **Жизнеспособность:** Средняя.
* **Главный риск:** Загрязнение истории Git бессмысленными коммитами эфемерных сообщений. Webhook-будильник может падать по таймауту: GitHub требует успешного ответа (2xx) за 10 секунд [established] (https://docs.github.com/en/webhooks/about-webhooks, 2026). Если хаб-узел спит или локальный диспетчер подтупливает, хук отваливается без повторной попытки доставки.
* **Цена владения:** Средняя.
* **Прогноз (1/6 мес):** Само по себе разделение Vault на ядро и склад принесет огромную пользу, но шина в папке `messages/` станет бутылочным горлышком.

**S4. GITHUB ISSUES КАК ШИНА**
* **Жизнеспособность:** Средне-высокая.
* **Главный риск:** Жёсткие лимиты API. REST API GitHub ограничен 5000 запросами в час для аутентифицированных пользователей [established] (https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api, 2026). Если флоту нужно активно общаться или опрашивать состояние, лимит быстро исчерпается.
* **Цена владения:** Низкая, но полная привязка к вендору.
* **Прогноз (1/6 мес):** Решение будет жить, но скорее как "Task Queue" (очередь медленных задач), а не как low-latency рация.

**S5. ПРАВИЛЬНЫЙ ИНСТРУМЕНТ (NATS/MQTT на VPS + Git только для Ядра)**
* **Жизнеспособность:** Максимальная.
* **Главный риск:** Появление внешней точки отказа в виде арендованного VPS.
* **Цена владения:** ~$5/мес за дешевый VPS + настройка Tailscale.
* **Прогноз (1/6 мес):** Раз и навсегда решает проблему конфликтов файловой синхронизации, дает миллисекундное пробуждение по pub/sub. Через 6 месяцев легко масштабируется на 20+ сессий без задержек.

## 2. Рекомендуемый сценарий: S5 (Гибрид "Правильный инструмент")

**Уверенность:** [established] (комбинация легковесного брокера сообщений для связи и Git для декларативного состояния — это золотой архитектурный стандарт распределенных систем) (https://gitops.tech/, 2026).

**Суть:**
1. **Шина (Рация):** Выносится из Syncthing на **NATS JetStream**, поднятый на Linux VPS-якоре внутри вашей сети Tailscale. NATS легковеснее Kafka и поддерживает концепцию *Leaf Nodes* — ваш ноутбук в самолете/кафе может копить сообщения в локальном агенте NATS, и как только появится сеть, мгновенно и без конфликтов засинкать их в VPS [emerging] (https://docs.nats.io/nats-concepts/core-nats, 2026).
2. **Знания (Ядро):** Критически важное ядро (канон, регламенты, `.claude`, реестры) выделяется в отдельный приватный GitHub-репозиторий без мусорных сообщений. Syncthing остается ТОЛЬКО для мега-склада (150к+ файлов медиа, черновиков), снимая I/O-нагрузку с терминалов агентов.
3. **Будильник:** Локальный легковесный демон-подписчик NATS слушает топик и через сокет/MCP мгновенно будит агента, исключая поллинг.

## 3. Ответы на вопросы исследования (A-E)

### A. Архитектуры "git как message bus"
Хотя эксперименты по созданию очередей на базе Git существуют (например, gitmq), в реальных системах это считается грубым антипаттерном.
*   **Конфликты и CRDT:** Git строит историю на базе DAG (Directed Acyclic Graph) и текстовых Diff-ов. Он не умеет решать конфликты параллельной записи без человека [established] (https://crdt.tech/, 2026).
*   **Размер и мусор:** GitHub имеет soft-лимит репозитория в 1-5 ГБ [established] (https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github, 2026). Постоянные коммиты мелких JSON-сообщений раздуют индекс и объекты (`.git/objects`).
*   **Abuse Policy:** Использование инфраструктуры GitHub как БД для высокочастотных сообщений напрямую нарушает их ToS. Вы рискуете баном аккаунта.

### B. Разделение знаний на "ядро в git" + "склад вне git"
Это строго необходимый шаг, независимо от выбора шины. 
*   **Слабость Syncthing:** Syncthing не справляется с >100к файлов из-за бутылочного горлышка в SQLite и дисковом I/O при частых обновлениях [established] (https://docs.syncthing.net/users/faq.html, 2026). 
*   **Sparse Checkout:** Использование фичи `git sparse-checkout` в современном "cone" режиме ускоряет команды в рабочей директории, но скрытые файлы всё равно присутствуют в истории `.git/` [established] (https://git-scm.com/docs/git-sparse-checkout, 2026). Поэтому физическое разделение на 2 независимых хранилища (Git для Ядра и Syncthing для Склада) на порядок эффективнее, чем один монструозный репозиторий.

### C. Событийное пробуждение агентских сессий
*   **Проблема Webhooks:** GitHub Webhooks требуют ответа за 10 секунд и не имеют механизма автоматического retry при таймауте [established] (https://docs.github.com/en/webhooks/about-webhooks, 2026). Если хаб спит, сообщение исчезнет навсегда.
*   **Решение:** Локальный демон, который держит постоянное TCP-соединение с NATS брокером. При получении события демон пишет в локальный named pipe/Unix-сокет или шлет MCP-уведомление (Model Context Protocol), которое будит процесс агента.
*   **Антипаттерн "шторма":** Избегайте петель, где агент отправляет ACK, который снова будит отправителя. Адресация должна четко различать `ALL`, `@capability` и `REPLY`.

### D. Сравнение с альтернативами
*   **MQTT vs NATS:** MQTT (Mosquitto) — это стандарт для IoT сенсоров с архитектурой "хаб-и-спицы" [established] (https://mqtt.org/faq/, 2026). NATS JetStream, в свою очередь, спроектирован для распределенных кластеров. Фича NATS *Leaf Nodes* идеально подходит для ноутбуков: при потере сети Leaf Node сохраняет локальную работоспособность шины, а при подключении восстанавливает консенсус с VPS-якорем [emerging] (https://docs.nats.io/nats-concepts/core-nats, 2026).
*   **GitHub Issues как шина:** Отлично работает для долгоиграющих задач (issue = задача, label = маршрутизация) [established] (https://docs.github.com/en/issues/tracking-your-work-with-issues/about-issues, 2026). Но для heartbeat-статусов, OnAir-блокировок файлов и быстрых переговоров лимит в 5000 API-вызовов в час убивает идею.

### E. Риски
*   **Git history leak:** Очереди сообщений (особенно логи ошибок AI) могут содержать токены, пути и секреты. В Git они останутся навсегда.
*   **Слепые зоны (SPOF):** Переход на NATS означает, что при падении VPS-якоря машины не смогут общаться глобально. (Решается Leaf-нодами, которые сохранят локальные логи).

## 4. Минимальный пилот на 2 недели (Proof of Concept)

**Цель:** Доказать, что NATS JetStream поверх Tailscale убирает конфликты Syncthing и дает лаг пробуждения <1 секунды без нарушения ToS GitHub.

**Шаги пилота:**
1. **Час 1:** Скачать бинарник `nats-server` (весит <20МБ) на ваш Linux VPS. Запустить с ключом `-js` (включить JetStream) на IP-адресе Tailscale. Настроить персистентный стрим для топика `ai.fleet.messages`.
2. **Час 2:** Написать скрипт `nats_bus.py` (50 строк на Python с использованием библиотеки `nats-py`), который заменяет логику чтения/записи из «внутренний архив лаборатории» папки.
3. **Неделя 1:** Перевести OnAir-объявления и heartbeat-статусы на новую шину `nats_bus.py`. Полностью удалить папку шины из Syncthing.
4. **Неделя 2:** Создать в GitHub репозиторий `vault-core`, перенести туда регламенты, `.claude` и промпты (до 1000-3000 файлов). Настроить у агентов чтение канонов строго из `vault-core` (pull-only).
5. **Метрики успеха:** 0 файлов `.sync-conflict` в системе за 14 дней; доставка push-уведомлений о старте работы над файлом доходит до пиров за миллисекунды; отсутствие штрафов/отвалов по таймаутам.

**Decision-Oriented Ending:**
Настоятельно рекомендуется внедрить **Сценарий S5**. Он опирается на фундаментальное допущение: использование одного бинарника NATS, работающего через уже существующую у вас сеть Tailscale, привнесет кратно меньше боли и затрат на поддержку, чем попытки заставить Git работать как базу данных вопреки его дизайну (что гарантирует постоянные merge-конфликты), или борьба с жесткими таймаутами и лимитами GitHub API. Разделение Vault на GitHub-ядро и Syncthing-склад нужно провести немедленно в любом случае, так как это снимет парализующую дисковую нагрузку с терминалов.
