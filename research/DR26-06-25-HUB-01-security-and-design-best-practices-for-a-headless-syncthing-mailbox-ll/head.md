# Security and Design Best Practices for a Headless Syncthing-Mailbox LLM Agent

Current best practice from OpenAI, Anthropic, OWASP, and recent academic benchmarks is layered defense: strict least privilege, tool-level approvals for sensitive operations, deterministic validation, structured outputs, sandboxing, and human review whenever actions cross trust boundaries or have meaningful blast radius. ## Key Findings

The academic literature is unusually consistent on one point: **agent security failures are mostly architectural, not merely prompting mistakes**. AgentDojo, WASP, AgentHarm, OS-Harm, Imprompter, AgentXploit, ARGUS, and related work all treat prompt injection and harmful tool use as system-level vulnerabilities of tool-augmented agents, especially when untrusted content can influence action selection. WASP found that realistic prompt injections could partially hijack web agents in up to **86%** of cases, while full attacker-goal completion was lower only because current agents are still incompetent in many scenarios; the authors explicitly warn that this “security by incompetence” is unlikely to last as capabilities improve. citeturn12view0turn12view1turn13view2turn13view3turn12view3turn12view10turn12view11

The reliability of **LLM-as-classifier or LLM-as-judge** for permission gating is not good enough to be treated as a strong security boundary. Anthropic’s own production auto-mode data is the clearest industry datapoint: even after architectural hardening, a two-stage transcript classifier still missed **17%** of real overeager actions, and Anthropic explicitly states that manual approval can be safer for high-stakes cases. Research outside Anthropic points in the same direction. CAPTURE found severe context-aware weaknesses in current guardrail models, including domains where some systems hit **100% false-negative** or **100% false-positive** rates. Prompt Overflow showed that lightweight prompt-attack detectors can be bypassed at extremely high rates under fragmented/interleaved placement, including **above 99.5%** bypass for one tested detector family in a particular layout. Another 2026 evaluation found that across more than **20,000** adaptive attacks, every defense that relied on the attacked model to protect itself eventually failed; only hardcoded output filtering in separate application code held throughout that experiment. citeturn37view0turn37view3turn34view0turn20view2turn20view0

This is not only a benchmark problem. OpenAI’s current guidance for building agents says developers should design workflows so that **untrusted data never directly drives agent behavior**, and should extract only validated structured fields from external inputs. OpenAI also places orchestration, tool execution, state, and approvals in application-owned code, not in the model. Anthropic’s current guidance similarly says prompt injection requires defenses at several layers and that safeguards are not guarantees; users should think carefully about what tools, permissions, and environments an agent gets. citeturn7view1turn7view2turn16view0

Industry frameworks broadly converge on the same architecture. OpenAI’s Agents SDK and Codex expect the **application** to own orchestration, approvals, and sandbox policy; Codex defaults to network-off, uses sandboxing, and requires approval for destructive or side-effecting tool calls outside trusted conditions. LangGraph/LangChain implements human-in-the-loop as explicit interrupt policies on tool calls, with persisted state and configurable per-tool approval, edit, reject, or auto-approve logic. CrewAI exposes human-feedback pauses as first-class flow controls. Anthropic’s Claude Code treats project-scoped MCP servers as approval-gated, recommends trusted MCP servers only, and recommends VMs for risky tool use. Even the AutoGPT lineage—which historically pushed autonomy hardest—warned that continuous mode was potentially dangerous because the system could run forever or do actions the user would not typically authorize. citeturn15view0turn35view0turn30view0turn17view0turn7view7turn7view4turn10search3turn10search10

For a shared Syncthing mailbox specifically, distributed-systems failure modes are nontrivial even before the LLM enters the picture. Syncthing writes to temporary files and then moves them into place, can retain temp files when transfers are incomplete, and propagates conflict copies as normal files once they exist. It also warns that when things are not fully in sync, outcomes can become unpredictable about which changes “win.” That means a naive “folder as queue” design needs explicit handling for duplicates, stale messages, replays, conflict files, and partial-sync artifacts; otherwise you can get double execution, hidden poison-pill tasks, or loops in acknowledgements and reimports. citeturn7view9turn23view2turn32view0turn7view10turn23view1

## Contradictions & Debates

There is a real debate between **bounded autonomy** and **approval-everything**. On one side, systems like Anthropic auto mode exist because fully manual approval is expensive and users often already bypass it with dangerous blanket permission settings. Anthropic’s documented position is pragmatic: imperfect classifier gating can still be much safer than “dangerously skip permissions,” especially when users would otherwise remove checks entirely. On that comparison class, auto mode may be a net gain. citeturn37view3turn36view4

But your setup is **not** that comparison class. You already have a disciplined PLAN + SAFE-AUTO design, a protected-file hook, and a strong policy against auto-doing outbound messages, money, deletions, config changes, secret edits, installs, or uncertain operations. More importantly, your actual queue history says the safe-auto path has produced **no realized business value so far**. That changes the decision calculus. Anthropic itself says its auto classifier is **arguably a regression versus careful human approval** in cases where the human can review actions well. In your environment, the empirical question is not “is auto safer than YOLO mode?” but “is auto safer than a system that almost always needed human approval anyway?” On that question, the evidence points toward simplification. citeturn37view3

A second debate concerns whether a **narrow whitelist** can make headless automation acceptable. The answer is “sometimes, but only if the whitelist is enforced deterministically and the action wrappers are truly low-blast-radius.” The design-pattern literature is helpful here. It explicitly recommends action-selector and constrained-execution patterns, but it also warns that classifier-style fuzzy authorization can be gamed: binary topic or relevance classifiers can be bypassed by combining benign and malicious intents in one request or by manipulating embeddings. So a narrow whitelist is a good idea only when it is a software-enforced action vocabulary, not an LLM-inferred policy label. citeturn14view3turn12view9

A third debate is whether prompt injection is the whole story. It is not. The newer authorization-propagation literature argues that even if prompt injection were solved, multi-agent systems still face a distinct problem: **maintaining authorization invariants across delegation, task routing, aggregation, and time**. That is directly relevant to your mailbox design. A signed AUTHORIZATION note created in one interactive session is not equivalent to ambient permission for a headless daemon later. Without explicit machine-verifiable scope, time bounds, and one-time use constraints, authority drifts. citeturn12view4turn24search2

The main limitation in the public evidence is that much of the strongest quantitative work is on browser, coding, or generic tool-use agents rather than file-synced mailbox robots exactly like yours. So there is no paper that says “Syncthing vault bus + GPT scheduled every 20 minutes is unsafe in precisely this percentage.” The conclusion here is therefore an engineering inference from adjacent but highly relevant evidence: when untrusted content can influence tool use, and the proposed security boundary is an LLM classifier, current evidence says the default assumption should be **unsafe until deterministically constrained**. citeturn12view6turn16view0turn7view1

## Best Practices

The minimal design that best matches public best practice is a **split control plane**: the LLM may read, summarize, propose, and produce a PLAN, but the actual decision to execute must be taken by deterministic application code that validates a narrow action schema and current authorization state. This mirrors OpenAI’s harness/compute split, Codex’s approval and sandbox model, LangGraph’s explicit interrupt points, and Anthropic’s layering of allowlists, classifiers, and sandboxing. citeturn25view0turn15view0turn35view0turn16view2

For this setup, the shared mailbox should move from “natural-language task queue” toward **immutable signed envelopes**. Each task should be an append-only JSON document with: `task_id`, `issuer_machine`, `target_machine`, `created_at`, `expires_at`, `action_type`, `args`, `args_hash`, `dedupe_key`, optional `auth_token_ref`, and a detached Ed25519 signature from the issuing machine or interactive session. Messages should never be rewritten in place. Producers write only in their own namespace; consumers never edit task files, only append receipts and plans in their own namespace. This follows the direction of current agent authorization work toward authenticated delegation, capability tokens, signed audit trails, and least-privilege scoped permissions. citeturn29view0turn29view2turn29view1turn28view2turn28view3

The enforcement layer should treat **GREEN/RED as advisory, not authoritative**. The authoritative decision should be a deterministic rule table:

| Category | Enforcement rule |
|---|---|
| Read-only local operations | Allowed only if action enum and argument schema validate exactly, paths are within approved roots, no network, and wrapper binary is fixed |
| Idempotent local re-imports | Allowed only with content hash, prior-result cache, and single-effect proof |
| Reindex / local transcription | Allowed only through dedicated wrappers with fixed inputs, bounded resource limits, and no shell interpolation |
| Any outbound communication, deletion, config change, secret access, install, production write, or ambiguity | Always interrupt for human approval |

This matches OpenAI’s guidance to keep untrusted text from directly driving behavior, OWASP’s recommendation to validate expected output formats in deterministic code, and LangGraph’s and Codex’s per-tool policy model. citeturn7view1turn28view1turn35view0turn15view0

Sandboxing should be OS-enforced, not only prompt-enforced. The headless robot should run as its own service account with no shell home, no access to your main user secrets, a minimal writable filesystem, protected-policy files mounted read-only, and egress restricted to only what the runtime strictly requires. Anthropic and OpenAI both emphasize OS/container sandboxing, restricted filesystem roots, and network controls; Anthropic specifically recommends VMs or equivalent isolation when using risky tools, and OpenAI/Codex defaults to network-off with allowlist-first controls. Your existing `constitution_guard` hook is good defense-in-depth, but it should not be the primary guardrail; protected paths should also be blocked by OS permissions or mount policy. citeturn16view2turn15view0turn7view4

Finally, use **progressive authorization** rather than ambient authority. MCP’s current security guidance recommends minimal initial scopes, targeted elevation only when privileged operations are attempted, short-lived tokens, token validation, and no catch-all scopes. The right analogue in your mailbox is that any human blessing should be a one-time, short-lived, single-task authorization token that binds to the exact `task_id`, `action_type`, `args_hash`, and target machine. A copied quote block in markdown is not enough; it needs cryptographic binding and replay protection if you want it to mean more than “helpful context.” citeturn28view2turn28view3turn24search15

## Failure Modes

The clearest failure mode is **authorization confusion**: the robot receives a mailbox item that looks like a legitimate task, infers it is GREEN, and runs it even though the message was only ever meant as data or as a proposal from another machine. This is exactly the kind of agent-to-agent delegation/authentication problem highlighted in recent authorization work: secured transport alone is not enough; the system must verify who is delegating, under what scope, for how long, and whether that authority is transferable to the receiving agent. citeturn29view0turn12view4

The second failure mode is **indirect prompt injection through queue contents or referenced artifacts**. Public evidence now includes both proof-of-concept and observed-in-the-wild examples. Unit 42 reported large-scale telemetry showing indirect prompt injection being actively weaponized on the web rather than remaining merely theoretical. Microsoft describes indirect prompt injection as an inherent risk of modern LLM systems and uses defense in depth including deterministic exfiltration blocking and consent workflows. Security researchers have also shown practical demonstrations in autonomous/computer-use contexts where injected content can drive harmful tool use. citeturn22view0turn22view1turn22view3

The third failure mode is **approvals that look reviewable but are not actually safe**. AutoGPT’s history is a cautionary case. Its early design required user authorization for commands, but a later disclosed issue reported that an attacker could manipulate the review path via injected console output and unreliable statements about future actions, and that dockerized builds also had sandbox-escape problems. The lesson is not “never prompt for approval”; it is that approval surfaces can themselves be attack surfaces if the thing being approved is opaque, misleading, or decoupled from the precise executable payload. citeturn22view4

The fourth failure mode is **queue semantics failure under Syncthing**. Syncthing writes via temporary files and then moves them into place; incomplete transfers can leave temp files around; simultaneous edits can generate `sync-conflict` files, and those conflict files are then propagated as ordinary files. Syncthing also warns that when state is not already in sync, outcomes can become unpredictable about which changes win. A mailbox consumer that simply “list new files in folder and execute” is therefore vulnerable to duplicate delivery, partial-file pickup, conflict-file reprocessing, replay after conflict resolution, and acknowledgement loops. citeturn23view2turn32view0turn7view10

The fifth failure mode is **idempotency illusion**. In distributed systems, duplicate messages and retries are normal, not exceptional. Queue systems like SQS and payment systems like Stripe deal with this through idempotency keys, deduplication identifiers, and the assumption that retries can happen. If your headless robot performs any write-like side effect—even a “safe” import or acknowledgement—without a deterministic idempotency key and a local executed-task ledger, you do not have safe replay. citeturn26search6turn26search3turn26search2turn26search5

A sixth failure mode is **atomicity mismatch**. The right pattern for producers is to write a task file completely, fsync it, and then atomically rename it into the visible queue name on the same filesystem. POSIX `rename()` provides atomic replacement semantics for that case. If instead producers stream directly into visible filenames, consumers can observe incomplete messages; if consumers modify shared task files in place, they multiply conflict risk under Syncthing. citeturn27search0turn23view2

## Strategic Recommendations

The highest-confidence recommendation is simple: **turn off bus-driven auto-execution now** and run the mailbox robot in **PLAN-only** mode until there is enough real GREEN volume to justify the complexity. Keep the robot alive, keep the planner, keep the single human ping, keep the audit trail, keep the AUTH concept for interactive sessions—but remove the headless path that lets loosely structured mailbox content directly result in execution. The reason is not abstract conservatism; it is the combination of three facts: current LLM gating is not reliable enough to be your security boundary, your queue backend has nontrivial distributed-systems hazards, and your own data says the auto path currently provides about zero operational value. citeturn37view3turn20view0turn34view0turn7view10turn23view2

If you want to preserve a future option for automation, redesign the system so the mailbox is **proposal transport**, while execution is controlled by a small deterministic kernel. Put differently: the LLM can output `proposed_action = REINDEX(local_index="notes")`, but it cannot itself authorize or parameterize arbitrary commands. The kernel should only accept a tiny enum of action types, each with a strict schema and a dedicated wrapper. No raw shell. No free-form paths. No string-concatenated arguments. No network unless the wrapper intrinsically requires it and the egress policy explicitly allows it. This is the architecture implied by OpenAI’s structured-input guidance, LangGraph’s per-tool HITL model, and the action-selector literature. citeturn7view1turn35view0turn14view3

Rebuild AUTHORIZATION as a **cryptographically bound execution token**, not a markdown quotation convention. A human approval minted in an interactive session should be short-lived, single-use, and bound to the exact task hash, target machine, allowed action, bounded argument set, and expiry. The headless robot should verify the signature and reject if any field mismatches or if the token has been seen before. This is the most important step if you ever want agent-to-agent coordination without authority leakage. Current work in authenticated delegation, capability tokens, and signed audit chains is directly aligned with that approach. citeturn29view0turn29view2turn29view1

Split the bus into **append-only per-writer namespaces**. For example: `tasks/<target-machine>/`, `plans/<writer>/`, `receipts/<writer>/`, `authorizations/<writer>/`. Each actor writes only to its own subtree. Consumers do not rename, edit, or delete shared task files. They mark local consumption in an unsynced SQLite ledger keyed by `task_id` and optionally emit an immutable receipt file for observability. This avoids a large class of Syncthing conflict problems. It also makes it easier to ignore `.syncthing.*.tmp`, `*.sync-conflict*`, expired tasks, duplicate `task_id`s, and out-of-order receipts. citeturn23view2turn32view0turn7view10

On the host side, harden the robot like an untrusted service. Dedicated OS user, minimal filesystem, immutable policy/config paths, no access to general secrets, no broad OAuth refresh tokens if avoidable, strict CPU/GPU and wall-clock quotas, and authenticated logging with task correlation IDs and artifact hashes. NIST zero-trust guidance is directly applicable here: assume the network is compromised, keep access decisions granular, and grant only the minimum privileges needed per request. citeturn18view0turn28view3

## Action Plan

**Immediate decision:** move the mailbox robot to **PLAN-only** for all sync-bus tasks. Keep current Tier-2 redlines exactly as they are. Remove the Tier-1 execution branch from the headless path, except possibly for self-scheduled maintenance that the robot originates locally and that is not triggered by mailbox content at all. This is the cleanest way to lower risk without losing most of the useful behavior you already have. citeturn15view0turn7view2turn16view0

**Near-term hardening:** convert task records to immutable signed JSON envelopes and add a local unsynced execution ledger. Producers should write to a temporary filename and atomically rename to final name only after full write/flush; consumers should ignore temp and conflict files, reject expired envelopes, reject unknown signers, reject duplicate `task_id`s, and reject any task whose `action_type` is not in the deterministic enum. Use append-only receipts rather than in-place updates. citeturn27search0turn23view2turn32view0turn26search2turn26search6

**Deterministic action kernel:** if automation is later reintroduced, support only wrappers such as `reindex()`, `transcribe_fixed_job()`, `read_report()`, `reimport_by_manifest_hash()`, and maybe `write_receipt()` if that write cannot trigger loops. Each wrapper must validate exact schemas, path prefixes, file-size limits, content hashes, and resource quotas. The LLM may select among wrappers only if the rule engine independently verifies the same choice from structured output; otherwise it falls back to human approval. citeturn7view1turn30view0turn14view3

**Authorization redesign:** replace the current free-text AUTH block with a signed, single-use authorization token generated by the human’s interactive session. Bind it to the exact task and expire it quickly. The headless daemon must refuse any broad, reusable, or time-unbounded “standing approvals.” This keeps your stated principle—“bus is data, not authority”—true in the enforcement layer, not only in prose. citeturn29view0turn28view3turn12view4

**Go/no-go criteria for bringing auto-exec back:** do not re-enable bus-driven auto-execution unless all of the following are true: there is sustained real GREEN volume that materially benefits from autonomy; every auto action has a dedicated deterministic wrapper; actions are replay-safe by construction; argument schemas are fixed and narrow; the wrapper has no general shell or ambient secret access; the host is sandboxed with restricted egress; and red-team testing against prompt injection, replay, duplicate delivery, and malformed/malicious envelopes is passed. If any of those conditions fails, the correct mode remains PLAN-only. citeturn20view0turn37view3turn22view1turn28view2
