# Insight (DR DR26-06-26-HUB-06): Выбор локальной LLM (3–6 GB VRAM) на GTX 1660 Super как фоллбэк для Claude Code

> Исследование отвечает на вопрос, какую локальную 3–6GB модель поставить на GTX 1660 Super как фоллбэк для Claude Code при исчерпании лимитов, и как технически организовать переключение.

## Ключевые выводы
- Рекомендуемые модели: Phi-4-mini (~3.8B, MIT, ≈3.5GB в Q4_K_M, ~20-30 ток/сек) или SmolLM3-3B (Apache-2.0, оптимизирована под reasoning и длинный контекст) — лучший компромисс скорость/качество для 6GB VRAM.
- Альтернативы: Qwen-2.5-3B (Apache, ~30-35 ток/сек, силён в мультиязыке/коде), Llama-3.2-3B (~38 ток/сек на 1660S, но лицензия Meta коммерчески-исследовательская, не CC0), Gemma-2 2B (~1.5-2GB, ~25-40 ток/сек). Модели 7B+ (>6GB) не помещаются.
- Claude Code не имеет встроенной поддержки сторонних LLM-провайдеров — фоллбэк-модели работают только внутри Anthropic; переключение на локальную модель нужно реализовывать ВНЕ Claude Code через внешний скрипт-роутер.
- Схема фоллбэка: скрипт вызывает `claude -p`, при ошибке (session/weekly limit, 5xx/429) переключает запрос на локальный OpenAI-совместимый эндпоинт (Ollama localhost:11434 или llama.cpp server localhost:8080/LM Studio localhost:1234) через curl.
- Сервер: llama.cpp HTTP-сервер (лёгкий C++ демон, OpenAI-совместимый API, компилируется через CMake/Visual Studio на Windows) — самый практичный вариант; Ollama — проще в установке (Win-инсталлятор); LM Studio — GUI-вариант; vLLM на Windows не готов/не рекомендуется.
- Детекция лимита: проверка кода возврата (`$LASTEXITCODE`) и текста ошибки («session limit», «weekly limit», «429»); можно использовать хук Claude Code `StopFailure` с матчером rate_limit/billing_error; рекомендован circuit-breaker с задержкой 5-15 минут перед повторной попыткой облачной модели.
- Локальная 3-4B модель годится только для простых задач (суммаризация, классификация, черновики, FAQ) — НЕ заменяет Opus для творческого письма/авторского голоса Антона, где важны глубина рассуждений и стиль.
- Эксплуатационные издержки: GTX 1660 Super ~150-200 Вт под нагрузкой 24/7 = ~1300-1750 кВт·ч/год, ≈$130-350/год на электричество плюс износ вентиляторов/чипов; рекомендуется выделить отдельную GPU под LLM (через CUDA_VISIBLE_DEVICES), оставив вторую для эмбеддингов/Whisper, и оформить сервис как Windows-службу (NSSM) для автоперезапуска.

## Рекомендации / решения
- Развернуть Phi-4-mini или SmolLM3-3B через llama.cpp server (или Ollama как более простую альтернативу) на одной GTX 1660 Super.
- Написать внешнюю обёртку-роутер (PowerShell/скрипт), которая сначала пробует `claude -p`, а при обнаружении ошибки лимита переключается на локальный API-эндпоинт.
- Использовать вторую GPU (если есть) для параллельных задач (эмбеддинги, Whisper), не смешивая с LLM-инференсом.
- Оформить локальный LLM-сервис как Windows-службу с автозапуском/автовосстановлением при сбое.
- Оценить экономику: если сбои с лимитами Claude редки, возможно дешевле просто ждать сброса лимита, чем поддерживать локальную инфраструктуру; при парке ~20 агентов локальный фоллбэк вероятно окупается.

## Открытые вопросы
- Реальная скорость (ток/сек) SmolLM3-3B и Qwen-2.5-3B конкретно на GTX 1660 Super не протестирована (цифры экстраполированы с RTX 2060 и других карт).
- Не проверено на практике, насколько надёжно текстовый матчинг ошибок Claude CLI («session limit» и т.п.) ловит все случаи лимитов — тексты могут меняться.
- Не оценено количественно, при каком именно объёме фоновых агентов (порог между 'редко' и '20 агентов') локальная инфраструктура окупает энергозатраты и сложность поддержки.
