A parallel 2025–2026 survey argues that older short-term/long-term labels are no longer enough, and instead separates memory by **form**, **function**, and **dynamics**, including factual, experiential, and working memory. A third 2026 systems paper finds that **no single memory architecture dominates**; performance depends on how well representation, extraction, retrieval/routing, and maintenance match the workload bottleneck. citeturn11view0turn12view0turn11view7

## Failure modes and what breaks in practice

The first hard failure is **write races**. Plain Markdown storage is human-friendly, but concurrent agents editing the same file are brittle. Filesystems can give you atomic replacement patterns for a single file, and libraries such as `write-file-atomic` serialize same-file writes inside one process, but files do not give you general multi-object transactions. SQLite in WAL mode improves the read/write experience for sidecar indexes, but it still serializes writers. The practical implication is straightforward: **do not let multiple runtimes free-edit the same “summary” notes.** Use append-only event records or leaf-note creation as the default write path, and reserve in-place patching for a guarded tool that carries a content hash or revision precondition. Keep the sidecar DB rebuildable, and let one logical writer own materialization of shared summaries. citeturn6search1turn6search2turn6search10turn23view2

The second failure is **agent drift**. The instruction surfaces now differ across runtimes. Claude Code reads `CLAUDE.md`, can import `@AGENTS.md`, and explicitly warns that instruction files are context rather than enforced configuration. Codex reads `AGENTS.md` directly, with global and project discovery rules. Cursor’s official docs now mention persistent rules and AGENTS.md. If you hand-maintain separate CLAUDE, Codex, Cursor, Gemini, and tool-specific files, they *will* drift. The fix is to make **root `AGENTS.md` canonical**, then generate or import runtime-specific shims from it. citeturn33view0turn33view2turn31search1turn31search3turn29search0

The third failure is **memory poisoning**. Persistent memory changes the threat model because an attacker can store malicious content in one session and let it steer a future consequential action. The newest work on poisoning argues that both content-based trust scoring and lineage-only trust can be laundered through summarization, “trusted tool” echoes, or manufactured corroboration, and another 2026 systematic study reports strong persistence of successful attacks with rates that increase as agents read and write memory more aggressively. The practical defense in a personal second brain is not “better prompts.” It is **trust separation**: store untrusted observations, imported snippets, and agent-generated summaries in a lower-trust class than confirmed rules; bind provenance at write time; require explicit approval or a deterministic promotion rule before any memory item can influence privileged actions; and never let recalled memory directly authorize destructive tools. citeturn11view4turn5search5turn33view2

The fourth failure is **hallucinated or stale memory**. HaluMem shows that errors accumulate especially in the extraction and updating stages, then propagate into retrieval and QA. LongMemEval and LongMemEval-V2 both stress temporal reasoning and knowledge updates because memory is not just about remembering that something was once true; it is about knowing when it changed, when it was superseded, and when to abstain. This is where plain note chunks are too flat. Your memory layer needs explicit temporal fields such as `valid_from`, `valid_to`, `supersedes`, `superseded_by`, `last_verified_at`, and `confidence`, plus a visible conflict queue instead of silent overwrite. Graphiti’s temporal knowledge-graph model is useful here as a design reference even if you never adopt Graphiti itself as the primary store. citeturn11view3turn2search0turn11view6turn10view4

The fifth failure is **framework churn and abandonment risk**. Agent-memory tooling is moving fast enough that coupling your canonical memory to one framework API is asking for migration pain. LangChain v1 moved large areas of older chain/retriever/indexing functionality into `langchain-classic`, and Letta’s maintainers explicitly moved active development from the older server framing into a newer agent/app-server direction after the MemGPT-to-Letta rename. That does not mean those projects are bad. It means your durable asset should be **files + open schema + rebuildable indexes**, not framework-native opaque state. citeturn19view0turn19view1turn10view6turn19view2

## Recommended architecture for your vault

The target architecture I would build for your vault is a **three-layer system**.

At the bottom is the **canonical substrate**: your existing Obsidian vault remains the source of truth, and your current retrieval stack remains intact. Add one top-level memory namespace—`Brain/` is the obvious choice because it matches the strongest current practice—but keep it **small, typed, and operational**, not a second PKM universe. PARA folders, MOCs, wiki-links, and provenance frontmatter stay where they are. The new namespace should hold only the artifacts that agents need to share reliably: rules, decisions, session digests, signal logs, source receipts, schema docs, and conflict queues. This is consistent with file-first systems such as Tolaria and Basic Memory, which keep structure in frontmatter and notes while treating indices as derived. citeturn21view0turn25view0turn10view2turn10view1

In the middle is the **local memory kernel**. This is the additive component you do not currently have. It owns a sidecar SQLite database in WAL mode for event logs, typed edge indexes, signal counters, and fast filters, but that database is explicitly **rebuildable** from the files. The kernel exposes one semantics layer for every agent runtime: safe note creation, guarded patching, search, schema validation, signal recording, promotion, conflict review, and rollback checkpoints. Existing grep/SQL/RAG continue to operate, but now as part of one memory service rather than as runtime-specific conventions. Basic Memory’s architecture is close to this pattern already—plain Markdown plus a secondary DB plus MCP tools plus consistency checks—and Anthropic’s client-side memory tool shows the same storage/control split from the application side. citeturn9search8turn8view2turn10view3turn15view2

At the top is the **cross-runtime contract**. Use MCP as the universal interface, but use the MCP primitives intentionally. Publish **resources** for read-only artifacts that should be stable and easy for hosts to load, such as `memory://agents`, `memory://active`, `memory://schemas`, `memory://recent-decisions`, and `memory://conflicts`. Publish **prompts** for maintenance workflows such as “capture session digest,” “propose rule candidate,” “resolve conflict,” and “review stale facts.” Publish **tools** only for side-effecting or query operations such as `search_memory`, `read_note`, `create_note`, `patch_note`, `append_signal`, `promote_rule`, `validate_schema`, and `rollback_snapshot`. That split follows the MCP spec directly: resources are read-only/context-sharing, prompts are structured templates, and tools are model-controlled actions. citeturn16search0turn16search1turn16search2turn16search4

For transport, I would not rely on “every client spawns its own fully independent stdio server that writes directly to the vault.” Instead, run **one canonical local kernel** and let runtimes talk to it through adapters. Where a host supports local HTTP cleanly, use loopback HTTP or a Unix socket. Where a host expects stdio, use a tiny stdio bridge that forwards calls to the same kernel. MCP explicitly supports both `stdio` and Streamable HTTP, and the host/client/server model is already designed for this kind of separation. This is the cleanest way to avoid multi-process write races without giving up MCP portability. citeturn16search8turn16search12turn16search7

For onboarding and behavioral consistency, make **`AGENTS.md` the canonical human-maintained document at the vault or working root**, and derive everything else from it. Claude Code should use a `CLAUDE.md` that imports `@AGENTS.md`, because Anthropic explicitly recommends that path when a repo already uses AGENTS.md. Codex should read the same `AGENTS.md` directly. Cursor’s official docs now treat AGENTS.md as part of the persistent-rules story. This immediately kills the “per-runtime fork” problem at the instruction layer. Runtime-specific differences should live only in short tail sections or generated shims. citeturn33view0turn31search1turn29search0

For note typing, do **not** try to type the whole vault. Start with the classes where agent writes create the most downstream value and the most damage when wrong. I would type at least these: `Rule`, `Decision`, `Session`, `Source`, `Procedure`, `Project`, `Person`, and optionally `Fact`. Tolaria is useful here because it treats `type:` as independent from folder location and lets Type documents define instance defaults/schema as ordinary frontmatter, which fits a large PARA-based vault far better than folder-implied semantics. Basic Memory’s schema layer is also useful because it supports inference, validation, drift detection, and diffs instead of forcing a top-down schema redesign. Obsidian properties remain the human-facing structural surface. citeturn8view6turn24view4turn10view1turn25view0

For deterministic consolidation, copy the *shape* of Open Second Brain’s dream pass, not necessarily its exact implementation. Let agents or humans record **signals** deterministically during work—corrections, approvals, rejections, successful recalls, contradictions, manual pins, and manual retirements. The nightly job should then promote or retire memory based only on counters and rules, never on freeform LLM reasoning inside the kernel. This also aligns with the systems literature: maintenance is its own module, and localized maintenance is often more cost-efficient than global reorganization. citeturn23view2turn11view7

A concrete promotion policy that fits your environment would look like this. A candidate rule is created only when the same normalized correction appears in at least **two distinct sessions**. It becomes a confirmed rule only after either **three confirmations** or **two confirmations from different runtimes or days**, with no unresolved contradiction. Contradictions move the item into a `Conflict` queue rather than overwriting it. Rules decay only when they have not been recalled or reaffirmed for a defined period and are non-pinned. Manual pin/unpin always overrides automation. This gives you deterministic non-LLM “memory consolidation” while satisfying the selective-forgetting requirement that benchmarks now emphasize. citeturn17search10turn23view2

On Git, the right role is narrower than many “git-native memory” pitches imply. Keep your existing commit-before-write snapshots. Add explicit **checkpoint tags** for promotion runs and bulk hygiene passes. Record the current commit SHA in note provenance when a memory item depends on code-state. Use **worktrees** for long-running code-editing agents and risky refactors, because both Git itself and modern coding-agent tooling now make isolated worktrees normal. But do not attempt to make every memory write a Git commit or treat commit history as memory retrieval. That yields perfect audit and terrible recall. citeturn6search0turn21view0turn31search2turn29search13

## Phased roadmap and anti-patterns

Start with a **contract phase**, not an indexing phase. Create `AGENTS.md` as the canonical onboarding file. Add a generated `CLAUDE.md` that imports it, verify Codex reads the same file directly, and keep any Cursor/Gemini/Codex-specific deltas in tiny generated shims. At the same time, define the small typed namespace under `Brain/`: `Rule`, `Decision`, `Session`, `Source`, `Conflict`, `Signal`, and `Schema`. Add frontmatter fields for `type`, `id`, `created_at`, `updated_at`, `provenance`, `source_refs`, `confidence`, `valid_from`, `valid_to`, `supersedes`, and `review_state`. This phase is low-risk and immediately arrests drift. citeturn33view0turn31search1turn25view0turn24view4

Next, build the **memory kernel phase**. Wrap your existing e5/RAG/SQLite/grep stack behind one local service. Give it read resources, safe search/read tools, and exactly three write tools at first: `create_note`, `patch_note`, and `append_signal`. `create_note` should write atomically and reject traversal/clobbering, much like Open Second Brain’s guarded note creation. `patch_note` should require a prior content hash or revision. `append_signal` should be idempotent and write only into a dedicated append-only log. Add a rebuild command so the sidecar DB can be regenerated from Markdown at any time. citeturn23view2turn9search8turn10view3

Then add the **deterministic maintenance phase**. Build nightly jobs that compute promotions, stale-memory candidates, near-duplicates, and conflicts from the signal ledger and typed notes. Keep these jobs fully deterministic. If you want LLM help, let it happen **outside** the kernel as a proposal step that writes a candidate signal, never as the authoritative promotion engine. This matches where the ecosystem is going: Open Second Brain uses counters and atomic moves; research now treats maintenance as a separate module; and hallucination work shows that unconstrained extraction/update is where many errors begin. citeturn23view2turn11view7turn11view3

After that, do the **typed-overlay phase**. Add a derived graph index from wikilinks, frontmatter relations, and typed entity references. Keep the graph in SQLite or DuckDB as a projection, not as the canonical store. Use it for higher-precision recalls such as “what decision superseded this one,” “which procedures mention this project,” or “show conflicting facts about X.” This gives you some of the benefits that temporal and graph memory systems provide without forcing a store migration. citeturn8view2turn24view4turn10view4turn2search1

Finally, add the **hardening phase**. Restrict runtime roots to the vault paths they need. Gate privileged writes or destructive external actions behind hooks or approval middleware. Separate trusted from untrusted memory classes. Add schema validation in CI or pre-commit for the typed `Brain/` namespace using JSON Schema tooling over Markdown frontmatter. The safest mature pattern is boring: small blast radius, visible files, rebuildable indexes, and explicit trust boundaries. citeturn16search9turn14search2turn19view0turn26view0turn26view1
