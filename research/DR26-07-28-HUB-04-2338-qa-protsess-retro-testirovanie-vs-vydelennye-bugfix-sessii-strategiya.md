# Insight (DR DR26-07-28-HUB-04-2338): QA-процесс: ретро-тестирование vs выделенные bugfix-сессии + стратегия test/agent harness

> Как правильно организовать QA (когда чинить баги внутри ретро, а когда выносить в отдельную сессию с seed prompt) и нужен ли уже harness для растущей кодовой базы с Codex/Grok.

## Ключевые выводы
- Ретро должно оставаться коротким (5-10 мин): мелкие локализованные баги чинятся сразу на месте с добавлением/обновлением автотеста (по практике Atlassian — 'fix and move on', но с тестом на регрессию).
- Критерии эскалации в отдельную bugfix-сессию: фикс займёт >10 мин, затрагивает несколько модулей/сервисов, поведение непонятно, либо контекст текущей сессии близок к лимиту токенов.
- Root-cause analysis (RCA) обязательна: точно определить баг, собрать доказательства (логи, падающие тесты), копать до реального триггера — 'заплатка' лишь маскирует симптом и баг возвращается.
- Test harness = вся обвязка вокруг тестов (fixtures, тестовые данные, настройка окружения, execution drivers типа pytest/CI, отчётность, teardown); без него ad-hoc тесты быстро ломаются при рефакторинге (устаревшие селекторы).
- Отдельно от test harness существует AI agent harness (по MindStudio) — инфраструктурный слой, управляющий тем, какой контекст видит модель, какие инструменты она может вызывать, как обрабатываются сбои и как задача декомпозируется на шаги.
- Рекомендуемые компоненты harness: управление контекстом (подтягивать только релевантный код/доку), интеграция инструментов (программный запуск тестов/линтеров), валидация вывода (синтаксис, pass/fail тестов), оркестрация подзадач.
- Seed prompt при переносе в отдельную сессию должен включать: контекст (что сделано), прогресс (какие тесты прошли/упали), точное описание проблемы (ошибка/трейс), цель фикса и ограничения окружения — даны текстовый и YAML-шаблоны.
- Для UI/интеграционных тестов предложен self-healing/intent-based подход: описывать цель пользователя, а не жёсткий селектор; при сбое кэшированного локатора — AI ищет элемент заново по намерению (аналог 'семантических' тестов, проверяющих поведение, а не детали реализации).
- Конфигурацию harness рекомендуется хранить как код (YAML в репозитории) и интегрировать с CI (GitHub Actions/GitLab CI) для воспроизводимости.

## Рекомендации / решения
- Тайм-боксить ретро ≤10 минут; если проблема не решена за это время — формально эскалировать в отдельную bugfix-сессию с seed prompt, а не тянуть в текущей.
- На каждый баг, исправленный в ретро, сразу добавлять/обновлять автотест, чтобы регрессия не проскочила повторно.
- Начать строить лёгкий test harness уже сейчас (pytest/Jest + CI-гейтинг) как первый шаг, постепенно эволюционируя в полноценный 'agent harness' для Codex/Grok.
- Использовать единый структурированный шаблон seed prompt (контекст / что сделано / симптом / конкретный запрос) для каждой эскалированной bugfix-сессии, чтобы не терять время на повторное объяснение.
- Развивать AI-agent harness слой вокруг Codex/Grok: retrieval релевантного контекста, обёртки над вызовом инструментов, валидация вывода, авто-ретрай при сбое.
- Исходный запрос Антона требовал 4 ОТДЕЛЬНЫХ deep research (QA-процесс, harness-стратегия, правила ретро/разделения сессий, библиотека seed-prompt шаблонов) — ChatGPT выдал один объединённый отчёт по всем четырём темам сразу, а не четыре отдельных исследования.

- Запрошенные отдельные deep research по harness-стратегии и по библиотеке seed-prompt шаблонов фактически не проведены как отдельные исследования — материал слит в один отчёт, детальность по каждой теме ниже заявленной.
- Конкретный выбор harness-фреймворка (pytest/Jest+CI vs LangChain/agent-harness проекты вроде ai-boost/awesome-harness-engineering) не решён, нужна отдельная оценка.
- Пороговые критерии эскалации (>10 мин, многомодульность и т.д.) не проверены на практике — нет метрик, подтверждающих, что именно эти пороги подходят команде.
