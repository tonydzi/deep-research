# Insight (DR DR26-06-26-HUB-04): Отказоустойчивость LLM-инфраструктуры: failover между Claude Opus, Sonnet и локальной LLM

> Отчёт разбирает текущую событийно-ориентированную архитектуру (инбокс + воркеры-слушатели, завязанные на облачный Claude) и предлагает многоуровневый failover-алгоритм с локальной резервной LLM для устранения единой точки отказа.

## Ключевые выводы
- Текущая архитектура: события кладутся в инбокс-очередь, воркеры/слушатели обрабатывают их через запрос к облачному LLM (Claude Opus/Sonnet) — единая точка отказа при недоступности провайдера.
- Нет активного health-check и мониторинга: воркеры узнают о проблемах провайдера только по таймауту/ошибке, а не проактивно.
- По статус-странице Claude на середину июня 2026 зафиксированы регулярные 'Elevated errors' 17–24 июня на Opus 4.6–4.8 и Sonnet 4.6; 16 июня ошибки ~10% запросов на всех моделях Opus/Sonnet.
- Uptime Claude API за ~90 дней ~99.5%, но июнь отмечен десятками кратковременных деградаций.
- Пользователи сообщают об исчерпании квот даже на крупных планах (пример: 20× план 'съедался' наполовину одним запросом и падал за несколько часов); в пиковые часы лимиты урезались.
- Anthropic заявляла о повышении лимитов Opus в мае 2026, но инциденты продолжались до конца месяца.
- Классификация ошибок для роутинга: 5xx/timeout → короткий ретрай с backoff и переход на резерв; 429 → уважать Retry-After и переключаться; 4xx (напр. content-filter) → не ретраить, вернуть ошибку пользователю напрямую.
- Для локального резерва подходят компактные модели с Hugging Face: Google Gemma 7B, SmolLM3 (3B, до 128K контекста, может работать на CPU), Llama 3.2 3B (мультиязычная, 8–12 ГБ GPU или 4-бит квантование), Mistral-7B (~16 ГБ VRAM fp16, ~8-10 ГБ при квантовании).

## Рекомендации / решения
- Внедрить иерархический failover-алгоритм: приоритет 1 — Claude Opus, приоритет 2 — Claude Sonnet, приоритет 3 — локальная in-house LLM (Gemma/Llama/SmolLM3/Mistral).
- Использовать централизованный шлюз/роутер (TrueFoundry Gateway, LiteLLM Proxy или механизм fallbacks в LangChain) вместо разбросанной по сервисам логики переключения.
- Настроить конфиг fallback_chain с явными кодами ошибок для ретрая (500/502/503/timeout) и для перехода на резерв (429/5xx).
- Добавить circuit breaker: при серии подряд идущих ошибок/429 временно отключать проблемный провайдер на несколько минут, чтобы избежать 'шторма ретраев'.
- Развернуть локальную LLM в Docker (transformers+FastAPI или llama.cpp), измерить латентность до продакшена.
- Настроить активные health-check пинги к каждому провайдеру каждую минуту + алерты при превышении порога ошибок (например >30% за 5 мин) + дашборды в Grafana/Prometheus/Datadog.
- Протестировать сценарии отказа: авария Opus, перегрузка Sonnet (принудительный 429), таймауты, восстановление и возврат трафика на приоритетный провайдер.
- Периодически перезапускать локальную LLM (чистка утечек памяти) и иметь заготовленное сообщение-заглушку на случай полного отказа всех LLM.
- Логировать причину и время каждого переключения провайдера для последующего анализа узких мест.

## Открытые вопросы
- Не указаны точные требования к качеству ответа локальной LLM (насколько допустима деградация по сравнению с Opus/Sonnet).
- Не проведено реальное измерение латентности предложенных моделей (Gemma/SmolLM3/Llama/Mistral) на конкретном железе.
- Не ясно, как унифицировать формат/качество ответов между разными моделями в цепочке failover.
- Не проверено на практике (только рекомендация), сработает ли предложенный алгоритм в текущей кодовой базе инбокс-воркеров.
