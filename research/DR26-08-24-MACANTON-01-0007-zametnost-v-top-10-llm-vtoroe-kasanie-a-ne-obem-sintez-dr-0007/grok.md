1. КОНВЕРСИЯ: лестницы и найм через вклады/комменты
------------------------------------------------

Вывод 1.1. Документированная лестница есть. Она про ВКЛАД, не про комментарии. (established)

Канон из Fogel / Bacon / Eghbal / Steinmacher / Zhou–Mockus / CONTRIBUTING.md:

1. Наблюдатель (issue/discussion, без кода).
2. Первый осмысленный артефакт, привязанный к уже живому запросу мейнтейнера (ваш замер холодных PR это подтверждает).
3. Повторный вклад в ТОТ ЖЕ репозиторий (returning contributor — CHAOSS; у Steinmacher обрыв после первого вклада — главный фильтр).
4. Мейнтейнер инвестирует: assignment, «could you take this?», review-права, CODEOWNERS, collaborator.
5. Внерепозиторный контакт: call / Discord / email / «we’re hiring».
6. Реферал или прямой оффер / trial / contract.

Комментарий — ступень 1–2. Оффер в публичных кейсах почти всегда сидит на ступенях 4–5. Публичных кейсов «меня наняли, потому что я хорошо комментировал, не отправив кода» почти нет. Есть кейсы «меня узнали по тредам, потом попросили PR / созвон».

Вывод 1.3. Сроки. (emerging на порядках; established что «недели до оффера» — исключение)

Публичных медиан «коммент→оффер» нет. Что можно честно сказать:

- Time-to-first-response на issue: часы–дни в живых репо, вечность в больших. Ваши 71–93% на 30 днях — аномально высокий first-touch, не норма Octoverse.
- Time to second contribution: в академической OSS-литературе обрыв после первого вклада — массовый. Возврат в тот же репо = уже отбор.
- Time to core/maintainer: в работах типа Zhou–Mockus и практиках ядра — обычно много месяцев, часто 6–24.
- Time to offer в OSS-native компаниях (PostHog-класс): в рассказах основателей встречаются недели–несколько месяцев, если роль уже открыта и человек закрыл боль. Это анекдоты, не выборка.
- Time to offer в frontier-лабораториях: публичной лестницы нет. Реалистичный горизонт «узнали имя → реферал на открытую роль» — кварталы, не 2 месяца ваших текущих данных. Исключения (редкий баг в Claude Code / eval, который команда сама хочет) могут быть быстрее; данных нет.

Ваша стадия по канонической лестнице (high confidence по вашим же цифрам): ступень 2–3. Разговоры у крупных, merge у малых/средних. Это нормаль, не провал. 20/75 merge ≈ 27% — для внешних PR в чужие репо это не «мало», у ядра VS Code/transformers/pytorch merge внешних без sponsor обычно хуже; точной отраслевой цифры не цитирую.

Вывод 1.4. Комментарии конвертят во ВНИМАНИЕ, PRs — в ДОКАЗАТЕЛЬСТВО, повтор одного человека — в ОТНОШЕНИЕ. (established как механика; speculative как «это предсказывает оффер»)

3. КАДЕНС И РИСК
------------------------------------------------

Вывод 3.1. Порога «полезный vs спамер» в открытых цифрах GitHub нет. (established: политики есть, числа нет)

GitHub AUP бьёт за: спам, inauthentic engagement, автоматизацию без раскрытия, массовые одинаковые issues/PR/комменты, манипуляцию. Secondary rate limits режут burst (документация GitHub описывает лимиты на actions, не «репутацию мейнтейнера»).

Что мейнтейнеры публично называют спамом (Hacktoberfest 2020 + волна AI slop 2024–26 + CONTRIBUTING-нормы):
- одинаковый текст в нескольких репо;
- typo/badge/README-only PR пачками;
- LLM-пересказ чужого issue («Here’s a summary… have you tried…»);
- @mention мейнтейнера без новой информации;
- повторный пинг «any update?» <7 дней в не-urgent;
- PR без issue там, где просят issue first (ваш холодный PR=0 — совпадает);
- график, который выглядит как бот: много репо, мало follow-up, CI красный.

Численного «N касаний/репо/неделя = бан» нет. Писать «5 в неделю безопасно» — выдумка. Не буду.

Вывод 3.2. Shadow-flag / скрытые ограничения. (emerging)

Публично описаны: rate limit, abuse-flag, block, repo interaction limits, «hidden» от поиска иногда у спам-аккаунтов. Нет официальной спецификации shadowban как у соцсетей. Симптомы, которые люди наблюдают: комментарии не вызывают нотификаций, PR не подхватывает CI-очередь как раньше, резкое падение reply. Причинность не доказана.

Отдельный риск 2025–2026: паттерн «маленькая лаборатория + AI-агенты + 75 PR / 2 мес». Для внешнего глаза это ближе к contribution farm, чем к двум инженерам. Даже при высоком качестве. Раскрытие агентности (Assisted-by) снижает риск «inauthentic», не риск «вы слишком частые».

Вывод 3.3. Каденс и reply-rate. (emerging на качественном уровне; ваших 71–93% как базы)

Литературы «+1 коммент/нед → −X% reply» нет.

Качественно из Eghbal + практика мейнтейнеров:
- reply-rate падает, когда вы увеличиваете ЧИСЛО ТРЕДОВ быстрее, чем глубину;
- reply-rate держится, когда вы отвечаете В УЖЕ ЖИВОМ треде по существу и не открываете новый;
- первый ответ дешёвый (вежливость, triage); второй ответ того же человека дорогой (это и есть отношение);
- burst в один день по 8 репо одного орg = корреляция со спам-эвристиками людей и ботов.

Ваш 71–93% на 94 тредах / 30 дн — актив, который объём убьёт первым. Норма внешнего first-response в больших репо гораздо ниже (CHAOSS/Octoverse показывают длинные хвосты без ответа; точную цифру «индустрии» сюда не подставлю — смеси репо несравнимы).

Практический потолок без фальшивых KPI (speculative, консервативно, из норм а не из A/B):
- один и тот же человек: не чаще 1 исходящего касания в 5–7 дней, пока он сам не ускорил;
- один репо: 1 новая нитка в неделю максимум, плюс follow-up в своих же живых;
- один вендор-орг (anthropics, openai, google, microsoft): 2–3 substantive публичных касания в неделю на ВСЮ лабораторию, не на человека;
- HF/inspect-ai/cookbook-слой: можно чуть чаще, если идут merge/assignment;
- никогда: копипаст, параллельные «я тоже» в 5 репо, второй PR в тот же репо пока первый не закрыт.

За что реально банят/режут на GitHub (established по AUP + публичным кейсам, не по мифу):
- спам и автоматизация;
- credential stuffing/скам (не ваш случай);
- harassment, doxxing;
- mass unsolicited;
- иногда: malware в репо, protestware в чужих PR.

За что «убивают репутацию» без бана (established как жалобы мейнтейнеров): AI-slop, Hacktoberfest-паттерн, contribution-graph farming, публичные посты «меня игнорят».

------------------------------------------------
4. ИЗМЕРЕНИЕ для одиночки / малой лаборатории
------------------------------------------------

Вывод 4.1. Корпоративные DevRel-метрики вам почти не предсказывают оффер. (established)

Thengvall / DevRelCon / Orbit / DX: hello-world time, SDK downloads, MAU Discord, NPS, «champions». Это метрики продукта. У вас нет продукта, который они адвокатируют. Переносить «Orbit level 3» как KPI оффера — category error.

CHAOSS полезен как операционка (скорость ответа ВАМ, returning contributor, time-to-merge), не как предиктор найма.

Вывод 4.2. Что ближе к предиктору оффера. (emerging; ранжирую по силе сигнала, не по коэффициенту — коэффициента нет)

Сильнее → слабее:

1. Инициатива с их стороны: assignment, review-request к вам, collaborator, «want to jump on a call?», интро к hiring manager. Это и есть конверсия. Считать штуками.
2. Повторные ответы ОДНОГО И ТОГО ЖЕ человека (2-й, 3-й ход) в разных днях. Прокси отношения. Ближайшее к «second-touch», что у вас есть.
3. Приглашение написать design note / взять связанный issue / посмотреть PR.
4. Merge в репо, который принадлежит целевому работодателю (не в соседний тулинг).
5. Глубина треда (число сообщений), если глубина = совместная отладка, а не спор.
6. Упоминания (@you) мейнтейнером в ДРУГОМ треде — они привели вас как ресурс.
7. Упоминания без контекста, звёзды, «great write-up» от случайных — vanity.

Глубина треда сама по себе — плохой предиктор: длинный тред бывает ещё и конфликт. Повтор одного человека важнее длины.

Вывод 4.3. Second-touch rate. (established в маркетинге; speculative в OSS-найме)

В CRM/маркетинге second-touch — стандарт атрибуции (HubSpot/GA, много лет). В OSS:

- CHAOSS: returning contributors, не «second maintainer reply».
- Steinmacher: second contribution со стороны НЬЮКАМЕРА.
- Нет исследования «second-touch rate мейнтейнера предсказывает оффер».

Рабочее определение для вас, без науки в кавычках:
second-touch = тот же уникальный человек ответил вам ещё раз спустя ≥48ч с новым содержанием.
Считать: second-touch / unique repliers за 30/90 дней.
Считать отдельно: vendor-employee second-touch (Anthropic/OpenAI/…) vs random.

Это ваша метрика. Не выдавать её за отраслевой стандарт.

Вывод 4.4. Что измерять еженедельно лаборатории из 2 человек. (emerging, заточено под оффер)

Знаменатели обязательны (иначе 75 PR врут):
- unique humans replied (у вас 40 / 30д — базовый капитал);
- % с second-touch;
- число инициатив с их стороны (assignment/call/review-request);
- merge только в target-org vs прочие;
- reply-rate на НОВЫХ тредах (если падает — вы жжёте внимание);
- холодные PR (должен оставаться 0 попыток);
- касаний на орg и на человека (потолки).

Не измерять как north star: звёзды, количество PR, «нас увидели N вендоров». Вы уже «увидены». Дальше — повтор.

------------------------------------------------
5. РЫЧАГ КОНТЕНТА: write-up вклада → ответы мейнтейнеров?
------------------------------------------------

Вывод 5.1. Данных, что блог/тред про свой PR повышает reply-rate ТОГО ЖЕ мейнтейнера — нет. (established как отсутствие evidence)

Не нашёл (и в публичной литературе не стоит ждать) A/B: «написал пост → мейнтейнер стал отвечать чаще». Утверждать, что конвертится — speculative.

Вывод 5.2. Что write-up реально делает, по смежным фактам. (emerging)

Документированные эффекты build-in-public / contribution blogs — на ТРЕТЬЮ аудиторию:
- другие работодатели и инженеры находят вас (поиск, HN, X, changelog-рассылки типа This Week in Rust);
- GDE/MVP-заявки требуют публичных артефактов — write-up = evidence pack, не ping мейнтейнера;
- туториал, который СНИЖАЕТ нагрузку («как воспроизвести / как пользоваться фичей после merge») иногда попадает в README/docs — это услуга, не пиар. Тогда мейнтейнер может сам сослаться. Кейсы есть как практика, не как серия с контрольной группой.

Негативный эффект тоже задокументирован качественно (посты мейнтейнеров, не RCT): публичный call-out «PR висит N дней» сжигает мост. Working in Public описывает асимметрию: ваша «заметность» = их «давление аудитории».

Вывод 5.3. Практический вердикт по контенту. (emerging)

Write-up конвертит в ответы мейнтейнера — нет данных.
Write-up конвертит в репутацию у ДРУГИХ нанимателей и в пакет на GDE/MVP/Fellows — да, это штатный вход в эти программы.
Write-up полезен мейнтейнеру только если это документация/репро/бенчмар, которое им не надо писать самим.

Не ставить CTA «замержите мой PR» в пост. Ставить: вот рецепт, вот до/после, вот ограничение.

Ваш рычаг сильнее контента уже измерен: живые ответы в чужих тредах 71–93%. Контент — усилитель третьей аудитории, не педаль reply-rate.

------------------------------------------------
6. АНТИ-КЕЙСЫ: что убивало репутацию «заметности через комментарии»
------------------------------------------------

Все ниже — реальные классы провала, не выдуманные имена вашей лаборатории.

1. Hacktoberfest 2020 (established). Массовые низкоценные PR «для заметности/свитшота». Репутация участников = спамеры. Репо ставили opt-out. Урок: каденс+типовые правки в сезон = яд.

2. Contribution-graph farming / README-badge / docs-typo mills (established). «Я контрибьютор N проектов» при нулевой глубине. Мейнтейнеры научились фильтровать. Убивает merge-trust на месяцы.

3. LLM-комментарии 2024–2026 (emerging→established как жалоба). «Thanks for raising this. A potential cause could be…» без репро. Тратит triage. Часть проектов ввела анти-AI правила или требует disclosure. Для лаборатории с агентами — главный карьерный риск, не «мало постов».

4. Hire-me в трекере (established как антипаттерн). Issue/PR с самопиар-абзацем. Закрывают, иногда mute. Найм идёт в стороне от трекера.

5. Публичный позор мейнтейнера (established). Блог «они игнорируют внешние вклады» по одному PR. Даже если факт верен — вы становитесь человеком, с которым не хочется впускать в Slack.

6. @core-team на каждый коммент (established этикет). Notification abuse. Люди ставят custom routing / ignore.

7. «Становлюсь мейнтейнером» на первом касании (established). Просьба прав без истории returning contributions.

8. Кросс-постинг одного и того же совета в 10 issues орg (emerging как spam-heuristic). Выглядит как бот, даже если совет верен.

9. Пиар своего продукта/агента внутри чужого бага (established). Kite-подобные badge-PR и «try our tool» в issues получали публичный отпор неоднократно.

10. Выбор самого знаменитого репо как сцены (established practically). Внешний коммент в pytorch/transformers/vscode без issue-якоря тонет и метит как шум. Разговоры без merge у больших вендоров — ожидаемая физика, не повод повышать громкость.

Что именно убивает: не «слишком мало хайпа», а (a) шаблон, (b) объём без возврата в тот же тред, (c) давление на человека публично, (d) скрытая автоматизация.

C. НЕДЕЛЬНЫЙ ПЛЕЙБУК ДЛЯ ЛАБОРАТОРИИ 2 ЧЕЛОВЕКА + АГЕНТЫ

Цель недели не «больше PR». Цель: second-touch с уже ответившими vendor-инженерами + 0 холодных PR + не уронить reply-rate на новых нитках.

C1. Капитал, который нельзя жечь
- 40 уникальных людей (особенно Anthropic CC-автор, OpenAI, MS, Google, Qwen, UK AISI, Pydantic) — CRM, не «ещё 75 PR».
- Reply-rate 71–93% — стоп-кран. Если за 7 дней reply на НОВЫХ нитках <60% — режем объём, не увеличиваем.

C2. Потолки касаний на лабораторию (не на агента). Speculative, зато fail-closed. Нет отраслевых чисел — это потолки риска, не оптимум.

Исходящее = новый issue, новый PR, первый коммент в чужом треде, публичный @. Не считается: ответ, когда вас спросили; CI-фикс своего PR; 1 follow-up по запросу.

На человека (vendor engineer):
- max 1 исходящее / 7 дней;
- 0 исходящих, если ваш последний шар не получил ответа >14 дней — только новая улика (репро, патч, бенч), не «ping».

На репо:
- max 1 новая нитка / 7 дней;
- своих открытых PR в одном репо: max 2 одновременно.

На вендор-орг в неделю (все репо орg суммарно):

Anthropic: 2 исходящих. Приоритет claude-code issues с репро / фикс того, о чём они уже пишут. 0 cookbook-спама.

OpenAI: 2. Только cookbook/evals/SDK с живым issue. 0 «open the model».

Google Gemini/DeepMind: 2 на Gemini cookbook/client; 0 на tensorflow/chromium «для галочки». Параллельно 1 шаг по GDE evidence pack (это не GitHub-пинг).

Microsoft: 2 на SK/AI samples ИЛИ 1 на vscode/typescript строго в assigned/labeled issue. Параллельно учёт на MVP (артефакты, не комменты).

Meta/PyTorch: 1. Только если есть их issue. Иначе 0.

Mistral: 1–2. Высокий SNR, не заливать.

DeepSeek: 0–1. Не строить неделю вокруг их ответа.

Qwen/Alibaba: 1. Не конкурировать с шумом.

Cohere/C4AI: 1 GitHub + лучше 1 содержательный вклад в Aya/eval, чем 3 SDK-коммента.

Hugging Face: 3, но только где зелёный CI и есть шанс review. 1 из них — follow-up своего PR, не новый.

Итого публичных исходящих GitHub на лабораторию: потолок ~12–15 в неделю, из них ≥50% — follow-up в УЖЕ живых тредах с теми 40 людьми, не новые сцены.
PR в неделю: ≤3, все issue-anchored. Не 9.

Агенты: не открывают новые треды без ручной приёмки. Могут готовить репро/дифф. Публичный текст — человеческий, короткий, без recap-слопа. Если агент пишет — disclosure в коммите, не в каждом абзаце issue.

C3. Лестница недели (повторяемый ритуал)

Пн (30–45 мин, без LLM-рассылки):
- список 40: кто ответил, ждал ли second-touch, открыт ли у них issue, где мяч;
- выбрать 5 человек, не 15 репо.

Вт–ср:
- по каждому из 5 — одна услуга: репро, failing test, review их PR, закрытие их TODO в треде;
- 0 новых вендор-ядер.

Чт:
- max 2 issue-anchored PR в малые/средние (там у вас merge) ЛИБО в cookbook/inspect/SK;
- большие вендоры — без PR, если вас не попросили.

Пт:
- 1 write-up ТОЛЬКО если есть merge или закрытый совместный баг. Формат: рецепт до/после, без CTA на мейнтейнера. Цель — пакет GDE/MVP/C4AI и третья аудитория.
- заявочный шаг в программу: GDE или MVP или HF/C4AI/inspect — один артефакт в неделю, не все сразу.

Не делать на этой стадии: холодные PR, мульти-репо копипаст, «наймите нас», рост 75→150 PR.

C4. Конверсия, которую вы форсируете (не оффер напрямую)

Единственные легитимные CTA в треде:
- «могу закрыть связанный issue X патчем, если хотите»;
- «нужен ли failing test в репо или достаточно gist».

CTA вне треда (когда second-touch уже был ≥2):
- короткий вопрос «есть ли у команды preferred place for this (discussion/issue)» — не Calendly в лоб;
- для программ: заявка GDE/MVP/Fellows/C4AI с тремя ссылками на ИХ репо, где вам ответили люди.

Оффер — следствие реферала одного из 40. Плейбук максимизирует число людей из 40, у которых есть 3-й контакт и совместный артефакт. Не максимизирует вендоров в портфолио.

C5. Что считать успехом недели (без фальшивых %)

Зелень: ≥3 second-touch от уже известных vendor-людей; ≥1 их инициатива (assignment/request); reply-rate новых ниток не ниже прошлой; холодных PR = 0.
Жёлтый: много новых ниток, мало повторов.
Красный: рост исходящих, падение reply, одинаковый текст, красный CI, пинг молчащих.

Горизонт оффера не ставить на 7 дней. Горизонт «кто-то из 40 инвестировал работу в вас» — да. По литературе ядра это месяцы. Ваш 2-месячный замер ещё ранний для ступени 5–6.

D. ТОП-5 ОШИБОК, КОТОРЫХ ИЗБЕГАТЬ

1. Открывать холодный PR в большой вендорский репо без живого issue. У вас два нуля. Третий будет стоить репутации, не данных.

2. Масштабировать агентами ПЕРВЫЕ касания. Объём 75 PR / 2 мес уже на грани «farm». Бан/ignore придёт от паттерна, не от одной фразы. Агенты — на репро и черновик диффа, не на «заметность».

3. Путать first-reply с отношением. 71–93% — triage. Оффер сидит на second/third-touch одного и того же человека и на его инициативе. Расти числом тредов = убивать метрику, которая у вас уникальна.

4. Писать «нас игнорят / вот наш PR» в блог/соцсети про конкретный вендор. Данные, что это повышает merge — нет. Данные, что это бесит — качественные, многолетние.

5. Целить ядро (transformers, pytorch, vscode, «настоящий» закрытый model repo) вместо дверей, где внешние ждут: cookbooks, evals, inspect-ai, SK, HF-libs, Claude Code issues с репро; плюс GDE/MVP/C4AI/Fellows как легальные комнаты. У больших мержей почти нет — это не чинится громкостью.
