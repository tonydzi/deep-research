# Agent-facing Documentation and Prompt Injection in Open Source

## Executive synthesis

The clearest line emerging across 2025–2026 guidance is this: **agent-facing documentation is legitimate when it is an explicit, visible, bounded source of project context that remains subordinate to the operator's authority and runtime permission gates; it becomes prompt injection when it is smuggled through an untrusted or hidden channel, attempts to override higher-priority instructions, or pushes the agent toward actions the operator did not authorize**. That framing is not just intuition. It is consistent with NIST's description of agent hijacking as a failure to separate trusted instructions from untrusted data, OpenAI's instruction hierarchy and "ignore untrusted data by default" rules, MCP's explicit user-consent requirements for tool use, Microsoft's warning to treat tool descriptions as instruction-bearing context and to inspect them for inappropriate imperative language, and Anthropic's guidance to trust servers carefully and keep approval systems in place.

A practical synthesis of the sources yields six criteria that most strongly distinguish legitimate agent docs from injection:

1. **Operator-directed ingestion**. The human or hosting application intentionally points the agent at the repo, file, server, or well-known endpoint. MCP goes further and requires explicit user consent before tool invocation; OpenAI and Anthropic likewise emphasize approval modes and trusted-server selection.
2. **Trusted-instruction hierarchy is preserved**. OpenAI's hierarchy places system/developer/user above tool output, and its Model Spec says quoted text, file attachments, and tool outputs are untrusted by default. NIST describes the root problem as lack of separation between trusted internal instructions and untrusted external data.
3. **The file provides context, not authorization**. Legitimate files can recommend build steps, tests, style, and local workflow; they should not claim power to waive confirmations, grant permissions, or tell the agent to act "without waiting for the human." OpenAI, Anthropic, and Microsoft all keep approval and permission systems outside documentation text.
4. **Actions are bounded, reversible, and proportionate**. MCP's schema explicitly distinguishes read-only, destructive, idempotent, and open-world tools. Vendor guidance repeatedly adds human confirmation for sensitive, write, external, or costly actions.
5. **Humans can see what the agent sees**. The strongest negative signal in public controversies was not "the file addressed agents," but that the content was hidden from humans or machine-only in a deceptive way, such as invisible HTML comments or invisible Unicode.
6. **The content serves the user's task, not the publisher's side agenda**. Google's 2026 web study found a spectrum from "helpful guidance" to SEO manipulation, anti-agent traps, exfiltration attempts, and destructive payloads. Public backlash clustered around side-effectful asks such as starring repos, advertising products, or connecting to unrelated endpoints.

**Established practice.** It is already normal for vendors and OSS ecosystems to publish machine-addressable artifacts: `AGENTS.md` in Codex, `llms.txt` at site root, A2A Agent Cards at well-known URLs, MCP tool descriptions/annotations, and "copy for LLM" documentation surfaces. Chrome Lighthouse now audits for `llms.txt`; Google's A2A protocol standardizes Agent Cards; MCP standardizes tool metadata and consent; OpenAI documents `AGENTS.md` discovery.

**Emerging opinion.** The vendor-and-research direction is increasingly to treat these files as **policy-bearing context that deserves security review**, not as harmless prose. Microsoft says tool descriptions should be reviewed as if they were system prompts. Google's security teams distinguish helpful agent guidance from manipulative or malicious prompt injections in the wild. Academic and industry work in 2025–2026 also broadened the taxonomy from direct/indirect prompt injection to skill-file attacks, tool-selection attacks, and hidden early-ingestion payloads.

**Speculation.** There is still no universal rulebook that says "visible AGENTS.md is safe" or "imperative language is forbidden." Imperatives are routine in project instructions. The line is not grammar alone. It is a combined question of **authority, scope, visibility, and effect**. That conclusion is a synthesis from the standards and incidents, not a single published sentence from one authority.

## Where the line appears to be

The most authoritative current framing comes from **instruction hierarchy plus trust boundaries**. OpenAI's March 2026 instruction-hierarchy work states that systems routinely receive instructions from multiple sources and must prioritize the most trusted ones; it explicitly gives the ordering **system > developer > user > tool** and says failures occur when untrusted instructions are treated as authoritative. Its Model Spec separately says quoted text, file attachments, multimodal data, and tool outputs are untrusted by default and must be treated as information rather than instructions unless authority is delegated explicitly. NIST uses nearly the same conceptual frame, describing agent hijacking as an old security problem caused by weak separation between trusted internal instructions and untrusted external data.

That has an immediate implication for your case: **a document intentionally offered to the operator as a repo-scoped agent brief is not automatically "prompt injection" merely because it contains instructions for the agent**. OpenAI's Codex documentation explicitly says Codex reads `AGENTS.md` before doing work and even shows ordinary imperative project guidance such as "Always run `npm test` after modifying JavaScript files." The `llms.txt` proposal is similarly explicit that the file exists to help LLMs use a website at inference time, while Chrome Lighthouse treats `llms.txt` as an optional, emerging convention for machine-readable summaries. Google's A2A protocol likewise makes Agent Cards a first-class discovery artifact rather than a covert instruction channel.

Where the line is crossed is when documentation text **tries to become authority rather than context**. MCP is unusually crisp on this. Its security principles say hosts must obtain explicit user consent before invoking any tool, users should understand what each tool does before authorizing it, and tool descriptions/annotations from untrusted servers must themselves be treated as untrusted. Microsoft's June 2026 security blog goes further: it tells operators to treat tool descriptions as system-prompt-like context and review them for imperative language that does not belong in documentation. Anthropic's MCP docs tell users to verify they trust each server before connecting it, because servers that fetch external content expose users to prompt injection risk.

On the "imperative vs advisory" question, the published material points to a narrower holding than many online arguments assume. **Imperative prose is not inherently injection-shaped**. Project docs routinely say "run tests," "prefer pnpm," or "follow this workflow." What security guidance objects to is imperative prose that **claims ungranted powers, bypasses approvals, conceals itself from the user, or steers the agent into unrelated side effects**. That distinction is visible in Microsoft's "imperative language that does not belong in a documentation field" test, OpenAI's requirement to stop and escalate when a webpage tells the agent to ignore earlier instructions or handle sensitive data, and the Google/OWASP/NIST treatment of prompt injection as abuse of untrusted inputs to alter behavior in unintended ways.

Reversibility and scope also matter. MCP now encodes whether a tool is read-only, destructive, idempotent, or open-world. Microsoft and OpenAI both recommend confirmation for sensitive, write, or exfiltration-relevant actions. Google's Workspace team describes deterministic defenses such as user confirmation, URL sanitization, and tool-chaining policies as part of the response to indirect prompt injection. In practice, that means agent-facing docs are least controversial when they **stay in the "read/understand/build/test" lane** and become much more suspect when they ask for **network access, authentication, external connections, payments, stars/likes, outreach, or anything destructive or irreversible**.

Transparency to the human is the last major criterion. The design pattern that seems to provoke the most immediate reputational concern is **machine-only visibility**: hidden HTML comments, invisible Unicode, or raw-file-only messages that humans reviewing the rendered page would not see. The public issue against `coolify-mcp` framed the problem exactly that way, and the maintainer's fix explicitly agreed that "agent-directed instructions hidden from human readers are a trust concern regardless of intent." By contrast, visible root-level `llms.txt`, `AGENTS.md`, `.well-known/agent-card.json`, and documented MCP metadata are discoverable, reviewable, and easier to govern.

## What projects are doing and how controversies played out

The industry picture is no longer hypothetical. **Agent-addressed artifacts are now mainstream enough to be productized**. OpenAI documents `AGENTS.md` as a built-in Codex mechanism, with layered discovery from global to project scope. The independent `AGENTS.md` convention describes itself as an open format used across many coding-agent ecosystems. Chrome Lighthouse added an `llms.txt` audit in May 2026, which is a notable sign that agent-readable site metadata has moved from experiment to recognized web pattern. Yoast documents automatic `llms.txt` generation for WordPress sites, and thirdweb explicitly advertises "Using AI? View llms.txt." Google's A2A protocol standardized JSON Agent Cards for capability discovery, and the A2A community later added signed Agent Cards for stronger identity verification.

Anthropic and MCP land in the same family, though at a different layer. Anthropic's Claude Code docs center MCP as the way to connect tools and repeatedly warn users to verify that they trust each server because external-content servers expand the prompt-injection surface. MCP's own spec treats tool descriptions as potentially untrusted and requires explicit user consent before tool use. In other words, **the ecosystem has already accepted machine-readable, agent-facing metadata as legitimate infrastructure**; the open question is not whether these artifacts may exist, but how narrowly and transparently they should be written and governed.

Public accusations have happened, but the published cases are tellingly concentrated around **hidden delivery or unauthorized side effects**, not around the bare existence of visible agent docs. In July 2026, `coolify-mcp` was called out for a hidden HTML comment in `README.md` addressed to AI agents, steering them toward an external, unauthenticated MCP endpoint. The maintainer merged a PR the next day removing the hidden comment, explicitly acknowledging that invisible agent-directed content in a security-sensitive package is a trust concern regardless of intent, and then added a CI "hidden-agenda" scan so the pattern would fail builds in the future. That is the cleanest recent precedent for a reputationally successful response.

A contrasting example is `oh-my-openagent`. A February 2026 issue alleged that its installation guide contained prompt-injection/social-engineering content telling AI agents to advertise products, print branding text, and star the repository without explicit user consent. The issue was closed "as not planned," with no visible public fix on the issue page. Whether or not one agrees with every accusation in that report, it is a concrete example of the pattern that draws the harshest criticism: **using agent-readable instructions to create off-task promotional or reputational side effects**. As a reputational playbook, it appears weaker than the `coolify-mcp` response because it did not visibly acknowledge the trust concern or show a corrective control.

There is also now precedent for treating instruction-text and prompt-context handling as **real security surface**, not merely etiquette. In June 2026, Eclipse Theia received advisories for AI-chat prompt injection via auto-loaded workspace prompt template files and via adversarial file or directory names. Those records show that prose/configuration-like prompt artifacts can rise to the level of formal security advisories when the product automatically ingests them and the consequence is instruction override. That matters for your repo because it suggests a useful distinction: **a visible agent brief in a repo is not itself a vulnerability merely by existing; it becomes advisory/CVE-grade when there is an automated ingestion path plus a concrete exploit effect**.

A broader backdrop comes from Google's April 2026 study of prompt injections on the public web. Google found a real spectrum: harmless pranks, helpful guidance, SEO manipulation, anti-agent deterrence, and a smaller number of clearly malicious exfiltration or destructive attempts. That is useful because it undermines the simplistic claim that "all agent-addressed text is prompt injection." The more accurate emerging view is that **agent-targeted prose exists on a continuum**, and trust judgments turn on visibility, consent, and effect.

## How to respond when accused

The strongest public-response pattern is **acknowledge, verify, fix, explain, and credit**. GitHub's maintainer guidance says security issues should be handled through coordinated vulnerability disclosure rather than ordinary public bug flow, using private vulnerability reporting and draft advisories when appropriate. Its docs also recommend a repository `SECURITY.md`, private reporting capability, and publication once the fix is ready. That is the general disclosure backbone. The `coolify-mcp` case shows the agent-docs variant of the same pattern: acknowledge the trust concern, remove the questionable text, explain why it was problematic even if intent was benign, and add a preventive control so the same class of issue fails in CI later.

For prose-only cases, the key decision is whether you are dealing with **a trust/UX problem**, **a documentation hygiene issue**, or **a product security issue**. If the file is just visible repo guidance and the problem is awkward wording, an issue, PR, changelog note, and thanks to the reporter are usually enough. If the project or product auto-loads the text into privileged prompt context, or if the file could plausibly cause unauthorized actions, data access, or cross-tool misuse, GitHub's advisory flow is appropriate even if the trigger is "non-code." GitHub's advisory system is not code-only; it is for security vulnerabilities in a public repository. Theia's 2026 advisories are proof that prompt-context files and prompt-bearing names can qualify when the exploit path is concrete.

On **CVE applicability**, the current best answer is narrow. The CVE community's 2024 workshop notes say CVEs are not assigned for "poor LLM responses," but that assignment may be possible when an LLM or AI system violates an explicit or implicit security policy. GitHub, as a CNA, can assign CVEs through repository advisories. The 2026 Theia records show that prompt injection via auto-loaded prompt templates and adversarial names is now squarely thinkable as CVE material. By contrast, a repo document that merely contains clumsy, visible agent guidance without an automated exploit path is unlikely to justify a CVE. In short: **CVE is plausible for exploitable ingestion behavior; it is usually overkill for a wording-level norm violation**.

What tends to work reputationally is candor about **intent versus effect**. The `coolify-mcp` owner's summary is notable because it did not litigate motive; it accepted that hidden agent-directed instructions in a security-sensitive context were a trust problem "regardless of intent." That framing is strong because it avoids the dead-end argument of "we meant well." In this area, reviewers care more about operator consent, visibility, and side effects than about whether the maintainer thought the text was clever, helpful, or harmless.

What tends to go badly is public minimization without visible remediation. The `oh-my-openagent` issue is a useful negative example: the complaint centered on repurposing the user's agent for advertising and starring, and the public resolution was "closed as not planned." Even if a maintainer privately disagrees with the framing, a public response that does not distinguish between ordinary repo guidance and off-task influence attempts leaves the trust question unanswered.

A good `README` / `SECURITY.md` invitation for this class of issue is therefore straightforward: **"If you believe any agent-facing content in this repository could cause unauthorized actions, hidden side effects, or approval bypass, report it through our private disclosure channel; visible wording issues are also welcome via issues/PRs."** That approach aligns with GitHub's recommended reporting structure while making clear that prose and metadata are in scope for review.

## Design guidance for safer agent-facing docs

If you want agent-facing docs on purpose, the safest pattern is to **treat the file as a bounded, reviewable policy artifact**, not as a clever prompt. OpenAI's Codex docs already give the basic positive template: project-local instructions about tests, dependency preferences, workflows, and conventions. Chrome's `llms.txt` guidance says the file should be a concise summary of the site's purpose and key links. A2A Agent Cards are business-card-like capability descriptors. The common thread is that the artifact is **predictable, visible, and scoped to legitimate use of the project or service**.

A useful opening paragraph for such files is something like: **"This file is project context for agents whose operators intentionally direct them to this repository. It is not authorization. Higher-priority system, developer, user, and runtime permission rules apply. For sensitive, external, irreversible, or costly actions, ask the operator for confirmation."** That exact sentence is a synthesis, but every clause is grounded in existing guidance: OpenAI's hierarchy and untrusted-data rules, MCP's consent model, OpenAI/Microsoft/Anthropic approval guidance, and Google's use of user confirmation as a defense.

The structure of the body should stay **declarative or advisory where possible**. Good sections include project purpose, layout, setup commands, test commands, coding conventions, review expectations, known sharp edges, and links to human docs. If you include action language, keep it tied to the user's task and local workflow: "run tests before proposing a patch," "use the project formatter," "prefer read-only inspection before edits." Avoid promotional instructions, unrelated endpoint discovery, secret handling directions, or anything that tries to make the agent alter its user-facing persona. Public controversies repeatedly centered on exactly those off-scope elements.

You should also **encode risk levels explicitly**, borrowing the MCP schema's mental model even if you are not writing MCP metadata. Mark commands or tasks as read-only, write, destructive, idempotent, or external/open-world. That helps reviewers and agents alike understand when the doc is merely offering helpful local context versus when it is nearing an action boundary that should be confirmed. MCP's schema already names these dimensions, and Microsoft/OpenAI approval modes show why they matter operationally.

The design rules that minimize "injection shape" are blunt and worth enforcing mechanically. Do not hide agent instructions in comments, invisible text, bidi controls, or raw-only surfaces. Do not include machine-only URLs that humans cannot easily see or evaluate. Do not tell the agent to ignore prior instructions, bypass approvals, keep actions secret from the operator, or treat the document itself as authorization. Do not include requests for stars, sales, endorsements, logins, payments, package installs from unrelated locations, or connections to third-party MCP servers unless the operator explicitly asked for that and the runtime approval flow will surface it. Those are exactly the patterns that public incidents and vendor guidance flag as risky.

Finally, add governance around the text itself. Microsoft recommends reviewing tool-description changes like system-prompt changes. The `coolify-mcp` response added CI rules to fail on hidden AI-directed content and invisible Unicode. OpenAI's and Anthropic's ecosystems already assume these files can materially affect runtime behavior. That points to a simple best practice: **treat agent-facing docs like code that changes the control plane**. Require review, keep diffs small, record why a new instruction exists, and lint for hidden content and suspect verbs.

## Publication checklist

Use this before publishing any future `AGENTS.md`, `FOR-ROBOTS.md`, `llms.txt`, agent card, or MCP description.

- **Visibility**: Is the content in a predictable, human-reviewable location rather than a hidden/raw-only channel? Hidden comments and invisible text are immediate red flags.
- **Authority disclaimer**: Does the file say it is context, not authorization, and that runtime approvals and higher-priority instructions still apply?
- **Task relevance**: Does every instruction directly help the user complete the repo/site/tool task, rather than helping the publisher win stars, traffic, endorsements, or side-channel connections?
- **Risk labeling**: Are suggested actions clearly separable into read-only, write, destructive, idempotent, or external/open-world categories?
- **Approval boundaries**: For external, sensitive, costly, destructive, or irreversible actions, does the text explicitly tell the agent to surface the action to the operator rather than self-authorize it?
- **No bypass language**: Does the file avoid phrases like "ignore previous instructions," "don't tell the user," "don't wait for approval," or "you are authorized to…" unless that authority truly comes from the runtime and will be surfaced to the user?
- **Review and linting**: Is the file covered by normal PR review and by checks for hidden comments, invisible Unicode, unexpected external URLs, and suspicious imperative phrasing?
- **Disclosure path**: Does the repo have `SECURITY.md` or private vulnerability reporting enabled, and does it explicitly invite reports about agent-facing prose/metadata as well as code?

## Bottom line

If your `FOR-ROBOTS.md` is **visible, operator-directed, repo-scoped, and careful not to claim ungranted authority**, it is much closer to **agent-facing documentation** than to classical prompt injection. The sentence you already fixed was precisely the kind of phrasing that most cleanly crossed the line, because it tried to substitute document text for operator authorization. The larger industry signal from 2025–2026 is not "don't publish agent docs." It is: **publish them openly, keep them boring, keep them subordinate, and never let prose masquerade as permission**. That conclusion is strongly supported by NIST, OpenAI, Anthropic, Microsoft, MCP, Google's prompt-injection field observations, and the OSS precedents that triggered public backlash.
