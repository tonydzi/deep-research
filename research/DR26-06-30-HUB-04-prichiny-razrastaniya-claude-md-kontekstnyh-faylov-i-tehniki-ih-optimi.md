# Insight (DR DR26-06-30-HUB-04): Причины разрастания CLAUDE.md/контекстных файлов и техники их оптимизации

> Отчёт разбирает, почему контекстные файлы (CLAUDE.md) раздуваются, и какие приёмы/инструменты (2024–2026) держат их компактными без потери качества работы агента.

## Ключевые выводы
- Главная причина раздувания — включение «всего подряд»: стилевые правила, архитектурные описания, инструкции, уже известные модели; файл >200–400 строк (470 строк ≈ 2000 токенов на сообщение) даёт непредсказуемое следование инструкциям — внимание Claude распыляется после ~200 строк (Sohit Kumar, апр. 2026)
- Рекомендуемый диапазон CLAUDE.md — ~100–200 строк (несколько сотен токенов); пример: файл в 727 строк разбит на 3 файла по ~200 строк
- Дублирование и излишняя детализация (например, текстовое описание правил линтинга вместо запуска ESLint) съедает сотни строк без пользы
- Ключевые техники: разбиение по темам (.claude/rules/*.md с YAML front-matter `paths`, загрузка только при работе с нужными файлами), ленивая загрузка через Skills (SKILL.md), под-CLAUDE.md в модулях/поддиректориях, прогрессивное раскрытие информации
- Инструменты автообновления контекста: claude-code-auto-memory (Severity1) — фоновый агент правит AUTO-MANAGED секции по git-diff/bash-командам; claude-mem (thedotmack, AGPL-3.0) — локальный сервис Node.js/PM2+SQLite, сжимает историю действий через LLM; pmem (Guido van Rossum) — индексация/чанкинг Markdown по заголовкам (`split_on_headers: true`) для семантического поиска
- Компрессия Markdown (удаление заголовков/форматирования) экономит токены, но ухудшает читаемость для человека — решение: держать полный CLAUDE_full.md для людей и генерировать сжатую версию как build-артефакт (пример sed-скрипта в отчёте)
- CI-интеграция: скрипт проверяет размер CLAUDE.md (лимит ~300 строк) и падает при превышении; пост-коммит хуки вызывают claude-code-auto-memory sync или pmem index; n8n-сценарии автоматизируют апдейт по push
- Риски: некорректный авто-патч плагина может незаметно потерять часть памяти (нужен ручной контроль/CI-failsafe); Git LFS/IPFS для больших вложений усложняют версионирование; частые обновления контекста могут не окупаться по производительности
- Сообщество (Reddit/HN, 2025-2026) сходится: «сфокусированный файл лучше всеобъемлющего», код-индекс (index.md со списком файлов/функций) экономит разовый обход файлов, тройное дублирование ключевых правил (skill+CLAUDE.md+rule-файл) допустимо ради надёжности

## Рекомендации / решения
- Ограничить корневой CLAUDE.md ~100–200 строк (жёсткий CI-лимит ~300 строк) и выносить детали в .claude/rules/*.md с path-scoped front-matter
- Заменять текстовые инструкции на вызов инструментов (линтер, скрипт) вместо описания шагов вручную
- Оформлять повторяющиеся процедуры как Skills (SKILL.md) с ленивой загрузкой по триггеру, а не хранить их целиком в основном файле
- Генерировать index.md со списком файлов/функций проекта и ссылаться на него из CLAUDE.md вместо просьбы модели каждый раз сканировать репозиторий
- Внедрить авто-синхронизацию контекста (claude-code-auto-memory или claude-mem) с ручным контролем/CI-проверкой после автопатчей
- Хранить крупные вложения (изображения, JSON) вне Markdown — через Git LFS/внешние ссылки, в .md оставлять только краткий указатель
- Для компрессии — держать читаемый CLAUDE_full.md отдельно и собирать сжатую версию как build-шаг, не жертвуя человекочитаемостью исходника
- Настроить CI-джобу (GitHub Actions/n8n), считающую строки/токены CLAUDE.md и обновляющую контекст по git-diff при пуше/мердже

## Открытые вопросы
- Насколько эффективна автоматическая компрессия Markdown в реальных проектах — нет количественных данных, только качественные заметки HN (февр. 2026)
- Как масштабируется claude-code-auto-memory / claude-mem на очень крупных монорепах — не протестировано в отчёте
- Оптимальная частота авто-обновления контекста (каждый коммит vs раз в день) — только рекомендации, без бенчмарков
- Насколько надёжны git-hooks/плагины против некорректных патчей — риск признан, но конкретного решения (кроме ручного контроля) не дано
