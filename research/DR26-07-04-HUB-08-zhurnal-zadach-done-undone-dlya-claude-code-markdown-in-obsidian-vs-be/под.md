## Что реально делает комьюнити Claude Code

### Встроенные tasks Claude Code и их реальный потолок

По состоянию на Claude Code v2.1.142+ и Agent SDK 0.3.142+ встроенный todo-механизм перешёл с `TodoWrite` на структурированные `TaskCreate`, `TaskUpdate`, `TaskGet` и `TaskList`. Это уже не просто переписывание массива задач, а нормальные атомарные события со статусами `pending`, `in_progress`, `completed` и возможностью читать снапшот списка. В hooks есть события `TaskCreated` и `TaskCompleted`, а также общий `UserPromptSubmit`, так что Claude Code уже умеет быть источником событий для внешнего журнала. citeturn16view2turn16view1turn35view0

Но этот встроенный слой не надо переоценивать. Anthropic описывает сессии как локально сохраняемые разговоры, привязанные к директории проекта; по умолчанию транскрипты лежат в «внутренний путь лаборатории», а auto memory тоже живёт локально в «внутренний путь лаборатории»<project>/memory/` и **не шарится между машинами**. Общий multi-host resume возможен, но уже через отдельный `SessionStore` в SDK, то есть это не “из коробки общий backlog”, а отдельная интеграционная работа. Отсюда практический вывод: нативные tasks хороши как **внутрисессионный рабочий чеклист и UI-сигнал прогресса**, но не как долговременный done+undone ledger для вашей мульти-машинной схемы. citeturn17view1turn17view0turn36search0turn36search6

Комьюнити это считывает примерно так же. В HN прямо звучит, что у Claude Code уже есть built-in tracker для short/mid-term tracking, а на Reddit пользователи, которые строят более сложные пайплайны, либо зеркалят actionable items в native tasks, либо держат рядом внешний слой памяти/спеков/тикетов. Практический паттерн: встроенные tasks — для исполнения, внешний журнал — для долгой памяти и координации. citeturn6view4turn19view1

### PLAN.md, TODO.md, BACKLOG.md и спек-файлы

Это, без шуток, самый устойчивый паттерн у сильных пользователей Claude Code и соседних агентных CLI. Anthropic сама продвигает режим “plan before editing”, `/plan`, разделение plan mode и execution mode, и даже автоматическое именование сессии из принятого плана. В пользовательских практиках 2025–2026 повторяется одна и та же схема: **написать план в файл, очистить контекст, начать новую сессию, сказать “читай план и выполняй фазу N”**. Для длинной работы это снижает drift и делает фазы воспроизводимыми. citeturn21search0turn21search1turn21search10turn20search2turn20search18turn20search11

На Reddit и HN это звучит почти одинаково: “spec > plan > code”, “fresh session per phase, but the plan file is the through-line”, “the plan file basically becomes the spec”. Это не просто красивый ритуал. Это прямое следствие того, что контекст конечен, старые данные гниют, а Anthropic в 2025 отдельно описала context engineering и structured note-taking как внешний persistent memory вне окна контекста. citeturn6view1turn20search18turn26view0turn26view1

Под ваш кейс это означает: **план-файл нужен**, но не как единственный регистр задач. Он должен остаться рядом с задачами как “почему и что именно хотели сделать”, а не подменять собой журнал состояний. Когда один файл начинает одновременно быть спецификацией, TODO, историей решений и местом handoff между сессиями, он быстро превращается в противоречивую простыню. Это ровно та проблема, против которой Beads и другие инструменты вообще появились. citeturn7view2turn26view1

### Beads

Beads — самый заметный “AI-native issue tracker” этого цикла. В актуальной документации он описан как **Dolt-powered issue tracker для AI-supervised coding workflows**, с зависимостями, типами, приоритетами, `bd ready` для unblocked work, интеграциями с Claude Code и hash-based IDs для параллельной агентной работы. Репозиторий крупный и живой: в открытом GitHub-репозитории на момент просмотра было 25k+ stars, а документы прямо подают его как persistent structured memory for coding agents. citeturn7view0turn7view1turn8view2turn27view2

Сильные стороны Beads для агентов настоящие, а не маркетинговые. Он умеет dependency-aware execution, structured JSON output для агентов, multi-agent coordination, а в server mode поддерживает multiple concurrent writers. Из комьюнити есть положительные кейсы: Beads хвалят за то, что он создаёт “atomic context” на задачу и уменьшает риск потери контекста/галлюцинаций; есть и рабочие схемы, где issues режут на epics/tasks/subtasks, а Claude/Codex двигают их по одному. citeturn7view0turn8view2turn19view2turn19view3

Но под ваш конкретный AK-47-кейс Beads плох по трём причинам. Во‑первых, он **CLI-first** и остаётся достаточно инженерным продуктом. Во‑вторых, у него уже есть два режима хранения: embedded Dolt с single-writer lock и server mode с отдельным `dolt sql-server`; это сильнее, чем markdown, но и заметно сложнее в обслуживании. Во‑третьих, его синхронизация идёт через Dolt remotes/`bd dolt push`/`pull`, а `.beads/issues.jsonl` уже не source of truth, а export/interchange. Это конфликтует с вашей ставкой на “локально + git/Syncthing + чинится не-технарём”. Комьюнити-обратная связь тоже не идеальна: есть прямые отзывы, что Beads «раздулся», и люди ушли обратно в простые tickets/markdown. citeturn8view2turn7view0turn19view0

Итог по Beads: **сильный выбор для инженерной команды, которая живёт в CLI и хочет dependency-aware external memory для роя агентов**. Для одного оператора, который работает глазами через HTML и Obsidian, это почти наверняка будет избыточно и дороже в поддержке, чем даст пользы. citeturn26view2turn19view0turn8view2

## Какая схема журнала у вас должна быть

Для команды из одного человека плюс AI-агенты минимально достаточная схема должна быть **богаче обычного TODO-списка, но беднее полноценного issue-трекера enterprise-класса**. Здесь важно не “максимум полей”, а правильный раздел между тем, что действительно несёт управленческую информацию, и тем, что является шумом. Общая тенденция 2025–2026 такая: выносить долгую память и состояние во внешний persistent слой, но держать его **простым и композиционным**, а не превращать в фреймворк поверх фреймворка. citeturn26view2turn26view1

Я бы оставил такими **обязательные** поля:

- `id`
- `title`
- `state`
- `type`
- `priority`
- `created_at`
- `touched_at`
- `born_from`
- `blocks`
- `blocked_by`
- `supersedes`
- `evidence`
- `outcome`
- `review_after`

Этого хватает, чтобы покрыть и **undone**, и **done journal**, и родословную, и handoff, и aging. Для Obsidian это естественно: properties поддерживают текст, ссылки, даты, числа, чекбоксы; internal links и backlinks дают вам двустороннюю сеть связей; Bases умеет строить по этим свойствам table/cards views, а Dataview умеет индексировать и агрегировать масштабные аннотированные коллекции заметок. citeturn22view6turn22view4turn22view5turn22view0turn22view3

Я бы не вводил отдельное поле `unblocks`, потому что оно **выводимо** как обратная сторона `blocked_by`/`blocks`. То есть “done → что разблокировала” лучше считать производным фактом на момент закрытия и показывать в дашборде, а не заставлять человека поддерживать ещё одно поле вручную. По той же причине я бы не заводил отдельные `epic`, `sprint`, `estimate_story_points`, `assignee`, `team`, `milestone` и прочую корпоративную фауну, пока у вас один оператор. Это почти гарантированный путь к протуханию журнала. citeturn26view2turn19view0

Для связей я бы оставил четыре типа как **ядро**:

- `born_from` — откуда родилась задача
- `blocks` / `blocked_by` — блокировки
- `supersedes` — чем заменила старую формулировку
- `related` — слабая смысловая связь, если нужна

Этого достаточно. Всё остальное является либо вычислением, либо текстом в `outcome`, либо обычной ссылкой в теле заметки. GitHub Issues и Beads тоже в основе держат именно dependency/relationship primitives, а не десятки типов связей. citeturn23view0turn7view0

Статусы я бы рекомендовал такие:

- `inbox`
- `open`
- `wip`
- `blocked`
- `done`
- `dropped`
- `someday`
- `archived`

Здесь критично **не смешивать `someday` и `dropped`**. GTD-шная Someday/Maybe полка нужна именно как место для честно захваченных, но не принятых к исполнению идей; official GTD материалы прямо подчёркивают, что туда можно класть вещи, которые вы, возможно, никогда не сделаете, но хотите сохранить и регулярно пересматривать. Отдельный `dropped` нужен для осознанного отказа: “решили не делать”. Это две принципиально разные семантики, и смешивание их убивает доверие к журналу. citeturn31search1turn31search2turn31search7

**Evidence-gated close** в вашем случае надо не просто сохранить, а сделать жёсткой нормой. Закрытие `done` без `evidence` должно считаться неполным. На практике evidence может быть: ссылка на коммит/PR, HTML-артефакт, заметка-результат в волте, файл-выход, скрин, diff, опубликованный документ, или проверочный чеклист. Backlog.md отдельно двигает acceptance criteria и final summary; GitHub и Claude workflows тоже строятся вокруг traceable artifacts. Ваш нынешний принцип здесь лучше среднего рынка — его не надо ослаблять. citeturn29view3turn23view3

Для aging я бы не делал “автоподнятие приоритета” в лоб. Лучше правило такое: если `touched_at` старее порога, задача получает флаг `stale=true` и попадает в отдельный обзорный lane. Пороги можно завязать на приоритет:

- P0: stale через 1 день
- P1: через 7 дней
- P2: через 21 день
- P3: через 45 дней
- `someday`: через 90 дней на re-review, но не на “эскалацию”

Регулярный review вообще важнее, чем сложные статусы. GTD Weekly Review официально строится именно вокруг регулярного обновления project lists, next actions и someday/maybe; без review система перестаёт быть trustable. citeturn32search0turn32search2

## Хранилище и единый источник истины

### Почему SQLite не должен оставаться главным реестром между машинами

Если у вас 4+ машины и поверх них Syncthing, **SQLite как главный синкаемый артефакт — плохая идея**. Не потому, что SQLite плох сам по себе, а потому что он хорош, когда **движок и файл находятся на одной машине**. Официальная документация SQLite прямо предупреждает о проблемах sync/locking на network filesystems, о риске corruption и отдельно отмечает, что на Windows locking сетевых файлов считается ненадёжным. FAQ SQLite тоже прямо советует избегать shared SQLite на NFS/сетевых сценариях при конкурентном доступе. citeturn34view0turn34view1

Syncthing, в свою очередь, работает на уровне файловых блоков и при конфликте переименовывает одну из версий в `.sync-conflict-...`; такие conflict copies потом синкаются как обычные файлы дальше по кластерам. Это нормальная модель для markdown/text, где конфликт можно визуально разрулить. Для live database file это уже плохая механика. Практически: **не синкайте write-active `tasks.db` как источник истины**. Если SQLite вам нужен, пусть он живёт на всегда-включённом хабе как локальный read model / index / materialized view, который при необходимости можно пересобрать из markdown. citeturn34view2turn34view0turn34view1

### Почему markdown-задачи в волте лучше всего совпадают с вашим стеком

Obsidian уже умеет то, что вам нужно для человеческой стороны системы: properties, internal links, heading/block links, backlinks, базы с cards/table views. Всё это живёт в локальных markdown-файлах и естественно дружит с вашим волтом и Syncthing. Важнейший бонус: **перелинковка у вас “бесплатная”**, а не надстроенная поверх отдельного tracker’а. `born_from` может быть ссылкой на заметку, дневник, session note, research note, проект, decision note; `done` может ссылаться на то, что задача разблокировала. Obsidian автоматически обновляет internal links при rename, а backlinks дают обратную навигацию из карточки задачи без отдельной логики. citeturn22view4turn22view5turn22view6turn22view0

Под ваш масштаб волта это тоже не выглядит безумием. Dataview прямо пишет, что работает на metadata в Markdown и масштабируется к **hundreds of thousands of annotated notes**. Это не означает, что любая криво спроектированная query будет быстрой, но ваш объём 130k заметок уже лежит в зоне, где такой подход концептуально допустим. А одна задача на один файл ещё и отлично локализует sync-конфликты: если одновременно меняют разные задачи, это разные файлы; если конфликт случился, он текстовый и разборчивый. citeturn22view3turn34view2

### Где здесь место текущему SQLite

Не выбрасывать. **Понизить в статусе**.

Правильная роль текущего `tasks.db` в вашей архитектуре:

- кэш для быстрого фильтра/сортировки/статистики
- двигатель ночного аудита
- источник статического HTML
- место для денормализованных индексов и вычисляемых флагов (`stale`, `blocked_count`, `age_days`, `missing_evidence`)

Неправильная роль:

- первичный write-target с мульти-машинным sync
- единственный store для born-from / backlinks / narrative outcome
- человеческий интерфейс редактирования

Иными словами: **markdown — canonical write model; SQLite — regenerated read model**. Это тот редкий случай, когда event-sourced/derived-подход реально упростит жизнь, а не усложнит её. citeturn34view0turn34view1turn22view0turn22view3

### Почему не git-backed tracker как основной слой

Git-backed issue trackers хороши, когда вы живёте в кодовом repo и готовы принимать Git/Dolt как транспорт состояния. Но ваш центр тяжести — не один repo, а большой Obsidian-вольт, плюс несколько машин, плюс человеческая визуальная работа. Beads сегодня уже вообще опирается не на “git как БД” в наивном виде, а на Dolt как источник истины; Backlog.md остаётся git/ecosystem-centric и советует пользоваться своей CLI/MCP/Web-обвязкой для консистентности метаданных. Для вас это всё **не даёт бесплатного выигрыша**, который уже не даёт сам Obsidian-волт. citeturn8view2turn9view0turn29view1

Моя чёткая рекомендация по storage therefore такая:

**source of truth**  
`/Tasks/*.md` в Obsidian-волте, одна заметка на задачу

**derived stores**  
`tasks.db` на always-on hub  
`dashboard/*.html` как статический export  
`audit/*.jsonl` как ночные отчёты/аномалии

**capture/event layer**  
Claude Code hooks → создают/обновляют task notes сразу при появлении сигнала в сессии citeturn35view0

## Как это красиво показывать не-технарю

Главный принцип здесь такой: **редактирование там, где естественны ссылки и взгляд; итоговая витрина там, где стабильна картинка**. Это ведёт к двухслойному UI.

### Что делать в Obsidian

Obsidian должен стать **живой рабочей панелью**, потому что там уже живут ваши контекстные заметки. Bases как core plugin умеет table/cards views на локальных markdown+properties. Tasks умеет query across vault, done dates, фильтры и правку из query result обратно в source file. Dataview даёт быстрые агрегаты и сложные выборки, но сам по себе больше про display, а не про редактирование. Это почти идеальный набор для “оператор работает глазами”. citeturn22view0turn22view1turn22view3

Я бы сделал в волте три главные страницы:

**`📋 Несделанные`**  
Cards/table view по `state in [inbox, open, wip, blocked]`, с колонками: `priority`, `type`, `age_days`, `blocked_by`, `born_from`. Нужны быстрые фильтры по `type` и `priority`, плюс saved views “stale”, “blocked”, “new today”. citeturn22view0turn22view3

**`✅ Журнал сделанных`**  
Timeline/list grouped by `closed_at week` или `done week`, с обязательным превью `outcome` и `evidence`. Это не просто кладбище чекбоксов; это **ledger результатов**. Здесь особенно полезны backlinks: из результата видно, что было сделано, а из любой проектной заметки видно, какие задачи к ней привели. citeturn22view4turn22view5

**`🗄 Когда-нибудь`**  
Отдельный cards/list view по `state=someday`, сортировка по `review_after`, не по приоритету. Смысл полки Someday/Maybe — удерживать идеи без ложного чувства обязательства, но при регулярном обзоре. Если вы смешаете её с `open`, система станет бесчестной; если никогда не будете смотреть, она станет свалкой. citeturn31search2turn32search0

Kanban в Obsidian возможен, но я бы не делал его главным интерфейсом. Community Kanban plugin всё ещё существует, но репозиторий прямо пишет, что ищет новых maintainers. Для вашего критерия “живее и дешевле в поддержке” это минус. Лучше сделать основу на Bases cards/table + Tasks/Dataview, а kanban только как дополнительный view. citeturn22view2turn22view0turn22view1

### Что оставить в HTML

Статический HTML-дашборд нужно оставить, но **сузить его до витрины**, а не редактора. Его преимущества у вас уже есть: он самодостаточный, открывается где угодно, не требует Obsidian, удобен для ночного snapshot’а и визуально дешёв в поддержке. Просто не надо пытаться сделать из него primary editing surface. Эту работу Obsidian делает лучше, потому что прямо редактирует исходный markdown и сразу сохраняет связи. citeturn22view0turn22view1

Лучший layout для HTML я бы предложил такой:

- **верхняя строка метрик**: open / wip / blocked / done last 7d / stale / someday
- **левая колонка**: `📋 Несделанные` в 4 lanes — Inbox, Active, Blocked, Stale
- **правая колонка**: `✅ Недавно сделанные` как timeline, с outcome + evidence icons
- **нижняя полоса**: `🗄 Когда-нибудь`, компактные cards с next review date
- **карточка по клику**: показывает `born_from`, `blocks`, `related`, `supersedes`, `evidence`

То есть не классический “корпоративный kanban на всё”, а **гибрид board + journal**. Для вашего вопроса “сделанные + несделанные” это важнее, чем канбан-пуризм. citeturn23view2turn22view0

## Где такие журналы умирают

Первая точка смерти — **ручной capture**. Если новая задача рождается в сессии Claude Code, а записать её “потом”, потом почти никогда не наступает. Anthropic в 2025–2026 много пишет о внешней памяти, structured note-taking и persistent memory outside context window именно потому, что это не optional luxury, а необходимая часть длинных агентных циклов. Ваше новое требование про мгновенный capture абсолютно правильное. Реализовать его надо через hooks: `UserPromptSubmit` для раннего захвата и `TaskCreated`/`TaskCompleted` для зеркалирования внутренних task-событий Claude Code во внешний markdown-ledger. Hooks могут жить в project `.claude/settings.json`, то есть их можно разделять между машинами через ваш Git/Syncthing-поток. citeturn26view1turn35view0turn36search5

Вторая точка смерти — **plugin bloat и process theater**. На Reddit сильные пользователи прямо пишут, что Bare Claude Code достаточно хорош для small projects, что они в итоге оставили себе лишь handful of skills, что context bloat от многих надстроек болезненен, а тяжёлые frameworks — overkill для простых задач. Это хорошо совпадает с рекомендацией Anthropic: использовать simplest solution possible и увеличивать сложность только когда это оправдано. citeturn19view0turn26view2

Третья точка смерти — **смешивание разных сущностей в один файл**. Когда один `PLAN.md` начинает быть и спекой, и backlog’ом, и дневником прогресса, и журналом решений, система быстро расходится. У Beads/Task Master/Backlog.md весь смысл как раз в том, чтобы разнести “спека”, “задача”, “комментарий”, “итог” по нормальным сущностям. Для вас это решается проще всего через note-per-task плюс отдельные spec/decision notes. citeturn7view2turn9view0turn10view1

Четвёртая точка смерти — **свалка Someday/Maybe**. Official GTD-материалы прямо предупреждают: Someday/Maybe надо регулярно пересматривать; иначе вы перестаёте доверять этой полке и перестаёте туда честно складывать идеи. Значит, `someday` должен иметь `review_after`, а weekly review должен включать отдельный проход по этой полке. citeturn31search2turn32search0turn32search2

Пятая точка смерти — **нет weekly review, только “новая красивая система”**. GTD Weekly Review называется у David Allen критическим фактором успеха метода не случайно: без регулярной проверки список быстро теряет доверие. Для вас это нужно перевести в механику, а не в лозунг:

- nightly audit — уже есть, сохранить
- weekly review — обязательно добавить как отдельный ritual
- WIP limit — максимум 3 активных `wip` одновременно
- stale lane — отдельный обзор вместо тихого гниения
- evidence gate — без proof нельзя в `done`
- overdue someday review — в отдельный список, не растворять в backlog citeturn32search0turn32search2

### Топ-рекомендации под ваши ограничения

**Первая рекомендация**  
Сделать **Obsidian markdown task note-per-file** главным журналом `done + undone`, а ваш `tasks.db` оставить как **перестраиваемый индекс**. Это даёт лучший UX для не-технаря, минимальный vendor/ops risk, и натуральную связность с “вторым мозгом”. citeturn22view0turn22view3turn22view4turn22view5turn34view2

**Вторая рекомендация**  
Использовать **Claude Code hooks как auto-capture bus**, а нативные tasks Claude Code — как front-end для оперативного исполнения. То есть не спорить с нативным task layer, а зеркалить его события в ваш долговременный markdown-ledger. Это позволяет выполнить требование “задача записывается в момент формулирования в чат-сессии”, не делая built-in tasks источником истины. citeturn35view0turn16view2turn17view1

**Третья рекомендация**  
Оставить **два UI-слоя**: Obsidian для живой работы и статический HTML для snapshot/reporting. Не пытаться заставить HTML быть редактором, а Obsidian — идеально выглядеть для всех сценариев. У этих поверхностей разные задачи, и вместе они дешевле, чем одна “универсальная” сложная. citeturn22view0turn22view1turn22view3

### Одна рекомендуемая архитектура

**Источник истины**  
`Vault/Tasks/*.md`  
Одна задача = один markdown-файл.

**Слой контекста**  
`Vault/Projects/*`, `Vault/Research/*`, `Vault/Daily/*`, `Vault/Decisions/*`  
Задача ссылается на origin и артефакты обычными wikilinks.

**Capture**  
Claude Code hooks:

- `UserPromptSubmit` → ранний capture задачи/кандидата задачи
- `TaskCreated` → создать/обновить task note
- `TaskCompleted` → потребовать evidence и заполнить close metadata
- при желании `SessionStart`/`SessionEnd` → писать session notes / audit trace

Hooks проектно разделяемы через `.claude/settings.json`. citeturn35view0

**Read model**  
Hub-local `tasks.db`, который:
- индексирует frontmatter и связи
- считает stale/aging
- строит nightly audits
- генерирует static HTML

**Views**
- Obsidian Bases: Active / Done journal / Someday
- Dataview: отчёты и агрегаты
- Tasks plugin: быстрые интерактивные task queries
- HTML: board + journal snapshot

### План миграции с текущего SQLite-реестра

**Шаг первый**  
Зафиксировать текущую схему SQLite как legacy canonical snapshot и сделать одноразовый export всех задач в markdown-files. Для каждой записи создать задачу-заметку с сохранением `id`, `status`, `priority`, `created_at`, `closed_at`, `evidence`, plus migration note в теле. Старый `task_id` оставить как стабильный внешний ключ. Это позволит не ломать ссылки в текущем HTML и аудитах.

**Шаг второй**  
Добавить в markdown-схему новые поля, которых вам не хватает сейчас: `born_from`, `blocks`, `blocked_by`, `supersedes`, `type`, `review_after`, `outcome`, `someday`. На старых задачах эти поля можно частично оставить пустыми; не пытайтесь ретрокодировать всю историю идеально. Критично только начать правильно с новых записей.

**Шаг третий**  
Перевернуть направление синхронизации:  
раньше было **SQLite → HTML**,  
должно стать **Markdown → SQLite → HTML**.

То есть nightly job больше не “ведёт реестр”, а **индексирует заметки**, валидирует схему, ищет missing evidence / stale / dangling links / broken relations и уже потом строит HTML.

**Шаг четвёртый**  
Поднять hooks в Claude Code на всех машинах через проектный `.claude/settings.json`, чтобы новые задачи появлялись сразу в `Vault/Tasks/`. Поскольку hooks в project scope shareable, это нормально распространяется вашим текущим Git/Syncthing-потоком. На Windows избегайте shell-экзотики; Anthropic отдельно замечает, что в exec form на Windows нужно указывать реальный executable, а `.cmd/.bat`-shim’ы требуют shell form или вызов `node` напрямую. citeturn35view0

**Шаг пятый**  
Сделать в Obsidian три основные страницы и обучить только одному правилу:

- всё новое — либо сразу task note, либо попадает в `inbox`
- `done` без evidence запрещён
- `someday` и `dropped` не путать
- одновременно `wip` не больше трёх
- weekly review обязателен

**Шаг шестой**  
Через 2–4 недели перевести `tasks.db` из “главной правды” в “перестраиваемый кэш” официально. Старый write-path оставить только как аварийный fallback на хабе, затем удалить.

## Ограничения и открытые вопросы

Есть одна реальная неопределённость: я не видел в официальной документации Claude Code прямой формулировки “built-in tasks предназначены для межсессионного общего backlog”. Документы убедительно показывают, что они встроены в сессионный agent loop, а multi-host persistence отдельно вынесена в session storage SDK и auto memory остаётся machine-local; поэтому вывод, что native tasks — не лучший глобальный backlog under your constraints, является **сильным выводом из документации и практики**, а не буквальной цитатой одной страницы. citeturn16view2turn17view0turn36search0

Вторая неопределённость — точный UX ваших hooks на не-технической стороне. Технически hooks решают задачу capture, но удобство конкретного trigger pattern — “все prompts”, специальные префиксы, отдельная skill-команда, capture only on explicit user intent — надо выбирать уже по вашим реальным разговорам с Claude. Высокоуровневый вывод от этого не меняется: **capture должен быть автоматическим или полуавтоматическим, иначе система умрёт**. citeturn35view0turn32search0turn32search2

Если сжать всё до одного решения: **перенесите главный журнал из SQLite в markdown-задачи внутри Obsidian, дайте Claude Code hooks мгновенно писать туда новые задачи и статусы, а SQLite и HTML оставьте как быстрые производные представления.** Это самый надёжный, красивый и ремонтопригодный путь под ваш стек в 2025–2026. citeturn26view2turn22view0turn22view3turn34view2
