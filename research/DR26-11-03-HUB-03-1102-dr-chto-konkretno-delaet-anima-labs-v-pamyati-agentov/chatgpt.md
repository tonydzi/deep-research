## Architecture in detail

### The fundamental data model: history is authoritative; context is a view

**[established]** The cleanest mental model is:

`raw events/messages → durable archive → derived summary artifacts → per-turn projection → provider-normalized request`

The raw history is not “compressed in place.” Context Manager’s README says every message is stored in Chronicle and a strategy decides what a compile sends; `hermes-autobio` states the stronger invariant: “The archive is authoritative; the live view is a projection.” (GitHub, accessed 2026-11-03: https://github.com/anima-research/context-manager ; https://github.com/antra-tess/hermes-autobio) citeturn776046view2turn586456view0

That means summary generation and prompt construction are conceptually separate operations. A model may precompute a summary for a region without forcing that region to become summarized in the next prompt. The 2026 adaptive-resolution redesign explicitly corrected an older implementation that conflated “write a higher-level summary into the archive” with “replace lower-resolution items in the visible context.” [established] [single-source] (design rev. 2, 2026-05-12: https://github.com/anima-research/context-manager/blob/main/docs/adaptive-resolution-design.md) citeturn586456view2

This is much closer to **multi-resolution event sourcing** than to a traditional “memory DB.” Raw events are durable facts of experience; summaries are materialized views; the prompt is a query/projection over those views.

### Hierarchical autobiographical compression

The original/fixed hierarchy, visible in the earlier design lineage, is approximately:

- L0 = verbatim conversation.
- A raw region of roughly **6K tokens** is summarized to an L1 memory of roughly **2K tokens**.
- **6 L1** summaries are merged into an L2.
- **6 L2** summaries are merged into an L3.
- Higher-level stable memories are ordered before lower-level/changing ones to reduce prompt-prefix churn.

Those figures are from the Antra/OpenClaw autobiographical-memory design lineage and should be treated as **implementation defaults, not a law of Connectome**. [emerging] [single-source] (GitHub, accessed 2026-11-03: https://github.com/antra-tess/openclaw-memory-hierarchical).

The current Context Manager design changed the abstraction. Rev. 2 states that it moved from fixed L0–L3 to **unbounded \(L_n\)**, while retaining default fan-out \(N=6\); each chunk can have a currently selected resolution. The resulting prompt can contain a heterogeneous landscape—some old intervals at L3/L4, some at L2/L1, and a recent L0 tail. (design revision dated 2026-05-12: https://github.com/anima-research/context-manager/blob/main/docs/adaptive-resolution-design.md) citeturn586456view2

This redesign was triggered by a real pathology. The document records a live “Lena” session of about **430K tokens**, with a configured recent budget of **475K**, that nonetheless collapsed nearly everything through L1→L2→L3 because merging was driven by count thresholds rather than actual context pressure. The design calls this a contradiction of the intended adaptive-resolution model. [established] [single-source] (2026-05-12 design/postmortem: https://github.com/anima-research/context-manager/blob/main/docs/adaptive-resolution-design.md) citeturn586456view2

That failure is important: the desired system is **pressure-driven resolution selection**, not “older automatically means maximally summarized.”

### Chronology, pins and “as-of” semantics

`hermes-autobio` names four load-bearing invariants:

> “The archive is authoritative; the live view is a projection.”

> “Compression is always chronological and never destructive.”

> “Pins are display locks, not write locks.”

> “Summarization preserves the as-of moment.”

These are short excerpts from the repository’s own spec pointer. (GitHub, accessed 2026-11-03: https://github.com/antra-tess/hermes-autobio) citeturn586456view0

**Chronological-only compression** means the hierarchy is built from contiguous temporal regions, not by clustering semantically similar experiences from arbitrary dates. That gives summaries an interpretable provenance interval and prevents a memory such as “what I believed in March” from being silently contaminated by an event in August. The trade-off is obvious: chronology preserves subjective trajectory but is weaker than semantic indexing for answering arbitrary associative queries.

**As-of-that-moment** is more important than it sounds. A summary of turns 1–100 should reflect what the agent/user knew by turn 100. A later contradiction at turn 500 must not be retroactively injected into the summary of turns 1–100. Otherwise the memory system destroys epistemic history and can produce false continuity: the agent appears to have always known something it learned later. This is explicit in `hermes-autobio`’s invariant and is reinforced by the archive/projection separation. [established] [single-source] (GitHub, accessed 2026-11-03: https://github.com/antra-tess/hermes-autobio) citeturn586456view0

**Pins/locks do not freeze the archive.** The design distinction is: summary artifacts may continue to be produced, but a pinned/locked interval should remain at the requested display resolution in the current prompt. Rev. 2.1 of the adaptive design describes `lockedByAgent` as a persisted setting and explicitly says eager/background summary production remains safe because it does not itself change the live view. [established] [single-source] (2026-05-12: https://github.com/anima-research/context-manager/blob/main/docs/adaptive-resolution-design.md) citeturn586456view2

### Who writes memory

There are two related but not identical policies.

In `hermes-autobio` and the early autobiographical design, summarization is deliberately **on-policy**: the conversation is presented to the agent-model in its native participant structure, and the model produces a first-person autobiographical account. The rationale is to preserve subjective salience and voice instead of having an external generic summarizer decide what matters. The repo describes itself as “KV-preserving, on-policy compression for long-lived agents.” (GitHub, accessed 2026-11-03: https://github.com/antra-tess/hermes-autobio) citeturn827886view0

The modern Context Manager is more configurable: “older history [is represented] as summaries in the agent’s own words, written by the model you name.” Its host defaults can point `compressionModel` at the same model used by the resident, while `summaryParticipant` identifies the summary as authored in that agent’s voice. Therefore: **same model by default/strong design preference; not technically mandatory.** (GitHub, accessed 2026-11-03: https://github.com/anima-research/context-manager ; https://github.com/anima-research/connectome-host/blob/main/docs/AGENT-ONBOARDING.md) citeturn776046view2

For a multi-vendor lab this distinction matters. You can keep first-person continuity while using a stable/available compressor during provider retirement—but then the “autobiography” is generated by a different model emulating the resident’s voice. Anima’s own deprecation framing makes that an identity-adjacent choice rather than an implementation triviality. [emerging inference] (https://animalabs.ai/deprecations/why/ accessed 2026-11-03) citeturn964388search1

### Context selection and re-expansion

A `ContextManager` stores messages and strategy state, then `compile()` produces exactly the messages that will go to inference under a token budget. The strategies exposed in the README are `PassthroughStrategy`, `WindowedPassthroughStrategy`, `AutobiographicalStrategy`, and `KnowledgeStrategy`. `WindowedPassthroughStrategy` deliberately advances its anchor in coarse jumps to keep the provider-visible prefix stable; autobiographical mode mixes recent raw messages with older summaries. (GitHub, accessed 2026-11-03: https://github.com/anima-research/context-manager) citeturn586456view1

The adaptive design treats the current context as a **resolution-allocation problem**: maintain a protected raw tail; estimate token pressure; pick lower-resolution representations for older intervals; preserve locks/pins; refuse or escalate when a valid budget cannot be achieved rather than silently dropping history. Summary generation may occur speculatively in the background so alternate resolutions already exist when pressure requires them. [established] [single-source] (design updated through 2026-08-05: https://github.com/anima-research/context-manager/blob/main/docs/adaptive-resolution-design.md) citeturn586456view2

The phrase “Context Manager agent decides what to re-expand” needs one correction. In **`hermes-autobio`**, there is explicitly a dedicated CM agent/dialogue component (`cm.py`) and search/read tools; in the modern TypeScript Context Manager, much of adaptive resolution is deterministic strategy/policy machinery rather than a free-form LLM agent making every display decision. `hermes-autobio` lists `cm.py` as “Context Manager dialogue + dashboard” and `compression.py` as fold/unfold machinery. (GitHub, accessed 2026-11-03: https://github.com/antra-tess/hermes-autobio) citeturn586456view0

So the accurate answer is: **Anima has both algorithmic resolution management and an LLM-mediated memory-management path, depending on implementation.**

### KV-cache-stable design

The motivation is economic as well as cognitive. At 100K–500K-token resident contexts, rewriting the early prompt every turn defeats provider prefix caching. Anima therefore treats the compiled prompt as a structure whose **left prefix should mutate rarely**.

`WindowedPassthroughStrategy` explicitly says its coarse anchor moves are designed so that “between moves the window only grows at its end,” keeping the compiled prefix stable for provider prompt caches. (GitHub, accessed 2026-11-03: https://github.com/anima-research/context-manager) citeturn586456view1

The autobiographical hierarchy follows the same idea: old/high-level representations are relatively stable; newer/lower-level regions churn. `kv-stable` folding is therefore not merely a semantic compression policy—it is an ordering/transition policy designed to minimize prefix invalidation when a region changes resolution. The adaptive design explicitly discusses `kv-stable` as a folding strategy and prepared transitions. [established] [single-source] (https://github.com/anima-research/context-manager/blob/main/docs/adaptive-resolution-design.md, revs. 2026-05 to 2026-08) citeturn586456view2

`kv-rotation` attacks an even lower layer: if a prefix is physically evicted from a transformer KV cache, the remaining keys/values are positionally wrong relative to a fresh run over the shorter sequence. The project explores rotating/translating cached state so inference after prefix removal approximates the output of the original full-context computation while reclaiming KV memory. Its notes report vLLM-oriented experiments and parity-style checks against a full-prefix oracle, but this is experimental inference research, not a production guarantee. [emerging] [single-source] (GitHub, accessed 2026-11-03: https://github.com/anima-research/kv-rotation ; https://github.com/anima-research/kv-rotation/blob/main/notes/feasibility.md) citeturn827886view6

### Storage, search, namespaces and provider switching

There are **two storage regimes** that should not be conflated.

For the main Connectome stack, Context Manager depends on **Chronicle**, not SQLite. Multiple Context Managers may share one Chronicle store; `namespace` gives each its own context log/strategy state/summaries; `isolate: true` additionally gives the manager its own messages. Agent Framework opens per-agent managers under namespaces such as `agents/<name>`. (GitHub, accessed 2026-11-03: https://github.com/anima-research/context-manager ; https://github.com/anima-research/agent-framework) citeturn586456view1turn586456view4

For **`hermes-autobio`**, the repository explicitly lists `store.py — SQLite archive with FTS5`, plus `memory_search`, `memory_grep`, and `memory_read`. It also contains a Claude Code importer and web viewer. (GitHub, accessed 2026-11-03: https://github.com/antra-tess/hermes-autobio) citeturn586456view0

I found **no primary-source evidence that the core Chronicle-based Context Manager uses a vector database by default**. The default memory mechanism is temporal/hierarchical. Search/retrieval is an additional path; the Hermes plugin’s verified retrieval mechanism is SQLite FTS5/grep/read. `[no source found]` for a core Connectome vector index.

Provider switching is enabled at the representation boundary. Membrane takes a provider-neutral request containing named participants, system context, tools and generation settings, then translates it into the provider’s expected API format; Context Manager compiles history to Membrane `NormalizedMessage`s. (GitHub, accessed 2026-11-03: https://github.com/antra-tess/membrane ; https://github.com/anima-research/context-manager) citeturn776046view1turn776046view2

This is why memory can survive Anthropic→Bedrock→OpenAI-compatible→Gemini transitions: **the authoritative history is not an Anthropic messages array or OpenAI chat-completions payload.** Provider-specific formatting happens after memory/context selection. ChapterX separately demonstrates multi-provider conversation support across Anthropic, Bedrock, OpenAI-compatible and Gemini. (GitHub, accessed 2026-11-03: https://github.com/antra-tess/chapterx) citeturn586456view5

One real failure mode remains: provider-specific **thinking/reasoning artifacts** can be model-bound. Anima’s onboarding documentation warns that signed thinking blocks retained from a different Anthropic model can trigger request failures after a model switch. Thus provider-neutral *semantic messages* do not make every opaque provider artifact portable. [established] [single-source] (https://github.com/anima-research/connectome-host/blob/main/docs/AGENT-ONBOARDING.md, accessed 2026-11-03).

The likely failure modes, based on code/docs rather than speculation, are therefore:

1. **Premature information loss in the *projection*** even though raw data survives in the archive.
2. **Summary drift** if repeated higher-level merges omit minority details.
3. **Temporal distortion** if “as-of” discipline fails.
4. **Context-budget instability** when summaries are not ready in time.
5. **Cache-cost cliffs** when an old prefix changes resolution.
6. **Provider-specific artifact incompatibility** during model migration.
7. **Compression-model outage/deprecation** stalling memory maintenance.
8. **Search blind spots** because chronological hierarchy is not a substitute for arbitrary semantic retrieval.

Items 1, 4, 5, 6 and 7 are directly motivated by Anima’s own implementation/postmortem material; items 2, 3 and 8 are architectural risks that I infer from the design and should be tested rather than assumed. **Anima vs Letta.** Both start from “agent state persists across calls,” but their emphases differ. Letta explicitly stores experience/recalled history and gives the agent editable persistent memory; its newer docs describe **MemFS, a git-backed memory filesystem**, plus background “dreaming” that consolidates memories. Letta Code’s prompt says message history is automatically stored in recall memory and cannot be mutated. (Letta, accessed 2026-11-03: https://github.com/letta-ai/letta ; https://github.com/letta-ai/letta-code/blob/main/src/agent/prompts/letta_local_memfs.md ; https://github.com/letta-ai/letta-docs-md/blob/main/configuration/memory/index.md) citeturn371766search10turn371766search35turn371766search29

Anima’s differentiator is more specific: **chronological, first-person, multi-resolution reconstruction of a complete durable history, optimized for prompt-cache stability**. Letta is the more general stateful-agent memory system; Anima is the more opinionated temporal/autobiographical one.

**Anima vs Mem0.** Mem0 is principally a **memory extraction/indexing layer**: it derives compact facts/preferences from interactions and retrieves them later under user/agent/app/run scopes. Its current OSS package is Apache-2.0. (Mem0, accessed 2026-11-03: https://github.com/mem0ai/mem0 ; https://github.com/mem0ai/mem0/blob/main/docs/core-concepts/how-it-works.mdx) citeturn371766search1turn371766search13 Anima refuses to make extracted facts the sole canonical history; it keeps the experience and treats compression as a view. For identity/continuity, I prefer Anima’s provenance. For “what shipping address does this user currently prefer?”, Mem0’s fact-store approach is cleaner and cheaper.

**Anima vs Graphiti/Zep.** Graphiti is fundamentally a **temporal knowledge graph**: episodes are ingested, entities/relations extracted, and retrieval combines graph/vector/full-text style mechanisms; it supports evolving facts and temporal provenance. Graphiti declares Apache-2.0 in its package metadata. (Graphiti, accessed 2026-11-03: https://github.com/getzep/graphiti ; https://github.com/getzep/graphiti/blob/main/pyproject.toml) citeturn371766search0turn371766search21 Graphiti is better for “who/what relates to this query now, and how did that fact change?” Anima is better for “what was the agent experiencing/believing during this contiguous period?”

**Anima vs LangMem.** LangMem exposes explicit agent tools for searching/managing memory and background reflection/extraction tied to LangGraph stores. (LangMem, accessed 2026-11-03: https://github.com/langchain-ai/langmem ; https://github.com/langchain-ai/langmem/blob/main/docs/docs/background_quickstart.md) citeturn371766search4turn371766search45 Its abstraction is closer to programmable semantic memory than Anima’s chronological autobiographical compression.

**Anima vs Cognee.** Cognee emphasizes graph/vector cognition pipelines over source material rather than an agent’s uninterrupted subjective transcript. The core design value is structured associative retrieval; Anima’s is temporal continuity. (Cognee, accessed 2026-11-03: https://github.com/topoteretes/cognee ; https://www.cognee.ai/how-cognee-builds-ai-memory).

**Anima vs A-MEM.** A-MEM’s 2025 paper explicitly borrows the Zettelkasten metaphor: memories become linked notes with keywords/tags/context, and existing memories can be updated as new ones arrive. (Xu et al., 2025: https://arxiv.org/abs/2502.12110 ; repo https://github.com/WujiangXu/A-mem) Anima is almost the opposite on one axis: it strongly resists retroactively rewriting historical experience; new interpretations should be additional artifacts, not silent mutation of old experience. citeturn298727academia9turn298727search4

**Anima vs Claude Code / Anthropic memory.** Anthropic’s API memory tool is intentionally generic and client-side: Claude can list, read, create, update and delete files in an application-provided memory directory. Compaction is a separate context-engineering operation. (Anthropic, accessed 2026-11-03: https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool ; https://platform.claude.com/cookbook/tool-use-context-engineering-context-engineering-tools) citeturn298727search5turn298727search6 Anima provides a much stronger historical semantics: immutable source, explicit resolution levels, chronology and cache-aware transitions.

**Anima vs ChatGPT memory.** OpenAI’s consumer memory is user-level personalization that synthesizes useful information from past chats; in 2026 OpenAI described a “dreaming” architecture for background synthesis over conversation history. It is a closed product behavior rather than a user-programmable event store/projection engine. (OpenAI, updated 2026: https://help.openai.com/en/articles/8590148-memory-faq ; https://openai.com/index/chatgpt-memory-dreaming/) citeturn298727search7turn298727search8

**Anima vs plain RAG.** Classical RAG retrieves chunks by relevance from an external corpus and conditions generation on those results; it does not inherently preserve temporal perspective, first-person narrative or full chronological continuity. (Lewis et al., 2020: https://arxiv.org/abs/2005.11401) citeturn298727academia8 For your lab, this is why the best design is probably **not Anima instead of your current vector+graph+keyword ladder**; it is Anima-style chronology/projection **alongside** your retrieval system.

For an outside engineer wanting a small first PR, the safest concrete classes of contribution—derived from documented pain points rather than claiming a currently assigned issue—are:

- deterministic regression tests for adaptive-resolution selection under near-budget conditions;
- import fixtures for Claude Code/Codex/provider-switch histories;
- tests that summaries do not introduce facts from after the summarized interval;
- cache-stability instrumentation/regression tests for `kv-stable`;
- documentation or diagnostics for model-bound thinking blocks during provider migration.

## What an outside lab should take or avoid

For your architecture—large immutable note/transcript corpus, heterogeneous retrieval, multiple model vendors—the best move is **selective adoption**, not replacement.

**Highest priority: adopt the archive/projection split.** Keep every raw agent turn as an immutable canonical event. Treat “memory visible to the next inference” as a disposable/rebuildable view with provenance pointers into that archive. Never let a summary become the sole surviving representation of experience. This is Anima’s most defensible architectural contribution because it makes compression errors recoverable. [established recommendation based on established design] (https://github.com/antra-tess/hermes-autobio ; https://github.com/anima-research/context-manager, accessed 2026-11-03) citeturn586456view0turn586456view1

**Second: add chronological multi-resolution memory beside, not instead of, semantic retrieval.** Your vector+graph+keyword ladder solves associative recall. It does not inherently solve “what was my state of knowledge and project trajectory at time \(t\)?” A hierarchical temporal projection does. Use them as orthogonal axes:

`semantic relevance retrieval × chronological autobiography`

rather than forcing one to replace the other.

**Third: make every summary interval-addressable and provenance-complete.** Store `source_start`, `source_end`, source hashes, summary model, summary prompt/version, generation timestamp, summary level and parent/child relationships. This goes slightly beyond the public Anima schema as summarized here, but it follows directly from their archive/projection and source-relation principles. [recommendation/inference]

**Fourth: enforce as-of summarization in tests.** Construct adversarial histories: state A at turns 1–50; contradiction B at turn 200; then evaluate the turn-1–50 summary for leakage of B. I would make this a release-blocking property test. Anima states the invariant; I found no public quantitative metric for it. (https://github.com/antra-tess/hermes-autobio, accessed 2026-11-03) citeturn586456view0

**Fifth: copy the resolution-selection idea, not the historical fixed L1/L2/L3 numbers.** Fixed 6K→2K and fan-out 6 are sensible bootstrap parameters, not evidence-backed universal optima. The project itself moved from fixed L0–L3 to adaptive \(L_n\), which is an implicit warning against overfitting your design to the first implementation. (2026-05-12: https://github.com/anima-research/context-manager/blob/main/docs/adaptive-resolution-design.md) citeturn586456view2

**Sixth: treat prompt-cache topology as part of memory policy.** For multi-hundred-k contexts, “which token appears where” has direct dollar/latency consequences. Separate stable old context from mutable tail, batch/coarsen resolution transitions, and measure cache hit rates per turn. Anima is ahead of most memory frameworks here. (https://github.com/anima-research/context-manager ; https://github.com/anima-research/kv-rotation, accessed 2026-11-03) citeturn586456view1turn827886view6

**Seventh: preserve provider-neutral canonical messages.** Your archive should not store the authoritative conversation only in Claude/OpenAI/Gemini wire formats. Normalize participants, content blocks, tool calls, results, timestamps and opaque-provider extensions; render provider-specific requests at inference time. This is exactly where Membrane is useful conceptually. (https://github.com/antra-tess/membrane, accessed 2026-11-03) citeturn776046view1

**Eighth: borrow wake/event continuity from MCPL only if your agents actually need initiative.** A heartbeat is not memory, but it lets a persistent agent *use* memory between human prompts. The important security property is that MCPL keeps host-controlled capability grants for server-initiated actions rather than giving every server unconditional authority to wake/inject. (https://github.com/anima-research/mcpl ; https://github.com/anima-research/heartbeat-mcpl, accessed 2026-11-03) citeturn776046view3turn776046view4

What I would **not** adopt uncritically:

**Do not make autobiographical summaries your factual database.** First-person summaries optimize continuity and salience, not exact fact retention. Your one-fact-per-file memory and structured graph are better for atomic facts, provenance and correction.

**Do not rely on one compression model.** Anima’s own docs identify compressor availability/deprecation as an operational failure mode. Keep at least two tested compressors and record which model created every summary. This is particularly important in a multi-vendor lab.

**Do not treat “same model writes its own memory” as automatically superior.** It may improve stylistic/subjective continuity, but it can amplify the resident’s omissions and self-model errors. A strong setup would retain an agent-authored autobiography **plus** independently extracted factual/event metadata.

**Do not deploy experimental KV rotation as a dependency on continuity yet.** It is promising research, not mature infrastructure. Keep it as an optimization layer whose failure cannot corrupt the canonical archive. [emerging] (https://github.com/anima-research/kv-rotation, accessed 2026-11-03) citeturn827886view6

**Do not ignore licensing gaps.** A public GitHub repository without a clear license is source-visible, not necessarily reusable. Before contributing code you may later need internally, resolve licensing for Context Manager/Chronicle/host components whose current repository pages do not expose an obvious license. By comparison, Membrane and Agent Framework are explicitly MIT and Eidoverse explicitly AGPL-3.0. (GitHub, accessed 2026-11-03: https://github.com/antra-tess/membrane ; https://github.com/anima-research/agent-framework ; https://github.com/anima-research/eidoverse-worlds) citeturn827886view1turn586456view4turn586456view6

**Best collaboration entry point: Context Manager + evaluation tooling.** Anima already has a functioning architecture; what it lacks publicly is convincing memory science. Your lab’s existing corpus of tens of thousands of notes, complete agent transcripts, multi-vendor operation and shared fact files is exactly the sort of environment in which to test:

`raw archive → chronological summaries → semantic retrieval → mixed-resolution context → provider migration`

A high-leverage collaboration would be an open evaluation harness measuring **as-of fidelity, factual retention, retrieval complementarity, context-cache hit rate, amortized compression cost, recovery after branch/revert, and continuity across model/provider changes**. That would contribute something Anima does not presently publish and would also let you evaluate the system without becoming dependent on it. Anima’s public invitation explicitly asks collaborators to identify a concrete research/engineering problem and show relevant work. (Anima Labs, accessed 2026-11-03: https://animalabs.ai/participate/) citeturn324000search0

**Overall judgment:** **[established]** Anima’s memory work is technically substantive, not just marketing. The strongest pieces are the immutable archive/projected-context distinction, temporal/as-of semantics, adaptive resolution and cache-aware context topology. **[emerging]** The implementations are actively evolving and have enough real-deployment scars to be interesting. **[speculative]** The larger claim—that this architecture better preserves a long-lived agent’s identity or welfare-relevant continuity than competing memory designs—has not yet been demonstrated by public controlled evaluations.
