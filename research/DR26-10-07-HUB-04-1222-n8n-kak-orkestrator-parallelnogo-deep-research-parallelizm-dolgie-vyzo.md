# Insight (DR DR26-10-07-HUB-04-1222): n8n как оркестратор параллельного Deep Research: параллелизм, долгие вызовы, кворум

> Годится ли self-hosted n8n как оркестратор суточного веера Deep Research по 5-6 LLM-вендорам: реальный параллелизм, долгие внешние вызовы, кворум и добор, сравнение с Temporal/Prefect/Windmill/Inngest/Trigger.dev.

## Ключевые выводы
- Ветки одного исполнения n8n идут по очереди (Execution order v1: одна до конца, затем следующая; сверху вниз, на одной высоте слева направо). Реальная параллельность возникает только между отдельными исполнениями. Практик 01.12.2025 замерил на двух HTTP-ветках: второй стартует примерно через 10 с после первого. Это чужое наблюдение одного воркфлоу, не бенчмарк.
- Queue mode (EXECUTIONS_MODE=queue) параллелит исполнения, а не ветки: main кладёт id в Redis (Bull), воркеры забирают. Дефолт worker --concurrency 10 (рекомендация n8n: 5 и выше). В обычном режиме лимита нет, пока не задан N8N_CONCURRENCY_PRODUCTION_LIMIT (дефолт -1). Для 6 суточных задач queue mode не нужен. В queue mode нужны Postgres, Redis, общий N8N_ENCRYPTION_KEY, бинарные данные не в filesystem.
- Merge ждёт все входы и кворума «4 из 6» не умеет: упавшая или молчащая ветка блокирует синтез. Execute Sub-workflow с wait=false не отдаёт родителю результат ребёнка. Опция есть с 1.26.0. По отчётам сообщества на «Run once with all items» нода не дожидается всех подворкфлоу, а на 1.57.0 wait=false вместе с Continue on error обрывал ребёнка.
- Wait: дока всё ещё пишет, что ожидание короче 65 с не уходит в базу, но в master Wait.node.ts порога 65000 уже нет (PR #27066, смёржен 02.04.2026; связан с n8n 2.14.0). Waiting-исполнения лежат в базе и не чистятся. Отчёты о переживании рестарта противоречивы: «да, если жив том с БД» (январь 2026) против зависания Waiting с версии 2.16 (апрель 2026). Поведение на нашей базе не воспроизводилось. Версия инстанса не проверена.
- Deep research у вендоров длится десятки минут. OpenAI предписывает background:true и poll GET /v1/responses/{id} или вебхук; ответ хранится около 10 мин, режим несовместим с ZDR. Модели o3/o4-mini-deep-research помечены на выключение 23.07.2026. Держать HTTP 40 минут в одной ноде плохо: слот воркера занят, у HTTP Request чужой замер дефолтного таймаута 300000 мс, N8N_AI_TIMEOUT_MAX равен 1 часу. Правильный каркас: старт (секунды) + Wait на вебхук либо цикл Wait → HTTP-статус.
- В n8n нет встроенных DLQ, ключа идемпотентности и кворума. Есть Retry on Fail (фиксированная пауза, без экспоненты), Error Workflow с Error Trigger и шаблоны DLQ на Google Sheets или Postgres. Предупреждение от 10.06.2026: Retry при потерянном ответе создаёт дубль платного заказа. Идемпотентность, кворум и добор строятся только внешней таблицей со статусами pending/done/error и ключом (run_date, vendor).
- История исполнений чистится по умолчанию: старше 336 часов (14 суток) или больше 10000 записей; waiting/running/new и помеченные не удаляются. Экран исполнений n8n не архив, сырые ответы ДР надо хранить вне n8n. Единого run_id на 6 вендоров нет: у каждой ветки свой execution id. Execution Data (customData) ограничена планами Pro/Enterprise. Алерт на тихо не доехавшую ветку даёт только леджер (строка старше N минут в pending).
- Публичные шаблоны не закрывают задачу: шаблон 14497 (консенсус OpenAI/Anthropic/Gemini/Groq) заявляет «одновременно», но при Execution order v1 ветки идут по очереди; шаблон 16330 — роутер-Switch, а не веер. Шаблона с кворумом 4 из 6 и добором опоздавших найдено не было. Windmill (branch all, parallel for-loop, каждый шаг — отдельный job), Inngest (waitForEvent без живого процесса, fan-out отдельными функциями), Trigger.dev (wait.for не считается в compute, idempotency key) устроены под такую задачу лучше.
- Грабли n8n: Code-нода без доступа к ФС и HTTP; Pyodide-Python снят в 2.0, нативный Python с 1.111.0 с allowlist модулей, раннер по умолчанию 5 одновременных задач, таймаут 300 с. N8N_PAYLOAD_SIZE_MAX 16 МиБ; бинарные в памяти по умолчанию, filesystem в queue mode не поддерживается. Внешние секрет-сторы только Enterprise. Environments/Git описаны противоречиво (Enterprise или Business), конфликты воркфлоу не детектируются, значения секретов в git не уезжают.
- Вердикт: n8n годится как диспетчер веера, но не как система записи. Схема: Schedule Trigger (раз в сутки) → проверка внешней таблицы → шесть отдельных исполнений (вебхук на вендора) → короткий HTTP-старт с background-режимом, запись vendor_job_id → Wait на колбэк или цикл Wait + статус → синтезатор по расписанию (done >= 4 пишет синтез, следующий тик дописывает опоздавших) → один Error Workflow в чат. Retry on Fail только на коротких HTTP.
- Не переносить в n8n: файловую систему хоста и общий диск воркеров, git как действие воркфлоу, GUI/браузер и клики, локальные процессы Windows/macOS и пути E:\ и «внутренний путь лаборатории», сырой текст длинных ДР в items между нодами. Три дешёвых улучшения: таблица из 5 колонок с уникальным ключом (run_date, vendor); один вендор = одно исполнение через свой вебхук вместо холста с Merge; один Error Workflow плюс Retry на коротких HTTP и синтезатор, читающий таблицу.

## Рекомендации / решения
- Завести внешнюю таблицу-леджер (run_date, vendor, status, vendor_job_id, execution_id) с уникальным ключом (run_date, vendor) и проверять её до любого платного вызова: это даёт защиту от двойного заказа, кворум и добор.
- Не строить веер шестью ветками одного холста с Merge: запускать отдельное исполнение на каждого вендора (вебхук либо Execute Sub-workflow с выключенным ожиданием как запал).
- Для долгих вызовов использовать двухшаговую схему: короткий HTTP-старт с id задачи (у OpenAI background:true), затем Wait на вебхук с Limit Wait Time или цикл Wait + HTTP-статус; не держать сокет на 40 минут.
- Синтез вынести в отдельный воркфлоу по расписанию: при done >= 4 писать синтез, следующим тиком дописывать опоздавших без перезаказа.
- Повесить один Error Workflow на все воркфлоу веера и синтезатор; Retry on Fail включать только на короткие HTTP статуса и старта, не на шаг, создающий задачу у вендора.
- Сырой текст ответов хранить в таблице или файле вне n8n (в исполнении только id и статус) из-за pruning через 14 суток и лимитов payload.
- Не включать queue mode ради 6 суточных задач; рассматривать его, когда одновременных ожиданий станут десятки или основной процесс начнёт тормозить редактор.
- До внедрения проверить версию наш сайт (поведение Wait, порог 65 с, срок политики пропущенных запусков Schedule) и воспроизвести рестарт при Wait на своей базе.
- Если вендор не умеет фоновый id + вебхук, либо оставлять его вне n8n, либо рассматривать Windmill/Inngest/Trigger.dev/Temporal или Python asyncio + cron.

## Открытые вопросы
- Версия, режим (regular или queue), база и число воркеров на наш сайт не проверены, а от версии зависит поведение Wait (порог 65 с).
- Поведение Wait после рестарта на нашей базе не воспроизводилось; отчёты сообщества противоречивы (в том числе зависания с 2.16).
- Уходит ли Execute Sub-workflow с wait=false в отдельный джоб Redis или бежит внутри процесса родителя, не подтверждено по исходнику.
- Стоит ли в шаблоне 14497 Execution order v0 и реально ли четыре ветки идут одновременно, не проверено (JSON не импортировался).
- Интервал опроса WaitTracker (около 5 с) взят из описания PR, сам wait-tracker.ts не открывался.
- Дефолт Timeout у HTTP Request в официальной доке не назван; 300000 мс — сообщение форума от 11.08.2026.
- Какие вендоры (Anthropic, Gemini, Grok, Mistral, DeepSeek) умеют фоновый id + вебхук как OpenAI, не проверено; для умеющих только синхронный ответ схема не годится.
- Первичные доки Temporal, Prefect, Dagster, Airflow и Python asyncio не открывались; сравнение опирается на доки Windmill, Inngest, Trigger.dev и две обзорные статьи, бенчмарка «6 вендоров, 40 минут» нет.
- Стриминг логов n8n во внешнюю систему не читался; покрытие /metrics на инстансе неизвестно.
- Секция Gemini в отчёте содержит только повтор заказа без ответа по существу (вторая секция помечена REJECTED echo), поэтому вклад этого вендора отсутствует.
