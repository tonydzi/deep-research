## Что Terminum фактически делает и где проходят его границы

Terminum — self-hosted Rust server `terminumd`, работающий с tmux через control mode. Он не эмулирует терминал сам: документация говорит, что он читает grid tmux через `capture-pane`/control notifications и отправляет изменившиеся строки browser client. Его собственные tmux-сессии, пользовательские tmux-сессии и tmux на SSH-hosts сводятся в один UI. citeturn349731view0turn187654view1 Источники: https://github.com/extractumio/terminum/blob/main/docs/USAGE.md ; https://github.com/extractumio/terminum/blob/main/docs/ARCHITECTURE.md

Подтверждённые возможности, а не только marketing copy: Claude Code и Codex отображаются в одном session list; remote host добавляется через `terminum hosts add ... --files`; файловая панель умеет browse/edit, JSON/YAML tree, CSV/TSV table, images, PDF, audio/video, загрузку файлов; браузерный UI заявлен и документирован для desktop, iPhone/iPad; clipboard screenshot сохраняется на host session; upload ограничен 100 MB. citeturn398023view0turn349731view0 Источники: https://github.com/extractumio/terminum ; https://github.com/extractumio/terminum/blob/main/docs/USAGE.md

Состояния агента имеют два уровня. Без hooks Terminum пытается интерпретировать экран; после `terminum hooks install` Claude Code и Codex сообщают working/waiting-for-approval/waiting-for-answer/stop/fail/subagent более точно. Но этот же install добавляет `terminum mcp` в Claude/Codex для plans/progress/notes. Для данного workflow это существенный минус: пользователь уже имеет свои plans/progress/notes, а каждый agent session получает дополнительный stdio MCP process. Сам Terminum пишет, что MCP запускается в каждой Claude Code/Codex session, хотя вне Terminum pane он не предлагает tools. citeturn349731view0 Источник: https://github.com/extractumio/terminum/blob/main/docs/USAGE.md

Следовательно, **полезная часть Terminum для данного пользователя — browser terminal, fleet aggregation, remote files, agent attention states и SSH/tmux integration; менее ценная — встроенные plans/notes**. Практически важно проверить, можно ли оставить hooks для статусов без ненужной MCP-части или жить с screen inference; документация описывает `hooks install` как пакетную установку hooks + MCP, поэтому независимое использование только статусов по официальной документации не доказано. citeturn349731view0

Особенно важно не переинтерпретировать “Survives reboots”. README говорит, что sessions/windows/splits возвращаются и показывают последние 300 lines. Подробный guide уточняет: если tmux server исчезает, Terminum создаёт структуру снова; для terminal programs требуется ручное `claude --continue` / `codex resume --last`. Это аналог восстановления рабочего стола после reboot, а не продолжение вычисления с точки прерывания. citeturn398023view1turn349731view0 Источники: https://raw.githubusercontent.com/extractumio/terminum/main/README.md ; https://github.com/extractumio/terminum/blob/main/docs/USAGE.md . Это также согласуется с базовой семантикой tmux: если сам tmux server умер, его процессы потеряны; официальный tmux FAQ прямо говорит, что если server не работает, sessions gone. citeturn496716search7 Источник: https://github.com/tmux/tmux/wiki/FAQ

Security boundary у Terminum сравнительно чёткий: bind только на `127.0.0.1`; для других устройств рекомендуемый путь — `tailscale serve`; password login даёт 256-bit session token, который хранится не cookie, а origin storage и отправляется custom header; есть Origin/Host checks, rate limiting, защита против DNS rebinding/CSRF. Документ отдельно говорит, что `tailscale funnel` получает 403. citeturn187654view2 Источник: https://github.com/extractumio/terminum/blob/main/SECURITY.md . Это заметно лучше, чем у некоторых browser terminals с “поставьте reverse proxy перед нами”.

## Карта рынка и отсев похожих, но не эквивалентных продуктов

Полезно разделить рынок на четыре архитектуры.

**Тип A — remote control существующих CLI-agent sessions.** Здесь Terminum наиболее чистый пример. **Agent Deck** приблизился к этому классу благодаря tmux и remote fleet endpoints. **HAPI** и original Happy CLI выглядят похожими визуально, но фактически требуют запускать agent через wrapper. Это важное различие для уже работающего парка.

**Тип B — agent/worktree orchestrator, который запускает работу сам.** Сюда относятся Superset, HAPI, Agent of Empires, Agent Deck при его обычном использовании, Happy current harness, CloudCLI и Vibe Kanban. Они могут быть лучше Terminum для *новых задач*, но “поднять существующие произвольные tmux sessions” у большинства не является первой архитектурной целью.

**Тип C — general remote IDE/terminal.** code-server, Wave Terminal, ttyd, WeTTY. Они дают browser/SSH/file access, но почти не решают “какие из двадцати Claude/Codex сейчас ждут approval?”. Поэтому они не являются полной функциональной заменой.

**Тип D — desktop-first.** cmux и Wave. Они могут быть очень сильными локальными interfaces, но browser/iPad/phone requirement автоматически ограничивает их как замену Terminum.

Самая важная строка в матрице — **existing-session attach vs sessions launched by the product**. ## Рейтинг для реального workflow и рекомендации

### Dashboard поверх существующего флота

**Первое место — сохранить Terminum как контрольный вариант.** Для описанной Windows + Macs + always-on Linux + SSH/tmux + private tailnet topology он уже находится в правильном архитектурном слое. Он может жить на одной Mac/Linux/WSL-подобной точке управления, видеть remote tmux через SSH и не требует перехода на worktree-per-task или vendor cloud. Его browser client соответствует требованию desktop/iPad/phone без native-app lock-in. citeturn398023view0turn187654view1

Главный конкретный недостаток — optional agent-state integration связана с hooks/MCP bundle, тогда как у пользователя plans/progress уже решены отдельно. Второй недостаток — reboot wording легко принять за гораздо более сильную гарантию, чем документация реально даёт. Третий — проект молодой: активные releases полезны, но означают меньшую накопленную production history, чем у code-server или tmux. citeturn349731view0turn187654view0

**Lead alternative — Agent Deck.** Причина не в количестве функций, а в правильном incremental value. Он также строится вокруг tmux, уже имеет понятие remote fleet endpoints, где remote sessions становятся соседями local sessions, и даёт agent-aware waiting state. Это единственный исследованный альтернативный продукт, который столь явно движется к *единой панели над несколькими уже существующими машинами*. citeturn103998search0turn485808search0

Trade-off: его UX пока более “session manager/TUI с web companion”, чем полноценный browser IDE. В просмотренных primary sources я не нашёл доказательства эквивалентного Terminum файлового browser/editor, rich previews, clipboard image routing, Quote & Ask или столь polished touch terminal. Поэтому Agent Deck стоит тестировать именно как **fleet dashboard**, а не заранее считать full replacement.

**Fallback — HAPI.** Он превосходит Terminum по mobile control-plane sophistication: pending approvals, push, PWA, paid native apps, file browsing/diffs, multi-machine grouping. Один Hub может принимать несколько machines и Runner может запускать session на конкретной машине. citeturn103998search3turn103998search2turn948260search4 Но HAPI не является нейтральным наблюдателем произвольных существующих tmux sessions: для полноценной видимости session должна быть создана/обёрнута HAPI. Для пользователя, который уже имеет большой парк живых Claude/Codex sessions, это архитектурная цена, а не мелкая настройка.

**Agent of Empires** идёт следом. Он прекрасен, если один host содержит множество agent sessions и нужен tmux-native web/TUI manager с worktrees и containers. Но я не нашёл столь же сильной primary-source гарантии одного dashboard над несколькими независимыми SSH hosts. Поэтому в конкретной multi-machine постановке он уступает Agent Deck/HAPI. citeturn596919search0

### Основная среда для запуска новой агентной работы

Здесь **Superset** выходит вперёд. Его архитектура целенаправленно решает parallel agents: каждый агент может работать в isolated worktree, есть diff/editor/terminal, remote hosts, mobile. Он явно поддерживает Claude Code, Codex и большое число других CLI agents и сохраняет subscription-based economics вместо принудительного API billing. citeturn437311search2turn437311search5 Источники: https://github.com/superset-sh/superset ; https://github.com/superset-sh/superset/blob/main/apps/docs/content/docs/agent-integration.mdx

Но Superset **не следует покупать как замену Terminum только ради dashboard**. Remote/mobile находятся в Pro, native mobile сейчас iOS 26+, Android отсутствует, Windows host app пока отсутствует, а architecture более opinionated. Для будущей среды new work это оправдано; для существующего heterogeneous fleet — значительно менее очевидно. citeturn596919search5turn596919search6turn485808search4

**Fallback для new-work environment — HAPI.** Он проще, self-hosted и ближе к “официальные CLI остаются официальными CLI”. Для Claude/Codex он предоставляет remote session semantics и approvals, а Codex поддерживается через native terminal + `codex app-server` в современных версиях. citeturn896369search3turn896369search27 Источники: https://hapi.run/docs/guide/agents ; https://hapi.run/docs/guide/codex-shared-sessions . Для пользователя, который не хочет API migration и уже платит за подписки, это очень сильное свойство.

**Happy** интересен как более радикальный future architecture. Современный Happy уже не просто remote control Claude Code: Happy Agent реализует собственный harness, remote server может запускать Claude/Codex через существующие subscriptions и продолжать работу независимо от laptop. citeturn103998search4 Источник: https://happy.engineering/guides/remote-server/ . Это потенциально удобнее CLI wrapping, но означает больший semantic distance от “я хочу те же Claude Code/Codex процессы, которыми уже управляю”. Поэтому для существующего fleet я ставлю его ниже; для greenfield workflow он достоин отдельного эксперимента.

**CloudCLI** подходит, если browser-first интерфейс важнее topology fidelity. Его self-host UI удобен, но отсутствие built-in authentication — существенный operational/security footgun: официальный guide прямо требует внешний auth proxy. citeturn948260search13 Дополнительно GitHub Security показывает несколько critical advisories в марте 2026; нынешний проект активно релизится, но history требует дисциплины обновлений. citeturn106305search5turn106305search6

**cmux** чрезвычайно интересен для Mac workstation, особенно после добавления SSH agent states, remote tmux, scp uploads и agent resume. Release notes 0.65.0 от 5 октября 2026 заявляют Claude/Codex status over SSH и crash recovery. citeturn596919search12 Источник: https://cmux.com/docs/changelog . Но отсутствие browser client делает его плохой прямой заменой Terminum для Windows/iPad/phone. Он скорее superior Mac cockpit, который может сосуществовать с server-side tmux, чем общий fleet web UI.

## Ограниченный план проверки на пяти реальных задачах

Никакой миграции или reboot production hosts для этой оценки не нужен. Достаточно отдельного disposable test session или non-production host. Критично **развести disconnect test и reboot-equivalent test**, потому что почти каждый продукт хорошо переживает потерю клиента, но гораздо меньше продуктов реально продолжают agent work после смерти host/process.

| Тест | Что сделать | Условие принятия | Условие отказа | Какие данные собрать |
|---|---|---|---|---|
| **Fleet visibility** | На Linux и Mac запустить по Claude Code и Codex session, причём хотя бы одна уже существует до подключения dashboard; открыть desktop browser и iPad/phone | Один список ясно показывает host, session, working/waiting/idle/approval; существующая session не требует destructive restart | Продукт видит только sessions, которые сам создал, если именно attach-existing является обязательным use case; или multi-host требует отдельные несвязанные dashboards | Время до появления session, число дополнительных daemons/helpers, возможность attach existing tmux, корректность статуса |
| **Approval round-trip** | Запустить безопасный task, который намеренно запросит permission/question; уйти с desktop и ответить с phone browser/native app | Pending state заметен без открытия каждой session; approve/deny/reply действительно продолжает ту же session | Нет distinct waiting state, требуется SSH вручную, approval теряется при переключении клиента | Notification latency как наблюдаемое событие без формального benchmark, UI path, ложные working/waiting states |

Для **Terminum** особенно важен последний тест: ожидаемый по документации результат — восстановленный layout/folders/last lines и затем отдельное возобновление Claude/Codex, а не continuation mid-turn. Если практический тест покажет автоматический native-session resume без ручного вмешательства, это повысит его оценку относительно текущего source-backed понимания; пока такое поведение официальными docs не подтверждено. citeturn349731view0

Для **Agent Deck** рекомендацию перевернёт вниз обнаружение того, что remote fleet view фактически требует существенной перестройки существующих sessions или что web UI недостаточно пригоден на iPad/phone. Наоборот, если он без restart/import friction обнаружит существующие remote sessions, даст точные approval states и приемлемый file access, он станет наиболее вероятным challenger Terminum.

Для **HAPI** рекомендацию перевернёт вверх наличие официально поддержанного attach к уже запущенным raw Claude/Codex/tmux sessions без wrapper restart. В просмотренной документации я этого не нашёл; вся documented architecture строится вокруг `hapi <agent>` и Runner. citeturn948260search5turn948260search7 Источники: https://hapi.run/docs/guide/installation ; https://hapi.run/docs/guide/how-it-works

Для **Superset** рекомендацию поднимет доказательство browser-based control, Windows-host support и более прозрачного self-host remote path без обязательного paid relay/account. В текущих docs mobile/remote — Pro feature, host requirement — macOS primary/Linux experimental. citeturn596919search5turn596919search6

Для **CloudCLI** серьёзным условием принятия является внешний auth boundary. Открывать его напрямую на tailnet/public interface без auth proxy не следует: собственный guide проекта прямо пишет, что self-hosted CloudCLI UI не имеет встроенной аутентификации. citeturn948260search13

Итоговый уровень уверенности: **высокий** в выводе, что Terminum и Agent Deck архитектурно лучше всего соответствуют “существующий tmux/SSH fleet”; **высокий** в том, что HAPI и Superset сильнее как environments for new sessions; **средний** в сравнении mobile polish без практического тестирования; **низкий/UNKNOWN** в reboot continuation там, где vendor docs не описывают конкретный agent-native resume mechanism.
