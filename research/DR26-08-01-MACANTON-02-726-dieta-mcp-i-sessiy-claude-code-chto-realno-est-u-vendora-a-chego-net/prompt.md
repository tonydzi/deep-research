# Deep Research: диета MCP-коннекторов и сессий Claude Code на мульти-сессионной машине

## Контекст (все цифры — живые замеры, macOS, Claude Code 2.1.219, 01.08.2026)

Машина 32 ГБ RAM, на ней одновременно живут 15–36 сессий Claude Code + десктоп-приложение Claude.
Пиковое состояние: своп 94% (13.1 из 14.3 ГБ), load average 61.

Что мы уже сделали и что доказано:
1. **telegram-MCP (stdio) плодил процесс ~350–380 МБ на КАЖДУЮ сессию** (Telethon + прогрев кэша
   диалогов). Вылечено переключением на встроенный в сервер SSE-режим: один долгоживущий
   launchd-демон на 127.0.0.1:8765, клиенты ходят по HTTP. Реальных python-процессов telegram
   стало 0, живой вызов через демона работает.
2. **whatsapp-MCP уже устроен правильно**: один Go-мост-демон держит связь, на сессию — тонкий
   python ~8 МБ. Экономить нечего.
3. **Отдельного процесса computer-use НЕ существует** (ps по comm = 0 совпадений) — инструменты
   computer-use/браузера обслуживаются ВНУТРИ бинаря сессии («builtin MCP presets»).
4. После чисток главный потребитель — **сами бинари сессий: 24 шт × ~340 МБ = 8.2 ГБ**.
   Соседний фикс уже закрывает idle-сессии старше 5 ч (<10% CPU).

## Вопросы (по убыванию ценности)

1. **Диета одной сессии.** Чем определяется резидентный вес бинаря сессии Claude Code (~340 МБ)?
   Есть ли ВЕНДОРСКИЕ ручки (settings.json, env, флаги CLI), отключающие неиспользуемые
   встроенные пресеты MCP (computer-use, браузер, iOS-симулятор, визуализация) per-session,
   per-project или глобально? Что из этого документировано и поддерживается, что — фольклор?
2. **Ленивая загрузка тулов.** Deferred tools / ToolSearch уже откладывают СХЕМЫ. Откладывается
   ли при этом сам рантайм пресета? Есть ли способ, чтобы пресет вообще не поднимался до первого
   вызова?
3. **Паттерн «общий демон» как норма.** Для каких классов MCP-серверов индустрия рекомендует
   один shared-процесс (SSE / streamable HTTP) вместо stdio-на-сессию? Есть ли готовые
   supervisor'ы/мультиплексоры MCP (агрегаторы, прокси), которые дают один порт на много
   серверов + ленивый старт? Что из этого зрелое (наш принцип: строить по промышленному
   стандарту, а не своему протоколу)?
4. **Пределы.** Сколько одновременных сессий Claude Code на машину считается разумным потолком
   у самого вендора и у практиков? Есть ли официальные рекомендации по флоту/оркестрации вместо
   толпы интерактивных сессий?
5. **Анти-паттерны.** Чем тихо ломается вынос MCP в общий демон (авторизация, состояние на
   процесс, изоляция сессий, гонки записи)? Наш телеграм-кейс: 48 Telethon-клиентов дрались за
   одну sqlite и светили Telegram'у толпу сессий — какие ещё известные грабли этого класса?
