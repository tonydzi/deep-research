# Вывод  
Локальная 3–4B LLM на GTX 1660 Super может помочь для простых задач (суммаризация, классификация, краткие черновики), но **не заменит** Opus в творческом режиме (Антонов голос). Рекомендуем **Phi-4-mini (ок. 3.8B, MIT-лицензия)** или **SmolLM3-3B (Apache-2.0)** как компромисс скорость/качество. Запускать через OpenAI-совместимый сервер (например, встроенный `llama.cpp` HTTP-сервер) на одной карте. Фоллбэк делать вне Claude (обёртка): первым пытаем `claude -p`, при ошибке («session limit» или 5xx/429) переключаем на локальную модель через API.  

- **Модель:** Phi-4-mini (3.8B, занимает ≈3.5 GB в 4-bit при Q4_K_M, хорошо работает на ограниченном железе) или SmolLM3-3B (≈3B, высокое качество на этом масштабе, Apache-лицензия). Qwen-2.5-3B (≈3B) в 4bit примерно как SmolLM3 по скорости и мультиязычности; 7B-версии (>6 GB) не поместятся.  
- **Сервер:** `llama.cpp` HTTP-сервер – лёгкий C++ демен, поддерживает OpenAI-API. На Windows собрать по инструкции из репо и запустить как сервис. Альтернатива – Ollama (есть Win-инсталлятор, OpenAI-совместимый endpoint на `localhost:11434`). LM Studio (GUI) тоже может работать как сервер (порт 1234). VLLM под Windows не готов.  
- **Фоллбэк:** Claude Code не может сам переключиться на сторонний LLM (фоллбэк-модели работают лишь внутри Anthropic). Поэтому нужно оборачивать `claude -p` скриптом: при выходе с ошибкой (см. п.4) брать тот же запрос и посылать через `curl` к локальному API (например, Ollama или `llama.cpp` endpoint).  

## 1. Выбор модели (3–6 GB)  
- **Qwen-2.5B** (инг.) – 3B параметра, поместится в 6 GB 4bit. Около **30–35 ток/сек** на 1660 Super (≈36 tok/s на RTX2060, скорректируем вниз). Хорош в мультиязыке и коде. Лицензия Apache (Alibaba).  
- **Llama-3.2-3B** – ~3B, ~50 tok/s на RTX2060 (на 1660S ≈ 38 tok/s). Комьюнити-экосистема сильна; качество инструкций близко к Llama3-8B. Лицензия **коммерчески-исследовательская** (Meta), не CC0.  
- **Gemma-2 2B** – 2B параметра, займёт около 1.5–2GB в 4bit. Схожая архитектура с Mistral; ожидается ~25–40 tok/s. Лицензия, возможно, Apache (Google). Gemma-2 9B не поместится (6GB < требуемого VRAM).  
- **Phi-3.5-mini / Phi-4-mini** – 3.82B (MIT-лицензия), потребляет ≈3.5GB в Q4_K_M, ~20–30 tok/s. Предназначена для ограниченного железа, по качеству часто лучше Llama-3.1-8B. Реализует отличную генерацию на 3–4B.  
- **SmolLM3-3B** – 3B, Apache-2.0, оптимизирована для reasoning и длинного контекста. Вероятно, даёт сравнимое качество с Qwen2.5/Llama3 3B. Скорость – не тестировалась на 1660, но 3B-модель.  
- **Использование двух карт:** Без NVLink разделить модель на 2 GPU сложно. Лучше запускать на одной карте (6GB). Вторую карту можно задействовать для параллельных задач (эмбеддинги, Whisper) или запустить отдельный экземпляр модели.

  

## 2. Сервер на Windows  
- **llama.cpp server:** Самый лёгкий путь. Скачайте репозиторий llama.cpp и соберите утилиту `server` (через CMake/Visual Studio). Запустите как `server --model <путь_к_модели.gguf>`. Он слушает HTTP на `0.0.0.0:8080` (по умолчанию) с OpenAI/Anthropic API (chat). Подходит для long-context (>40K токенов). Можно оформить Windows-службу (через NSSM или sc.exe) для автозапуска. Документация: поддерживает OpenAI-совместимые `/v1/chat/completions`.  
- **Ollama:** Есть Windows-установщик. Команда `ollama serve` запустит сервис, который отвечает на OpenAI-подобные запросы на `http://localhost:11434` (см. пример использования). В качестве модели используйте: `ollama pull <модель:колонка-квант>` (например, `qwen3:7b-instruct-q4_K_M`). Оставьте Ollama в автозагрузке.  
- **LM Studio:** Графический, но умеет поднять сервер (на localhost:1234) через GUI: вкладка *Local Server*. Менее гибкий для автоматизации, но прост в настройке.  
- **vLLM:** Не тривиально на Windows, требует Linux-среды. Не рекомендуется для простого деплоя на 1660.  

Шаги (пример llama.cpp):  
```bash
git clone https://github.com/ggerganov/llama.cpp
cd llama.cpp
mkdir build && cd build
cmake -DCMAKE_CUDA_ARCH=75 -DLLAMA_CUBLAS=ON ..
cmake --build . --target server
```
Затем настроить службу запуска `server.exe`.  

  

## 3. Интеграция с Claude Code  
Claude Code **не имеет встроенной поддержки** произвольных LLM-провайдеров (фоллбэк-модели — только модели Anthropic). Чтобы использовать локальную LLM, поступаем так: пишем внешний скрипт-роутер. Шаги:  
1. В скрипте вызываем `claude -p --model opus` (OAuth авторизация).  
2. Если команда завершилась нормально – берём ответ.  
3. Если `claude -p` упёрся в лимит (см. п.4) или сессия упала – вместо ответа посылаем тот же запрос на локальный эндпоинт OpenAI (например, `curl http://localhost:11434/v1/chat/completions` для Ollama) или `127.0.0.1:1234` (LM Studio).  
4. Возвращаем результат локальной модели.  

Т.е. failover реализуется **вне Claude Code**. По протоколу: можно настроить Anthropic LiteLLM Gateway (LiteLLM) с переменными окружения `ANTHROPIC_BASE_URL`/`ANTHROPIC_AUTH_TOKEN`, но это актуально лишь для своих API-key или встраивания через LiteLLM. Практичнее обойтись обёрткой, как описано выше.  

  

## 4. Детекция лимита и переключение  
Claude CLI при исчерпании квоты пишет сообщения вроде «You’ve hit your session limit», «...weekly limit», «server is temporarily limiting requests» или просто возвращает ошибку с HTTP 429. Эти тексты приведены в документации ошибок.  

- В скрипте после `claude -p` проверяйте код возврата (`%ERRORLEVEL%` в cmd, `$LASTEXITCODE` в PowerShell). Если он не 0 и вывод содержит «session limit» или «weekly limit» (или «429»), – значит лимит исчерпан.  
- Также можно использовать систему хуков Claude: событие `StopFailure` с матчером `rate_limit` или `billing_error` срабатывает при лимитных ошибках. Тогда скрипт-обработчик получает уведомление и может переключить модель.  
- Реализуйте **circuit-breaker**: после срабатывания задерживайте новые запросы к облачной модели 5–15 минут (время до сброса окна) и используйте локальную модель. Либо помечайте аккаунт как «temporarily disabled» в скрипте на несколько минут.  

Пример на PowerShell:  
```powershell
$output = claude -p --model opus -c "Ваш запрос" 2>&1
if ($LASTEXITCODE -ne 0 -and $output -match "session limit|weekly limit|429") {
    # переключаем на локальную модель
    $response = curl http://localhost:11434/v1/chat/completions -H "Content-Type: application/json" -d '{...}'
} else {
    $response = $output
}
```
  

## 5. Когда локаль годится (и когда нет)  
- **Подходит:** короткие помощнические задачи без сложного творчества. Например, классификация, поиск/грунтовка («отнеси-подай»), базовые черновики, простая инструкция. Для них 3–4B моделей достаточно, и время отклика на 1660S (~20–30 tok/s) ещё приемлемо. Локаль можно использовать как «сервисный LLM» для выполнения вспомогательных функций (например, предварительная обработка данных, составление списка, ответы на FAQ).  
- **Не подходит:** авторский стиль, творческое письмо или сложный анализ (где важен «голос Антона»). Для таких задач нужна сила Opus или больших моделей. Локаль не даст аналогичной креативности/слога. Даже Phi-4-mini или SmolLM3 уступают крупным моделям в глубине рассуждений.  
- **Затраты:** развитие и отладка локальной инфрастуктуры даёт пользу лишь при частых простых запросах. Если сбои происходят редко, возможно, выгоднее просто ждать сброса лимитов и звукового оповещения, чем тратить время на поддержку локальной LLM. Однако при автопарке из 20 агентов вероятность частых лимитов велика, так что локаль может спасти время в долгосрочной перспективе.  

  

## 6. Эксплуатация (энергопотребление, износ, изоляция)  
GTX 1660 Super потребляет до ≈125 Вт, плюс материнская плата/CPU – итого ~150–200 Вт в нагрузке. 24/7 это ≈3.6–4.8 кВт·ч в день (~1300–1750 кВт·ч/год), при цене ≈0.1–0.2 $/кВт·ч – порядка $130–$350/год на электричество (и соответствующее выделение тепла). Постоянно включённый GPU всё время вращает кулеры, ускоряя износ вентиляторов и чипов.  

Чтобы избежать конфликтов с другими задачами (эмбеддинги, Whisper), **выделите для LLM отдельную видеокарту**. Задайте `CUDA_VISIBLE_DEVICES` или аналог, чтобы сервис LLM всегда работал на одной GPU, а остальные задачи – на другой. Например, если есть 2×1660, запустите `server` LLM на GPU 1, а все PyTorch-скрипты (Whisper/эмбеддинг) – на GPU 0. Это предотвратит конкуренцию за VRAM и вычисления.  

Для изоляции и надёжности: заведите LLM-сервис как Windows-службу (через NSSM, Task Scheduler или `sc.exe`), чтобы при сбое он автоматически рестартовал. Следите за температурой карт (можно снизить частоты, если перегреваются). SSD износ незначителен – модели загружаются в память, лишь иногда обновляются на диске.  

Итого, эксплуатация локального LLM – дорогостоящая в смысле энергии/нагрева (несколько сотен долларов в год) и усложняющая инфраструктуру задача. Решать её стоит, если отказоустойчивость системы важнее операционных затрат. В противном случае – стриггер алертов и ожидание сброса лимитов могут быть дешевле.
